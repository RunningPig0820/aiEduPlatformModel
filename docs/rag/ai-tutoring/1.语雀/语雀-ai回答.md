现状我已经摸了一遍。你给的这个 28 点清单很完整，但有几个关键事实会直接改变答案——你的地基比想象中厚，真
正缺的东西反而很少。先给你看现状，再回答你的三个问题（技术栈、对话存哪、需求是否合理）。

点亮逻辑"。 工作量比清单看起来小得多——但也说明真正的设计难点不在管道，在流程编排。

二、技术栈怎么分：Java 管状态机，Python 管智能
这是最核心的决策，也是你"不需要全部在 Java 后端"的正确打开方式。
答疑流程本质是一个确定性状态机，箭头是 Java 的业务逻辑，箭头上的每个"智能动作"才是 Python/LLM：
用户输入
│
▼
┌────────────┐   F1 意图/题型/学科分类（LLM 返回结构化 JSON）
│ 安全过滤    │ ── 高危 → 终止
└────────────┘
▼
┌────────────┐
│ 意图路由    │ ── 无关 → 默认回复并结束（Java 侧一个 if）
│            │ ── 学习指导 → 鼓励话术（Python prompt）
└────────────┘
▼
┌────────────┐   F2 模糊 → 澄清反问（LLM）
│ 澄清/引导   │ ── F3 每一步苏格拉底提示（LLM 根据全量历史生成）
└────────────┘
▼
┌────────────┐   F4 评估学生回答 → 正误 + 错误类型 + 情绪（LLM）
│ 评估反馈    │ ── F9 错误事件 → 落库（Java）
│            │ ── F7 连续错误 → 话术切换（Prompt 内置，几乎免费）
└────────────┘
▼  （循环直到学生解出 / 放弃 / 防作弊触发）
┌────────────┐   F14 学生确认知识点（结尾一次性确认卡）
│ 知识点确认  │
└────────────┘
▼
┌────────────┐   F8/F18 提取知识点 → Neo4j 点亮 + 能力分（Java 调现有 KG 仓储）
│ 图谱点亮    │
└────────────┘
▼
┌────────────┐   F10 会话摘要 + F6 归档（Java）
│ 总结归档    │
└────────────┘
落地方式：完全复用现有 scene 机制，给 Python 网关加 4 个场景：
┌─────────────────────┬────────────────────────────────────────────────────────────────┬────────────┐
│      场景 code      │                              职责                              │ 对应功能点 │
├─────────────────────┼────────────────────────────────────────────────────────────────┼────────────┤

├─────────────────────┼────────────────────────────────────────────────────────────────┼────────────┤

├─────────────────────┼────────────────────────────────────────────────────────────────┼────────────┤
│ tutoring_eval      │ 输入：学生回答 + 上下文 → 输出：正误 + 错误类型 + 情绪         │ F4, F7     │
├─────────────────────┼────────────────────────────────────────────────────────────────┼────────────┤
│ tutoring_kp_extract │ 输入：整段对话 → 输出：知识点候选列表                          │ F8, F14    │

Java 侧新增一个 tutoring 有界上下文（TutoringSession 聚合 + TutoringAppService），它编排这 4
个场景、驱动状态机、调用已有的 KG 仓储点亮图谱。
一个建议：LangChain 在这里可以不上。 你的流程是 Java 驱动的确定性状态机，Python 侧只是"单次 prompt +
JSON schema 结构化输出"，直接调模型 API 比 LangChain 编排更干净。LangChain 的价值（agent、tool、复杂
chain）在这个场景用不上。

但有几个设计假设，你必须先想清楚，否则会埋雷：
① "严禁直接输出答案"是产品赌博，有流失风险。 真实学生会直接说"给我答案"。如果硬封锁且无出口，学生会弃用
。需要定一个"看答案"逃生通道——比如学生明确要求或尝试 N 步之后，允许揭示答案（设计文档的 F6
支持中途终止，但终止后给不给答案，文档没写）。这是业务决策，不是技术决策，得你拍板。
② 知识点确认的交互打断。 设计文档说"AI 预判 + 学生确认"，但如果是在对话中途弹一个确认卡，会很割裂。建议
放结尾一次性确认（答疑结束后给一张"本次涉及知识点，是否正确？可修正"的卡），而不是边聊边确认。你强调"通
过学生来确定知识点"，这个一定要保留，但位置决定体验。
③ "条件点亮"的规则必须写死在 Java，不能交给 LLM 猜。 "完成一次完整引导式交互"太模糊——学生第一步就答对了
算不算？学生放弃算不算？需要定确定性规则（如：进入引导且至少正确回应 1 个关键提问 →
点亮；连续答错最后给答案 → 半亮）。否则图谱点亮率会失控。
④ 图谱目前只有数学（人教版）。 学科分类可以做（KgSubjectEnum
已存在），但语文/英语没有图谱节点，点亮无处可落。MVP
建议：学科分类正常做，但"点不亮"要优雅降级（提示"该知识点暂未收录"）。这也反过来印证阶段 2
才需要题库指纹。

②知识点确认的交互打断。 设计文档说"AI 预判 + 学生确认"，但如果是在对话中途弹一个确认卡，会很割裂。建议放结尾一次性确认（答疑结束后给一张"本次涉及知识点，是否正确？可修正"的卡），而不是边聊边确认。你强调"通过学生
来确定知识点"，这个一定要保留，但位置决定体验。
③"条件点亮"的规则必须写死在Java，不能交给LLM猜。 "完成一次完整引导式交互"太模糊——学生第一步就答对了算不算？学生放弃算不算？需要定确定性规则（如：进入引导且至少正确回应 1 个关键提问 → 点亮；连续答错最后给答案
→ 半亮）。否则图谱点亮率会失控。
④图谱目前只有数学（人教版）。 学科分类可以做（KgSubjectEnum 已存在），但语文/英语没有图谱节点，点亮无处可落。MVP 建议：学科分类正常做，但"点不亮"要优雅降级（提示"该知识点暂未收录"）。这也反过来印证阶段 2
才需要题库指纹。

五、需要你拍板的决策点
1. 答案出口策略——苏格拉底引导过程中，学生明确要答案时给不给？（这是产品决策，影响最大）
2. 知识点确认的时机——结尾一次性确认卡 vs 对话中确认？
3. 点亮规则——什么情况算"完整交互"？连续失败算什么状态？
4. 多学科范围——MVP 只做数学（图谱齐），还是学科分类做全、点亮只对数学生效？
5. 会话深度——MVP 是否限制单次会话轮数（比如最多 20 轮，防 token 失控）？
