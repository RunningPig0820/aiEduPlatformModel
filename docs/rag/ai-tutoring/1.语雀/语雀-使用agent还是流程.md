# 语雀原文：使用agent 还是流程

> 来源: 语雀 业务实施→AI答疑→方案设计→使用agent还是流程 (doc 279938375, 3976字)
> COS路径: ai-tutoring/rag-source/语雀/语雀-使用agent还是流程.md
> 核心结论: AI答疑是 Workflow（确定性编排），不是 LLM Agent。自适应学习才是 agent 的主场。

---

**Q: ai答疑里面有 agent 的编排吗**

**A: 没有——这个设计里刻意不采用 LLM agent 编排。** 但要先把概念说清楚，因为"有没有 agent"取决于你问的是哪种"agent"。

## 先区分两种"agent"

```
┌──────────────────────────────────────────────────────────────┐
│ ① LLM Agent（自主编排）                                      │
│ LLM 自己决定下一步做什么：调用哪个工具、要不要问澄清、          │
│ 要不要给提示……模型持有控制权，动态规划路径                    │
├──────────────────────────────────────────────────────────────┤
│ ② Workflow / 工作流（确定性编排）——本设计的形态              │
│ 代码（Java 状态机）决定每一步走哪条路，每一步调一次 LLM        │
│ 做"一个认知动作"，模型不决定流程走向，只完成当前这一步          │
└──────────────────────────────────────────────────────────────┘
```

AI 答疑是典型的 ②Workflow。

> ⚠️ **最新逻辑（2026-08 代码）**：本节"Java 状态机总控器决定调哪个 scene"是**中间态**——后续演进为**受限 agent + 护栏**：Java 不再做流程状态机（仅 3 生命周期 ACTIVE/ARCHIVED/TERMINATED + 护栏计数器），Python 4 个 scene 收敛为 **decide/generate 两端点**（decide 出动作元数据 + Java 动作出口审批）。「LLM 无自主决策权、决策靠 Java 计数器」的结论仍成立，但"Java 决定调哪个 scene"改为"Java 审批 type 闭集"。Java 的 TutoringSession 状态机像"总控器"，它决定该调哪个 scene（intent / socratic / eval / kp_extract），每个 scene 就是一次"单发 prompt + 结构化 JSON 输出"。LLM 没有任何自主决策权——它不决定"下一步是问提示还是给答案"，这个决定是 answer_request_count、round_count 这些 Java 计数器做的。

```
Java 状态机（总控，决定流程）               Python scene（执行单步认知，不决定流程）
┌──────────────────────────┐              ┌──────────────────────┐
│ GUIDING？→ 下一轮用哪个 mode│──调用──▶   │ socratic: 生成一条引导语│
│ round>=20？→ 强制收尾      │              │ eval: 判断对错+信号     │
│ answer 2次？→ REVEALING   │◀──返回──    │ intent: 分类意图        │
└──────────────────────────┘              └──────────────────────┘
```

## 为什么刻意不用 Agent

1. **苏格拉底原则是硬约束**：严禁直接给答案、每轮只一条提示——这些不能交给 LLM 自主判断，agent 的"灵活性"在这里是风险（它可能哪次就给你甩出完整答案）。
2. **业务规则必须确定**：20 轮上限、2 次答案出口、掌握度单调不减、图谱点亮——这些是产品规则，agent 不可控。
3. **成本与可测性**：每次调用边界清晰、单步可测；agent 循环的调用次数和路径不可预测，难测也难控预算。

> 换个视角：你可以把 4 个 scene 理解成 4 个

> ⚠️ **最新逻辑（2026-08 代码）**：「4 个 scene = 4 个工具」的落地形态 = **ActionMeta type 闭集 + Java 护栏**——decide 一次输出 type，Java `TutoringGuardrailService` 校验放行（答案/轮次/安全），非 agent 自由调工具。"工具"，Java 状态机是一个带固定策略的控制循环——它像 agent 控制器，但决策策略是写死的代码，不是模型推理。这就是 workflow 和 agent 的本质区别。

## 什么情况下才值得引入真正的 agent 编排

如果答疑想变成这样，才需要 agent：
+ **自适应路径**：让 LLM 根据学生情绪、掌握度现场决定"下一步是继续引导、插一道变式题、还是跳去讲前置知识点"（动态，而非 3 条写死的 mode）。
+ **多源检索组合**：阶段 2 的"举一反三"要同时查题库、查图谱、查错题本，让 agent 决定检索顺序和组合。
+ **跨工具动作**：比如"学生卡住时自动拉取一条相关微课并推送"。

这些目前都不在 MVP 里。而且即便到了阶段 2，仍建议把 agent 的决策面控制在单个 scene 内部，而不是把整个答疑循环交给 agent——确定性边界保住，灵活性在边界内放开。

> ✅ **最新逻辑（2026-08 代码）**：方向一致——MVP = **L0 单次调用**（decide/generate），阶段2 升级 L1/L2 LangGraph 多步 agent 时，ActionMeta 契约已预留、工具 API 形状早定，迁移成本低（`design-python-ai-tutoring` 决策12）。

**一个伏笔**：现有 llm-gateway 的 AiEduChatRequest / 响应里已经有 tool_calls 字段——说明网关层支持工具调用，将来真要上 agent 模式，管道是现成的，不用改网关。

**Q: 其实我想做一个 langchain 的业务 是不是ai自适应学习更符合agent 逻辑**

**A: 你的直觉是对的——这是一个实质性的架构分叉。** 一句话结论：**苏格拉底答疑是"执行问题"（workflow），自适应学习是"决策问题"——决策问题才是 agent 的主场。**

## 为什么自适应学习天然是 agent 逻辑

两者的差别不在"用没用 LLM"，而在智能坐在哪里：

```
苏格拉底答疑（执行问题）                    自适应学习（决策问题）
─────────────────────────               ─────────────────────────
策略固定：一步步问，不问对错               策略可变：根据状态选"下一步做什么"
"下一步"由代码规则决定                      "下一步"取决于学生状态，需动态决策
   · answer_request_count → 出口          · 掌握度 < 40 → 补前置知识点
   · round_count → 收尾                   · 连续错 3 次 → 降难度 + 换讲解方式
   · 每轮 mode 固定                        · 情绪沮丧 → 先给鼓励再推进
                                         · 已掌握 → 加快 / 出变式题
策略是写死的 → workflow                   策略本身是智能 → agent
```

自适应学习的核心是一个决策循环：观察状态 → 决定教学动作 → 执行 → 观察新状态。这恰恰是 agent 的标准结构——状态 + 工具 + 决策者。LangChain/LangGraph 的价值在"决策层"真正发挥出来，而不只是拼个 JSON。

## 但正确形态是"受限 agent"，不是自由 ReAct

教育产品最大的 agent 坑是"自由 agent"：LLM 想调啥调啥、想咋教咋教 → 教学法不可控、成本失控、难审计。正确形态是封闭动作集 + 业务规则守门：

```
Python 侧：LangGraph agent 循环（LangChain 业务的核心）
┌────────────────────────────────────────────────────┐
│ Agent 决策：给定学生状态，从封闭动作集里选下一步       │
│   move ∈ { 给提示 / 评估回答 / 出变式题 /            │
│           讲知识点 / 查薄弱点 / 推荐资源 }           │
│         ↑ 这是 LLM 的自主决策点（自适应所在）          │
│  工具：query_kg（薄弱点）/ generate_hint /           │
│        evaluate_answer / generate_question /         │
│        lookup_question_bank                          │
└──────────────┬─────────────────────────────────────┘
               │ 每次决策 / 每步动作，仍受约束：
┌──────────────▼─────────────────────────────────────┐
│ Java 侧（守门 + 事实源，不做决策）                     │
│  · 20 轮上限、禁答案策略、安全过滤（硬不变式，LLM 碰不到） │
│  · 掌握度 / 错误事件 / 会话持久化 / 图谱点亮            │
│  · 暴露工具化 API 给 Python agent 调用（KG/题库/掌握度） │
└─────────────────────────────────────────────────────┘
```

**关键区别**：agent 决定"教什么、怎么教"，Java 决定"什么不能做、边界在哪"。这样既拿到了自适应的灵活性，又守住了教育产品的确定性底线。

## 架构上会怎么变

| 维度 | 当前 workflow 设计 | 自适应 agent 设计 |
|------|-------------------|-------------------|
| Python 侧 | 4 个无状态 scene 端点 | LangGraph 有状态 agent 循环 + 工具集 |
| 智能位置 | 每一步的内容生成 | 下一步动作的选择（升级了） |
| Java 侧 | 状态机总控流程 | 守门 + 工具 API 提供方（决策权移交） |
| 会话状态 | Java Redis 单源 | Python agent 有状态（LangGraph 检查点）+ Java 守门 |
| LangChain 用量 | 只结构化输出（薄） | agent + tools + memory + 状态图（厚）——真正的 LangChain 业务 |
| 成本/延迟 | 每轮 1 次调用 | 决策 + 执行多次调用（更高，需设上限） |

## 三个诚实的代价

1. **成本**：agent 每轮可能 2-3 次 LLM 调用（决策 + 工具生成），且要配 LangGraph 的 token 预算护栏。20 轮 × 3 = 60 次/会话，比 workflow 贵不少。
2. **可测性**：决策路径不固定，"20 轮内强制收尾""第 2 次要答案必须给"这类硬规则好测（在 Java 侧），但"教法是否合理"只能靠 prompt 约束 + 人工抽检。
3. **"严禁给答案"更难守**：这条规则在 agent 内部容易漏（LLM 哪个动作就带出来了）。必须在 Java 守门层做最终兜底，而不是只写进 prompt。

## 建议：混合演进

1. MVP 保持 workflow（苏格拉底引导，快、稳、成本低），但 Python 侧从一开始就用 LangChain 的 with_structured_output + 模块化场景，为后续 agent 化留好接口。
2. 阶段 2 升级为受限 agent：把"下一步动作"交给 LangGraph 决策循环，动作集先放 4-5 个，跑通后再扩。

这样既拿到一个能上线的 MVP，又有一个真正用上 LangChain agent 能力的第二阶段目标。
