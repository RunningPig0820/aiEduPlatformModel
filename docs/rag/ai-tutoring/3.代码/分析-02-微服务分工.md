## 业务情况（三方各管什么）

### 1. 前端 `aiEduPlatformFront` = 纯交互层
- **不碰智能逻辑、不碰数据规则**：只负责渲染 + 会话状态机 + SSE 消费 + localStorage 离线缓存。
- 职责：交互（`AiQa.jsx`）、会话生命周期/SSE 消费/断点对账（`useTutoringSession.js`）、API 封装（`api/modules/tutoring.js`）。
- 前端不直接连 COS（无签名 URL 泄露/无 CORS 依赖）——transcript 由后端代理读取（`GET /sessions/{id}/transcript`）。
- 本地持久化只做兜底：localStorage 存 ACTIVE 会话快照（最多 10 条），挂载时 `reconcileSession` 与服务端对账。

### 2. 后端 `aiEduPlatform` = 平台层（认证/护栏/数据）
- **认证**：`TutoringController` 从 HttpSession 取 studentId + 校验 STUDENT 角色，请求体不传身份，服务端不信任客户端。
- **编排总控**：`TutoringAppService` 串起「安全预检 → 学科门 → decide → 护栏 → 落库副作用 → COS 归档 → generate 流式」。
- **护栏**：`TutoringGuardrailService` 是动作出口的确定性规则引擎（答案/轮次/安全）。
- **数据**：Redis（活跃会话/消息/锁/计数）+ MySQL（会话/掌握度/题目/错误事件）+ COS（transcript/题目图片）。
- **不透出 Python 内部端点**：decide/generate/ocr 仅内部可达，前端只面向 `/api/tutoring/**`。

### 3. Python `aiEduPlatformModel` = 纯智能层（L0 两端点，无状态）
- 只暴露 4 个内部端点：`decide`（决策）/ `generate`（生成）/ `question-understand`（看图识别题型）/ `subject-classify`（学科门）。
- **无状态**：DecideRequest 无 `current_question` 字段——当前题目由 Python 从 history 推断；Java 零题目状态。这保证了 Python 可水平扩展、单次调用可重试。
- **模型统一**：全链路写死 doubao `doubao-seed-2-0-mini-260428`（decide/generate/understand/classify 同款），不做路由/白名单——非视觉模型在构造上不可能进入看图端点。
- 掌握度快照/历史由 Java 从 Redis/MySQL 组装好传过来，Python 不做存储。

### 4. 智能位置与决策权
- **内容生成（generate）** 在 Python；**动作决策（type）** 名义上 Python 的 decide 输出，但**最终审批权在 Java 护栏**——Python 输出 `type=reveal`，Java 看 `answer_request_count` 决定放行还是降级 approach。这就是「决策靠 Java 确定性规则，LLM 无自主决策权」的落地形态。
