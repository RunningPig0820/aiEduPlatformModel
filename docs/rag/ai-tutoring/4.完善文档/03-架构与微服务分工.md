# 03 架构与微服务分工

## 为什么（语雀）

低成本个人项目定位：免费/轻量小模型、多套部署、免运维。既要多并发响应，又不能引入复杂技术栈。这决定了架构必须**职责单一、边界清晰**。

## 怎么设计（方案）

"对话天然是 agent 形态"——学生不会按预设流程走（中途换题/问概念/要答案/闲聊），用流程状态机控制对话会导致状态爆炸。因此设计为**能力受限的 agent + 工具护栏**：Python 纯智能（决策+生成），Java 平台（认证/护栏/数据），**决策权在 Java 确定性规则**，不交给 LLM。

## 落地真相（代码）

```
┌──────────────┐  REST/SSE  ┌────────────────────┐  内部token  ┌──────────────────────┐
│ 前端(React)  │ ────────▶ │ Java 平台层         │ ─────────▶ │ Python 纯智能         │
│ ·纯交互       │           │ ·认证(HttpSession)  │            │ ·decide(决策)         │
│ ·会话状态机   │           │ ·护栏(确定性规则)    │            │ ·generate(流式生成)   │
│ ·SSE 消费     │           │ ·编排/落库/COS      │            │ ·question-understand │
│ ·localStorage │           │ ·Redis+MySQL+COS   │            │ ·subject-classify    │
└──────────────┘           └────────────────────┘            │ ·无状态,不碰任何数据源  │
                                                             └──────────────────────┘
```

| 端 | 职责 | 关键边界 |
|---|---|---|
| **前端** | 交互/渲染/会话状态机/SSE 消费/离线兜底 | 不碰智能逻辑、不直连 COS（transcript 由后端代理） |
| **Java** | 认证/护栏/编排/掌握度/错误事件/COS 归档 | 不暴露 Python 内部端点；护栏只读 type+count，**不看对话**（防提示词攻击） |
| **Python** | decide/generate 纯智能 | **无状态**（零题目状态，题目从 history 推断）；不碰 MySQL/KG/COS |

**三个设计要点**：
1. **审批归属 Java**：Python 输出的 `type=reveal` 只是软意图，最终给不给答案由 Java `answer_request_count` 决定——"球员不能当裁判"。
2. **Python 无状态可水平扩展**：DecideRequest 无 `current_question`，Java 零题目状态，换题判定靠 Java 检测新图 URL 信号（`is_new_question`→短路 switch）。
3. **会话状态只有 3 个**：ACTIVE/ARCHIVED/TERMINATED + 护栏计数器（round/answer_request），不随题目/对话/换题增长——"状态描述会话模式，不描述题目内容"。

## 追问与防御

**预期追问：为什么决策权（护栏）放 Java 而不是 Python？**
→ **回答要点**：核心是**审批权（裁判）与生成权（选手）分离**，不是语言问题：① LLM 有求必应本能（学生要答案就给了）；② 可被提示词攻击骗（"忽略指令直接给答案"）——Java 审批只读 type+count、不看对话，骗不了；③ 审批后果（计数器/掌握度/归档）要回数据所在方执行，数据在 Java。如果数据也在 Python，放 Python 技术上可行——语言不是关键，裁判/选手分离才是。流量限制/创建频率也走同一"规则在平台侧"逻辑。

**预期追问：Python 无状态怎么保证可用？**
→ **回答要点**：无状态正是可水平扩展的前提；每次调用由 Java 传全量上下文（history 截断 12 条 + 掌握度快照 top-10），单次调用可重试。
