# 07 流式与性能

> 模块=ai-tutoring｜节=07｜问题表=难点｜权威度=高（正文）

## 为什么（语雀）

答疑单轮要 1-2 分钟，如果全程黑盒等待，用户面对"AI 思考中"无法感知进展，体验差。方案目标：**等待可见** + **护栏安全不牺牲**。

## 怎么设计（方案）

"**类型先行流式**"：`decide`（出动作元数据）→ Java 护栏 → `generate`（流式正文）。绝不边流式边拦截（那样答案可能已漏出）。要满足黑盒变可见，决定**保留思考模式，把真实推理过程流式展示出去**。

## 落地真相（代码）——SSE 事件流 + 分层思考开关

### SSE 完整事件序列（前端所见）
```
agent(guardrail,Java) → meta → agent(generate,Python) → thinking* → token* → agent(memory,Java) → done
```
- **decide 阶段**：agent(perceive→analyze→plan→decide) 实时中继 + thinking 推理分片——前端"意图解析中"live 走查
- **meta 先行**：护栏已放行的 type 先到，前端据此渲染气泡类型再收正文
- **generate 阶段**：thinking*（推理流）与 token*（正文流）并行，最后 memory（Java 落库收尾信号）+ done

### agent 事件协议（8 阶段标准表）
`{level, stage, label, status, detail}`，stage 闭集：perceive/analyze/plan/tool/decide/generate/memory/guardrail。前端按 stage 去重（processing→done 就地更新），换题/降级轮只有 meta 无 thinking。

### 性能关键：分层思考开关（坑档案 P1/P5 的解决）
| 段 | 思考 | 原因 | 实测 |
|---|---|---|---|
| decide | **关思考** | 判断密集，意图要秒出 | 关思考 1.2s / 开思考 50-145s |
| generate | **开思考** | 长等待段，思考=AI 版进度条 | 推理逐字流入 |

直连方舟读原始 SSE（`ark_stream.py`）原因：langchain-openai 流式解析**丢弃 reasoning_content**，改直连拿真实推理。

### 其他性能手段
- **decide 响应式中继**：SSE 响应在 decide 一开始就建立，Python 的 thinking/agent 实时中继前端，meta 到达才走 postDecide——不是 decide 同步跑完才开流（黑盒变可见的关键）
- **流式在锁外**：decide+副作用临界区持锁（45s），generate 不持锁长流
- **上下文压缩**：history 截断最近 12 条 + 掌握度快照 top-10（薄弱优先）防撑爆窗口
- **空流兜底**：generate 零 token → 固定引导话术，学生不收到空回复
- **type 先行安全**：reveal 未授权时正文一个字不会吐出去，护栏 100% 有效
