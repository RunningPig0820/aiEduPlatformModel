## 一、Python 端（aiEduPlatformModel）

### P1. 图片分析慢 50~145s（卡顿根源）
**1. 问题现象**：拍图识别（`question-understand`）和看图答疑肉眼不可用，一次调用慢到 50~145s；Java 侧每轮等满超时才收到结果，答疑链路被拖成"卡顿"。前端表现是"AI 看图分析中"长时间无进展。

**2. 触发流程**：Java 上传题目图到 COS 后调 Python 同步 JSON 端点——`POST /api/tutoring/question-understand`（`api/tutoring.py:121-133`）→ `core/tutoring/question_understand.py:74-111` `understand_question`；学科判定 `POST /api/tutoring/subject-classify` → `subject_classify.py:58-87` `classify_subject`。两者都走 `core/gateway/factory.py:165-171` `LLMFactory._create_doubao` → ChatOpenAI 方舟兼容接口，多模态 HumanMessage（text + image_url）invoke。

**3. 根因分析**：修前工厂构造只传 provider/model/temperature，缺少三件套——① doubao mini **默认开思考**（先写草稿再答），实测开思考 50~145s、关思考看图 1.2s（连 120×120 白图都要 32s）；② 无 `request_timeout`，openai SDK 默认 600s 才放弃；③ 未关 SDK 重试，慢调用无限等。本质是**视觉任务被"思考草稿"拖慢 + 超时参数缺失**，不是网络问题。

**4. 排查过程**：先复现确认是 Python 侧慢而非网络——最小化请求逐项排除：关思考后立即降到 1.2s，锁定了思考开关；再看 SDK 超时默认值（600s）确认没有快速失败兜底。`ark_stream.py:8-9` 注释记录"思考模式 = 模型写草稿，是卡顿的根源"。

**5. 解决方案 & 改动点**：`question_understand.py:82-90` / `subject_classify.py:66-73` 两处工厂构造统一加三件套：`extra_body={"thinking": {"type": "disabled"}}`（关思考）、`request_timeout=20`（20s 内部超时）、`max_retries=0`（关 SDK 重试）。慢/失败 20s 内快速返回空 `topic_labels` / `subject=None`（HTTP 200），Java 降级 PENDING / 按 math 放行。回归护栏 `tests/tutoring/unit/test_question_understand.py:126-156`（断言三参数）。

**6. 面试口述要点**：讲"**视觉模型默认思考模式是性能陷阱**"——doubao 开思考要 50~145s 关思考 1.2s，差两个数量级。技术权衡：意图/分类这类低认知任务果断关思考，长生成才开；配套"20s 超时 + 关重试 + 快速空降级"让 Java 不无限等。踩坑收获是"**默认值不信任**"——模型厂商的默认思考策略会悄悄吃掉延迟预算。

### P2. 答疑链路"网络波动"排查
**1. 问题现象**：答疑链路 decide / generate / `/api/kp/resolve` / analyze-question **每轮**报「网络波动，请重试」，非偶发；而 Python 本机自测全通。

**2. 触发流程**：Java 每轮 orchestrate 调 Python 各端点 → 连接失败 → `friendlyErrorStream` 兜底「网络波动」→ 前端收到失败态。Python 侧本身健康：监听 `0.0.0.0:9527`（`main.py:165` uvicorn）、`GET /health` 200、最小 decide SSE 全事件流正常、token 比对一致。

**3. 根因分析**：**后端 `gateway.base-url` 写死 `localhost:9527`**（`ai-edu-backend/ai-edu-interface/src/main/resources/application.yml:104`）。`localhost` 只在后端与 Python 同机时成立；部署环境 ≠ Python 所在机器时指向后端自己，导致连接失败被误报为"网络波动"。本服务代码内**没有** `LLM_GATEWAY_BASE_URL` 之类配置（grep 无命中），根因完全在 Java 后端仓库。

**4. 排查过程**：先 Python 本机全链路自测排除 Python 侧（health/decide SSE/token 全通）；再对照部署拓扑怀疑 Java→Python 连接配置；最后在后端 application.yml 发现写死的 `localhost`。`docs/backend-connectivity-2026-08-19.md:3-4, 27-49` 有完整排查记录。

**5. 解决方案 & 改动点**：转后端改 `application.yml` 一行配置（走配置不写死），按部署形态选：同机 Docker 容器 → `http://host.docker.internal:9527`；k8s/同内网 → `http://<python-svc>:9527` 或内网 IP；跨机器 → `http://<Python服务IP>:9527`。Python 侧**零改动**；需重构建/重启后端生效（`target/classes/application.yml` 是编译产物）。

**6. 面试口述要点**：讲"**跨服务联调用 localhost 是经典坑**"——本机全通、部署全挂，一查是 base-url 写死。排查方法论：先确定故障边界（Python 自测排除自身），再看连接配置（拓扑决定），避免误判为网络/对方服务故障。踩坑收获：**跨服务地址永远走配置/服务发现，不写死**。

### P3. 答错的学生被"恭喜"
**1. 问题现象**：decide 断言答对但答案错误时输出 `type=end`，Java 真收尾——**答错的学生收到"恭喜"**，且 end 的 summary 偶发直接泄出完整解答。

**2. 触发流程**：Java 每轮调 `POST /api/tutoring/decide`（SSE 流式）→ `decider.py:92-166` `iter_decide_events` → 直连方舟读原始 SSE，`acc[0]["arguments"]` → `ActionMeta.model_validate`（`decider.py:147-148`）；非流式兜底走 `decide()` → `structured.py:251-277` `generate_action_meta`（四段降级）。两条路径最终都过 `_sanitize_end_consistency`（`decider.py:89`、`:166`）。实测 doubao「断言答对但答案错误」场景：reason 明说"不应收尾/继续引导"，却**稳定输出 type=end**，且 end_reason 偶发 null/COMPLETED/ANSWER_REVEALED 与 correct=false 矛盾。

**3. 根因分析**：模型 end 输出与 eval 字段**自相矛盾**，无确定性护栏兜底。`_sanitize_end_consistency` 判定 invalid 的条件（`decider.py:37-43`）：`end_reason is None`，或 `COMPLETED` 但非 `correct && exercise_complete`。本质是**不能信任模型对"是否该收尾"的自述**。

**4. 排查过程**：从"答错却被恭喜"反推——对照 end 判定链，发现 end 输出与 eval 矛盾（reason 说不该收尾却输出 end）；再逐个 end_reason 值（null/COMPLETED/ANSWER_REVEALED）与 correct/exercise_complete 交叉验证，确认模型输出不一致是常态而非偶发。

**5. 解决方案 & 改动点**：end 联动一致性护栏（`decider.py:24-53`）：type=end 但缺 end_reason、或 COMPLETED 但非 `correct && exercise_complete` → 降级 `type=CONCEPT`、清空 `end_reason`/`summary`，保持会话 ACTIVE 不终止。`decide()` 与 `iter_decide_events` 双路径接入（幂等）。`prompts.py:70-76` 同步加「答对判定与收尾」规则：判对前必须代入验算、疑问/不确定措辞也算作答（看数值不看语气）、答错告知"答案不对"并继续引导绝不 end。单测 `tests/tutoring/unit/test_decider.py:428-523`（护栏 8 例）。

**6. 面试口述要点**：讲"**模型自述不可信，要用确定性护栏兜底**"——LLM 可能 reason 说一套、type 输出另一套。技术权衡：端到端加护栏（end 联动一致性）不信任模型格式；这是"AI 应用安全关键输出"的标准做法——**结构化输出 + 业务护栏**双保险，宁可降级不误收尾。

### P4. 掌握度主体翻转（知识点→题型）
**1. 问题现象**：方案口径"掌握度按知识点/单调不减"，与落库（题型/累计平均）完全对不上——文档与实现脱节。

**2. 触发流程**：Java 组装 `mastery_snapshot`（`List[KpSnapshot]`）→ 每轮传 `DecideRequest.mastery_snapshot`（`models/tutoring.py:141`）→ `decider.py:79`/`:118` `snapshot_top_n` → `core/tutoring/context.py:33-43`（按 mastery_level 升序，薄弱在前）→ 取 `s.label`（`decider.py:80`、`:118`）→ `prompts.py:152-176` 把快照标签注入 `_DECIDE_SYSTEM` 的 `{snapshot_labels}` 段。

**3. 根因分析**：掌握度事实源从知识点表切成题型表，`kp_key` 语义从 TextbookKP URI 变为**题型名（canonical，如「鸡兔同笼」）**，`mastery_level` 变为题型累计平均正确率（0-100）。**契约字段名不变、值语义变了**——容易误导后续开发者拿 kp_key 反查图谱/做题型↔知识点映射。

**4. 排查过程**：对账契约文档与实际落库（题型表/累计平均）发现口径冲突；再全代码搜 kp_key 用途，确认 Python 侧只在模型字段定义处出现、decide 只用 label+mastery_level 作背景上下文、从不反查图谱。

**5. 解决方案 & 改动点**：Python 侧核查后确认**天然兼容、无需逻辑改动**。改动为契约文档对齐 + 验收测试：`models/tutoring.py:70-79` `KpSnapshot` docstring 明确"Python **不要**拿 kp_key 反查图谱/做题型↔知识点映射（桥已移到后端 ADMIN 维护接口）"；`prompts.py:88-89` 快照段标题改"学生题型掌握度快照"；`context.py:33-43` 注释知识点→题型；`test_decider.py:195-205` 验收测试 `kp_key="鸡兔同笼"` 正常处理。

**6. 面试口述要点**：讲"**契约字段名不变但语义漂移的坑**"——kp_key 从 URI 变题型名，文档没跟上。技术权衡：Python 无状态只看 label+level，天然兼容；关键是把"不要反查图谱"写进模型契约注释防止误用。踩坑收获：**跨端契约语义变更时，不只要改实现，还要改文档 + 验收测试锁住新语义**。

### P5. langchain 流式丢 thinking
**1. 问题现象**：流式想展示"思考过程"（decide 的推理 / generate 的推理），但前端/Java 拿不到 reasoning。

**2. 触发流程**：decide/generate 的流式主路径（`api/tutoring.py:41-81` decide、`:84-118` generate）→ `decider.py:115` / `generator.py:42` `streamer = ark_stream.stream_chat` → `core/tutoring/ark_stream.py:89-144` `stream_chat`（httpx.stream POST `{api_base}/chat/completions`）→ `_parse_sse_lines`（`:31-86`）逐行解析原始 SSE → yield `{"reasoning": delta.get("reasoning_content"), ...}`（`:81-86`）。decide 侧把 reasoning 吐成 thinking 事件（`decider.py:134-135`）；generate 侧 `enable_thinking=True` 流式展示推理。

**3. 根因分析**：langchain-openai 的 `ChatOpenAI` **流式解析会丢弃 `reasoning_content`**（实测 `additional_kwargs` 也为空）——不是模型不吐，而是 **SDK 解析层丢字段**。前端/Java 因此拿不到思考过程，reasoning 也无法用于流式决策。

**4. 排查过程**：前端说"没思考过程"→ Java 中继查 thinking 事件为空 → Python 打印流式 delta 发现 `reasoning_content` 存在但被 ChatOpenAI 丢弃 → 对比直连方舟原始 SSE 能拿到 → 定位为 SDK 解析层缺陷而非模型配置。

**5. 解决方案 & 改动点**：decide/generate 主路径改**直连方舟读原始 SSE**（`ark_stream.py`），请求体 thinking 开关参数化（`:126`）：`"thinking": {"type": "enabled" if enable_thinking else "disabled"}`。分层思考：decide 关思考（意图秒出 ~1.5s）、generate 开思考（`enable_thinking=True`，解答段思考 = AI 版进度条）。`generator.py:8-9`、`decider.py:134-135` 同步。测试 `tests/tutoring/unit/test_ark_stream.py`（`_parse_sse_lines` 纯函数）。

**6. 面试口述要点**：讲"**框架封装层丢字段，直连底层才拿到**"——langchain 流式丢 reasoning_content，是 SDK 兼容层缺陷。技术权衡：直连方舟读原始 SSE 换取字段完整性，但丢失框架的便捷性（自己拼消息、解析、错误处理）。踩坑收获：**流式字段依赖框架解析时，先验证框架是否真的透传**；分层思考（decide 关/generate 开）既是性能决策也是体验决策。

### P6. decide 两分法（不答题不该收尾）
**1. 问题现象**：学生没答题/在闲聊，decide 也可能判 `end` 收尾——会话被 Java 直接终止，引导链断裂。

**2. 触发流程**：decide 端点 → `build_decide_messages`（`prompts.py:152-176`）→ `_decide_system`（`:127-130`）把 `_DECIDE_SYSTEM`（`:18-90`）整段注入 → 模型据此选 type。

**3. 根因分析**：修前 `_DECIDE_SYSTEM` 是"终止型无关 vs 澄清型模糊"分类（见 `1f0b517` 前身）："完全与学习无关（闲聊…）→ type=end（终止会话）"——**模型对"是否该结束"判定过松**，学生没答题/在闲聊也可能判 end 收尾。

**4. 排查过程**：从会话异常终止的日志反推——对比被误收尾会话的 message 内容，发现多是"闲聊/没答题"场景；再对照 `_DECIDE_SYSTEM` 的分类档位，确认"无关→end"这档过松、没有"作答但答错→引导"档。

**5. 解决方案 & 改动点**：重写为**两分法**（`prompts.py:61-68`「核心判定：是否在答题」）：
- **在答题**（作答/答错/答偏/求助/提问/追问）→ 引导解题，**绝不 end、绝不 reveal**（否定硬规则）
- **不在答题**（闲聊/状态/离题/打招呼/非数学题/无法确定）→ 一律 `concept` 引导回题，保持会话 ACTIVE，**绝不 end**
- **唯一例外**：只有明确结束（"我不做了""结束吧""再见"）才 `end(ABANDONED)`
`GENERATION_RULES` 同步收紧 end/concept 语义（`prompts.py:185-187`）。

**6. 面试口述要点**：讲"**两分法比多分类稳**"——把"是否在答题"二分类作为唯一核心判定，其余全部回退 concept 引导，杜绝模型自由发挥"是否该结束"。技术权衡：宁可引导回题（低风险）也不误收尾（高风险）；"否定式硬规则"（绝不 end/绝不 reveal）比"正向列举"更抗模型幻觉。

### P7. 集成测试 403 误报
**1. 问题现象**：`test_chat_api` integration 组合跑报 403，单跑可能通过——测试结果不可复现。

**2. 触发流程**：`tests/llm/integration/test_chat_api.py` 的 `headers` fixture 构造 `{"x-internal-token": ...}` → 请求 Python `verify_internal_token`（`api/chat.py:27-35`，token 缺失或不等 → 403）。

**3. 根因分析**：修前 headers 用 `os.environ.get("INTERNAL_TOKEN", "test_internal_token")`。组合跑时**其他测试顶层 import 提前实例化 `settings` 单例**（锁定 `.env` 真实 token），而 `os.environ` 的 test 值（`tests/conftest.py:51` 设为 `test_internal_token`）与之不匹配 → 403 误报。本质是**测试 token 来源与鉴权校验端不一致**。

**4. 排查过程**：单跑通过、组合跑挂 → 怀疑测试间污染 → 对比 headers token 来源（os.environ）与校验端（settings 单例）→ 确认单例锁定导致来源分叉。

**5. 解决方案 & 改动点**：headers 改用 `settings.INTERNAL_TOKEN`（`api/chat.py` 校验同一来源），与 tutoring integration 测试既有做法一致（`tests/tutoring/integration/test_tutoring_api.py:78-80` `_headers` 默认 `settings.INTERNAL_TOKEN`）。`bed0bb1` 验证：integration 组合 37 passed，全量离线套件 241 passed。

**6. 面试口述要点**：讲"**测试环境的全局单例污染**"——settings 单例被组合测试提前实例化，导致 os.environ 与单例 token 分叉。技术权衡：测试里 token 来源必须与校验端一致（都走 settings）；踩坑收获是"**测试隔离性**"——共享全局状态时，用同一条取值路径，别一个 os.environ 一个 settings 各拿各的。

## 二、后端端（aiEduPlatform）

### J1. 会话卡死 SENDING（P0 防卡死）
**1. 问题现象**：会话永久卡"发送中"，前端无法恢复（会话 116 卡死根因）。学生发一条消息后 UI 永远转圈，发不了下一条。

**2. 触发流程**：`start/sendMessage/requestAnswer`（TutoringController → `TutoringAppService.java:206/267/299`）→ `orchestrate`（`:578`）→ `llmPort.decideStream(ctx)` 中继（**SSE 200 已发出**）→ meta 到达 → `postDecide`（`:618`）→ `applySideEffects` 落库（DB）→ `buildStream` → `llmPort.generate`。任意环节抛异常都会落到 `orchestrate` 的 `onErrorResume(e -> handleDecideFailure(session, e))`（`:614`）。

**3. 根因分析**：修复前 `handleDecideFailure` 只对 `TutoringAgentException` 降级，其他异常（DB 落库等）原样 `Flux.error(e)` 上抛——**SSE 200 已发出后直接断连，前端收不到 meta/done 终态** → 永久卡 SENDING。本质是"流已建立但无终态事件"。

**4. 排查过程**：从"永久 SENDING"反推——前端等 done 终态；Java 看 orchestrate 日志发现落库异常被原样抛给 SSE；确认断连发生在 `applySideEffects` DB 落库环节。

**5. 解决方案 & 改动点**（`TutoringAppService.java`）：
- `postDecide` 内 `applySideEffects + save` 包 try-catch，异常**降级继续不阻断 SSE**（`653-656`）
- `handleDecideFailure` 不再区分 agent/非 agent：`session.getId()==null` 才重抛，否则一律 `friendlyErrorStream(session)` 兜底终态流（meta + 「网络波动，请重试」token + done），**会话保持 ACTIVE 可重试**（`676-686`）
前端配合 F1 加 SSE 看门狗。

**6. 面试口述要点**：讲"**SSE 会话的终态保证**"——流式接口最怕"连接活着但没终态"。技术权衡：落库失败降级继续（数据最终一致）优先于阻塞流式体验；任何异常都兜底终态流让前端可恢复。踩坑收获：**流式协议必须有 done/error 终态契约，异常路径不能静默断流**。

### J2. 落掌握度 ReflectionException
**1. 问题现象**：答疑落掌握度抛反射异常，掌握度写库失败。

### J4. 答对信号丢失（score=0 / 直接答对不落库）
**1. 问题现象**：学生**直接答对**收尾（END 轮），掌握度却记 0 / 不落库。

**2. 触发流程**：`applyMasteryAndErrors`（`TutoringAppService.java:727`）→ 第 3.1 节信号累计判定（`:734-740`）→ 结算时 `persistQuestionAttempt`。

**3. 根因分析**：修复前 `settlingRound = SWITCH || END || REVEAL` **整轮跳过累计**。但 END 轮有真实 eval（学生答对 `exerciseComplete` 收尾）也被跳过 → rounds 空 → 结算时无信号 → score=0 / 直接答对不落库。本质是**"收尾轮"一刀切跳过，误伤了 END 轮的真实作答**。

**4. 排查过程**：从"直接答对掌握度 0"反推——看结算分支的 settlingRound 判定，发现 END 轮整轮跳过；再确认 END 轮其实携带 eval（答对 exerciseComplete），被误伤。

**5. 解决方案 & 改动点**（`TutoringAppService.java:734-740`）：
```java
boolean noRealAnswer = allowedType == ActionType.SWITCH
        || ((allowedType == ActionType.END || allowedType == ActionType.REVEAL) && action.getEval() == null);
if (!noRealAnswer) {
    boolean hinted = session.getAnswerRequestCount() > 0;
    boolean correct = action.getEval() != null && Boolean.TRUE.equals(action.getEval().getCorrect());
    session.onRoundSignal(correct, hinted);
}
```
`noRealAnswer` 收紧：SWITCH 恒跳过；END/REVEAL 仅当 `eval==null`（无真实作答评估）才跳过，有 eval 即真实作答应累计。回归测试：END 答对 → 0.70。

**6. 面试口述要点**：讲"**一刀切跳过策略误伤真实信号**"——SWITCH 整轮跳过没问题，但 END/REVEAL 轮可能有真实 eval。技术权衡：用"是否有真实作答"（eval 非空）替代"是否是收尾轮"作判定，精确不误伤。踩坑收获：**信号收集的排除条件要按"有没有数据"而不是"轮次类型"判断**。

### J5. 题型误并（一元一次/一元二次）
**1. 问题现象**：向量聚类把"一元一次方程/一元二次方程"归并成一个题型，掌握度被污染。

1. 流结束（EOF）但没收到 done/error → `onError({ code: 'SSE_EOF' })`「连接中断，请重试」
2. 看门狗：`watchdogTimeout` 内无任何字节 → `onError({ code: 'SSE_TIMEOUT' })`「答疑响应超时，请重试」+ `reader.cancel()`
错误进入 `handleTurnError` → `setPhaseBoth('IDLE')` 回退可重试态，最近 user 消息标记 `retryable`。

**6. 面试口述要点**：讲"**前端对流式协议也要有终态兜底**"——后端保证终态（J1），前端再加看门狗双保险。技术权衡：EOF 判失败 + 超时看门狗 + 回退可重试态，把"卡死"变成"可重试"；看门狗用"无字节"而非"无事件"判定，抗思考长停顿。踩坑收获：**SSE 客户端必须有 EOF/超时两条兜底，别只依赖 done 事件**。

### F2. 刷新后找不到 ACTIVE 会话 / 同题孤儿会话
**1. 问题现象**：generate 卡死/中断时本轮无 done，刷新后 sessionId 归 null → 下一条消息重复建会话，历史里堆出同题单轮孤儿。

**2. 触发流程**：`send()`（`useTutoringSession.js:493`）无 `sessionIdRef` → `startSession`；有 → `sendMessage`（路由判定在 `:527-531`）。会话 id 只在 `handleDone`（`:419`）持久化到 localStorage。挂载恢复在 `:850-873`：从 localStorage 找 `status === 'ACTIVE'` 的会话。

**3. 根因分析**：generate 卡死（后端曾漏 `.timeout`，本轮无 `done`）→ `handleDone` 不执行 → `persistSession` 不落库 → 刷新后 localStorage 无 ACTIVE 会话 → `sessionIdRef` 归 null → 下一条消息走 `startSession` 重复建会话。本质是"**持久化时机太晚（只等 done）**"。

**4. 排查过程**：从"历史里同题单轮孤儿"反推 → 看会话 id 持久化时机（只在 handleDone）→ 确认卡死轮无 done 时 id 未落库。

**5. 解决方案 & 改动点**：提交 `873bd78`——`handleMeta` 收到 `meta.sessionId` 即 `persistSession(meta.sessionId, messagesRef.current, 'ACTIVE')`，**不等 done**。`writeStoredSession` 按 id 幂等更新（`useTutoringSession.js:45-56`），刷新后挂载恢复能找回 ACTIVE 会话续走 `sendMessage`。

**6. 面试口述要点**：讲"**关键状态要在最早可得的时机持久化**"——sessionId 在 meta 到达就有，别等 done。技术权衡：meta 即持久化（幂等）换取刷新可恢复，代价是提前落库（会话可能未完成就存 ACTIVE）。踩坑收获：**"恢复能力"的边界 = 状态持久化的时机**；卡片式恢复要拿"最早可靠信号"而非"最完整信号"。

### F3. 50002 残留 ACTIVE 反复重放
**1. 问题现象**：后端清库后本地残留 ACTIVE，发消息仍走旧 id——每次刷新重放"会话已失效"notice，挂载恢复死循环。

**2. 触发流程**：后端清库（删孤儿会话）后，本地 localStorage 仍残留 `ACTIVE` 陈旧条目。挂载时 `useTutoringSession.js:850-873` 找到本地 ACTIVE → `setSessionState('active')` + `reconcileSession(active.id)`。`reconcileSession`（`:664`）调 `getSession(id)`，后端返回 50002。

**3. 根因分析**：旧行为 50002 分支只 `setSessionState('ended')`，**不清 localStorage、不重置 `sessionIdRef`** → `sessionIdRef` 残留 → 发消息仍走旧 id（`send()` 的 `!sessionIdRef.current` 判定不触发 `startSession`）。本质是"**把确定性错误（会话不存在）当历史回看处理，没清理本地状态**"。

**4. 排查过程**：从"反复重放已失效会话"反推 → 看 50002 分支行为（只 setState('ended')）→ 确认未清 localStorage、未重置 id。

**5. 解决方案 & 改动点**：提交 `c8fcd90`：
- 新增 `removeStoredSession(id)` helper（`:59-67`）
- `reconcileSession` 与 `loadSession` 的 50002 分支改为：`removeStoredSession(id)` + `resetState()`（回新建态）+ `setNotice('会话已失效,可发起新会话')`（`:704-711`、`:826-831`）
- 与接口失败兜底区分：网络失败仍保留本地快照

**6. 面试口述要点**：讲"**确定性错误要清理本地状态，网络错误才保留快照**"——50002 是"会话不存在"，本地残留必须清；网络失败才是"暂不可用"应保留。技术权衡：区分错误类型（确定性 vs 瞬时）决定本地状态策略。踩坑收获：**本地缓存的生命周期要跟后端状态对齐，过期条目要能自愈**。

### F4. 图片直看超时中断
**1. 问题现象**：图片分析（多模态）最坏 ~60s，前端 30s 先超时中断，误报失败。

**2. 触发流程**：`QuestionAnalysis.jsx` 粘贴/拖拽/拍题 → `captureImage` → `handleDirectAnalyze` → `tutoringApi.analyzeQuestionImage(file)`（`QuestionAnalysis.jsx:193-213`）。后端：Python `question-understand` 单次 30s（慢转 Python）+ Java retry 叠加 60s（转 Java），最坏约 60s。

**3. 根因分析**：`analyzeQuestionImage` 原先 `timeout: 30000`（提交 `b9fc538` 前），后端最坏 60s > 前端 30s → 前端先超时中断（axios `ECONNABORTED`）。本质是"**前端超时 < 后端最坏耗时**"。

**4. 排查过程**：从"图片分析偶尔报超时失败"反推 → 看后端最坏耗时（60s）→ 对比前端 axios timeout（30s）→ 确认前端先断。

**5. 解决方案 & 改动点**：提交 `b9fc538`：
- `tutoring.js` `analyzeQuestionImage` timeout 30s→60s（`:266-273`）
- `QuestionAnalysis.jsx` 超时（`ECONNABORTED`/`ETIMEDOUT`）区分专属文案「AI 看图分析耗时较长（约 30~60 秒）」+ loading 时长提示
对比：`recognize`（OCR 文本识别）仍为 30s。

**6. 面试口述要点**：讲"**前端超时要覆盖后端最坏路径**"——后端 retry 叠加到 60s，前端 30s 必然误断。技术权衡：超时放大到后端最坏耗时 + 专属文案管理预期；用错误码区分"超时"与"真失败"。踩坑收获：**前端 timeout 必须 >= 后端最坏耗时（含重试），否则误报是必然的**。

### F5. AI 步骤消息无换行
**1. 问题现象**：AI 输出的步骤列表挤成一行——流式期间有换行，done 后反而消失（会话 103 实测 5 步挤成一段）。

**2. 触发流程**：AI 输出「步骤1:…\n步骤2:…」用单个换行分隔。流式期间 `MessageBubble.jsx:83` 用 `whitespace-pre-wrap` 有换行；`done` 后切 `ReactMarkdown` 渲染。

**3. 根因分析**：markdown 软换行（单个 `\n`）**默认被折叠成空格** → `ReactMarkdown` 把多步骤挤成一段。流式/完成两种渲染方式行为不一致。

**4. 排查过程**：从"完成后步骤挤一行"反推 → 对比流式（pre-wrap 有换行）与完成（ReactMarkdown 折叠）→ 确认是 markdown 软换行折叠。

**6. 面试口述要点**：讲"**渲染层行为要跟流式预览一致**"——markdown 软换行折叠 vs pre-wrap 保留，导致完成态比流式难看。踩坑收获：**AI 输出里单换行是语义（步骤分隔），要显式保留**；remark-breaks 是低成本方案，关键是不让"完成态"比"流式态"退化。

### F6. 夜间模式覆盖无效
**1. 问题现象**：登录页跟随全局夜间模式，`data-theme` 覆盖无效——白底+深色组件混搭。

**2. 触发流程**：登录页为硬编码浅色设计（白卡片/浅渐变），`main.jsx` `import 'daisyui/dist/full.css'` 引入全部内置主题 + `prefers-color-scheme` 自动深色。系统深色模式下，登录页组件（input 等）走 dark 变量变黑。

- 提交 `6dc6531`：`tailwind.config.js:77-81` `themes` 数组追加第二主题 `"light"` 占位 → 触发 daisyUI 生成 `[data-theme=aiedu-light]` 具名规则 → 覆盖真正生效，保持品牌色

**6. 面试口述要点**：讲"**主题框架的具名规则生成是有条件的**"——daisyUI 单个主题只注入 :root，两个才生成 data-theme 覆盖。踩坑收获：**用 UI 框架的主题覆盖前，先搞清楚具名规则的触发条件**；"加了属性但不生效"要往框架生成逻辑查，别怀疑 CSS 优先级。

### F7. isEnded TDZ 白屏
**1. 问题现象**：历史链路触发 TDZ（temporal dead zone）白屏——页面直接白屏不可用。

**2. 触发流程**：历史链路（HistoryDrawer 选中会话 / 挂载恢复）走 `loadSession`/`reconcileSession`。提交 `ef8ee61` 前的代码：`const isEnded = sessionState === 'ended'` 声明在**文件尾部**（`useMemo` 之后、`return` 之前），而前面 `useEffect(() => { refreshHistory() }, [sessionId, roundCount, isEnded])` 的依赖数组**引用后部的 `const isEnded`**。

**3. 根因分析**：JS 暂时性死区（TDZ）：`const isEnded` 在声明前被 `useEffect` 依赖数组读取 → `ReferenceError: Cannot access 'isEnded' before initialization` → 组件白屏。本质是"**变量声明位置晚于被引用处**"。

**4. 排查过程**：从"白屏"反推 → 看浏览器 console ReferenceError → 定位到 `useEffect` 依赖数组引用后部 `const`。

**5. 解决方案 & 改动点**：提交 `ef8ee61`——`isEnded` 声明**提前到该 `useEffect` 之前**（当前 `useTutoringSession.js:753`），消除依赖数组引用后部 `const` 的 TDZ。

**6. 面试口述要点**：讲"**TDZ 是 JS 常见但隐蔽的初始化坑**"——const 声明前被读必抛 ReferenceError。踩坑收获：**hook 依赖项用到的变量要声明在 hook 之前**；这类白屏优先看 console 的 ReferenceError，比猜渲染问题快。
