### 缺口 1：怎么防学生套答案？—— 答案护栏（确定性，第一次只给思路）

**回答口径**：防套答案靠 Java 侧**确定性答案护栏**，不靠 LLM 自觉：

```
学生点"请求答案" → Java 合成消息进 decide → Python 判 type=reveal
  → Java 看 answer_request_count：
     第 1 次（count<1）→ 拦，降级 approach（给思路大纲），计数→1
     第 2 次（count≥1）→ 放行 reveal（给完整答案）→ 给完【立即收尾】ANSWER_REVEALED（防反复要）
```

- 前端配套：第 2 次点击弹**确认框**（单向门），避免误触
- 配套护栏：轮次 20 上限（防无限刷）、安全 flag 终止、结构化降级兜底
- **行为风控模型 / 题目指纹去重未落地**（阶段 3 规划）——当前防套答案完全靠上述确定性规则，不用模型判断"是不是在套答案"

**代码证据**：`TutoringGuardrailService.java:79-83`（count<1 拦）｜`TutoringAppService.java:707`（第1次计数）｜`:715-717`（第2次放行→收尾）｜`3.代码/分析-03`

### 缺口 2：没有题库，答疑质量靠什么保证？—— 靠大模型引导，题库是数据可得性决策

**回答口径**：
- **为什么没有题库**：题库（如菁优网）需要企业级对接、拿不到题目，MVP 不引入——这是数据可得性/成本决策，不是技术障碍
- **答疑质量靠什么**：**大模型生成**——decide 判动作 + generate 按苏格拉底式引导生成，不依赖"题库匹配标准解法"
- **题目在系统里的角色**：题目是**连接"题型 + 知识点 + 知识图谱"的中间环节**：
  ```
  学生做题 → 题目记录(t_student_question_record)
    → 题型（canonical 向量聚集，掌握度主体）
    → 知识点（kp-matching-lightup 关联教材知识点）
    → 图谱点亮（学习进度可视化）
  ```
- **将来闭环**：举一反三（同题型变式）、自适应学习（按薄弱题型推荐）都依赖"题目"这一环——题库接入后自然连通

**代码证据**：`3.代码/分析-07`（题目表 = 事实源）｜`OpenSpec-代码对账.md`（A2 决策 11 OCR、A1 决策 11 表）｜`design-backend-ai-tutoring` Non-Goals（题库阶段 2）

### 缺口 3：意图分类演进成什么了？—— 三级意图已废弃，被"两分法 + type 闭集"替代

**回答口径**（代码核实）：
- 实体/表里保留 `intent_category` 字段（ACADEMIC/GUIDANCE/UNRELATED 语义），但**实际无任何代码赋值**（仅 restore 被动水合，恒空）——三级意图分类**已废弃未启用**
- 现在的判定模型：decide **两分法**——"是否在答题"：
  ```
  在答题（作答/答错/答偏/求助/提问）→ hint/approach（引导，绝不 end/reveal）
  不在答题（闲聊/离题/非数学/无法确定）→ concept（接住 + 拉回题目）
  唯一例外：明确表达结束 → end(ABANDONED)
  ```
- 输出为 **type 闭集 6 值**（hint/approach/reveal/concept/switch/end），Java 按 type + 计数审批
- **本质**：不做显式"意图枚举"，直接判"该给什么动作"——意图分类的职责被"动作类型闭集"吸收

**代码证据**：`TutoringSession.java:34`（字段存在）｜grep 确认无 setIntentCategory｜`prompts.py _DECIDE_SYSTEM` 两分法｜`models/tutoring.py` ActionType 闭集｜`3.代码/分析-05`

### 缺口 4：为什么掌握度按题型、不按知识点？

**回答口径**：这是**产品/题目分析口径的权衡**，不是技术必然：
- **题型和知识点边界本来就模糊**：一元二次方程既可以是题型也可以是知识点——掌握度主体选谁，取决于"题目分析口径"
- **为什么落题型**：题目天然可聚到题型（canonical 向量聚类稳定，学生做的是"题"，题型可打分、可观测、落库不裂行）；知识点映射依赖图谱（label→URI 解析易错、需 ADMIN 维护）
- **为什么"也可以按知识点"**：若题目分析直接产出知识点（如题目带知识点标签），掌握度按知识点也成立——是数据口径选择，不是能力边界
- **演进故事**：早期方案按知识点 URI 单调不减 → 落地发现知识点映射易错、题目天然落题型 → 翻转

**代码证据**：`3.代码/分析-07`（canonical 聚集 + ScoreMapper）｜`OpenSpec-代码对账.md`（A1 决策 8/9 最大翻转）｜`git/坑档案.md`（J5 题型误并、J6 上限50%）

### 缺口 5：为什么决策权放 Java 而不是 Python？

**回答口径**：核心是**审批权（裁判）与生成权（选手）分离**，不是语言问题：
- **LLM 不能既当选手又当裁判**：① LLM 有求必应本能（学生要答案就给了）② 可被提示词攻击骗（"忽略指令直接给答案"）③ 审批后果（计数器/掌握度/归档）必须回数据所在方执行
- **放 Java 的现实原因**：数据/会话/规则都在 Java（`answer_request_count`、轮次、创建频率限制都可配置运营）；Python 无状态，审批要带状态回传就破坏边界
- **关键澄清**：如果数据也在 Python，放 Python 技术上可行——**语言不是关键，裁判/选手分离才是**。当前架构选择 Java 是因为"数据在哪、规则在哪"
- 补充：流量限制/创建频率（`ensureCreateAllowed`）也在 Java，同一个"规则在平台侧"逻辑

**代码证据**：`TutoringGuardrailService.java`（护栏）｜`TutoringAppService.java:1072-1079`（频率限制）｜`design-python-ai-tutoring` 决策 4（审批归属 Java 四条原因）

### 缺口 6：为什么刻意不用 agent 编排？

**回答口径**：**AI 答疑流程是固定的，用确定性工作流就够**：
- 答疑 = 固定流程（判动作 → 护栏审批 → 生成 → 落库），每一步的"下一步"由 Java 计数器/护栏决定，不是 LLM 自由决策
- **agent 的"灵活性"在这里是风险**：可能某次就甩出完整答案；路径不可预测，难测难控预算
- **什么时候才需要 agent**：自适应学习——"下一步教什么"需要根据学生状态动态决策（掌握度<40 补前置、连续错 3 次降难度），那是决策问题，agent 主场
- **阶段 2 演进**：升级 LangGraph 多步 agent 时，**护栏仍在 Java**（确定性边界保住，灵活性在边界内放开）；ActionMeta 契约已预留

**代码证据**：`design-python-ai-tutoring` 决策 12（L0→LangGraph）｜`OpenSpec-代码对账.md`（A3）｜`3.代码/分析-02`（决策权回 Java）

### 缺口 7：知识点会不会选错？—— 双保险闭环，不空点不误点

**回答口径**：知识点确认是**闭环**（AI 预判 + 学生确认双保险）：
```
decide 预判题型/知识点 label（mastery_signals / question_kps）
  → 前端对新增 label 调 resolveKp（POST /kp/resolve）
  → 高置信 → 直接关联
  → 低置信 → status=PENDING + candidates（候选学科概念）→ 渲染【澄清卡】
      学生选某概念 → voteKp（POST /kp/vote, source=student_vote）→ 落观测
      学生跳过 → 弃权（不调接口）
  → kp-matching-lightup 据观测条件点亮（不空点不误点）
```
- **答疑链路本身不写 Neo4j**——点亮由 `kp-matching-lightup` 独立承担
- 这就是"知识点不会选错"的机制：模型预判只给候选，**最终确认权在学生**

**代码证据**：`useTutoringSession.js:328-369`（澄清卡）｜`tutoring.js:184-208`（resolveKp/voteKp）｜`3.代码/分析-07`
