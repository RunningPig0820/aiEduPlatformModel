## 业务情况（答案对错的判定链）

### 1. decide 输出：动作类型闭集 + 评估（软硬信号分离）
Python decide 输出 `ActionMeta`：
- **硬信号** `type`（闭集 6 值）：`hint / approach / reveal / concept / switch / end`——Java 护栏据此放行/拒绝。
- **软信号** `eval`：`correct(对错) / error_type(错误类型) / emotion(F7七态) / exercise_complete(是否独立解出)`。
- **答对判定的真相**：`eval.correct` 由 decide 的 LLM 对**学生上一轮回答**做判断（两分法——正确/不正确），不是靠关键词匹配。

### 2. end 收紧三类（确定性护栏，不信任模型格式）
`_sanitize_end_consistency`（decide 输出收尾前必过）：`type=end` 必须满足 end 联动契约，否则降级：
- **COMPLETED**（独立解出）必须 `correct=true` **且** `exercise_complete=true`——否则 invalid
- `end_reason` 缺失 → 无效 end
- 无效 end → **降级 `type=concept`**（生成规约允许"明确引导/确认、拉回题目、不给答案"），清掉 end 字段，**保持会话 ACTIVE、不终止**。
- 动机（代码注释）：实测模型「断言答对但答案错误」场景，reason 明说"不应收尾"却输出 end，且 end_reason 偶发与 correct=false 矛盾——若放行，答错的学生会被"恭喜"，summary 还可能泄出完整解答。

### 3. reveal 门禁（判对链的出口管制）
- `type=reveal`（要答案）→ Java 答案护栏：count<1 → 降级 approach；count≥1 → 放行 reveal 并**收尾 ANSWER_REVEALED**（见分析-03）。
- 判对链在 Java 侧还有一个「学生断言答对」的确认复核路径：低置信时走澄清卡（resolve/vote）让学生**确认知识点**，而非直接采信模型。

### 4. 作答信号如何落掌握度（判对 → 分数）
- 每轮 `eval.correct` + `session.getAnswerRequestCount()>0`（是否被引导过）→ `session.onRoundSignal(correct, hinted)` 累计到当前题。
- 结算时 `ScoreMapper.effectiveScore`：直接答对 1.0 / 引导后答对 0.5 / 答错 0.0 × per-题型打折（详见分析-07）。
- 错误事件 B3 门控：只有 hint/approach 轮且模型明确给出 `error_type` 才算**真实学生错误**写入（switch/end/reveal/concept 轮的 correct=false 是模型默认值，非真实错误）。
