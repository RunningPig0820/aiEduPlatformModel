## 业务情况（防并发、防滥用、防卡死的三道防线）

### 1. 会话并发锁（防同一会话消息错乱）
- **Redis 锁**（`SET NX EX`，key `learning:tutoring:lock:{sessionId}`，TTL **45 秒**）包裹临界区：decide + 落库副作用。
- 锁未获取（并发双发）→ 同步抛「会话繁忙，请稍后再试」（4xx，不回流）；锁在 decide+副作用结束后由 orchestrate 释放，**generate 流式在锁外**（不持锁长流）。
- 错误/取消路径 `doFinally` 兜底释放锁（幂等，AtomicBoolean compareAndSet）；同步构建阶段异常立即释放后重抛。
- 未注入 RedisService（纯单元测试）时直通。

### 2. 会话创建频率限制（防滥用）
- `ensureCreateAllowed`：Redis 计数器（`learning:tutoring:create:{studentId}`），窗口内 > 上限（`ai-edu.tutoring.create-window-minutes` / `create-limit`）→ 抛 50004「创建会话过于频繁」。
- 仅真正建会话时限制（start）；非 math 跳过不消耗创建配额。

### 3. 多级降级兜底（SSE 已建立后绝不卡死）
| 兜底 | 触发 | 行为 |
|---|---|---|
| **Python 结构化四段降级** | decide 四段管线全失败 | 返回 `type=hint + degraded=true`（Java 监控降级频次），不 503 |
| **decide 原始流失败** | 流式决策失败 | 降级非流式 decide()（四段管线） |
| **Java agent 调用失败** | Python 调用失败重试后仍失败 | 已有会话 → `friendlyErrorStream`：「网络波动，请重试」+ 会话保持 ACTIVE 可重试 |
| **SSE 卡死防线** | SSE 已建立后任何异常（含 DB 落库） | `handleDecideFailure`：已有会话一律降级为终态流（meta + 兜底 token + done）——曾导致会话卡死 SENDING 的根因修复 |
| **generate 空流** | 模型零 token | 固定引导话术（`_EMPTY_STREAM_FALLBACK`），学生不收到空回复 |
| **落库副作用失败** | 掌握度/记录写库异常 | try-catch 降级继续，SSE 不中断，教学回答照常流式；完整日志供 P1 定位 |
| **学科分类失败** | subject-classify 异常/超时 | `classifySafely` → null → 按 math 放行（宁可漏拦不误拦） |
| **护栏降级** | reveal 未授权 / 轮次达顶 | 降级 approach / 强制收尾固定话术 |
| **COS 归档异步** | COS 上传慢/失败 | 单线程调度器异步提交，SSE 不等待；幂等整写防覆盖 |

### 4. 前端韧性
- 会话级错误（50002/50003）→ 直接切 ended + 提示；消息级错误 → 标记可重试（`retryLast` 重发最近一条 user 消息，仅消息轮次）。
- localStorage 离线兜底（对账失败保留本地快照）；transcript 获取失败回退 recentMessages。
- 每次刷新挂载对账，避免 sessionIdRef 残留导致重复建会话。
