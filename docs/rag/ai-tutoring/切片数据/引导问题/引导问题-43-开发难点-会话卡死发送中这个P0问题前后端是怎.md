## 回答

**核心结论**：三端配合——后端兜底终态流 + 前端 SSE 看门狗 + meta 早持久化，把"永久 SENDING"从根源解决。

**分层展开**：
- **现象**：会话永久卡"发送中"，前端无法恢复（真实会话 116 卡死）。
- **根因**：SSE 200 已发出后 Flux.error 直接断连，前端收到流结束却无终态（无 done/meta）→ 永久 SENDING；落库副作用异常也会把整个流打挂。
- **Java 侧**：落库副作用异常**降级继续**（不阻断回复）；非 agent 异常（含 DB 落库）也**兜底终态流**——meta + 兜底 token + done，会话保持 ACTIVE 可重试。
- **前端侧**：SSE 看门狗——长时间无事件判定流已断，回退可重试态（不永久转圈）；meta 到达即持久化 localStorage（防 generate 中断丢 sessionId → 重复建会话）；50002 清理陈旧 ACTIVE。
- **配套**：Python stream_generate 每轮检测 request.is_disconnected()，客户端断开即中止。
- **教训**：SSE 流必须保证"有开始必有终态"，兜底终态流 + 看门狗双保险，是流式架构的工程底线。
