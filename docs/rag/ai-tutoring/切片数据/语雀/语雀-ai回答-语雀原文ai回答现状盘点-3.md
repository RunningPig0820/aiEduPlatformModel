关键决策点：Python侧要不要有状态？
- 方案 A（推荐 MVP）：Python无状态，Java 每次把全量历史消息传过去。单一事实来源，不会有两套会话状态打架。
- 方案 B：Python 用自己的 session_id 缓存上下文（网关已返回 session_id，说明它本来就支持）。省 token，但会引入"Java 状态 vs Python 状态"双源问题，调试地狱。
MVP 用 A，对话变长后再切 B 也不迟——session_id 字段早就预留了。

四、业务需求合不合理：28点要砍，砍完核心其实很小
你明确要的（学科/题型判断、无关就默认回复、学生确认知识点、图谱点亮）——这些恰恰是最便宜的，因为都只是"分类 + 落库 + 调图谱"。真正重的是题库指纹、结构化步骤、易错分支、行为风控——这些全都可以是第二阶段。

但有几个设计假设，你必须先想清楚，否则会埋雷：
①"严禁直接输出答案"是产品赌博，有流失风险。 真实学生会直接说"给我答案"。如果硬封锁且无出口，学生会弃用。需要定一个"看答案"逃生通道——比如学生明确要求或尝试 N 步之后，允许揭示答案（设计文档的 F6
支持中途终止，但终止后给不给答案，文档没写）。这是业务决策，不是技术决策，得你拍板。
②知识点确认的交互打断。 设计文档说"AI 预判 + 学生确认"，但如果是在对话中途弹一个确认卡，会很割裂。建议放结尾一次性确认（答疑结束后给一张"本次涉及知识点，是否正确？可修正"的卡），而不是边聊边确认。你强调"通过学生
来确定知识点"，这个一定要保留，但位置决定体验。
③"条件点亮"的规则必须写死在Java，不能交给LLM猜。 "完成一次完整引导式交互"太模糊——学生第一步就答对了算不算？学生放弃算不算？需要定确定性规则（如：进入引导且至少正确回应 1 个关键提问 → 点亮；连续答错最后给答案
→ 半亮）。否则图谱点亮率会失控。
④图谱目前只有数学（人教版）。 学科分类可以做（KgSubjectEnum 已存在），但语文/英语没有图谱节点，点亮无处可落。MVP 建议：学科分类正常做，但"点不亮"要优雅降级（提示"该知识点暂未收录"）。这也反过来印证阶段 2
才需要题库指纹。

五、需要你拍板的决策点
1. 答案出口策略——苏格拉底引导过程中，学生明确要答案时给不给？（这是产品决策，影响最大）
2. 知识点确认的时机——结尾一次性确认卡 vs 对话中确认？

> ⚠️ **最终拍板（2026-08 代码）**：**未采用"结尾一次性确认卡"**——落地为**低置信澄清卡**：mastery_signals 的 label 前端调 `/kp/resolve`，若 PENDING+candidates → 弹卡学生选/跳过 → `/kp/vote` 落 `source=student_vote` 观测。解决的是"题型解析归属确认"，非"图谱点亮确认"。
3. 点亮规则——什么情况算"完整交互"？连续失败算什么状态？
4. 多学科范围——MVP 只做数学（图谱齐），还是学科分类做全、点亮只对数学生效？
5. 会话深度——MVP 是否限制单次会话轮数（比如最多 20 轮，防 token 失控）？
