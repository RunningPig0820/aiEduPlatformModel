二、技术栈怎么分：Java 管状态机，Python 管智能
这是最核心的决策，也是你"不需要全部在 Java 后端"的正确打开方式。
答疑流程本质是一个确定性状态机，箭头是 Java 的业务逻辑，箭头上的每个"智能动作"才是 Python/LLM：

落地方式：完全复用现有 scene 机制，给 Python 网关加 4 个场景：

> ⚠️ **最终拍板（2026-08 代码）**：落地不再是「4 个 scene」——Python 侧收敛为 **decide**（非流式出动作元数据 type 闭集：hint/approach/reveal/concept/switch/end）+ **generate**（流式正文）两端点，外加两个 stateless 小端点（`subject-classify` 学科门 / `question-understand` 图片题型识别）。4 个 scene 的能力被 decide 单次调用合并（intent/socratic/eval/kp_extract → ActionMeta 一次输出）。

Java 侧新增一个 tutoring 有界上下文（TutoringSession 聚合 + TutoringAppService），它编排这 4
个场景、驱动状态机、调用已有的 KG 仓储点亮图谱。
一个建议：LangChain 在这里可以不上。

> ⚠️ **最终拍板（2026-08 代码）**：结构化输出**实际用了 LangChain**——`bind_tools([ActionMeta])` function calling + 四段降级管线（tool_call → JSON mode → 正则 → 兜底 hint），保证 API 绝不吐畸形 ActionMeta。「直接调模型 API」的建议未采纳：复用网关现有 LangChain 通道 + 白拿结构化约束。 你的流程是 Java 驱动的确定性状态机，Python 侧只是"单次 prompt +
JSON schema 结构化输出"，直接调模型 API 比 LangChain 编排更干净。LangChain 的价值（agent、tool、复杂
chain）在这个场景用不上。
