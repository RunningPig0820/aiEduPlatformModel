# RAG 双池检索方案（全量池 + 切片池）

> 状态：**方案设计**（2026-08-26，待评审落地）
> 目的：回答两类不同查询方向的问题——整体/全局问题用完整文档（全量池），细节/步骤问题用切片（切片池），两池独立索引、各召回一次、RRF 融合。

---

## 1. 背景与动机

当前 RAG 是**单一索引** `rag-index`（324 块，全部是切片）。面试问题分两类查询方向：

| 问题类型 | 示例 | 需要的数据形态 |
|---|---|---|
| **整体/全局** | "AI答疑是什么？" "架构怎么分工？" | **完整文档**（权威整篇，不丢上下文） |
| **细节/步骤** | "某一步怎么走？" "J1 这个坑根因？" | **切片**（细粒度块，精准命中） |

单一索引用切片块回答整体问题，会丢失整篇上下文；用完整文档回答细节问题又会太泛。**双池检索**让两池互补：全量池管整体、切片池管细节，各召一次再融合。

## 2. 用户决策（2026-08-26 确认）

| 决策项 | 结论 |
|---|---|
| **全量池内容** | `1.语雀/`(5) + `4.完善文档/`(8) + `3.代码/`(10) 的**完整文档**，每篇一块 → **23 块** |
| **切片池内容** | `docs/rag/ai-tutoring/切片数据/` 下全部 → **324 块**（当前 jsonl） |
| **索引隔离** | 两个独立索引 `rag-full` + `rag-slice`，同一 RAG 桶 `rag-1318177119` 下 |
| **召回融合** | 全量池召一次 + 切片池召一次 → **RRF 融合**取 Top-K；切片池可按 category 筛选优化 |

## 3. 数据流全景（改造后）

```
全量池源(语雀5+完善文档8+代码10) ─slice_full.py─▶ rag_slices_full.jsonl(23块, tags.pool=full)
切片池源(切片数据/ 324块)          ────────────▶ rag_slices.jsonl(324块, tags.pool=slice)
                                                      │
                          build_index.py --pool full  │  build_index.py --pool slice
                                                      ▼
                                        rag-1318177119 / rag-full + rag-slice
                                                      │
查询: retrieve_dual(question) ──▶ rag-full 查一次 + rag-slice 查一次
                                                      │
                          orchestrate: 三路 RRF 融合(全量向量 + 切片向量 + BM25)
                                                      ▼
                                          generate(doubao)
```

## 4. 关键架构约束

1. **text 不进 metadata**（COS 向量索引 ~20KB/条限制）——text 在编排阶段按 `key` 从本地 jsonl 反查。
2. **key 是唯一 join key**：`_key_of` = `ai-tutoring/{file}/{anchor}#{_idx}`。全量池与切片池是**不同块**，需加**池命名空间**防同 `(file, anchor)` 冲突。
3. `retrieve_vector` 当前硬编码 `vector_type="rag"`；`orchestrate` 是 3 元 RRF（vec + bm25 + 锚定加权），可扩展第三路。
4. `_resolve_bucket_index` 只特判 `vector_type == "rag"` → 需改 `startswith("rag")`，否则 `rag-full/rag-slice` 会落默认桶（错误）。

## 5. 设计细节

### 5.1 数据准备
- **新增 `scripts/rag/slice_full.py`**：`1.语雀/` + `4.完善文档/` + `3.代码/分析-*.md` 每篇整文件一块（mode="file"）→ `rag_slices_full.jsonl`（23 块）
  - tags：复用 `_tags`（source/authority/module/section/file/file_path/anchor）+ `category` + `pool: "full"`
- **切片池**：现有 `rag_slices.jsonl` 324 块，脚本补 `tags.pool = "slice"`（幂等）

### 5.2 key 加池命名空间
```python
# 全量池 key:  rag-full/{file}/{anchor}#{idx}
# 切片池 key:  rag-slice/{file}/{anchor}#{idx}
```
- `build_index.make_key(pool, file_, anchor, idx)`
- `query._key_of(b)` 从 `b["tags"]["pool"]` 取前缀

### 5.3 索引写入（`build_index.py`）
- `VECTOR_TYPE` 写死 → 支持 `--pool full|slice`
- `rag-full` 读 `rag_slices_full.jsonl`；`rag-slice` 读 `rag_slices.jsonl`
- 分别 `_resolve_bucket_index("rag-full")` / `("rag-slice")`；`--clear` 各清各的
- `settings.COS_VECTORS_INDEXES` 加 `"rag-full": "rag-full"`, `"rag-slice": "rag-slice"`

### 5.4 桶路由（`vector_store.py`）
- 特判 `vector_type == "rag"` → `vector_type.startswith("rag")`

### 5.5 双池召回（`query.py` + `assistant.py`）
- `retrieve_vector(question, vector_type="rag")` 加参（默认 "rag" 兼容）
- 新增 `retrieve_dual(question)`：
  ```python
  full  = retrieve_vector(question, vector_type="rag-full")
  slice = retrieve_vector(question, vector_type="rag-slice")
  return {"full": full, "slice": slice, "bm25": ...}
  ```
- `orchestrate` 加可选参数 `vec2_result`（默认 None 向后兼容）：
  - 融合集 = `set(vec_full_rank) | set(vec_slice_rank) | set(bm_rank)`
  - rrf 累加三路 `1/(RRF_K + rank)`
- **切片池 category 筛选**：策略带 `locked_categories` 时，只对 slice 池命中按 category 过滤；全量池不过滤

### 5.6 调用方核对
- `query.py:352`、`api/rag.py:57/63`、`scripts/rag/rag_query.py:33/41`、`core/rag/assistant.py:76/111` 同步
- `generate` 层零改动（只消费 hit["text"]）

## 9. BM25 与双池的关系（2026-08-26 实测结论）

### 9.1 BM25 不能去掉——双池和 BM25 是正交的

**双池解决"存哪"（全量/切片），BM25 解决"多一路召回"**。双池后是三路 RRF 融合，BM25 作为独立关键词路继续保留：

```
查询 ──▶ 全量池向量(rag-full) ─┐
       ──▶ 切片池向量(rag-slice)─┼──▶ RRF 融合 ──▶ top-K
       ──▶ BM25(本地jsonl) ─────┘   ← 这路还在
```

**BM25 独特价值（向量替代不了）**：

| 场景 | 向量能否替代 | 为什么 BM25 有用 |
|---|---|---|
| 专业术语/代码名（decide / SseMasterySignalDTO / 表名） | ⚠️ 可能 miss | 精确关键词命中 |
| 短问题精确匹配（"J1 会话卡死"） | ⚠️ 语义漂移 | 精确命中坑编号 |
| 向量召回质量差时兜底 | ❌ | 第二路独立信号 |
| COS 向量桶挂了（断网） | ❌ 全断 | **BM25 纯本地，可降级查询** |

**结论**：双池把向量路从 1 路变 2 路，BM25 是第 3 路，三路互补都要留。去掉 BM25 会掉精确召回（术语/编号）。等块数上千 BM25 变慢时，优化方向是**缓存倒排索引**或**分模块独立 BM25**，而不是去掉。

### 9.2 只 BM25 summary 的权衡（实测 324 块）

| 方案 | 耗时 | 加速比 | Top-10 命中重合 |
|---|---|---|---|
| 全量（text+summary） | 170 ms | 1× | — |
| **只 summary** | 9.6 ms | **~18× 快** | **7/10** |

**结论：不建议只 BM25 summary**：
- summary 是 LLM 生成的一句话（几十字），信息密度低
- 精确关键词（decide / 坑编号 / 表名）多在 **text 正文**，不在 summary → 漏 30% 精确召回
- 当前 170ms 相对 COS 网络 + LLM 生成**不构成瓶颈**，为省 160ms 牺牲 30% 召回不划算

**正确优化路径**（块数上千、真慢时）：缓存 BM25 倒排索引（块不变复用，查询只打分）→ 保留全 text；或 `select_corpus` 按模块过滤只打目标模块池。
