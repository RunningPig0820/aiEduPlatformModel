### 1. LLM 推理的成本与效率
+ **成本控制**：优先使用免费的 GLM-4-flash 模型作为主力，零成本兜底；DeepSeek 仅作为备选补充，就算全量 5.6 万知识点跑通，单轮调用的 token 量极低，整体成本也在百元以内，demo 阶段不做严格的成本预算，优先跑通流程。
+ **推理节奏**：接受 3-9 小时的总串行推理时长，demo 阶段不追求极致速度，先保证稳定性，不做复杂的并行调用开发，后续核心流程跑通后再做优化。
+ **执行策略**：不一次性全量处理所有学科，**先从数学学科（4490 个知识点）起步**，单学科仅需 90 次左右的 LLM 调用，1 小时内就能跑完验证，确认流程通顺、效果达标后，再扩展其他学科。

---

### 2. 质量保障机制
+ **人工审核**：demo 阶段完全不设置教研人工审核环节，无相关人员参与，全流程自动化执行。
+ **准确率要求**：demo 阶段不设严格的准确率指标，只要核心知识点的前置依赖逻辑通顺，抽样测试准确率≥70% 就完全满足 demo 演示需求。
+ **低置信度处理**：置信度 < 0.7 的关系直接过滤丢弃，不做人工复核，仅保留高置信度的强依赖关系，既减少 LLM 幻觉带来的逻辑错误，也简化 demo 阶段的处理流程，不追求全量关系覆盖。

---

### 3. Neo4j 部署状态
+ **部署与版本**：已完成单机部署，使用 Neo4j 社区版 4.4.x 版本，兼容现有操作，避免高版本新特性的兼容问题。
+ **配置情况**：单机 8G 内存、100G 以上存储，完全满足十万级节点、百万级关系的 demo 使用需求，无集群部署计划。
+ **备份策略**：demo 阶段采用 CSV 文件全量备份，每次数据库导入前，先备份核心 CSV 源文件，无需复杂的数据库定时备份机制，简单可控，出问题可快速通过 CSV 文件重建数据库。

---

### 4. 业务优先级
所有优先级完全围绕「AI 引导式答疑」这个核心 demo 场景展开，排序如下：

1. **P0（核心必做）**：前置依赖查询 → 这是所有业务场景的核心基础，也是当前方案的核心目标
2. **P1（demo 必实现）**：知识点识别、知识缺陷诊断（学情掌握度计算）→ 直接支撑 AI 答疑的核心功能闭环
3. **P2（可选迭代）**：学习路径推荐、年级 / 学科定位 → 核心场景跑通后再补充，demo 阶段不做强制要求

---

### 5. 数据更新机制
+ **基准数据**：demo 阶段使用 edukg 的静态权威基准库，知识点永久固定不变，不考虑教材更新、新课标调整等变动，原始 TTL 数据源永久冻结只读。
+ **维护规则**：demo 阶段仅做增量的「题目 - 知识点」关联数据补充，不修改基准知识点和已生成的前置依赖关系，无长期持续维护计划。
+ **版本管理**：demo 阶段不设计复杂的版本管理机制，仅通过 CSV 文件命名做简单的版本区分（如`knowledge_points_v1.csv`），后续正式迭代再补充完整的版本管理能力。

### 补充核心诉求
我当前的核心目标，是先快速跑通**数学学科的最小闭环**，验证「TTL 解析→LLM 生成前置关系→Neo4j 导入→AI 答疑场景验证」的全流程可行性，全量学科处理、性能优化、复杂功能扩展，都是核心闭环跑通后的迭代内容，当前所有设计都要优先保证「简单、快速、可落地」。
