# 知识图谱项目 - 问题与解决方案总结
> 基于 kg-math-complete-graph 项目实践总结  
搭建者: 用户 + GLM5

最终成果: 6,757 节点 + 20,887 关系 + 97.1% 匹配率

## 一、数据缺失问题
### 问题描述
原始教材 JSON 数据中，部分年级的知识点字段为空：

| 学段 | 知识点数 | 问题 |
| --- | --- | --- |
| 小学1-2年级 | 47 | 部分有知识点 |
| 小学3-6年级 | **0** | knowledge_points 全空 |
| 初中7-9年级 | 252 | 较完整 |
| 高中必修 | **0** | 仅有综合测试标记 |


### 解决思路
**方案**: LLM 推断补全

1. 使用双模型投票机制（GLM-4-flash + DeepSeek-chat）
2. 根据章节信息（学段、年级、章节名、小节名）推断知识点
3. 支持断点续传，避免重复调用

**结果**: 缺失章节 295 个 → 推断知识点 1052 个 → 平均置信度 0.93

---

## 二、知识点匹配效率问题
### 问题描述
原方案遍历所有图谱知识点进行 LLM 匹配：1350 × 5000 = 675万次 LLM 调用 → 不可行

### 解决思路
**方案**: 两阶段匹配（向量粗筛 + LLM投票）

+ 粗筛: BAAI/bge-small-zh-v1.5 向量检索 top-20
+ 精筛: LLM 双模型投票（DS=0.6, GLM=0.4, threshold=0.5）

**效果**: LLM调用次数从 500万 → 2.7万（下降 99%）

---

## 三、语义匹配问题
### 问题描述
difflib 只能匹配字符相似度，无法理解语义：

+ "勾股定理" vs "毕达哥拉斯定理" → difflib 不匹配
+ "百分数" vs "百分比" → difflib 不匹配

### 解决思路
**方案**: 向量检索 + 完整词同义词映射

+ 向量检索自动理解语义相似度
+ 同义词完整词匹配（避免 "加法交换律" 误匹配 "加法"）

---

## 四、同义词过度匹配问题
### 问题描述
原方案使用 `key in name` 进行同义词扩展，导致过度匹配：

+ "加法交换律" 不应等同于 "加法"

### 解决思路
**方案**: 完整词精确匹配（normalized_name == normalized_key）

---

## 五、Topic继承偏差问题
### 问题描述
知识点 topic 字段直接继承章节 topic，导致语义矛盾：

+ "加法" 属于 "位置" 章 → 错误继承为 "图形与几何"

### 解决思路
**方案**: 基于匹配的 EduKG Concept 的 Class 类型修正

+ 规则映射: 数学概念→数与代数, 几何图形→图形与几何
+ 修正144个知识点 topic

---

## 六、断点续传问题
### 问题描述
LLM 任务耗时较长（推断2-3小时、匹配1-2小时），中断后需要重新执行

### 解决思路
**方案**: 集成 llmTaskLock 模块（TaskState + CachedLLM + ProcessLock）

+ 中断后可继续执行
+ 相同 Prompt 不重复调用 LLM

---

## 七、进度显示问题
### 问题描述
断点续传时，循环索引作为进度显示不准确（已恢复500个，显示 0.1%）

### 解决思路
**方案**: 使用实际已完成数量（包含已恢复的断点）

---

## 八、异常处理问题
### 问题描述
LLM 调用失败时中断整个知识点处理

### 解决思路
**方案**: try-catch 继续下一个候选，不中断主流程

---

## 九、未匹配记录问题
### 问题描述
原方案只输出匹配成功的知识点，无法分析未匹配原因

### 解决思路
**方案**: 输出所有知识点，增加 `matched` 字段，记录未匹配原因

---

## 十、向量索引构建问题
### 问题描述
每次匹配都重新加载模型和计算向量索引（~60秒）

### 解决思路
**方案**: 预构建索引（一次构建，多次复用）

+ 输出: kg_vectors.npy, kg_texts.json, kg_concepts.json, index_meta.json

---

## 十一、属性覆盖率低问题
### 问题描述
```plain
textbook_kps.json:       1350 个知识点
textbook_kps_enhanced.json: 299 个知识点（仅 22% 有属性）
```

### 根因分析
**执行顺序问题**: 属性增强在 LLM 推断之前执行

### 解决方案
LLM 推断完成后重新运行属性增强，对 1052 个推断知识点补充属性

---

## 十二、知识点匹配率低问题（结构错位）
### 问题描述
初始匹配率仅 17%，LLM 匹配率仅 2%

### 根因分析
+ 小学 69.6% 教材知识点（如 "1-5的认识"）无法匹配 EduKG 抽象概念
+ EduKG 以高中抽象概念为主

### 解决方案
**两阶段匹配**: LLM 标准化预处理 → 向量检索 → LLM 投票

+ "1-5的认识" → LLM推断 "自然数的基本概念" → 匹配 EduKG "自然数" ✓

---

## 十三、LLM 调用效率低问题（穷尽遍历）
### 问题描述
原始逻辑遍历全部 20 个候选，每个调用 2 次 LLM → 最坏 40 次 API/知识点

### 解决方案
**三重优化**:

1. 相似度阈值检查（< 0.5 跳过）
2. LLM 调用上限（前 3 个候选）
3. 早停策略（匹配成功立即退出）

**效果**: 整体提速约 50x

---

## 十四、缓存机制
### 缓存作用
+ 存储 GLM + DeepSeek 双模型投票结果
+ 相同知识点对重复匹配时直接读取，跳过 2 次 API 调用
+ 8255 个缓存 → 可节省 16,510 次 API 调用

## 经验总结
### 1. 性能优化优先级
```plain
LLM调用次数 > 字符比较次数 > 内存占用
```

减少 LLM 调用是核心，其他优化是次要。

### 2. 语义匹配策略
```plain
向量检索 > 同义词映射 > difflib
```

向量检索是最强大的语义匹配方式。

### 3. 健壮性设计
```plain
try-catch > 断点续传 > 进度显示
```

确保任务可恢复、可中断。

### 4. 数据完整性
```plain
输出全部 > 仅输出成功
```

输出所有结果便于分析和改进。

### 5. 导入脚本设计
```plain
--clear 幂等 > 增量更新
```

所有导入脚本支持 --clear 先清后导，保证幂等性。

### 6. 长上下文价值
三个多星期、几十次对话，长上下文能力让每个 Phase 的设计决策都能传承，避免了重复解释和重复踩坑。
