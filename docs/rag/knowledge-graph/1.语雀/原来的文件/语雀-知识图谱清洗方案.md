### 🔍 为什么要这样做？（核心优势）
如果每计算出一条关系就去数据库插入一次，会有很多问题。现在的方案解决了以下痛点：

#### 1. 性能瓶颈
+ **错误做法**：循环 5000 个知识点，每次调用 LLM 后立即执行 `CREATE` 语句。这会导致数据库连接频繁开关，速度极慢。
+ **正确做法**：在 Python 内存中处理好所有关系，最后通过 `LOAD CSV` 或批量事务一次性写入。速度快几十倍。

#### 2. 数据安全与回滚
+ **场景**：假设 LLM 跑到一半报错了，或者定义抽取规则写错了。
+ **后果**：如果是边跑边写，你的数据库里已经写入了一半的脏数据，清理非常麻烦。
+ **优势**：现在的方案会先生成 CSV 文件。你可以**先检查 CSV 文件**，确认逻辑没问题了，再执行导入脚本。

#### 3. 方便调试与验证
在导入数据库之前，你可以直接打开生成的 CSV 文件检查：

```plain
# PREREQUISITE.csv 示例
from_uri,to_uri,confidence,source
http://...整式方程,http://...一元二次方程,0.85,definition_dependency
```

这比去数据库里查 Cypher 要直观得多。

### 🛠️ 具体实施步骤演示
根据方案，你的脚本执行顺序应该是这样的：

#### 步骤 1：导入节点（先打地基）
运行 `import_nodes.py`。

+ 此时 Neo4j 里只有：学科、年级、教材、章节、知识点节点。
+ **没有任何 PREREQUISITE 或 TEACHES_BEFORE 关系**。

#### 步骤 2：计算关系（离线加工）
运行 `build_prerequisites.py`。

+ **输入**：知识点 CSV 文件。
+ **处理**：
    - 函数 A：读取章节顺序 -> 生成 `teaches_before_list`。
    - 函数 B：读取定义文本 -> 匹配关键词 -> 生成 `prerequisite_list`。
    - 函数 C：调用 LLM -> 生成 `candidate_list`。
+ **输出**：生成三个 CSV 文件在磁盘上。
    - `relations_teaches_before.csv`
    - `relations_prerequisite.csv`
    - `relations_candidate.csv`

#### 步骤 3：导入关系（盖楼）
运行 `import_relations.py`。

+ **读取**：上一步生成的 CSV 文件。
+ **执行**：Cypher `MATCH ... MERGE ...` 批量创建关系。
+ **结果**：Neo4j 中形成完整的知识图谱。

---

### 💡 总结
**处理关系时，数据还在 Python 脚本的内存或本地 CSV 文件里，并没有进 Neo4j。**  
只有在最后一步“导入关系”脚本执行时，才会真正写入数据库。这种**“计算与存储分离”**的设计是处理大数据构建图谱的最佳实践。
