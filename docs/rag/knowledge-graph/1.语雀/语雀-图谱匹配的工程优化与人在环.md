> summary: 解答「教材知识点如何匹配进 EduKG 数学知识图谱——匹配率为何初始只有 17%、经哪些工程优化才可落地、匹配不上的 308 个又靠什么人在环兜底」：本文档是知识图谱匹配的完整工程优化实录，面试官追问"匹配率怎么从 17% 提到 97.1%""LLM 调了多少次""匹配不上的怎么办"时可整段引用。一、17% 根因不是算法差而是"数据抽象层级错位"：69.6% 教材知识点是小学具体知识（小学940/初中252/高中158），EduKG 1295 个概念几乎全是高中抽象概念（余弦定理、一元二次方程），具体对抽象天然对不上，初始 LLM 匹配率仅 2%；解法是匹配前先用 LLM 把教学名标准化成抽象概念列表再匹配：1-5的认识→[数的认识,自然数,数字]→匹配自然数（相似度0.711），连加连减→[减法]（0.655），秒的认识→[秒]（0.830）。二、LLM 调用三重优化：穷尽 top-20 候选×2 模型=最坏 40 次 API/知识点（3.5 小时仅处理 290 个）；三个参数——相似度<0.5 直接跳过（SIMILARITY_THRESHOLD）、候选上限 3（LLM_CANDIDATE_LIMIT）、首候选命中即早停——把调用压到 2 次/知识点，整体提速约 50 倍，LLM 调用从 500 万降至 2.7 万（降 99%）。三、双模型投票与缓存：匹配用 GLM-4-flash+DeepSeek-chat 双模型投票且必须 consensus（两模型一致）才算匹配，抑制单模型幻觉；一致取平均置信度，不一致按 DS=0.6/GLM=0.4 加权且 DS 有否决权；缓存键 md5(教材知识点+图谱概念)，存完整决策（decision/confidence/primary_reason/secondary_reason+两模型完整响应），8255 个缓存文件省 16,510 次 API 调用，支持"为何判不匹配"审计。四、人在环兜底：最终仍 308 个未匹配，按根因分两类处置——297 个颗粒度差异（教材比图谱更细，如"分数除法意义"）+11 个图谱缺失（如"田忌赛马故事背景""莫比乌斯带定义"）；审核闭环=进 MySQL 审核表 textbook_kp_match_review（前5候选JSON+置信度）+LLM 推荐接口 /api/kp-match/recommend+Web 人工审核（确认/拒绝/改选/新建），结果回写 Neo4j MATCHES_KG（置信度+方法），新建知识点用 v3.2 URI，reviewer_id/review_time 可追溯可回滚。五、Topic 继承污染的逆向修复（数据血缘 bug）：知识点属性 topic 直接继承章节，导致"加法"在"位置"章节被错标为"图形与几何"；修复用下游匹配到的 Concept 的 Class 类型反推 topic（数学概念/数学运算→数与代数，几何图形/几何性质→图形与几何，统计概念→统计与概率），修正 144 个（数与代数+36、图形与几何-44）。附录（仅供人工查阅、不参与 RAG）：完整踩坑实录 edukg/core/textbook/problems_and_solutions.md（763行16问题），匹配代码 kp_matcher.py 与双模型投票 dual_model_voter.py，审核系统 edukg/scripts/kg_data/+design-python-kp-match-review-system.md。

## 一、匹配率 17% 的根因：不是算法差，是"数据错位"

### 抽象层级错位：小学知识点 vs 高中抽象概念
> 状态：
> 检索摘要：匹配率为什么一开始只有 17%？不是算法问题——69.6% 教材知识点是小学具体知识（1-5的认识），而 EduKG 1295 个概念几乎全是高中抽象概念，抽象层级错位，直接匹配自然对不上。

一开始匹配率只有 **17%**（LLM 匹配仅 2%），一开始以为是算法不行，查下来根因是**数据抽象层级错位**：

| 侧 | 内容 |
|---|---|
| 教材知识点 | 小学 940（**69.6%**）/ 初中 252 / 高中 158，是"1-5 的认识""连加连减"这种具体知识 |
| EduKG 概念 | 1,295 个，几乎全是"余弦定理""一元二次方程"这种高中抽象概念 |

**具体知识点直接匹配抽象概念，天然对不上**——这不是 LLM 能力问题，是数据不在一个抽象层级。

### 解法：LLM 标准化预处理，先翻译成抽象概念
> 状态：
> 检索摘要：抽象层级错位怎么解？先用 LLM 把教学名标准化成抽象概念列表再匹配——1-5的认识→[数的认识,自然数,数字]，匹配自然数（相似度0.711）。

解法不是换算法，而是**在匹配前先用 LLM 做标准化预处理**：把具体的教学名翻译成抽象概念列表，再走向量粗筛 + 投票：

```
"1-5 的认识" → LLM 标准化 → ["数的认识", "自然数", "数字"] → 匹配 EduKG "自然数"（相似度 0.711）
"连加连减"   → LLM 标准化 → ["减法"]（相似度 0.655）
"秒的认识"   → LLM 标准化 → ["秒"]（相似度 0.830）
```

> 一句话面试答案："匹配率 17% 的根因是抽象层级错位——69.6% 小学具体知识点对不上 EduKG 高中抽象概念；解法是匹配前先用 LLM 把教学名标准化成抽象概念列表，1-5的认识翻译成[数的认识,自然数]再匹配。"

## 二、LLM 调用三重优化：40 次 → 2 次，整体提速 50 倍

### 问题：全量遍历候选，LLM 调用爆炸
> 状态：
> 检索摘要：LLM 匹配为什么会调用爆炸？穷尽遍历 top-20 候选 × 2 个模型 = 最坏 40 次 API 每个知识点，3.5 小时才处理 290 个。

三段式匹配里 LLM 是最后一道，但**穷尽遍历候选**会爆炸：top-20 候选 × 2 个模型 = 最坏 **40 次 API 调用**每个知识点。实测 3.5 小时才处理 290 个知识点。

### 三重优化：相似度阈值 + 候选上限 + 命中早停
> 状态：
> 检索摘要：LLM 调用怎么降下来？三重优化——相似度 <0.5 直接跳过（不调 LLM）+ 候选上限 3 个 + 首候选命中即早停，每个知识点从 40→2 次 API，整体提速约 50 倍。

三个参数把 LLM 调用压下来：

| 优化 | 参数 | 效果 |
|---|---|---|
| 相似度阈值跳过 | `SIMILARITY_THRESHOLD=0.5`，低于直接跳过 | 大多数知识点根本不进 LLM |
| 候选上限 | `LLM_CANDIDATE_LIMIT=3` | 最多调 3 个候选 |
| 命中早停 | 首候选匹配成功即停 | 从 40→2 次 API（20 倍） |

**整体效果：约 50 倍提速**，LLM 调用从 500 万 → 2.7 万（降 99%）。

> 一句话面试答案："LLM 调用爆炸是因为全量遍历候选——40 次 API/知识点；三重优化（相似度<0.5 跳过、候选上限 3、命中早停）压到 2 次，整体提速约 50 倍、调用降 99%。"

## 三、双模型投票与缓存：抑制幻觉 + 可审计

### 双模型必须共识：抑制单模型幻觉
> 状态：
> 检索摘要：为什么双模型投票要共识？GLM 和 DeepSeek 两个模型判断一致才算匹配（consensus），抑制单模型幻觉；缓存同时保存两个模型响应供审计。

匹配判断用 **GLM-4-flash + DeepSeek-chat 双模型投票**，而且**必须 consensus（两模型一致）才算匹配**：

- 两模型一致 → 取平均置信度采纳
- 不一致 → 加权投票（DS=0.6/GLM=0.4），DS 有否决权

这是**抑制单模型幻觉**的工程答案——一个模型可能自信地错，两个模型一起错概率低得多。

### 缓存存"决策 + 双模型理由"，可审计可复用
> 状态：
> 检索摘要：匹配缓存设计有什么讲究？缓存键 md5(教材知识点+图谱概念)，8255 个缓存文件省 16,510 次 API 调用；缓存内容保存两模型完整响应（决策/置信度/主次理由），支持"为何判不匹配"审计。

匹配结果缓存不只是存"结论"，**存完整决策**：

- **缓存键**：`md5(textbook_kp + kg_kp)`，确定性可复用
- **缓存内容**：`decision / confidence / primary_reason / secondary_reason` + **两模型完整响应**
- **效果**：8255 个缓存文件，省 16,510 次 API 调用
- **审计价值**：面试/复盘时能解释"为什么这个判定不匹配"——不是黑盒

> 一句话面试答案："匹配缓存存的是完整决策——两模型响应+置信度+理由，8255 个缓存省 16,510 次调用；为什么判不匹配随时可审计，不是黑盒。"

## 四、人在环：匹配不上的 308 个怎么办

### 未匹配按原因分类，不是"剩下就丢掉"
> 状态：
> 检索摘要：匹配不上的知识点怎么处理？308 个未匹配按根因分两类——297 个颗粒度差异（教材更细，如分数除法意义）+ 11 个图谱缺失（如田忌赛马背景、莫比乌斯带定义），分开处置。

最终仍有 **308 个未匹配**，关键是不当"垃圾"丢掉，而是**按根因分类**：

| 分类 | 数量 | 原因 |
|---|---|---|
| 颗粒度差异 | 297 | 教材更细（"分数除法意义"图谱里没有这么细的概念） |
| 图谱缺失 | 11 | 图谱真没有（"田忌赛马故事背景""莫比乌斯带定义"这类） |

颗粒度差异是"教材比图谱细"，图谱缺失是"图谱该补但还没有"——两类处置方式完全不同。

### 审核闭环：MySQL 审核表 + LLM 推荐 + Web 人工确认
> 状态：
> 检索摘要：未匹配的审核闭环怎么设计？308 个进 MySQL 审核表（textbook_kp_match_review），LLM 推荐前 5 候选，Web 页面人工审核（确认/拒绝/改选/新建），审核结果回写 Neo4j MATCHES_KG。

审核闭环 = **自动化 + 人在环**，可解释且可回滚：

```
308 未匹配
  → MySQL 审核表 textbook_kp_match_review（前 5 候选 JSON + 置信度）
  → LLM 推荐接口 /api/kp-match/recommend（输入教材知识点 → 前 5 候选）
  → Web 审核页：人工确认 / 拒绝 / 改选 / 新建知识点
  → 审核结果回写 Neo4j MATCHES_KG（置信度 + 方法）
```

- 新知识点用 **v3.2 URI** 前缀（不与已有版本冲突）
- 批量误确认可追溯（reviewer_id/review_time）

> 一句话面试答案："308 个未匹配按根因分类——297 个颗粒度差异、11 个图谱缺失；进 MySQL 审核表，LLM 推荐前 5 候选，Web 人工确认后回写图谱，可追溯可回滚。"

## 五、Topic 继承污染的逆向修复（数据血缘 bug）

### 简单继承的代价：加法被标成"图形与几何"
> 状态：
> 检索摘要：知识点专题继承有什么 bug？属性规则里 topic 直接继承章节，导致"加法"在"位置"章节被错标为图形与几何——用匹配到的 Concept 的 Class 类型反向修正 144 个。

匹配工程里还踩了一个**数据血缘 bug**：知识点属性 `topic` 直接继承章节，结果"加法"知识点出现在"位置"章节，被错标成"图形与几何"。

**修复是逆向数据流**——用**下游匹配结果回改上游字段**：

- 知识点匹配到的 EduKG Concept → 拿它的 Class 类型 → 反推规则映射 topic
- 映射表：数学概念/数学运算 → 数与代数；几何图形/几何性质 → 图形与几何；统计概念 → 统计与概率
- 结果：**修正 144 个**（数与代数 +36、图形与几何 -44）

> 一句话面试答案："踩过数据血缘 bug——topic 直接继承章节，加法在位置章节被错标成图形与几何；用下游匹配到的概念 Class 类型反向修正了 144 个。"
