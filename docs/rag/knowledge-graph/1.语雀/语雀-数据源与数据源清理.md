## 一、图谱的数据都是哪来的？

### 主数据源：为什么选清华 EduKG，而不是自己建
> 状态：✅
> 检索摘要：知识图谱主数据源为什么用 EduKG？清华 THU-KEG 学术开源、官方 SPARQL 端点背书，8 学科 39,890 实体——教育图谱没有比它更权威的现成资源，自己从零建图谱成本和准确性都不可控。

图谱的"语义层"（概念/定义/概念类）用的是**清华大学 THU-KEG 组的 EduKG 开源图谱**，这是教育领域最权威的现成资源。选它的理由很朴素：

- **权威可背书**：学术机构开源，官方 SPARQL 端点导出，面试被问"数据可信吗"有底气
- **覆盖够广**：8 个学科、约 39,890 个实体，数学一个学科就 4,252 个概念
- **自己建不划算**：从零建教育图谱，成本高、准确性不可控，不如站在学术成果上

> 一句话面试答案："语义层用的是清华 EduKG 开源图谱，权威、覆盖广、官方端点背书——教育领域没有比它更成熟的现成资源。"

### 但 EduKG 有个致命短板：初高中为主，小学初中几乎空白
> 状态：✅
> 检索摘要：EduKG 有什么短板？知识点以高中抽象概念为主、没有按学段划分，小学教材知识点几乎对不上——这是后面补爬虫和课标数据的直接原因。

选型时发现 EduKG 不是完美的：

- 它的知识点**以初中高中抽象概念为主**（余弦定理、一元二次方程这类），小学数学的"1-5 的认识"这种具体到不行的知识点它基本没有
- 知识点**本身没有学段标注**，按学科划分，不按小学/初中/高中划分
- 结果就是：小学 69.6% 的教材知识点在 EduKG 里匹配不上

这个短板直接决定了后面要补两条数据路。

### 补路一：爬人教版教材目录，把"教材结构"补全
> 状态：✅
> 检索摘要：小学初中教材数据怎么补？EduKG 的 main.ttl 只覆盖高中教材，于是写爬虫爬教师之家，拿到人教 K-12 数学 23 册完整目录（小学12+初中6+高中人教A版5），高中只保留 2019 新课标版本。

教材的"结构层"（教材→章节→小节→知识点）EduKG 提供不全——main.ttl 只标注了高中教材，小学初中是空的。所以：

- 写了个爬虫爬**教师之家**（人教版教材目录站），拿到人教 K-12 数学**完整 23 册**（小学 12 册 + 初中 6 册 + 高中人教A版 5 册）
- 高中特意**只保留 2019 新课标的人教A版**，其他旧版不爬——数据要跟最新课标对齐
- 爬虫做成**断点续爬**，爬一半断了接着爬，不用重来

> 一句话面试答案："教材结构是爬教师之家拿的，人教 K-12 数学 23 册完整目录，高中只保留 2019 新课标版本。"

### 补路二：从课标补充小学知识点
> 状态：✅
> 检索摘要：小学知识点怎么补？义务教育课程标准 2022 是扫描版 PDF，用 OCR 识别后结合教材爬虫数据，补出小学概念类 1 个、知识点 20 个、定义 122 条、关联 312 条。

小学这块 EduKG 和教材 JSON 都缺，就找**课标**——义务教育课程标准 2022 是唯一把小学知识点写全的权威文件。问题是它是扫描版 PDF（189 页），得先 OCR 出来：

- OCR 用的是百度 OCR API（扫描版只能这么识别）
- OCR 结果 + 爬虫教材数据互相印证，补出小学数学：**概念类 1 个、知识点 20 个、定义 122 条、关联 312 条**
- 好未来的小学知识图谱 JSON 还拿来做层级参考

> 一句话面试答案："小学知识点从义务教育课标 2022 补的——扫描版 PDF 先 OCR，再和教材数据互相印证补进去。"

### 数据源整合：source 编码当跨图谱 join key
> 状态：⚠️（方案已定，整合脚本待做）
> 检索摘要：多数据集怎么打通？同一领域数据散在 4 个独立数据集（EduKG 0.1 图谱 / material.ttl 3.0 教材 / all_concept Class / meta 分类）且 ontology 版本不同，用知识点 source 编码（1.1.1.1.1）和教材章节编码（1.1）做前缀映射，不改模型就打通知识点↔章节。

数据不是"一个库"，同一领域的数据散在 **4 个独立数据集**而且 ontology 版本不同（0.1 vs 3.0），缺统一关联机制：

| 数据集 | ontology 版本 | 内容 |
|---|---|---|
| EduKG math | 0.1 | 知识点图谱 |
| material.ttl | 3.0 | 教材结构 |
| all_concept | - | Class 概念 |
| meta/math | - | Category 分类 |

整合方案对比（三选一）：
- **章节编码映射（低成本启发式，选它）**：知识点 `source=1.1.1.1.1` 与教材章节 `1.1` 做编码前缀映射，**不改模型就打通知识点↔教材章节**
- 统一数据模型（规范但重构大）
- SPARQL 整合（直接拉取，但耦合源）

> 一句话面试答案："多数据集整合用编码映射——知识点 source=1.1.1.1.1 和教材章节 1.1 做前缀匹配，不改模型就打通了知识点和章节的关系。"

### 教材数据双格式：JSON + TTL 兼容 EduKG
> 状态：✅
> 检索摘要：教材爬虫数据为什么出两种格式？JSON 面向程序处理 + TTL 兼容 EduKG main.ttl 可直接 n10s 导入 Neo4j——为互操作性预留数据格式。

爬虫出来的教材数据**同时输出 JSON 和 TTL 两种格式**：

- **JSON**：面向程序处理（结构化、易改）
- **TTL**：兼容 EduKG main.ttl，可用 n10s 插件**直接导入 Neo4j**

层级 schema 自带章节序号规范化：`subject/stage/grade/semester/publisher/edition/chapters[chapter_name → sections[section_name → knowledge_points]]`。这是**为互操作性预留格式**的设计——下游无论是程序还是 Neo4j 都能直接消费。

> 一句话面试答案："教材数据出 JSON + TTL 双格式——JSON 给程序、TTL 兼容 EduKG 能直接 n10s 进 Neo4j，为互操作性预留。"

### 数据可信度：面试被问"数据靠谱吗"怎么答
> 状态：✅
> 检索摘要：知识图谱数据可信度怎么保证？四层来源各有权威背书（清华学术 SPARQL / 教材出处 / 爬虫结构校验 / 课标 OCR+人工），且权威基准冻结只读、业务数据不污染，最终匹配率 97.1% 就是质量背书。

数据可信度是面试必问，核心讲四层来源各有背书 + 一条铁律：

| 来源 | 背书是什么 |
|---|---|
| EduKG 语义层 | 清华学术开源 + 官方 SPARQL 端点 |
| main.ttl 教材出处 | 教材基准文件 |
| 爬虫教材结构 | 网站结构 + 课标对齐校验 |
| 课标小学补充 | OCR + 人工校验 |

**一条铁律**：权威基准数据（TTL）**冻结只读，绝不修改**；业务产生的派生数据只存 MySQL，永远不写进权威图谱——错误只发生在可纠正的派生层，权威数据物理上不可能被污染。

**质量背书**：整个清洗流程下来，最终匹配率 **97.1%**（1690/1740），平均置信度 0.975——这就是数据质量的最终答卷。

## 二、数据不是拿来就用：四道质量防线

### 第一道：解析与生成——把原始素材变成结构化数据
> 状态：✅
> 检索摘要：数据第一道防线是什么？把 23 册教材 JSON 和 TTL 解析成标准节点/关系结构——TTL 用 rdflib 自动解码 Unicode，教材 JSON 生成 Textbook/Chapter/Section 节点和包含关系。

原始数据进来第一件事是**解析成统一结构**：

- TTL 用 rdflib 解析，自动处理 Unicode 解码（`一` → 中文）
- 教材 JSON 生成标准的 Textbook/Chapter/Section/TextbookKP 节点 + 层级包含关系

这一步不做任何判断，只是把"原始素材"变成"统一格式"，为后面清洗打底。

### 第二道：清洗——去掉教材自带的"脏"
> 状态：✅
> 检索摘要：教材数据有什么脏要洗？"通用"标签被反复复用到多个章节（88 组）会重复挂载、小节名带序号前缀影响排序、全角字符影响匹配——DataCleaner 全部处理，且坚持"先出报告、人工确认、再动手"。

爬下来的教材有个很现实的"脏"：

- **"通用"标签复用**：教材里"通用"这种标签会被反复复用到多个章节（检测出 88 组），不清掉一个知识点会被挂到 N 个地方
- **小节名带序号**：`1.1 正数和负数` 这种，序号不单独提出来，排序就是乱的
- **全角字符**：教材混全角标点，不统一成半角，后面匹配"（" vs "(" 会漏配

清洗的**安全设计**很重要：**先跑分析出报告 → 人工确认 → 再动手清洗**。宁可慢一点，也不能让脚本误删教材结构。每次清洗有日志（谁改了什么、原来是什么）可回溯。

> 一句话面试答案："教材自带'通用标签复用、序号混在标题里、全角字符'这些脏，清洗前先出报告人工确认再动手，防止误删。"

### 第三道：增强——给知识点补上"属性"
> 状态：✅
> 检索摘要：知识点属性（难度/重要性/认知层级/专题）怎么补？刻意用规则不用 LLM——属性是客观可枚举的，规则快、可复现、不编造；难度 1-5 按年级基础+关键词微调，认知层级按布卢姆分类。

知识点建出来还得有属性才有业务价值：**难度、重要性、认知层级、所属专题**。这里有个关键决策——**用规则，不用 LLM**：

- **难度 1~5**：按年级给基础难度（一年级=1、必修三=5），再按关键词微调
- **重要性**：核心 > 重要 > 了解，关键词优先级
- **认知层级**：分析 > 应用 > 理解 > 识记，布卢姆分类
- **所属专题**：章节名关键词匹配，分成数与代数/图形与几何/统计与概率/综合与实践

为什么不用 LLM？属性是**客观可枚举**的，规则又快又可复现，LLM 反而可能给你"编"一个不存在的属性——该用规则的地方用规则，LLM 只留给真正需要语义判断的地方。

> 一句话面试答案："属性推断刻意用规则不用 LLM——属性客观可枚举，规则快且可复现，LLM 该用在真正需要语义的地方。"

### 第四道：过滤——别把"活动/复习题"当成知识点
> 状态：✅
> 检索摘要：哪些"知识点"要被拦下来？教材目录里的数学活动、小结、整理和复习、复习题、例题这类非知识点条目，用关键词+正则过滤掉，不建图谱节点，防止图谱被污染。

教材目录里混着很多**不是知识点**的东西：数学活动、小结、整理和复习、复习题、`例1` 这种例题。这些如果不拦下来，图谱里会全是垃圾节点：

- 用**关键词黑名单**（数学活动/小结/整理和复习/复习题…）
- 加**前缀 + 正则**（`^例\d` 这类例题编号）
- 过滤掉的不建节点，保证图谱里每一个 TextbookKP 都是真知识点

## 三、清洗踩过的坑：让面试有血有肉

### 坑一：属性补全顺序搞反了，先增强后推断
> 状态：✅
> 检索摘要：踩过什么坑？属性增强在 LLM 推断之前跑，导致推断出的 1052 个知识点全没属性（覆盖率只有 22%）——流水线顺序依赖，必须"先推断、后增强"。

当时属性增强是放在 LLM 推断**之前**跑的，结果 LLM 推断出来的 1052 个知识点**一个属性都没有**，整体覆盖率只有 22%。

- **根因**：流水线顺序依赖，先增强的只覆盖了已存在的知识点，推断出来的没赶上
- **修复**：调整顺序——先推断补全知识点，再统一补属性，1052 个全部补齐

> 面试讲法："踩过流水线顺序的坑——先增强后推断，推断出来的 1052 个知识点全没属性；调成先推断后增强就对了。教训是数据管线的顺序本身也是要验证的。"

### 坑二：知识点专题继承错了，靠匹配结果校正
> 状态：✅
> 检索摘要：知识点专题继承错是什么问题？属性规则里 topic 直接继承章节，结果"加法"知识点在"位置"章节被错标成图形与几何——用匹配到的 Concept 的 Class 类型批量修正 144 个。

属性规则里 `topic` 直接继承章节，但这个策略有 bug：**"加法"这个知识点出现在"位置"这个章节，就被错标成了"图形与几何"**。

- **根因**：规则继承简单，但章节语义和知识点语义不一定一致
- **修复**：用知识点匹配到的 Concept 的 Class 类型来校正，批量修正了 144 个

> 面试讲法："简单继承会出错——加法在位置章节被错标成图形与几何；后来用匹配到的图谱概念类做二次校正。"

### 坑三：小学和高中知识点是空的，得靠 LLM 补
> 状态：✅
> 检索摘要：小学高中知识点缺失怎么处理？教材数据小学 3-6 年级、高中必修知识点全空，用 LLM 根据章节信息推断补全 1052 个（平均置信度 0.93），初中 252 个完整不用补。

数据下载下来才发现：**小学 3-6 年级和高中必修的知识点字段是空的**，只有初中是完整的。

- 缺的用 **LLM 根据章节信息（学段/年级/章节名/小节名）推断**知识点，补了 **1052 个**，平均置信度 0.93
- LLM 推断是长任务（2-3 小时），所以配套做了**断点续传**（llmTaskLock），中断了接着跑

> 面试讲法："EduKG 和教材数据在小学高中都是空的，用 LLM 根据章节信息推断补了 1052 个，平均置信 0.93；因为是长任务还做了断点续传。"

### 坑四：匹配率从 17% 提到 97.1% 的历程
> 状态：✅
> 检索摘要：匹配率怎么从 17% 提到 97.1%？一开始纯靠 LLM 匹配只有 17%、调用爆炸（500万次）；改成"精确匹配+向量粗筛+LLM 双模型投票"三段式后到 97.1%，LLM 调用降了 99%、提速 50 倍。

匹配率是数据质量的核心指标，讲这个历程最能体现工程能力：

- **最初**：纯靠 LLM 匹配，匹配率只有 17%，而且遍历所有候选 LLM 调用爆炸（500 万次）
- **演进**：改成三段式——① 精确匹配（标准化 + 同义词）兜住 86.8% ② bge 向量粗筛 top-20 把候选压下来 ③ 只有拿不准的才交 LLM 双模型投票
- **结果**：匹配率 **97.1%**（精确 1511 + LLM 179 + 未匹配 50），LLM 调用从 500 万降到 2.7 万（**降 99%**），整体提速约 50 倍

> 面试讲法："匹配率从 17% 提到 97.1%——核心是别让 LLM 干所有事：精确匹配兜确定性、向量粗筛压候选、LLM 只处理拿不准的，LLM 调用降了 99%。"
