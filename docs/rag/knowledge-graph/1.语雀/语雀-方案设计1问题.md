你这份方案整体已经非常完整，思路清晰，从数据模型到 LLM 推理流程都考虑到了。主要建议集中在 3 个方向：

1. 数据模型与 EduKG 标准进一步对齐（尤其是“先修于/所需知识是”这些标准关系）。  
2. 前置关系推断上，更充分地利用教材结构 + 多证据融合，而不是主要依赖 LLM。  
3. 在验证与业务闭环上，把“前置依赖 → 诊断/路径”的查询模式和评估指标提前设计好。  
下面按模块说具体建议。

## 一、数据模型：建议更贴近 EduKG / 国家标准
### 1.1 对齐 EduKG 标准关系命名
从基础教育知识图谱规范来看，知识点之间已经标准化的关系包括：

+ 类内关系（知识点之间）：  
    - `具有子知识点`  
    - `先修于`（可以理解为 prerequisite）  
    - `包含` 等
+ 类间关系：  
    - `所需知识是`（从资源/活动指向知识点）  
    - `相关知识点是` 等  
你当前用的是 `PREREQUISITE` 和 `RELATED_TO`，语义是合适的，但建议：
+ 在 Neo4j 里**同时**保留 EduKG 标准关系类型（如 `先修于`）和业务别名：

```cypher
(kp1)-[:PREREQUISITE {source:"llm",...}]->(kp2)
(kp1)-[:先修于 {source:"llm",...}]->(kp2)
```

+ 或者至少在元数据里标注 `standard_relation: "先修于"`，方便未来与外部 EduKG 系统互操作。  
这样，当你对接其他 EduKG 平台或做标准合规时，可以少做一层映射。

### 1.2 区分“学习依赖”和“教学顺序”
你的方案里“教材章节顺序 → 前置关系”会有一个坑：  
**教材顺序是教学顺序，不一定等于学习依赖顺序。**

+ 比如“函数的概念”可能在必修一，但“二次函数”在必修一后面，而“一元二次方程”在初三。  
+ 教学顺序：先学“函数概念”，再学“二次函数”；  
+ 学习依赖：解一元二次方程需要“因式分解、方程概念”，不一定依赖“函数概念”。  
建议：
+ 把 **章节顺序** 映射为一种**教学顺序关系**，比如：

```cypher
(kp1)-[:TEACHES_BEFORE {source:"textbook", confidence:0.8}]->(kp2)
```

+ 真正的 `PREREQUISITE` 留给“学不会前者就很难学会后者”的**强依赖**，由教材线索 + LLM + 教师标注共同决定。  
这样在业务上也可以区分：  
+ 学习路径推荐：用 `PREREQUISITE`。  
+ 课程编排、章节排课：用 `TEACHES_BEFORE`。

## 二、前置关系构建：建议“教材 + LLM + 多证据融合”，而不是单一来源
你现在的方案是：  

+ 同章节：按章节顺序 → `PREREQUISITE`（confidence=0.85）。  
+ 跨章节：LLM 推理。  
+ < 0.7 的关系直接丢弃。  
结合现有研究，可以再强化一下：

### 2.1 利用教材结构做“证据型前置关系”
在 MOOC 领域，有工作直接从课程介绍文本中抽取“先修课程”关键字，再匹配到课程名称，准确率在 80% 左右。对 K12 来说，教材比 MOOC 描述更结构化，可以做得更细致：  
建议你增加几类“证据型”前置关系来源，而不是只按章节顺序：

1. **章节标题/节标题中的显式依赖**  
    - 例如“一元二次方程的解法（公式法、因式分解法）” → 明确依赖“因式分解”。  
    - 可以用规则 + 小模型抽取“方法/工具性知识点”。
2. **定义/定理文本中的概念依赖**  
    - 一元二次方程的定义：“含有一个未知数，且未知数的最高次数是 2 的整式方程”。  
    - 依赖：“整式方程”“方程概念”。  
    - 可以在 LLM prompt 里明确要求：  

> “先列出定义中出现的、必须事先理解的关键概念，再判断前置关系”。
>

3. **例题/习题的技能组合**  
    - 例题：解方程 (x^2 - 5x + 6 = 0) 需要因式分解。  
    - 这类信息可以作为“弱证据”，记录在关系上，如 `evidence: "exercise_solution"`。  
实现上，可以给每个前置关系打上 `evidence_types` 数组：

```json
{
  "from": "一元二次方程求解",
  "to": "因式分解",
  "confidence": 0.9,
  "evidence_types": ["definition_dependency", "example_solution"],
  "source": "textbook_analysis"
}
```

这样后续可以按证据质量调权重，而不是只依赖一个章节顺序。

### 2.2 LLM 推理：建议把“零样本”结果视为“候选”，而非直接落地
你现在的做法是：  

+ 用 GLM-4-flash / DeepSeek 做零样本前置推理。  
+ 置信度 < 0.7 丢弃。  
从已有研究看，主流 LLM 在零样本前提下，对“技能前置关系”的预测 F1 大约在 0.82 左右——已经不错，但仍然会引入错误。  
建议：
1. **把 LLM 结果当作“高优先级候选”，而不是直接落地**  
    - 新建一个 `PREREQUISITE_CANDIDATE` 关系类型，或者用属性 `status: "candidate"`。  
    - 在 Demo 阶段，你可以在业务层只使用 `status: "verified"` 的关系，但把候选关系存好，方便后续迭代。
2. **Prompt 上加强“概念依赖”而非“时间先后”**  
你现在的 prompt 是判断“学习前需要先掌握哪些知识点”，可以加一句约束：

> “请区分‘必须先学会才能学当前知识点’的核心前置，和‘通常在教学顺序上更早’的教学前置。  
优先输出核心前置关系。”  
这样可以减少“因为都在第一章，所以互为前置”的情况。
>

3. **多模型/多策略投票**  
    - 你已经准备 GLM-4-flash + DeepSeek，可以增加一个“多数投票”机制：  
        * 至少 2 个模型输出同一个前置关系，才提高置信度。
    - 或者同一个模型用两种 prompt（“概念依赖视角”和“教学顺序视角”）对比结果。

### 2.3 多证据融合与置信度计算
可以设计一个简单的融合策略：

+ 给每种证据来源设定基础权重：
    - 教材章节顺序：0.7（弱）  
    - 定义/定理依赖抽取：0.85  
    - LLM 推理：根据模型表现赋权（比如 GLM-4-flash 在类似任务中 F1≈0.82，可给 0.8）  
    - 教师标注：1.0
+ 最终置信度使用加权平均或“至少一条强证据则保留”的策略：

```python
final_confidence = sum(weight * confidence for weight, confidence in evidences) / sum(weights)
```

+ 在 Demo 阶段，可以只保留：
    - 至少有一条“定义/定理依赖”或“教师标注”的关系；  
    - 或 LLM 置信度 ≥ 0.8 且没有明显冲突（如年级倒置）。

## 三、年级/教材推断：建议引入“教材版本”维度
你现在的 `TEXTBOOK_TO_GRADE` 映射是“书名 → 年级”，但实际问题会更大：

1. 不同地区教材版本不同，章节顺序和知识点编排差异很大。  
2. 同一名称“必修第一册”，人教版、北师大版、苏教版内容不完全一致。  
建议：
3. 在 `Textbook` 节点上增加 `version` / `publisher` 字段，而不是只靠 `name`。  

```cypher
(:Textbook {
  name: "高中数学必修第一册",
  publisher: "人教版",
  version_year: "2019",
  isbn: "9787107336270"
})
```

4. 年级推断规则改成：  
    - **精确匹配**：`publisher + name` → 年级/学期；  
    - 模糊匹配：仅 `name` 匹配时，降低置信度，标记为“推断年级”。
5. 在前置关系上记录**推断时的教材版本**，方便后续按版本做差异分析。

## 四、验证与业务闭环：把“查询模式”和“指标”提前设计好
你当前验证方案是：  

+ 自动验证（循环依赖、年级倒置）。  
+ 抽样 100–200 条，人工判断合理性，目标 ≥ 70% 准确率。  
这些都合理，再补充几条：

### 4.1 面向业务的典型查询模式
建议你在 Demo 阶段就写好几个“业务查询模板”，比如：

1. **给定知识点，查所有前置依赖（多跳）**

```cypher
MATCH (target:KnowledgePoint {uri: $uri})<-[r:PREREQUISITE*]-(prereq)
RETURN prereq
```

2. **给定知识点集合，计算“知识缺陷”集合**  
    - 例如：学生做错一道题，关联知识点 A、B；  
    - 查询所有前置路径，找出未掌握的前置点。
3. **生成学习路径**  
    - 给定目标知识点，按拓扑排序输出一条从基础知识点到目标的路径。  
这些查询可以先在 Neo4j 中验证性能和正确性，再作为 LLM + 图谱联合服务的接口。

### 4.2 指标设计
除了“抽样准确率”，建议增加：

+ **图谱质量指标**：
    - 有前置关系的知识点占比（前置覆盖率）。  
    - 平均前置链长度（是否过长/过短）。  
    - 学科内形成 DAG 的比例（环的比例）。
+ **业务效果指标（后续可做）**：
    - 使用图谱后，诊断结果与教师人工判断的一致性。  
    - 学习路径推荐被学生采纳的比例。

## 五、分学科策略：强逻辑学科可以更激进，语言/人文学科要保守
你现在的学科划分是合理的，再细化一点：

+ **数学、物理、化学、生物**：  
    - 强依赖教材结构 + 定义/定理依赖。  
    - LLM 推理可以大胆用，但结果要经过“定义依赖”证据过滤。
+ **英语语法**：  
    - 前置关系更多体现在“句法结构层级”（如“简单句 → 并列句 → 复合句”），可以更多用教材章节 + 语法树规则。
+ **历史、语文、地理、政治**：  
    - 更适合用“主题/时间轴”关系，如 `主题相关是`、`发生在...之后`，而不是 `PREREQUISITE`。  
    - 建议单独设计 `RELATED_TOPIC` / `TEMPORAL_ORDER` 等关系。

## 六、实施层面的一些小建议
1. **脚本与流程**  
    - 你的 `kg_construction/` 目录结构已经很好，建议增加一个 `run_math_pipeline.py` 作为入口脚本，把 clean、merge、prereq、import 串起来，方便复现。
2. **日志与中间产物**  
    - LLM 每批推理结果建议落盘（JSON/CSV），不要只存在内存里，方便调参和回溯。  
    - 对错误或低置信度的关系，单独记录一个 `low_confidence_prerequisites.csv`，便于后续分析。
3. **版本管理**  
    - 你已经打算用 `knowledge_points_v1.csv`，建议再加一个 `manifest.json` 记录：
        * 数据版本、来源（edukg v0.1 / v3.0）、构建时间、模型配置等。
