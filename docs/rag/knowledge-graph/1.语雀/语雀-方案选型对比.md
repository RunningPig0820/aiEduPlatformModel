## 一、存储选型

### 选型1 图谱存储：Neo4j vs MySQL vs ES
> 状态：✅
> 检索摘要：知识图谱为什么选 Neo4j 不用 MySQL/ES？图遍历、前置依赖链查询、可解释路径，CSV 批量导入 10 倍性能。

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| Neo4j | 原生图查询/前置链/可解释路径/批量导入快 | 运维成本 | ✅ 采用 |
| MySQL | 成熟/团队熟 | 多跳查询难 | ❌ 否决 |
| ES | 全文检索强 | 无图语义 | ❌ 否决 |
| 证据 | 证据：语雀-知识图谱数据清洗方案.md / design-integrate-edukg D1 |  |  |

### 选型2 数据加工方案：方案C(CSV→Neo4j) vs 方案A/B
> 状态：✅
> 检索摘要：图谱数据怎么加工进 Neo4j？方案 C CSV→Neo4j 唯一最优——权威基准冻结、教研可维护 CSV、批量导入快。

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 方案 C（CSV→Neo4j） | 权威基准冻结/CSV 可维护/导入快/计算存储分离 | 多一步 CSV 生成 | ✅ 唯一最优 |
| 方案 A | 直接 | TTL 导入慢 | ❌ 排除 |
| 方案 B | - | 同上 | ❌ 排除 |
| 证据 | 证据：语雀-知识图谱数据清洗方案.md |  |  |

### 选型3 数据导入方式：CSV 批量 vs n10s TTL 导入
> 状态：✅
> 检索摘要：图谱数据导入 Neo4j 用哪种？CSV 批量导入（neo4j-admin/LOAD CSV）是 TTL 导入（n10s）性能 10 倍以上。

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| CSV 批量（LOAD CSV/UNWIND/MERGE） | 快 10x+、MERGE 幂等、断点可控 | 需先生成 CSV | ✅ 采用 |
| n10s rdf.import（TTL 直导） | 原生 RDF | 性能差、难控制 | ❌ 早期试后放弃 |
| 证据 | 证据：语雀-知识图谱数据清洗方案.md / design-integrate-edukg D2 |  |  |

## 二、匹配与 embedding 选型

### 选型4 匹配粗筛：bge-small-zh-v1.5 + numpy vs difflib
> 状态：✅
> 检索摘要：知识点匹配粗筛用什么？bge-small-zh-v1.5 向量粗筛 top-20（采纳 DeepSeek 建议）替代 difflib，语义更准、准确率提升 10-20%。

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| bge-small-zh-v1.5 + numpy | 中文 SOTA/语义强/≤5000 条 <10ms/内存约 3.5GB | 需建索引（60s） | ✅ 采用 |
| difflib 字符串相似 | 简单 | 语义弱 | ❌ 否决 |
| 证据 | 证据：design-complete-graph D4.3 |  |  |

### 选型5 LLM 主模型：GLM-4-flash vs DeepSeek vs 百炼 qwen
> 状态：✅
> 检索摘要：LLM 推理用哪个模型？GLM-4-flash 免费主力 + DeepSeek-V3 双模型投票，数学全流程成本 1-2 元。

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| GLM-4-flash（主） | 免费 | 单模型误判 | ✅ 主模型 |
| DeepSeek-V3（副） | 强/约 0.001 元千 token | 付费 | ✅ 双模型投票副模型 |
| 百炼 qwen | 生态 | 付费 | ❌ 未采用 |
| 证据 | 证据：语雀-LLM推理的成本与效率.md / design-prerequisite-inference D2 |  |  |

### 选型6 匹配方式：精确 + 向量 + LLM 组合 vs 单一
> 状态：✅
> 检索摘要：匹配策略为什么三段式？精确匹配 86.8% 兜底 + 向量粗筛降候选 + LLM 双模型投票，匹配率 97.1%、LLM 调用降 99%。

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 精确+向量+LLM 组合 | 确定性优先/成本低/匹配率 97.1% | 实现复杂 | ✅ 采用 |
| 纯 LLM 匹配 | 灵活 | 调用爆炸（500万）、匹配率低（17%） | ❌ 否决 |
| 纯精确匹配 | 零成本 | 覆盖率低（小学 69.6% 不匹配） | ❌ 否决 |
| 证据 | 证据：语雀-产品中心-问题记录.md / design-complete-graph D4 |  |  |

## 三、前置依赖选型

### 选型7 前置依赖构建：多证据融合 vs 教材顺序直转
> 状态：✅
> 检索摘要：前置依赖怎么建？多证据融合——教材顺序仅 TEACHES_BEFORE、定义依赖/LLM 投票才出 PREREQUISITE，避免"教学顺序≠学习依赖"误连。

| 方案 | 优点 | 缺点 | 结论 |

| 教材顺序直接转 PREREQUISITE | 简单 | 教学顺序≠学习依赖（勾股定理先于圆） | ❌ 早期方案，演进放弃 |
| 证据 | 证据：语雀-方案设计1(早期)/2/3(演进) / design-data-research 5.2 |  |  |

### 选型8 前置置信度低值处置：丢弃 vs 降级候选

## 四、工程化选型

### 选型9 断点续传：llmTaskLock vs 无断点重跑
> 状态：✅
> 检索摘要：LLM 长任务中断怎么办？llmTaskLock（JSON 状态 + SHA256 缓存 + portalocker 锁）支持 --resume，推断 2-3 小时可续。

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| llmTaskLock（状态+缓存+锁） | 断点续传/缓存省调用/跨平台 | 文件管理成本 | ✅ 采用 |
| 无断点全量重跑 | 简单 | 中断丢进度 | ❌ 否决 |
| 证据 | 证据：design-infrastructure-init D1-D5 / edukg/core/llmTaskLock |  |  |

> 状态：✅
> 检索摘要：LLM 任务状态存哪？MySQL（ai_edu_kg）替代早期 SQLite，并发/运维/备份更成熟。

## 五、页面化与消费选型

### 选型11 页面化同步：Neo4j→MySQL 同步 vs Neo4j 实时查询
> 状态：✅
> 检索摘要：图谱页面化用哪种？方案 B——Neo4j→MySQL 同步、前端读 MySQL，图谱关系直查 Neo4j + Redis 缓存降级，不做实时查询。

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| Neo4j→MySQL 同步（方案 B） | 前端轻量/查库快/物理隔离 | 需同步机制 | ✅ 采用 |
| Neo4j 实时查询 | 数据实时 | 前端重/连接管理复杂 | ❌ 否决 |
| 证据 | 证据：语雀-页面化-ui-design.md / design-backend-ui Decision 2 |  |  |

### 选型12 后端双数据源：dynamic-datasource vs AbstractRoutingDataSource/多套 Config
> 状态：✅
> 检索摘要：Java 双数据源怎么实现？dynamic-datasource-spring-boot3-starter + @DS("kg") + Mapper 包隔离，比手动路由/多套 Config 简洁。

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| dynamic-datasource + @DS("kg") | 注解简洁/Mapper 隔离/GitHub 10k+ stars | 三方依赖 | ✅ 采用 |
| AbstractRoutingDataSource | 无三方 | 手动路由复杂 | ❌ 否决 |
| 多套 MyBatis Config | 隔离彻底 | 配置量大 | ❌ 否决 |
| 证据 | 证据：语雀-页面化-datasource-design.md / design-backend-datasource Decision 1 |  |  |

### 选型13 前端图谱库：React Flow vs D3 vs ECharts
> 状态：✅
> 检索摘要：前端关系图谱用什么库？React Flow——React 原生、力导向布局内置，比 D3 集成成本低、比 ECharts 更合 React 范式。

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| React Flow | React 原生/力导向内置/轻量 | 生态相对小 | ✅ 采用 |
| D3 | 功能全 | 集成成本高 | ❌ 否决 |
| ECharts | 图表丰富 | 不合 React 范式 | ❌ 否决 |
| 证据 | 证据：design-frontend-ui-front Decision 2 |  |  |

### 选型14 图谱数据主键：URI vs 自增 ID
> 状态：✅
> 检索摘要：图谱节点主键用哪个？URI（非自增 ID），生成后永不修改、跨 Neo4j/MySQL 对齐、改动走合并流程。

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| URI 主键 | 跨源唯一/可对齐图谱 | VARCHAR 性能（<1 万节点可行） | ✅ 采用 |
| 自增 ID | 性能好 | 无法跨源对齐/漂移 | ❌ 否决 |
| 证据 | 证据：design-backend-ui Decision 6 |  |  |
