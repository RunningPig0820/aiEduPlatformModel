## 一、为什么需要这条链路：课标是小学的"知识源头"

### 课标知识点 ≠ 纯数学概念，是个复合体
> 状态：
> 检索摘要：课标知识点和普通概念有什么区别？课标知识点是"核心概念+教学属性"的复合体（100以内数的认识=数+范围+动作），直接当概念节点建会污染概念图谱，所以要先拆分。

为什么小学数据要专门从课标建一条链路？因为 **EduKG 和教材都缺小学**（教材 JSON 小学 3-6 年级知识点全空）。而义务教育课标 2022 是唯一把小学知识点写全的权威文件。

但课标有个特殊问题：**课标知识点不是纯数学概念，是"核心概念 + 教学属性"的复合体**：

```
"100以内数的认识"
  ├─ 核心概念: 数（EduKG 里已存在，uri 0.1/instance/math#341）
  ├─ 教学属性: scope=100以内（范围限定）
  └─ 教学属性: action=认识（认知动作）

"三角形内角和" → 核心概念: 三角形 + 属性: 内角和
"20以内加法"   → 核心概念: 加法 + 属性: 范围 20以内
```

**关键决策（方案 C）**：不能把"100以内数的认识"整个字符串当一个概念节点建进图谱——那会污染概念图谱（"100以内数的认识"不是概念，是"数"的一种教法）。要**拆成核心概念 + 属性**，只把核心概念建点，属性作为标签/字段保留完整信息。

> 一句话面试答案："课标知识点是核心概念+教学属性的复合体，直接建点会污染概念图谱，所以拆开——100以内数的认识拆成核心概念'数'加范围/动作属性。"

### 八步流水线：从扫描版 PDF 到图谱
> 状态：
> 检索摘要：课标怎么变成图谱？8 步流水线：OCR→知识点提取→教学知识点解析→概念聚合→Class推断→Statement生成→关系提取→校验导入，模块一一对应。

从课标到图谱不是一步到位，是 **8 步流水线**，每一步一个模块，模块清单明确标"是否用 LLM"：

| 步骤 | 模块 | 是否用 LLM |
|---|---|---|
| ① OCR | 扫描版 PDF → 文本（百度 OCR，收费） | 否 |
| ② 知识点提取 | 从课标文本提取教学知识点（434 个） | 是（glm-4-flash 免费） |
| ③ 教学知识点解析 | "复合体"拆核心概念 + 属性 | 否（规则） |
| ④ 概念聚合 | 去重合并 → 122 个概念 | 部分 |
| ⑤ Class 推断 | 概念归类到 Class（19 匹配 + 1 新建"数学符号"） | 部分 |
| ⑥ Statement 生成 | 每个概念生成定义（122 条） | 是（已缓存） |
| ⑦ 关系提取 | 312 条关系（relatedTo/partOf/belongsTo/HAS_TYPE/SUB_CLASS_OF） | **规则 vs LLM 分流** |
| ⑧ 校验导入 | 6 类本地校验 + 3 类 DB 冲突校验 → Neo4j | 否 |

## 二、增量扩图：怎么加数据不污染已有图谱

### URI 版本化：匹配上的用 v0.1，新增的用 v0.2
> 状态：
> 检索摘要：小学数据加进图谱会不会污染已有的？不会——匹配到 EduKG 已有概念用 v0.1 URI，新增概念用 v0.2 URI，带 version/is_existing 字段可解释、可回滚。

加数据最怕污染已有图谱。这里的关键设计是 **URI 版本化区分**：

- 课标知识点匹配到 **EduKG 已有的概念** → 用 **v0.1 URI**（复用现有节点，不新建）
- 匹配不到的 **新增概念** → 用 **v0.2 URI**（`{拼音}-{md5}`，如小学的"估算"）
- 每个概念带 **`version` / `is_existing`** 字段，可溯源、可审计

结果：434 个课标知识点 → 122 个概念（**102 个已存在于 v0.1 + 20 个新增 v0.2**），过滤 15 个非核心（购物/招聘/游戏这类跟数学无关的条目）。

> 一句话面试答案："加小学数据不污染已有图谱——匹配到 EduKG 概念的复用 v0.1 URI，新增概念用 v0.2 URI，每个带 version/is_existing 可溯源可回滚。"

### 关系生成"规则 vs LLM"分流：312 条只 47 条花 LLM 钱
> 状态：
> 检索摘要：关系生成怎么控制成本？5 种关系里 RELATED_TO/HAS_TYPE/SUB_CLASS_OF 用规则直接生成零成本，只有最模糊的 PART_OF/BELONGS_TO 才调 LLM——312 条关系只对 47 条花 LLM 钱。

构建关系的成本控制是面试亮点。**5 种关系，只有语义最模糊的才调 LLM**：

| 关系 | 生成方式 | 成本 |
|---|---|---|
| SUB_CLASS_OF（概念层级） | 规则映射 | 零 |
| HAS_TYPE（类型分类） | 规则 + LLM 推断 | 低 |
| RELATED_TO（定义关联） | **规则匹配**：Statement 标签去掉"的定义"即关联 Concept | **零、100% 可解释** |
| PART_OF（部分-整体） | LLM 分析 | 贵 |
| BELONGS_TO（所属关系） | LLM 分析 | 贵 |

最终 312 条关系，**只有 47 条（partOf 46 + belongsTo 1）花了 LLM 钱**，其余 265 条全部规则化零成本。

> 一句话面试答案："312 条关系只有 47 条花 LLM 钱——规则能解决的（类型、层级、定义关联）全部规则化，只把语义最模糊的 partOf/belongsTo 交给 LLM。"

### 收费 OCR vs 免费 LLM：贵的跑一次、便宜的随便跑
> 状态：
> 检索摘要：OCR 为什么用收费的百度 API？扫描版 PDF 只能 OCR 识别；成本选型是"贵的跑一次、便宜的随便跑"——百度 OCR 收费但一次性执行，后续全部 LLM 步骤用免费 glm-4-flash。

成本驱动架构的一个例子：**OCR 用收费的百度 API，LLM 用免费的 glm-4-flash**。

- **百度 OCR**：收费，但**一次性执行**（189 页扫描版 PDF 识别一次就完事）
- **glm-4-flash**：免费，后续所有 LLM 步骤（知识点提取/定义生成/关系分析）都用它

> 一句话面试答案："OCR 收费但只跑一次，LLM 免费所以全流程随便用——成本选型就是'贵的跑一次、便宜的随便跑'。"

## 三、数据质量门禁：进 Neo4j 前过五关斩六将

### 6 类本地校验 + 3 类数据库冲突校验
> 状态：
> 检索摘要：数据进 Neo4j 前怎么把关？6 类本地校验（关系类型/三元组完整/URI格式/自环/重复/双向冲突）+ 3 类数据库冲突校验（生成与已有冲突时保留数据库版），双向冲突 partOf/belongsTo 方向不能并存。

导入 Neo4j 前有一道**数据质量门禁**，不是直接倒进去：

**6 类本地校验**（生成的数据自查）：
1. 关系类型合法性
2. 三元组完整性（起点/终点/关系都在）
3. URI 格式合法
4. 自环检测（A→A）
5. 重复检测
6. **双向冲突检测**——`A→partOf→B` 与 `B→belongsTo→A` 不能并存（图谱语义一致性）

**3 类数据库冲突校验**（和 Neo4j 里已有数据对账）：
- 用 Cypher 查 Neo4j 已有边，对比生成的数据
- **冲突时"保留数据库版本、删生成版本"**——已有图谱优先，不覆盖权威数据

> 一句话面试答案："进 Neo4j 前有质量门禁——6 类本地校验（含双向冲突：partOf/belongsTo 方向不能并存）+ 3 类数据库冲突校验，冲突时保留已有图谱。"
