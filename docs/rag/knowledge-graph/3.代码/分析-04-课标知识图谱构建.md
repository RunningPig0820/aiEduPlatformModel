## 业务描述与业务场景

**业务描述**：EduKG 和教材数据都缺小学数学知识点，而义务教育课标 2022 是唯一把小学知识点写全的权威文件——这条链路就是把扫描版课标 PDF 变成可入图谱的小学节点（概念/定义/关系），补齐语义层的小学缺口。

**业务场景**：
- 教研把课标 PDF 放进来，系统 OCR 后提取"100以内数的认识"这类教学知识点，拆成核心概念"数"+范围/动作属性建点
- 图谱里已有高中抽象概念，加小学数据不能污染已有节点——匹配上的复用 v0.1 URI、新增的用 v0.2 URI
- 构建关系时 312 条只有 47 条语义最模糊的 partOf/belongsTo 花 LLM 钱，其余规则化零成本

## 职责

**职责**：课标扫描版 PDF → 小学图谱节点/定义/关系（概念类 1 + Concept 20 + Statement 122 + 关系 312），过质量门禁后供导入。
**不做什么**：不做教材数据（那是 core/textbook）、不做前置依赖（那是 kg_inference）、不直接导入 Neo4j（输出 JSON 供校验后导入）。
**分工要点**：模块在 `edukg/core/curriculum/`（class_extractor/concept_extractor/statement_extractor/relation_extractor/teaching_kp_parser/kg_builder 等），OCR 结果在 `edukg/data/eduBureau/math/`。

  │  "100以内数的认识" → 核心概念"数" + scope"100以内" + action"认识"

## 代码事实

### 8 步流水线模块清单（`curriculum/README.md` 612-624）
| 步骤 | 模块/脚本 | 是否用 LLM |
|---|---|---|
| ① OCR | pdf_ocr.py + 百度 OCR API | 否（收费一次性） |
| ② 知识点提取 | kp_extraction.py | 是（glm-4-flash） |
| ③ 教学知识点解析 | teaching_kp_parser.py（方案C 拆分） | 否（规则） |
| ④ 概念聚合 | concept_aggregator.py / concept_matcher.py | 部分 |
| ⑤ Class 推断 | class_inferrer.py / class_extractor.py | 部分 |
| ⑥ Statement 生成 | statement_extractor.py | 是（已缓存） |
| ⑦ 关系提取 | relation_extractor.py | 规则 vs LLM 分流 |
| ⑧ 校验导入 | kg_builder.py + 校验脚本 | 否 |

### 关键机制：课标知识点"核心概念+教学属性"拆分（方案C，`teaching_kp_parser.py`）
- 拆分示例（`curriculum/README.md:94-98, 238-257`）：
  - `100以内数的认识` → 核心概念 `数`（uri 0.1/instance/math#341，置信度 1.0）+ scope/action
  - `三角形内角和` → `三角形` + property
  - `20以内加法` → `加法` + scope
- 设计理由：教学知识点是"概念+教学属性"复合体，直接建点会污染概念图谱；只建核心概念节点，属性作字段保留完整信息。

### 关键机制：URI 版本化（`concept_matcher.py` / `kg_builder.py`）
- 匹配到 EduKG 已有概念 → 用 **v0.1 URI**（复用现有节点）
- 新增概念 → 用 **v0.2 URI**（`{拼音}-{md5_32bit}`）
- 每个概念带 `version` / `is_existing` 字段（`curriculum/README.md:31-36, 277-287`）
- 结果：434 → 122 概念（102 v0.1 + 20 v0.2），过滤 15 非核心（`README.md:103-117, 349-371`）

### 关键机制：关系生成"规则 vs LLM"分流（`relation_extractor.py` + `MAPPING.md:196-202`）
| 关系 | 生成方式 | 成本 |
|---|---|---|
| SUB_CLASS_OF | 规则映射（class_parents） | 零 |
| HAS_TYPE | 规则 + LLM 推断 | 低 |
| RELATED_TO | **规则匹配**：Statement 标签去"的定义"即关联 Concept | 零、100% 可解释 |
| PART_OF / BELONGS_TO | LLM 分析（语义最模糊） | 贵 |
- 结果：312 关系 = relatedTo 122 + partOf 46 + belongsTo 1 + HAS_TYPE 142 + SUB_CLASS_OF 1，**仅 47 条花 LLM 钱**（`README.md:389-399`）

### 关键机制：数据质量门禁（`README.md:402-562`）
- **6 类本地校验**：关系类型合法 / 三元组完整 / URI 格式 / 自环 / 重复 / **双向冲突**（A→partOf→B 与 B→belongsTo→A 不能并存）
- **3 类数据库冲突校验**：Cypher 查 Neo4j 已有边；冲突时"保留数据库版本、删生成版本"（`db_conflicts` 明细返回 generated vs existing）

### 枚举/常量/配置
| 类型 | 名称 | 取值 | 出处 |
|---|---|---|---|
| 拆分属性 | scope/action/property | 核心概念附加教学属性 | teaching_kp_parser.py |
| URI 版本 | v0.1 / v0.2 | 已存在 / 新增 | kg_builder.py |
| 过滤 | 非核心概念 | 购物/招聘/游戏/素养/能力 15 个 | concept_aggregator.py |
| LLM 模型 | glm-4-flash | 免费主力 | kp_extraction.py |

## 隐性坑与注意事项
- **直接建点污染图谱**：不拆复合体直接把"100以内数的认识"建 Concept 会污染概念图谱——方案C 拆分是前提。
- **新数据覆盖已有**：DB 冲突校验是硬门禁，冲突默认保留已有图谱，不覆盖权威数据。
- **OCR 一次性成本**：百度 OCR 收费，跑完一次就够；重跑要重花 OCR 钱，OCR 结果落盘复用。
- **双向冲突语义**：partOf 和 belongsTo 方向不能同时存在，否则图谱语义自相矛盾。

## 设计要点
- **方案C 拆分**：非结构化课标文本 → 图谱 Schema 的关键决策——"概念 + 教学属性"分离，既保语义又防污染。
- **规则优先、LLM 兜底**：能规则化（类型/层级/定义关联）全部规则化，只有语义最模糊的才交 LLM——成本控制贯穿全链路。
- **版本化扩图**：v0.1/v0.2 + is_existing 让增量扩图可溯源、可回滚，不破坏已有图谱。
- **人在环质量门禁**：导入前 6+3 校验 + DB 冲突保留已有，自动化 + 人工确认结合。
