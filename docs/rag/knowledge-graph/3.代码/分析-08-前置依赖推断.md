## 业务描述与业务场景

**业务描述**：学生学一个知识点前得先掌握什么，是学习路径推荐和薄弱诊断的核心。这段代码就是从图谱已有概念出发，用双模型投票判断「A 是不是 B 的前置」，产出带置信度的学习依赖关系，并验证这些依赖不成环——保证学生补课顺序不会出现死循环。

**业务场景**：
- 学生答疑时定位到「分数除法」学不懂，系统要沿前置链往回找「分数乘法」「倒数」是不是已掌握
- 教研把教材顺序导进来，但教材先教≠必须先学（勾股定理先于圆，学圆不需先学勾股定理），所以教学顺序只能作弱证据
- 推断结果要过 DAG 校验，出现环（A前置B、B前置A）要拦截报警，否则学习路径死循环

## 职责

**职责**：从 Neo4j 加载 Concept → 生成候选知识点对 → 双模型投票推断前置关系 → 输出 JSON → DAG 无环验证。
**不做什么**：不做教学知识点推断（那是 textbook_kp_inferer）、不做匹配（那是 match_textbook_kp）、不直接写回 Neo4j（输出 JSON 供人工验证后导入）、**年级倒置惩罚代码未实现**（仅语雀/design 方案）。
**分工要点**：核心逻辑在 `edukg/core/llm_inference/`（prerequisite_inferer + dual_model_voter + config），CLI 入口 `edukg/scripts/kg_inference/infer_prerequisites.py`，DAG 验证 `validate_dag.py`。本主题仅 Python 管道单端。

## 高层业务调用链（知识点前置依赖推断与 DAG 校验）

```
infer_prerequisites.py
  │ --dry-run → estimate_inference_cost(len(concepts)) → 打印成本估算（不调 LLM）
  │ --stats   → 读已有 llm_prereq.json 统计 PREREQUISITE/CANDIDATE 数量
  ▼
load_concepts_from_neo4j
  MATCH (c:Concept) OPTIONAL MATCH (s:Statement)-[:RELATED_TO]->(c)
  → 返回 uri/label/descriptions[0]（按 label 排序，约 1275+ 个）
  ▼
generate_kp_pairs（代码注释自述"简化版本"）
  每个概念与前后±5 个配对 → 约 10×N 个有序对
  ▼
PrerequisiteInferer.infer_batch(pairs)
  └─ _infer_pair: format_prerequisite_prompt → vote_with_retry(voter, prompt)
        └─ DualModelVoter.vote → asyncio.gather 并行调 GLM-4-flash + DeepSeek
             ├─ 两模型 decision 一致 → consensus=True，置信度=两模型均值
             ├─ 不一致 → 加权投票 DS=0.6/GLM=0.4/阈值0.5，仅 DeepSeek=True 可过线，
             │          置信度=胜者×0.7（vote_type=weighted）
             └─ 两模型都解析失败/加权不过 → consensus=False（vote_with_retry 对解析失败重试≤3次）
        ├─ consensus=False → 丢弃该对（不产出）
        └─ consensus=True 且 decision=True → confidence≥0.8 → PREREQUISITE，否则 PREREQUISITE_CANDIDATE
  ▼
save_results(results, llm_prereq.json)   ← 输出到 edukg/data/edukg/math/6_推理结果/output/
  ▼
validate_dag.py --report（读 final_prereq.json）
  ├─ detect_cycles：DFS 找环 → 有环退出码 1
  ├─ calculate_coverage / avg_chain_length / confidence_distribution
  └─ save_report → validation_report.json
```

### 关键机制
1. **候选对生成是简化版**：`generate_kp_pairs` 把每个概念与排序后前后各 5 个概念配对（`infer_prerequisites.py:110-125`），代码注释明示"实际应该基于启发式规则筛选候选对（同一章节/同一类型/有 RELATED_TO 关系）"——目前只按 label 排序邻近配对。
2. **投票决策**（`dual_model_voter.py:_check_consensus`）：
   - 两模型 `decision`（is_prerequisite/is_match/decision 三字段兜底）一致且非 None → 采纳，置信度取均值（:327-352）
   - 不一致 → 加权：`WEIGHT_DS=0.6 / WEIGHT_GLM=0.4 / THRESHOLD=0.5`，`weighted_score = GLM(True?0.4:0)+DS(True?0.6:0)`，≥0.5 才过线 → 实际只有 DeepSeek=True 才可能过（DS 一票否决），置信度=胜者×0.7（:354-386）
   - `confidence` 支持 `high/medium/low` 字符串 → 0.95/0.7/0.4（:207-215）
3. **关系分类阈值**：`_infer_pair` 用 `confidence >= 0.8` 判定 PREREQUISITE，否则 PREREQUISITE_CANDIDATE（`prerequisite_inferer.py:127`）。注意：`config.CONFIDENCE_THRESHOLD_LOW=0.6` 与 `vote_prerequisite()` 方法（≥0.8→PREREQUISITE、≥0.6→CANDIDATE、<0.6→None）**未被 infer_batch 主链路调用**——主链路实际只有 0.8 一个分界。
4. **TEACHES_BEFORE 与 PREREQUISITE 严格区分**：`infer_from_textbook_order` 仅限章节内部按小节顺序生成 TEACHES_BEFORE，conf=1.0，source=textbook_order（`prerequisite_inferer.py:140-181`）；LLM 投票产出 PREREQUISITE/PREREQUISITE_CANDIDATE。
5. **三来源融合 fuse_results 已实现但未接入 CLI**：`fuse_results(teaches_before, definition_deps, llm_prereq)` 按 (kp_a_uri,kp_b_uri) 去重；定义依赖标记 DEFINITION_DEP、与 TEACHES_BEFORE 重合升级 PREREQUISITE(0.9)；LLM 结果与已有 TEACHES_BEFORE/DEFINITION_DEP 重合升级 PREREQUISITE、置信度 min(已有+0.1, 1.0)、source=multi_evidence（`prerequisite_inferer.py:261-336`）。但 `infer_prerequisites.py` 主流程只调 `infer_batch` → `save_results(LLM_PREREQ_FILE)`，**从不调** `infer_from_textbook_order/extract_from_definition/fuse_results`。
6. **DAG 验证**（`validate_dag.py`）：只把 PREREQUISITE 与 PREREQUISITE_CANDIDATE 建图（:87），A→B 表示 A 是 B 的前置；`detect_cycles` DFS 找环；覆盖率=有前置(作 target)的节点/全部节点；平均链长=根到各节点最长路径均值；置信度分布 high≥0.8 / medium 0.5-0.8 / low<0.5（:212-214）。有环 `sys.exit(1)`，无环 `sys.exit(0)`（:356）。

### 边界与降级
- **LLM 不可用**：`_get_llm_gateway` 导入 `core.gateway.factory.LLMFactory` 失败时降级"模拟模式"，返回固定 `{"is_prerequisite": true, "confidence": 0.8}`（`dual_model_voter.py:75-91,137-156`）——测试/离线可用，线上会产假真值。
- **投票失败/解析失败**：`vote()` 捕获 LLMCallError 返回 consensus=False（:239-248）；`vote_with_retry` 仅对"响应解析失败"和异常重试（≤MAX_RETRIES=3），对"判断不一致"不重试（:500-507）。
- **pair 产出失败**：`_infer_pair` 返回 None 则不写入 results（`prerequisite_inferer.py:74`）。
- **文件缺失**：`validate_dag.py` 默认读 `final_prereq.json`，不存在抛 FileNotFoundError 退出码 1（:70-71,358-360）。

## 隐性坑与注意事项
- **final_prereq.json 没有生产方**：`infer_prerequisites.py` 只写 `llm_prereq.json`；`validate_dag.py` 默认读 `final_prereq.json`，但融合(fuse_results)未接入 CLI，**没有任何脚本产出 final_prereq.json**——直接跑 `validate_dag.py` 会 FileNotFoundError，需 `--input` 指定 llm_prereq.json 或先手动融合。
- **低阈值 0.6 形同虚设**：主链路 `_infer_pair` 只用 0.8 一个分界，`CONFIDENCE_THRESHOLD_LOW=0.6` 只在未被调用的 `vote_prerequisite()` 里生效；README/语雀口径"<0.6 丢弃"在代码主链路不存在。
- **候选对数量与成本估算严重不符**：`generate_kp_pairs` 实际产 ~10N 对，`estimate_inference_cost` 按 2N 对估算（`prerequisite_inferer.py:350`），成本预估偏低约 5 倍。
- **断点续传未落地**：design（D5/D11）要求 `--resume` + llmTaskLock（TaskState/CachedLLM/ProcessLock），但 `infer_prerequisites.py` 参数只有 `--dry-run/--batch-size/--stats`，无 `--resume`；`PrerequisiteInferer.infer_batch` 签名无 resume 参数。推断中途失败需重跑（成本虽低）。
- **年级倒置惩罚未实现**：语雀 D10 的 ×0.95/0.9/0.5/0.3 惩罚在代码中搜不到（validate_dag 无年级倒置检测）——方案有、代码无。
- **投票不一致的加权路径会放大误判**：只要 DeepSeek=True 且 GLM=False，加权 0.6≥0.5 就采纳为 PREREQUISITE，与 D7 语雀"两模型一致才采纳"口径不符（代码实际允许 DS 一票通过）。
- **模拟模式静默**：无网关时返回全 True+0.8 的假数据，跑完整流程不报错，容易把假前置导入。

## 设计要点
- **成本优先**：GLM-4-flash 免费做主模型 + DeepSeek 兜底，全流程成本估算 <0.01 元（README:280-288）——数学 1295 概念全推断代价可忽略。
- **DS 一票否决设计**：加权 DS=0.6>阈值 0.5 使 DeepSeek 拥有否决权（`dual_model_voter.py:365` 注释"只有 DeepSeek=True 才可能过阈值"），用更严格模型压误判。
- **两级置信产出**：PREREQUISITE（≥0.8）/ PREREQUISITE_CANDIDATE（<0.8）保留低置信候选供人工补审，不丢弃。
- **可解释性**：每对产出带 reason（primary_reason/secondary_reason），融合标记 multi_evidence，便于人工核对。
- **核心与 CLI 分离**：推断逻辑在 `core/llm_inference/`，scripts 只做入口——但融合/顺序推断方法未挂到 CLI 属于"半落地"。
