## 为什么（语雀）

学生答疑要定位"这个题考哪个知识点、这个知识点前置是什么"，掌握度诊断要沿前置链找薄弱根因，学习路径推荐要有知识点依赖关系——这些能力的前提是**一张"知识点之间如何关联"的结构图**，而不是一张扁平的知识点标签表。而人教教材、EduKG 开源概念、课标这些来源是分散的：教材给教学结构，EduKG 给抽象概念，两者名称对不上、颗粒度错位（"1-5 的认识"vs"自然数"）。早期方案曾考虑简单标签打标/关系库直存，已演进为**两层图谱 + 图数据库**的方案（见下）。

## 怎么设计（方案）

**（方案口径，已演进）** 早期方案是给知识点打简单标签、用关系库/全文检索存依赖；已演进为"**两层图谱 + Neo4j 存储 + 离线构建/在线消费分离**"，核心哲学是"**无限的业务事实与有限的权威结构分存、权威图谱零写入**"（语雀-方案总揽 §1）。

```
教材结构层(教学真值): Textbook(23) → Chapter(148) → Section(580) → TextbookKP(1740)
                          CONTAINS / IN_UNIT 结构关系
        └──────────── MATCHES_KG 匹配连接(1,690 条, 置信度 ≥0.5) ────────────┐
语义层(EduKG 概念):  Concept(1295) / Statement(2932) / Class(39)  ◄──────────┘
                     RELATED_TO(10,183) / HAS_TYPE(5,591) / BELONGS_TO / SUB_CLASS_OF
Neo4j 最终存储 ← 离线构建 CSV 批量导入(MERGE 幂等)
在线消费: api/kg.py 业务查询 + api/neo4j.py 通用 CRUD + Java 页面化同步 MySQL
```

- **两层图谱结构**：教材结构层 = 人教 K-12 数学教学真值（Textbook 23 / Chapter 148 / Section 580 / TextbookKP 1740，`CONTAINS`/`IN_UNIT` 结构关系）；语义层 = EduKG 开源概念（Concept 1295 / Statement 2932 / Class 39，`RELATED_TO`/`HAS_TYPE`/`BELONGS_TO`/`PART_OF`/`SUB_CLASS_OF` 语义关系）。两层靠 **MATCHES_KG** 匹配连接（TextbookKP → Concept，方向固定不可逆，置信度 ≥0.5）。文字复述：结构层回答"课程长什么样、知识点挂在哪"；语义层回答"概念是什么、概念间怎么关联"；MATCHES_KG 是这两层之间的软连接，软连接保证任意一层变化不污染另一层。
- **为什么 Neo4j 不用 MySQL/ES**：核心查询是"前置依赖链"这类**多跳图遍历**——MySQL 多跳 JOIN 难写难优化，ES 只有全文检索没有图语义；Neo4j 原生图查询 + 可解释路径，且 `neo4j-admin import` 对 CSV 批量导入是 TTL 导入 10 倍以上（语雀-决策记录 D1；语雀-方案选型对比 选型1）。
- **离线构建/在线消费分离**：关系处理在 Python 内存/CSV 完成，Neo4j 只是最后仓库，导入用 MERGE 幂等（语雀-方案总揽 §1）。
- **权威图谱零写入**：EduKG 静态权威库冻结只读，业务派生数据（掌握度/点亮/题型）只存 MySQL，物理上不污染权威图（语雀-决策记录 D17）。
- **边界（Non-Goal 演进口径）**：本期仅数学学科（全学科扩展不做）；页面化走方案 B（Neo4j→MySQL 同步、前端读 MySQL），Neo4j 实时查询被否决；复杂关系可视化不做——这些是方案边界，不是已实现能力。

## 落地真相（代码）

> ⚠️ **最大翻转（两个核心）**：①在线查询 `api/kg.py` 依赖的 `core/kg/service.py` 全部 `MATCH (e:Entity {...})`（service.py:101-109, 180-185），而离线导入用的是具体标签（Concept/Statement/TextbookKP 等，无统一 `Entity` 标签）——直接调 `/entities`、`/tree` 可能查不到离线导入的数据；②匹配率口径有批次差异：决策记录 1690/1740=97.1%，当前数据文件 1905 条匹配率 **96.96%**（exact 1639 + llm_vote 208 + candidate_review 50 + none 8，平均置信 0.973）。

- **✅落地：两层图谱与规模**：Neo4j 落地 7 类节点 6,757 个 + 8 类关系 20,887 条，两层结构（教材结构层 + 语义层）与 MATCHES_KG 连接均已落地，URI 唯一 100%（3.代码/分析-01）。
- **✅落地：离线构建管道**：Phase0 爬取 → Phase1 生成/清洗/推断 → Phase2 匹配 → Phase3 导入，TTL 按学科拆分 + schema 唯一约束先行（3.代码/分析-02）。
- **⚠️ 翻转（标签体系，核心①）**：在线服务查询统一用 `:Entity` 标签，导入脚本用具体标签，标签体系可能不匹配——要么 `Entity` 由 Java 通过 `api/neo4j.py` 动态建（该接口示例正是 `POST /api/neo4j/nodes/Entity`），要么 service.py 查询是"期望面"而非"实际数据面"，联调核对前 `/entities`、`/tree` 可能查不到数据（3.代码/分析-01 隐性坑）。
- **⚠️ 翻转（匹配率口径，核心②）**：对外讲"~97%"准确；精确数字要区分 97.1%（1690/1740 基线，决策记录快照）vs 96.96%（1905 基线，当前 matches_kg_relations.json 数据文件）（方案-代码对账 #6）。
- **⚠️ 翻转（Python 桥能力边界）**：`get_knowledge_tree`/`get_learning_path`/`get_recommendations` 是**简化桩**——知识树取前 100 实体平铺两层、学习路径只返回目标实体自身、推荐只看一跳邻居；页面化真层级走 Java 同步 MySQL 侧（3.代码/分析-01）。方案称 api/kg.py"八端点"，实为 10 路由（含 progress GET/POST 两态）。
- **消费链路（代码现状）**：Python 桥 `api/kg.py`（业务查询）+ `api/neo4j.py`（通用 CRUD，`x-internal-token` 鉴权）+ Java 页面化同步（Neo4j→MySQL ai_edu_kg）；`core/rag/query.py` 是 **AI 答疑 RAG 检索编排**（图谱文档切片按模块锚点召回），不是图谱数据查询——两条链路别混（3.代码/分析-01）。

## 追问与防御

**预期追问：图谱是不是摆设？真用上了吗？**
→ **回答要点**：不是。它支撑答疑知识点识别与前置回顾、掌握度薄弱根因诊断、学习路径推荐、页面化浏览，并作为模块锚点接入 RAG 检索。Python 桥知识树/学习路径是简化桩，真实消费在 Java 同步 MySQL + 前端页面侧。

**预期追问：6757 节点真的是你做的吗？**
→ **回答要点**：是。节点来自 EduKG 开源 TTL + 人教版爬虫 + 课标多来源，自己写 Phase0-3 管道（拆分→生成→清洗→增强→LLM 推断→匹配→导入→校验）；小学/高中缺失知识点是双模型推断补的 1052 个，匹配率从 17% 提到 ~97%，每类节点都能讲出来源。

**预期追问：为什么用 Neo4j 不用 MySQL/ES？**
→ **回答要点**：核心查询是前置依赖链的多跳图遍历，MySQL 多跳 JOIN 难、ES 无图语义；Neo4j 原生图查询 + 可解释路径，CSV 批量导入比 TTL 直导快 10 倍以上（D1/选型1）。MySQL/ES 用作页面化只读和全文检索，不是替代关系。

**预期追问：两层结构怎么连的？**
→ **回答要点**：靠 MATCHES_KG 匹配连接（TextbookKP → Concept，1,690 条，置信度 ≥0.5）；结构层内部 TextbookKP 有且仅有一个 IN_UNIT 指向 Section，语义层内部靠 RELATED_TO/HAS_TYPE 关联。连接链路是精确匹配 + 向量粗筛 top-20 + 双模型投票（参考：05 知识点推断与匹配）。
