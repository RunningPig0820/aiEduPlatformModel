## 为什么（语雀）

图谱数据不是"一个库拿来就用"——同一领域的教育数据散在 **EduKG TTL（v0.1 语义层）、main.ttl（v3.0 教材出处）、人教版爬虫目录、课标 OCR 结果** 四个独立数据集里，ontology 版本不同（0.1 vs 3.0）、小学/高中知识点还整片空白。核心诉求是把这些分散、异构、残缺的素材，加工成一张"教材结构 + 概念语义"两层互连、可检索可推理的 Neo4j 知识图谱（最终 **6757 节点 / 20887 关系 / 匹配率 97.1%**），支撑答疑定位知识点缺口、掌握度诊断、学习路径与图谱页面浏览。早期方案曾以"TTL 直接导入 + 纯 LLM 匹配"为主，实测匹配率仅 **17%**、LLM 调用爆炸（约 500 万次），已演进为"拆分→清洗→增强→推断→匹配→导入→校验→向量"的完整离线管道 + 三段式匹配。

## 怎么设计（方案）

**（方案口径，已演进）** 早期方案（`design-python-2026-04-10-knowledge-graph-data-research`）先做 TTL 数据整理与六级层级建模（学科→学段→年级→教材→章节→知识点）并区分教学顺序/学习依赖；已演进为（`design-python-2026-04-15-kg-math-complete-graph`）完整数据管道——教材 JSON 解析 → LLM 双模型推断补全缺失知识点 → 向量粗筛 + 双模型投票把 TextbookKP 匹配到 EduKG Concept → 输出 JSON 人工验证后导入 Neo4j；核心代码进 `edukg/core`，scripts 只做命令行入口，全链路支持 llmTaskLock 断点续传。

**主流程文字流程图（数据来源 → 拆分 → 清洗 → 推断 → 匹配 → 导入 → 校验 → 向量）**：

```
数据来源(四类) ──────────────────────────▶ Phase0 爬取(renjiaoshe_math_crawler 断点续爬)
  EduKG TTL v0.1(ttl/*.ttl + relations/*.ttl + entities/*.json)    │ 23 册教材 JSON(小学12+初中6+高中人教A版2019 5)
  main.ttl v3.0(教材出处, 约16MB)                                      ▼
  人教版爬虫(小学初中目录)                          Phase1 拆分/生成/清洗/增强/推断/合并/属性
  课标2022(OCR 补小学)                                split_main_ttl / split_material_ttl(按学科)
                                                       generate_textbook_data(节点/关系 JSON)
        ┌─────────────────────────────────────────▶ clean_textbook_data(--analyze→--clean 防误删)
        │                                             → enhance_chapters(专题) → infer_textbook_kp(双模型投票)
        │                                             → merge_inferred_kps(合并) → enhance_kp_attributes(推断后增强)
        ▼
  Phase2 匹配: build_vector_index(bge 512) → normalize_textbook_kp(LLM 标准化)
        → match_textbook_kp(精确匹配 → 向量粗筛 top-20 → 双模型投票) → matches_kg_relations.json
        ▼
  Phase3 导入: import/ 11 个脚本按依赖顺序 MERGE 幂等 → Neo4j(7类节点/8类关系)
        ▼
  校验: verify_import(重复URI/v0.2) + analyze_textbook_matching(匹配率) + validate_dag(环检测)
        ▼
  向量: 匹配侧 kg_vectors.npy(512维) 本地预构建 + checksum 校验 / 服务侧 dashscope 768 维写 COS 桶
```

整条链路是**单向离线流水线**：四个来源先做 TTL 按学科拆分与教材 JSON 生成，拆成按学科的单文件；随后过"清洗（DataCleaner）→ 增强（专题+属性）"两道质量防线；小学/高中缺失的知识点由 LLM 双模型投票推断补全并合并回主文件；进入匹配阶段，教材知识点经"标准化精确匹配 → 向量粗筛 top-20 → 双模型投票"三段式落到 EduKG 概念；产出的关系 JSON 由 11 个导入脚本按依赖顺序 MERGE 幂等写进 Neo4j；最后过 verify/DAG 校验并构建向量索引。

**关键设计（方案口径）**：
- **两层图谱 + MATCHES_KG 软连接**：教材结构层（Textbook/Chapter/Section/TextbookKP）是逐年可增的业务事实，语义层（Concept/Statement/Class）是有限的权威概念；两层不强行合一，靠 `MATCHES_KG`（TextbookKP→Concept，方向固定、置信度 ≥0.5 才连）连接，互不污染。
- **年级推断**：教材→年级映射表 `TEXTBOOK_TO_GRADE`（"必修第一册"→高一、"七年级上册"→初一）反推，学段 `STAGE_FALLBACK` 反向推断兜底，`mark` 字段兼容解析（`6.2.1`/`6-2-1`/`第六章第二节`）。
- **四道质量防线**：解析生成（统一结构）→ 清洗（"通用"标签 88 组/序号前缀/全角→半角）→ 增强（属性纯规则不用 LLM）→ 过滤（数学活动/复习题/`例\d` 不建点）。
- **缺失知识点 LLM 推断**：小学 1-6 与高中知识点为空，TextbookKPInferer 双模型投票（GLM-4-flash 主 + deepseek-chat 副）按章节信息推断，缺失章节 295→推断 1052、平均置信 0.93。
- **三段式匹配**：标准化精确匹配（同义词完整词匹配）兜确定性 → bge 向量粗筛 top-20 压候选 → 只有拿不准的交双模型投票（DS=0.6/GLM=0.4/阈值 0.5，DeepSeek 否决）；LLM 调用从 500 万降到 2.7 万（-99%）、提速约 50 倍。
- **断点续传 llmTaskLock 三件套**：TaskState（检查点）+ CachedLLM（SHA256 缓存）+ ProcessLock（进程锁），推断 2-3 小时、匹配 1-2 小时任务中断可续。

## 落地真相（代码）

> **最大翻转**：方案文档 D12 规划用 **MySQL 承接任务状态与断点续传**，代码落地是 **llmTaskLock 的 TaskState 用 JSON 文件落 `output/progress/`**（临时文件+rename 原子写+备份，`state_manager.py`），MySQL 状态表在 Python 管道里不存在——离线管道自洽、不依赖外部服务。另有两处局部翻转：import 脚本默认数据路径与 README 不符、前置推断 CLI 无 `--resume` 参数（断点靠检查点文件而非参数开关）。

**分阶段落地现状（谁负责 / 调什么 / 产出什么）**：

| 阶段 | 谁负责（脚本/核心类） | 调什么 | 产出 |
|---|---|---|---|
| 拆分 | `split_main_ttl.py` / `split_material_ttl.py` | rdflib；main 按 URI 学科前缀 `instance/{subject}#`，material 按 C3 类型+P4 名称关键词+BFS 沿 P13/P2/P3 传播 | `main-math.ttl`(14019 triples) / `material-math.ttl`(6024 triples) |
| Schema | `create_neo4j_schema.py` + `validate_schema.py` | 建 3 唯一约束（kp_uri/subject_code/textbook_isbn），性能索引延迟到导入后 | 6 标签+3 约束就绪，退出码 0/1 |
| 生成 | `generate_textbook_data.py` | 教材 JSON → Textbook/Chapter/Section/TextbookKP 节点 + CONTAINS/IN_UNIT | `textbooks/chapters/sections/textbook_kps.json` |
| 清洗 | `clean_textbook_data.py --analyze/--clean` | DataCleaner（通用标签复用 88 组/序号→order_in_book/全角→半角）；强制先分析报告再动手 | `duplicate_detection_report.json` + `clean_log.json` |
| 增强 | `enhance_chapters.py` + `enhance_kp_attributes.py` | ChapterEnhancer 4 大专题 + KPAttributeInferer 纯规则（difficulty 1-5/importance/cognitive_level/topic 继承章节） | 带教学属性的 `textbook_kps.json` |
| 推断 | `infer_textbook_kp.py` + `merge_inferred_kps.py` | TextbookKPInferer 双模型投票（两模型都有输出即采纳主模型 GLM，置信度取平均）；llmTaskLock 每 10 节存检查点 | `textbook_kps_inferred.json`（433 节→1616 条，平均置信 0.934）→ 合并进 `textbook_kps.json` |

**局部翻转（代码为准）**：
> **翻转（数据路径）**：README 称 import 读 `output/`，实际 `import_textbooks.py` 默认读根目录 `textbooks.json`、`import_math_statements.py` 读 `primary_math_statements.json`（非 `math_statement.json`）——跑脚本时用 `--file` 显式指定最稳（`import_textbooks.py` 已核）。

> **翻转（断点续传参数）**：design D5 写"前置推断 CLI 支持 `--resume`"，实际 `infer_textbook_kp.py` **无 `--resume` 参数**——断点续传基于 TaskState 检查点文件（`--no-resume` 才从头全量重跑），`match_textbook_kp.py` 同理；`--skip-validation` 在 split_main_ttl 是死参数（定义了但未生效）。

> **翻转（评审系统未落地）**：design D16 规划的"匹配评审系统"（MySQL 审核表 + `/api/kp-match/recommend` + 审核后导入）在 `edukg/scripts` 与 `ai-service/api` 均**无对应代码**，只有 `method='candidate_review'` 的 best_candidate 记录——未匹配 50 条目前没有线上审核闭环，属于规划非已上线功能（Non-Goal）。

**与方案一致处（落地）**：MERGE 幂等可重跑、加权投票 DS=0.6/GLM=0.4/阈值 0.5（DeepSeek 否决是加权数学结果，`dual_model_voter.py:356-396`）、llmTaskLock 三件套全复用、缓存键 `SHA256(prompt)[:16]`、三段式匹配三重优化（0.5 阈值+上限 3+早停）全部按方案落地。匹配率口径注意批次：语雀 canonical 为 97.1%（1690/1740），当前数据文件 96.96%（1847/1905），是同链路不同数据快照，对外讲"~97%"准确。

**存储拓扑（数据存哪 / 形态）**：

| 存储 | 存什么 / 形态 | 谁写 / 谁读 |
|---|---|---|
| Neo4j | 7 类节点（Textbook 23/Chapter 148/Section 580/TextbookKP 1740/Concept 1295/Statement 2932/Class 39）+ 8 类关系（CONTAINS/IN_UNIT/MATCHES_KG/HAS_TYPE/RELATED_TO/BELONGS_TO/PART_OF/SUB_CLASS_OF）；**URI 主键**；MATCHES_KG 置信度≥0.5 才连、RELATED_TO 方向固定 Statement→Concept | Python `import/` 脚本写；`api/kg.py` + `api/neo4j.py` 读 |
| MySQL（页面化） | 8 张表：`t_kg_textbook/chapter/section/knowledge_point` 4 主表（**URI 主键** + status + merged_to_uri）+ 3 张层级关联表 + 1 张同步记录表（edition/subject/stage/grade 维度 + reconciliation_status）；前端 SPA 读 MySQL | Java 同步（Neo4j→MySQL 手动按需 UPSERT + 状态机，**方案口径，本仓无 Java 代码真值**） |
| COS 向量索引 | 服务侧 dashscope 768 维写 COS 桶：`COS_VECTORS_INDEXES` 路由（topic→topic-index / rag-full→rag-full / rag-slice→rag-slice），put 后约 10s 异步生效；**索引维度固定不可改** | ai-service `vector_store.py` 写/查；匹配侧另用本地 bge 512 文件（kg_vectors.npy），两套维度互相不通用 |

**隐性坑（运维须知）**：① 在线查询标签坑——`api/kg.py` 依赖的 `KnowledgeGraphService` 统一 `MATCH (e:Entity {...})`，而离线导入用的是 Textbook/Concept 等**具体标签**，联调前直接调 `/entities`、`/tree` 可能查不到离线数据；② 属性增强必须在 LLM 推断**之后**跑（早期先增强只覆盖 22%，修复为推断后重跑补 1052 个）；③ topic 继承章节会错（"加法"在"位置"章被标成图形与几何），靠匹配 Concept 的 Class 类型修正 144 个——该修正是按批数据修正，未固化进属性推断代码；④ `clear_neo4j.py` 整库清空不可恢复、无确认提示。

## 追问与防御

**预期追问：图谱数据源可信吗？**
→ **回答要点**：可信，四层来源各有背书——EduKG 语义层来自清华 THU-KEG 学术开源（官方 SPARQL 端点）、main.ttl 是教材基准、爬虫目录经课标对齐校验、课标小学是 OCR+人工。一条铁律：权威基准 TTL **冻结只读**，业务派生数据只存 MySQL 永不写权威图；最终匹配率 97.1%、平均置信 0.975 就是质量答卷。

**预期追问：年级是怎么来的？**
→ **回答要点**：不是数据自带，是**教材→年级映射表反推**——`TEXTBOOK_TO_GRADE`（"必修第一册"→高一、"七年级上册"→初一）为主，学段 `STAGE_FALLBACK` 反向推断兜底，`mark` 字段（`6.2.1`/`第六章第二节`）兼容解析小节序号。设计口径如此，落地一致。

**预期追问：TTL 和教材数据怎么合一？**
→ **回答要点**：**不合一，两层分存 + MATCHES_KG 软连接**。TTL（v0.1）建语义层 Concept/Statement/Class，教材（v3.1 URI）建结构层 Textbook/Chapter/Section/TextbookKP，两层通过匹配关系连接（方向固定 TextbookKP→Concept、置信度 ≥0.5 才连边）；URI 版本化（v0.1/v0.2/v3.1）区分来源，互不污染，这也保证权威图谱零写入。

**预期追问：匹配失败怎么办？**
→ **回答要点**：不硬连、留兜底。三段式匹配里精确匹配兜 86.8%、向量粗筛压候选、双模型投票只处理拿不准的（相似度 <0.5 直接跳过、不一致时 DeepSeek 否决权 + 置信度 ×0.7）；未匹配约 3%（主要小学 69.6% 知识点与 EduKG 高中抽象概念不对齐）落入 `candidate_review`（当前 50 条）。**如实说明**：design 的评审系统（MySQL 审核表+推荐接口）未落地，当前只有 best_candidate 记录，审核闭环是规划非已上线功能。
