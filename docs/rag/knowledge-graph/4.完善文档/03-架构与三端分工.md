# 03 架构与三端分工
> summary: 解答「知识图谱五端怎么分工、Neo4j 怎么同步到 MySQL 给前端读」——Python edukg 管道离线构建(Phase0-3)导入 Neo4j 最终存储(7 类节点/8 类关系)+ai-service 桥在线暴露(api/kg.py 业务+api/neo4j.py 通用 CRUD x-internal-token)+Java 页面化同步(8 张表 URI 主键、@DS("kg") 双数据源、状态机 active/deleted/merged、大事务+对账)+前端 React SPA 三栏只读; 图谱关系直查 Neo4j Redis TTL 300s 降级; 权威图谱零写入、在线查询 :Entity 标签坑

## 为什么（语雀）

教材知识点与 EduKG 概念分散在 EduKG TTL、main.ttl、人教版爬虫、课标等多来源，要变成"教材结构 + 概念语义"两层互连、可检索可推理的知识图谱，才能支撑 AI 答疑 GraphRAG、掌握度诊断与前端图谱页面浏览。消费侧多元但单点扛不住：Java 后端没有 Neo4j 集成、前端是独立 SPA，Neo4j 实时查询又重——所以页面化不能靠前端直查图库。早期方案曾考虑"方案 A：Neo4j 实时查询"，已演进为"方案 B：Neo4j 同步 MySQL、前端读 MySQL"，架构因此被拆成 Python 管道 + Neo4j + ai-service 桥 + Java + 前端五端分工。

## 怎么设计（方案）

**演进口径**：早期方案 A（Neo4j 实时查询，Java 直连图库）被否——Java 无 Neo4j 集成、前端独立 SPA、实时查询重；已演进为**方案 B：Neo4j→MySQL 同步，前端只读 MySQL，图谱关系仍直查 Neo4j**（语雀 D13）。

**五端分工与数据流向**：

```
数据来源(EduKG TTL/main.ttl/人教版爬虫/课标)
  → [Python edukg 管道] 离线构建 Phase0 爬取→Phase1 生成/清洗/推断→Phase2 匹配→Phase3 导入
  → [Neo4j] 最终存储(7 类节点/8 类关系), 权威图谱零写入
  → 在线两条消费链路:
     ① ai-service 桥: api/kg.py 业务查询 + api/neo4j.py 通用 CRUD → 前端/答疑
     ② Java 同步: Neo4j→MySQL ai_edu_kg(@DS 双数据源) → 前端 SPA 只读; 图谱关系直查 Neo4j
```

| 端 | 角色 | 核心职责 | 关键设计 |
|---|---|---|---|
| Python edukg 管道 | 离线构建 | 数据来源→加工→导入 Neo4j（Phase0-3）；清洗/推断/匹配 | 方案 C：CSV→Neo4j，MERGE 幂等，Neo4j 只是最后仓库 |
| Neo4j | 最终存储 | 7 类节点/8 类关系；两层图谱；权威冻结只读 | 权威图谱零写入，派生数据（掌握度/点亮）只存 MySQL |
| ai-service 桥 | 在线 API | api/kg.py 业务查询 + api/neo4j.py 通用 CRUD | x-internal-token 鉴权；Java 经桥调 Neo4j |
| Java 后端 | 页面化同步 | Neo4j→MySQL 同步 8 张表；导航/知识体系 API；掌握度派生 | @DS("kg") 双数据源、状态机 active/deleted/merged、大事务+对账 |
| 前端 React SPA | 只读消费 | 三栏布局（树+图谱+详情）；逐级懒加载；同步管理/统计 | 读 MySQL；图谱关系经 Java 查 Neo4j，Redis TTL 300s 降级 |

分工一句话复述：**Python edukg 管道把多来源数据离线加工成 Neo4j 图谱**（计算与存储分离，Neo4j 只是最后仓库）；**Neo4j 是最终存储与权威事实，只读零写入**；**ai-service 桥把图谱能力在线暴露给 Java/前端**（业务查询 + 通用 CRUD）；**Java 把 Neo4j 教材结构按 URI 主键同步到 MySQL ai_edu_kg 并出导航/知识体系 API**；**前端 React SPA 只读 MySQL 逐级浏览、图谱关系经 Java 直查 Neo4j**。数据流单向：数据来源 → Python → Neo4j →（ai-service 桥在线 / Java 同步 MySQL → 前端）。

**关键设计**：
- **两层图谱**：教材结构层（Textbook/Chapter/Section/TextbookKP，真值）+ 语义层（Concept/Statement/Class，权威概念），MATCHES_KG 软连接（置信度≥0.5），互不污染。
- **同步策略**：手动按需（非 CDC）+ 按 URI UPSERT + 状态机 active/deleted/merged + 单大事务 + 对账校验；图谱关系（MATCHES_KG/PART_OF/RELATED_TO）**不同步**、直查 Neo4j（Redis key `kg:neo4j:{uri}:{query_type}` TTL 300s，Neo4j 不可用返回空关联 + `neo4jAvailable:false` 降级）。
- **双数据源 @DS("kg")**：dynamic-datasource-spring-boot3-starter，业务 Mapper 默认 ai_edu_user、图谱 Mapper（edukg.mapper.*）@DS("kg") 路由 ai_edu_kg，物理隔离；@Transactional 默认绑 user，图谱 Service 显式 @Transactional("kg")；primary=user、strict=true。
- **URI 主键**：非自增 ID，跨 Neo4j/MySQL 唯一锚点，同步按 URI UPSERT，URI 永不修改（改动走合并流程）。
- **Non-Goal（方案口径，非已实现）**：不做 Neo4j 实时查询（方案 B 已否）；后端 design 明确"不做前端页面开发（提供 API 由前端自行开发）"、"不做管理员审核/重跑"（后续阶段）。

## 落地真相（代码）

> **最大翻转**：方案画的是"Neo4j 同步 MySQL + 前端只读"的完整闭环，但本仓只能核验 Python 管道与 ai-service 桥（edukg/README.md + api/kg.py + api/neo4j.py），**Java/前端代码不在本仓**，分析-11 基于 design 撰写并标注"非代码真值"；且 Python 桥在线查询统一用 `:Entity` 标签、离线导入却是具体标签，联调前直接调 /entities、/tree 可能查不到导入的数据（分析-01 最大坑）。**权威度 1.0 判定**：方案素材（语雀+design）齐备 + Python 侧代码真值（edukg 管道 + ai-service 桥 + api/kg.py）本仓可核验，足够支撑 1.0；Java/前端按 design 口径，不作为代码现状写死。

**Python 管道（本仓可核验 ）**：`edukg/README.md:26-37` 定义 Phase0-3 全链路；11 个 import 脚本按依赖顺序（Class→Concept→Statement→关系→教材→章节→小节→知识点→归属→匹配）全 MERGE 幂等、可重跑不重复，缺失目标 OPTIONAL MATCH 静默跳过，`--dry-run`/`--clear`/`--stats` 三种运行模式（分析-10）。落地 6757 节点 / 20887 关系，与方案 D2（CSV→Neo4j）一致。

**ai-service 桥（本仓可核验 ，附局部翻转）**：
- `api/kg.py`（prefix /api/kg）实为 **10 个路由**（/entities、/entity/{uri}、/link、/subject/{subject}/tree、/classes、/student/{id}/progress GET/POST、/statistics、/recommend、/learning-path），方案总揽 §10 称"八端点"少算（分析-01 对账）。
- `api/neo4j.py`（prefix /api/neo4j）12 个路由全走 `x-internal-token` 鉴权（verify_internal_token 比对 settings.INTERNAL_TOKEN，不符 401），含裸 Cypher /query（read_only 默认 true 但调用方可关，生产需防 token 泄露）（分析-01）。
- `get_knowledge_tree`/`get_learning_path` 是简化桩（平铺两层/只返回单点），页面化真层级在 Java 同步 MySQL 侧，别从 Python 桥期待完整图谱能力（分析-01 隐性坑）。

> **翻转①（最大坑）：在线查询 `:Entity` 标签 vs 离线导入具体标签**。`api/kg.py` 依赖的 `KnowledgeGraphService` 全部 `MATCH (e:Entity {uri:...})` / `MATCH (e:Entity {subject:...})`（service.py:101-109, 180-185, 256-259），但 `edukg/scripts/kg_data/import/*.py` 导入的节点标签是 `Textbook`/`Chapter`/`Section`/`TextbookKP`/`Concept`/`Statement`/`Class`，没有统一 `Entity` 标签。要么 `Entity` 由 Java 经 api/neo4j.py 动态建（该接口示例正是 `POST /api/neo4j/nodes/Entity`，api/neo4j.py:71-74），要么 service.py 查询是"期望面"而非"实际数据面"——联调核对前，直接调 /entities、/tree 可能查不到离线导入的数据（分析-01 隐性坑）。

> **翻转②：core/rag/query.py 不是图谱查询桥**。它实为 **AI 答疑面试口述 RAG 检索编排**：`MODULE_ANCHORS` 四模块闭集含 knowledge-graph（query.py:68）、`MODULE_ANCHOR_RULES` 关键词"知识图谱/图谱/neo4j/知识点/概念/关系/节点"→图谱锚点（query.py:71-76），检索的是图谱**文档切片**进 RAG 池，不是 Neo4j 节点数据。图谱在线数据查询走 api/kg.py + api/neo4j.py，两条链路独立，面试表述勿混（分析-01 隐性坑）。

**Java 同步与前端页面（本仓不可核验，design 口径 ）**：8 张表（4 节点主表 URI 主键 + 3 层级关联含 order_index + 1 同步记录）、@DS("kg") 双数据源、状态机 active/deleted/merged、单事务 UPSERT + 对账 reconciliation_status，均为 design 文档层面一致（分析-11 对账），非代码真值。

> **翻转③：graph 接口与 API 前缀 design 自相矛盾**。backend-ui design 列了 `GET /api/kg/knowledge-points/{uri}/graph`（D12.3），但 frontend design 标注"后端当前未实现此接口"，替代方案待确认（补接口 / batchGetConceptRelations 自建 / 其他接口组合）（design-frontend:83-92,154）；且后端 design 用 `/api/kg/**`、前端 design 全部用 `/api/auth/kg/**`，前缀口径不一致，联调易 404（分析-11 隐性坑）。

## 追问与防御

**预期追问：为什么图谱在线查询查不到导入的节点？**
→ **回答要点**：标签体系不一致——在线查询统一 `:Entity`（service.py:101-109），离线导入用 Textbook/Chapter/Section/TextbookKP/Concept/Statement/Class 具体标签，无 Entity 标签。要么 Java 经 api/neo4j.py 动态建 Entity、要么查询是"期望面"。联调前必须对齐标签，否则 /entities、/tree 查不到导入数据（翻转①）。

**预期追问：Neo4j 同步到 MySQL 怎么保证一致性？**
→ **回答要点**：四重保证——手动按需（非 CDC）按 URI UPSERT 幂等可重跑；状态机 active/deleted/merged 软删可回溯（deleted 进度查询例外）；单大事务内重建关联表，提交前前端看不到中间态；同步后 MySQL vs Neo4j 计数对账写 reconciliation_status。图谱关系不同步、直查 Neo4j + Redis TTL 300s + 空关联降级，导航不依赖图谱可用性。

**预期追问：ai-service（Python 桥）和 Java 怎么分？**
→ **回答要点**：在线图谱查询走 Python 桥——api/kg.py 业务 + api/neo4j.py 通用 CRUD（x-internal-token）；Java 做页面化同步 + 导航/知识体系 API + 掌握度派生。core/rag/query.py 是 AI 答疑 RAG 检索编排（图谱是 4 个模块锚点之一）不是图谱桥，两条链路别混。Python 管图谱数据与查询，Java 管页面与派生。

**预期追问：图谱页面化真的落地了吗？**
→ **回答要点**：方案 B 已拍板、design 三份一致，但 Java/前端代码不在本仓、分析-11 基于 design 非代码真值；且 graph 接口未实现、`/api/kg/**` vs `/api/auth/kg/**` 前缀不一致是 design 内自相矛盾。Python 侧本仓可核验支撑 1.0；Java/前端按 design 口径待联调核对，讲页面化要注明"方案已定、代码以 Java 仓为准"。
