# 04 数据清洗与质量保障

> summary: 解答「知识图谱数据怎么保证干净、匹配率 97.1% 怎么来」——清华 EduKG+人教版教材+课标 OCR 四类来源各自背书、权威基准冻结只读、四道质量防线(生成解析→清洗→增强→过滤)、匹配三段式(精确匹配+向量粗筛+双模型投票 17%→97%)、LLM 调用三重优化、checksum 索引校验(3.1MB vs 懒加载 3.5GB)与 llmTaskLock 断点续传
> 权威度: 1.0
> 模块: knowledge-graph
> COS路径: rag-source/knowledge-graph/完善文档/04-数据清洗与质量保障.md
> 类别：开发难点

## 为什么（语雀）

图谱数据不是"拿来就用"：语义层用清华 EduKG 开源图谱（权威可背书），但短板是知识点以初高中抽象概念为主，小学 69.6% 的教材知识点对不上；初始匹配率只有 17%，瓶颈不是算法差而是抽象层级错位。数据必须过四道质量防线才进图谱，权威基准冻结只读、错误只发生在可纠正的派生层，最终匹配率 97.1% 就是数据质量的最终答卷。

早期方案曾"纯靠 LLM 全量匹配"，调用爆炸且匹配率仅 17%，已演进为"精确+向量粗筛+双模型投票"三段式。

## 怎么设计（方案）

**（方案口径，已演进）** 早期"数据直接入库 + 纯 LLM 全量匹配" → 演进为"四道质量防线 + 匹配三段式 + checksum 索引校验 + 断点续传"。

### 四道质量防线（入库前的完整链路）

```
解析与生成 → 清洗 → 增强 → 过滤 → 规范化数据 → 匹配/导入
```

1. **生成解析**：TTL 用 rdflib 解析（自动 Unicode 解码），教材 JSON 生成 Textbook/Chapter/Section/TextbookKP 标准节点——只做格式统一，不做任何判断。
2. **清洗（DataCleaner）**：清"通用"标签跨小节复用（88 组）、小节名序号提取到 order_in_book、全角→半角；**先 --analyze 出报告、人工确认、再 --clean**，防脚本误删教材结构。
3. **增强（ChapterEnhancer + KPAttributeInferer）**：章节专题增强 + 知识点属性补全——**刻意用规则不用 LLM**（属性客观可枚举，快、可复现、不编造）。难度 1~5 按年级基础+关键词微调，认知层级按布卢姆分类。
4. **过滤（filters）**："数学活动/小结/整理和复习/复习题/^例\d" 等非知识点条目不建图谱节点，保证图谱里每个 TextbookKP 都是真知识点。

### 匹配率 97.1% 怎么来：三段式 + LLM 标准化预处理

17%→97.1% 的关键不是换更强模型，而是先解决"教材名 ≠ 概念名"的抽象层级错位：

```
LLM 标准化预处理(教学名→抽象概念) → ①精确匹配(标准化+同义词) → ②向量粗筛 top-20 → ③LLM 双模型投票 → MATCHES_KG
"1-5 的认识" → LLM → ["数的认识","自然数","数字"] → 匹配"自然数"(相似度 0.711)
```

| 环节 | 参数 | 效果 |
|---|---|---|
| LLM 标准化预处理 | DeepSeek 教学名→抽象概念列表 + best_match | 解决抽象层级错位（提点关键） |
| 精确匹配 | 标准化+同义词（完整词匹配） | 兜确定性，conf=1.0 |
| 向量粗筛 | bge-small-zh-v1.5 本地 512 维 top-20 | 全量 5000+ → top-20 候选 |
| LLM 双模型投票 | 两模型一致采纳；不一致加权 DS=0.6/GLM=0.4、阈值 0.5（DS 否决） | 抑制单模型幻觉 |
| LLM 调用优化 | 相似度 <0.5 跳过 + 候选上限 3 + 命中早停 | 500 万 → 2.7 万（-99%），提速约 50 倍 |

### checksum 索引校验 + 断点续传

**checksum 校验流程**：`build_vector_index.py` 一次性构建图谱概念向量 → 落盘 `kg_vectors.npy`（512 维）+ `index_meta.json`（含 `neo4j_checksum`，即当前 Neo4j 概念 uri+label 按序拼接的 MD5）→ 匹配启动时用当前 Neo4j 概念实时算指纹与 meta 比对 → 匹配则用预构建索引（约 3.1MB、启动 <5ms）；失配告警"索引已过期"并回退懒加载（3.5GB）。

**断点续传（llmTaskLock）**：LLM 推断/匹配是 2-3 小时长任务，中断后从头重跑既费时又费钱——`TaskState`（每完成一个单位落检查点，重启 resume 过滤已完成）、`CachedLLM`（同 prompt 不重复调 API）、`ProcessLock`（文件锁防多进程并发写进度），三件套让长任务中断可续。

### 质量指标

| 指标 | 值 | 说明 |

## 落地真相（代码）

> **最大翻转：匹配率不是单一数字**——方案/决策记录讲 97.1%（1690/1740 早期里程碑、未匹配 50），当前代码产物 `matches_kg_relations.json` 是 **1905 条基线 = exact 1639 + llm_vote 208 + candidate_review 50 + none 8，匹配率 96.96%、平均置信 0.973**；两个口径都是"~97%"，但基线不同，面试讲 97.1% 必须能说清口径。（`3.代码/分析-07-知识点匹配与双模型投票.md` 实际数据）

**落地：四道防线全落地。**
- DataCleaner 四件套（`data_cleaner.py` 通用标签检测/`extract_section_order` 序号/全角→半角），`--clean` 强制要求先 `--analyze` 出报告否则拒绝执行（`clean_textbook_data.py`）——"先报告后动手"的安全设计真实存在。
- 属性推断纯规则无 LLM（`kp_attribute_inferer.py` GRADE_BASE_DIFFICULTY + 关键词 ±1，topic 继承章节）；filters 过滤"数学活动/复习题/^例\d"（`filters.py`）。
- 匹配三段式全落地（`kp_matcher.py` exact_match/_retrieve_candidates/llm_match_with_cache）；双模型加权投票 `WEIGHT_DS=0.6/WEIGHT_GLM=0.4/THRESHOLD=0.5`（`dual_model_voter.py:354-396`）；LLM 调用三重优化（`SIMILARITY_THRESHOLD=0.5`、`LLM_CANDIDATE_LIMIT=3`、命中早停）。
- checksum 校验真实存在：`MD5("".join(f"{uri}:{label}" 按 uri 排序拼接))`（`vector_index_manager.py:204-218`），失配告警并回退懒加载（`kp_matcher.py:486-491`）。
- 断点续传真实存在：TaskState 落 JSON 文件 `output/progress/`（`state_manager.py`）+ CachedLLM（`llm_cache.py:30` 缓存键 `SHA256(prompt)[:16]`）+ ProcessLock（`process_lock.py`）。

> **翻转：预构建索引大小**——方案/代码注释称"约 10MB"，实际索引文件 `kg_vectors.npy`≈2.6MB + kg_concepts.json≈0.29MB + kg_texts.json≈0.15MB，**合计约 3.1MB**；10MB 是注释口径偏大。（`3.代码/分析-09` index_meta 实测）

> **翻转：--skip-validation 是死参数**——`kg_split` 脚本 argparse 定义了该参数，但函数无签名、main 未传，实际不生效。（`方案-代码对账.md` #18）

> **翻转：匹配评审系统未落地**——D16（MySQL 审核表 `textbook_kp_match_review` + `/api/kp-match/recommend` + Web 人工确认回写 MATCHES_KG）是方案，代码仅有 `method='candidate_review'` 的 best_candidate 记录字段；审核闭环是规划不是已上线功能。当前未匹配 58（candidate_review 50 + none 8），非语雀的 308。（`3.代码/分析-07` 对账 #D16）

> **翻转：缓存键**——语雀称 `md5(textbook_kp + kg_kp)`，实际 `SHA256(prompt)[:16]`（`llm_cache.py:30`）；且 `vote_match/vote_prerequisite` 定义但主流程未调用（死代码）。

### 真实踩过的坑（坑档案 J-KG）

- **属性增强执行顺序 bug（J-KG2）**：增强跑在 LLM 推断之前，推断出的 1052 个知识点全没属性，覆盖率仅 22%（299/1350）——流水线顺序依赖，必须"先推断后增强"；规则类步骤设计成 `--force` 幂等重跑。
- **topic 继承污染（J-KG3）**：topic 直接继承章节，"加法"落在"位置"章被错标成"图形与几何"——用匹配到的 Concept 的 Class 类型反向修正 144 个；但这是数据级一次性修正未固化到代码，重跑属性增强会退回章节继承。
- **同义词过度匹配（J-KG9）**：早期 `key in name` 子串匹配把"加法交换律"精确匹配到"加法"——改完整词匹配（`normalized_name == normalized_key`），组合词交给向量/LLM 语义层。
- **内存 3.5GB（J-KG7）**：懒加载每次启动都"模型加载 + 全量 encode 1295 概念"，内存约 3.5GB、启动 ~60s——预构建索引把预计算结果落盘，运行期只读文件（3.1MB）。

## 追问与防御

**预期追问：数据源可信吗？**
→ **回答要点**：四层来源各有背书——EduKG 是清华学术开源 + 官方 SPARQL 端点、教材是爬虫 + 课标对齐校验、小学是课标 OCR + 人工校验；铁律是权威基准 TTL 冻结只读、业务派生数据只存 MySQL，错误只发生在可纠正的派生层，权威图谱物理上不可能被污染；匹配率 97.1% 就是最终质量背书。

**预期追问：匹配率 97.1% 怎么保证？**
→ **回答要点**：三段式互补——精确匹配（标准化+同义词完整词匹配）兜确定性、向量粗筛 top-20 压候选、只有拿不准的交 LLM 双模型投票（两模型一致采纳、不一致加权 DS=0.6/GLM=0.4 阈值 0.5、DeepSeek 一票否决抑制单模型幻觉）；匹配前 LLM 标准化预处理（"1-5 的认识"→"自然数"）是 17%→97% 的关键。口径要讲清：97.1% 是 1690/1740 基线，当前 1905 条产物基线 96.96%。

**预期追问：匹配失败怎么办？**
→ **回答要点**：不硬连——投票阈值 0.5 不过即不建 MATCHES_KG，未匹配记 `candidate_review`（保留 best_candidate）留人工审核；D16 的 MySQL 审核表 + LLM 推荐 + Web 人工确认是规划方案，代码现状只有 candidate_review 字段，审核闭环未上线。规则层只处理"字面等价"，语义模糊交向量/LLM 层，宁可留人工也不张冠李戴。

**预期追问：索引过期怎么办？**
→ **回答要点**：checksum 兜底——索引与 Neo4j 数据快照绑定（MD5(uri:label 排序拼接)），图谱变则指纹失配，启动告警"索引已过期"并回退懒加载（3.5GB）或 `--force-build-index` 重建；宁可回退慢的懒加载也不拿脏索引静默匹配。索引维度 512 建好不可改，换模型/维度需重建索引。
