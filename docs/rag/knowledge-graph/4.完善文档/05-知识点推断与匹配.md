# 05 知识点推断与匹配

## 为什么（语雀）

图谱要能支撑答疑定位知识点，先得让**教材侧的知识点存在且和语义层对得上**，而这恰恰是两条最痛的链路：一是**数据缺一半**——人教版教材 JSON 小学 3-6 年级、高中必修的 `knowledge_points` 全空，只有初中 7-9 年级 252 个完整，小学/高中学段"没有知识点可挂"；二是**名字对不上**——教材知识点"1-5 的认识"和图谱抽象概念"自然数"说的是同一回事但字面完全不同，初始匹配率只有 **17%**（LLM 匹配仅 2%）。所以要做两件事：LLM 把缺失知识点推断出来（补 1052 个），再走"精确匹配 + 向量粗筛 + 双模型投票"把每个教材知识点对到语义层 Concept 上建 MATCHES_KG。早期方案曾直接全量 LLM 遍历匹配，已演进为三段式成本可控的匹配链路。

## 怎么设计（方案）

**（方案口径，已演进）** 早期：全量 LLM 遍历 5000+ 图谱概念匹配（单知识点最坏 40 次 API 调用、总量约 500 万次）、单模型投票、同义词用子串包含扩展（"加法交换律"误配"加法"）。**已演进为**：三段式匹配 + 双模型加权投票 + LLM 标准化预处理。

### 链路一：LLM 推断补全缺失知识点

- 缺失判定：小学 1-6 年级且 `len(existing_kps)==0` 才推断、高中同、初中明确不推断（已有 252 个完整）。
- `TextbookKPInferer` 双模型投票：**glm-4-flash（免费）作主模型 + deepseek-chat 作副模型**，两模型都有输出即采纳主模型结果、置信度取平均；推断结果 `source=llm_inferred`，合并进 `textbook_kps.json` 并重写 IN_UNIT 关系。
- 任务级防护：llmTaskLock 断点续传三件套（TaskState 检查点 + CachedLLM 结果缓存 + ProcessLock 进程锁），推断 2-3 小时中断可续。

### 链路二：三段式匹配建 MATCHES_KG

```
① 精确匹配: 标准化(小写/去空格/统一括号) + 同义词(SYNONYM_MAP, 完整词匹配)
    命中 → confidence=1.0, method=exact_match（覆盖约 86%）
    未命中 → ②
② 向量粗筛: bge-small-zh-v1.5 512 维, 取 top-20 候选
    （向量不可用回退 difflib 字符匹配）
    对 top-20 中相似度 ≥0.5 的候选进 ③
③ 双模型投票: GLM-4-flash + DeepSeek-chat 并行
    两模型一致(consensus) → 采纳, confidence=两模型平均
    不一致 → 加权: weighted_score = 0.4(GLM=True) + 0.6(DS=True)
      weighted_score ≥ THRESHOLD 才采纳（仅 DS=True 可过 → DeepSeek 否决权）
      采纳时 confidence = winner × 0.7 打折
    全拒/不过 → candidate_review 待人工
```

### 置信度纪律与成本（阈值必须精确）

```
投票权重:  WEIGHT_DS = 0.6 / WEIGHT_GLM = 0.4
过线阈值:  THRESHOLD = 0.5 —— 不过 0.5 不创建 MATCHES_KG 硬连接(不硬连)
置信度过滤: 投票 <0.7 丢弃(不落 MATCHES_KG, 进 candidate_review/丢弃)
成本三重优化: SIMILARITY_THRESHOLD=0.5(低相似度直接跳过, 不调 LLM)
            + LLM_CANDIDATE_LIMIT=3(最多投 3 个候选)
            + 命中即早停 break
            → LLM 调用 500万→2.7万(-99%), 40→2 次/知识点, 整体提速约 50x
```

### embedding 维度双轨（索引维度固定不可改）

| 侧 | 模型 | 维度 | 用途 |
|---|---|---|---|
| 匹配侧 | BAAI/bge-small-zh-v1.5（本地） | **512** | 教材知识点 ↔ 图谱概念 粗筛候选（kg_vectors.npy 1295×512） |
| 服务侧 RAG | dashscope text-embedding-v3 | **768** | 答疑在线 embedding（rag-full/rag-slice 桶） |

- 维度是索引构建期定死的：`vector_index_manager.py VECTOR_DIM=512`，**索引建好维度不可改**，换模型必须重建索引（checksum 失配强制重建，详见分析-09）。

## 落地真相（代码）

> **最大翻转**：匹配"标准化"与"双模型投票"不是全链路——**kp_normalizer 只用 DeepSeek 单模型**（`kp_normalizer.py:220-222`），双模型投票只发生在精确匹配失败后的匹配阶段；"投票 <0.7 丢弃"是 design/面试口径（design D4.1：≥0.9 MATCHES_KG / 0.7-0.9 CANDIDATE / <0.7 不匹配），代码主链路实际过线阈值是加权 **THRESHOLD=0.5**。

### 翻转① 缓存键不是 md5，是 SHA256(prompt)[:16]
语雀称缓存键 `md5(textbook_kp + kg_kp)`，代码实际 `get_cache_key(prompt) = SHA256(prompt)[:16]`（`llm_cache.py:30`）——Prompt 含名称+描述+学段，**改提示词模板 = 旧缓存全部失效**。缓存内容存完整 `vote_result`（两模型响应/决策/理由，可审计"为何判不匹配"），8255 个缓存文件省 16,510 次 API 调用。

### 翻转② kp_normalizer 只用 DeepSeek 单模型（定位澄清）
"双模型投票"易被理解成全链路，实际**匹配前标准化预处理 `KPNormalizer` 只调 DeepSeek**（`kp_normalizer.py:220-222`，选更严格模型）：把"1-5 的认识"翻译成 `["数的认识","自然数","数字"]`，best_match 作向量检索 query，解决 17% 根因（抽象层级错位，69.6% 小学具体名 vs EduKG 抽象概念）。**双模型投票只在匹配阶段**（精确匹配失败后的候选投票）。

### 翻转③ vote_match / vote_prerequisite 是死代码
`vote_match`/`vote_prerequisite`（`dual_model_voter.py:398-437`）定义但主流程未调用；匹配主链路走 `vote()` → `_check_consensus` → 加权 `WEIGHT_DS=0.6/GLM=0.4/THRESHOLD=0.5`（`dual_model_voter.py:354-396`）。design 的 0.9/0.7 匹配分档在死代码 vote_match 里，**未生效**。DS 否决权是数学结果非显式分支：0.6+0.4 结构下只有 DS=True 时 `weighted_score≥0.5` 才成立。

### 翻转④ LLM 推断/匹配 50x 成本靠缓存 + 断点续传 + 早停缓解
推断 2-3 小时、匹配 1-2 小时的长任务中断全损，靠 **llmTaskLock**（`core/llmTaskLock/`）断点续传：TaskState 检查点（每 10 节存一次，`textbook_kp_inferer.py:316,344-348`）+ SHA256 结果缓存 + portalocker 进程锁；再叠加匹配侧三重优化（`kp_matcher.py:729,781-783` SIMILARITY_THRESHOLD=0.5、`:727,786-796` LLM_CANDIDATE_LIMIT=3、`:825-826,852-853` 命中早停）。实际数据：匹配 1905 条 = exact_match 1639 + llm_vote 208，LLM 调用 500万→2.7万。

### 落地（与方案一致）
- 三段式匹配链路全落地：`kp_matcher.py` exact_match / `_retrieve_candidates` / `llm_match_with_cache`（分析-07 对账 D6）。
- 加权投票权重/阈值与方案一致：`dual_model_voter.py:356-396`（对账 D7）。
- 完整词匹配防同义词过度匹配：`_expand_with_synonyms` 只在 `normalized_name == normalized_key` 全等时扩展，杜绝"加法交换律"误配"加法"（坑 J-KG9）。
- 推断特判路径：`knowledge_points` 分支**不比较两模型内容是否一致**，都有输出即采纳主模型 GLM 结果（`dual_model_voter.py:288-316`）；失败降级保留已有知识点 `confidence=0.0`（`textbook_kp_inferer.py:225-244`）。

### 批次差异（非错误，口径不同）
匹配率：早期里程碑 **1690/1740 = 97.1%**（决策记录 D6），当前数据文件 **1847/1905 = 96.96%**、平均置信 0.973。未匹配数：语雀 308（297 投票不通过 + 11 无候选）vs 当前 58（candidate_review 50 + none 8）。推断数同理：早期批次 295 章节 → **1052 知识点**（平均置信 0.93，坑 J-KG4），当前数据 433 节（小学 361 + 高中 72）→ **1616 知识点**（平均置信 0.934，分析-06）。

### 🚫 匹配评审系统（D16）方案有/代码无
语雀/design 的 MySQL 审核表 `textbook_kp_match_review` + `/api/kp-match/recommend` + Web 人工确认闭环（308 未匹配按颗粒度差异 297 / 图谱缺失 11 分类）**代码未见实现**——唯一痕迹是 `method='candidate_review'` 的 best_candidate 记录字段。审核闭环是规划，不是已上线功能。

## 追问与防御

**预期追问：双模型投票怎么防误判？**
→ **回答要点**：两模型一致才采纳，抑制单模型幻觉——单模型可能自信地错，两模型一起错概率低得多。DeepSeek 更严格（几乎不误报）所以给 0.6、GLM 宽松给 0.4，等价"DeepSeek 同意才过、DeepSeek 否决就挂"，权重=把低误报模型的意见设成硬约束。

**预期追问：投票不一致怎么办？**
→ **回答要点**：加权投票仲裁，不是丢弃。不一致时 GLM=True 得 0.4（<0.5 不过）、DS=True 得 0.6（≥0.5 过）——即只有 DeepSeek=True 才可能过阈值；过线时置信度再 ×0.7 打折，避免"仲裁出来的结果"冒充高置信。为什么不用 majority vote？两个模型没有多数，加权是最小可行的仲裁。

**预期追问：匹配率 97.1% 怎么做到？**
→ **回答要点**：瓶颈不在投票模型强，而在**把教材名先翻译成图谱语言**。17% 根因是抽象层级错位（69.6% 小学具体名"1-5 的认识"对不上 EduKG 高中抽象概念"自然数"），解法是匹配前 LLM 标准化预处理 + 精确匹配（标准化+同义词，覆盖约 86%）→ 向量粗筛 top-20 → 双模型投票；早期里程碑 1690/1740=97.1%，当前 1847/1905=96.96%。

**预期追问：剩下的 3% 呢？**
→ **回答要点**：不硬连、留人工。置信度不过阈值不创建 MATCHES_KG 硬连接（THRESHOLD=0.5 不硬连、投票 <0.7 丢弃）；当前 58 个未匹配（candidate_review 50 + none 8）按 method 分类保留。语雀设想的 MySQL 审核表 + LLM 推荐 + 人工确认闭环是设计规划，代码目前只落 candidate_review 字段，面试要如实讲"审核闭环未上线"。

**预期追问：维度不一致怎么办？**
→ **回答要点**：两套 embedding 各管一段、索引维度固定不可改。匹配侧 bge 512 维（kg_vectors.npy 1295×512）、服务侧 RAG dashscope 768 维（rag-full/rag-slice）；索引构建期维度定死，换模型必须重建索引，checksum 失配会强制重建、防止拿过期索引静默算错。
