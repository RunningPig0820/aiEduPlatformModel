## 为什么（语雀）

知识图谱不是一次做满的——MVP 只做"数学数据管道 + 两层图谱入库"，把页面化、全学科、审核系统这些复杂度后置。语雀方案勾画了一条从**数据加工 → 图谱入库 → 页面化消费**的完整演进线，同时要求边界清晰：哪些现在刻意不做（Non-Goal）、为什么，哪些将来做、怎么做。演进要回答的就是"模块走到哪了、边界在哪、下一步往哪走"。

## 怎么设计（方案）

**（方案口径，已演进）** 早期方案曾规划"Neo4j 实时查询页面化（方案 A）/全学科一次做齐/匹配失败自动审核重跑"。**已收敛**——本期只做人教版数学数据管道 + 页面化方案 B，其余归入 Non-Goal 或后续演进。

### 页面化方案 B（阶段 5 核心设计，已拍板）

- 方案 A（Neo4j 实时查询）被否 → **方案 B：Neo4j 教材知识点同步到 MySQL，前端 SPA 只读 MySQL**；图谱关系（MATCHES_KG/PART_OF/RELATED_TO）**不同步**，直查 Neo4j + Redis TTL 300s + 降级 `neo4jAvailable:false`（语雀-决策记录 D13）。
- **MySQL 8 张表**：4 张节点主表（t_kg_textbook/chapter/section/knowledge_point，**URI 主键** + status + merged_to_uri）+ 3 张层级关联表（含 order_index）+ 1 张同步记录表（reconciliation_status 对账）；同步策略=手动按需触发（非 CDC）+ UPSERT 按 URI + 状态机 active/deleted/merged + 大事务（按年级拆子任务 + 细粒度锁）+ 对账（design-backend-ui D1/D2）。
- **前端**：React SPA 独立部署三栏布局（左教材树 / 中 React Flow 关系图 / 右详情 2 层父级）；React Flow 力导向图（节点 >50 提供"简化视图"只显示 Top 10）；树形导航 6 级逐级懒加载（6757 节点不一次渲染）（design-frontend 2-9）。
- **双数据源**：dynamic-datasource-spring-boot3-starter + `@DS("kg")` 注解，图谱 Mapper 走 ai_edu_kg、业务走 ai_edu_user，物理隔离（语雀-决策记录 D14）。

### 本期边界（Non-Goal，刻意不做）

| 不做 | 为什么 | 将来要做的前置条件/风险 |
|---|---|---|
| 全学科扩展 | 本期只做人教版数学；全学科 56,391 知识点、逐学科成本估算 10-20 元/DeepSeek 调用 ~1120 次，导入优先级（数理化生 P1/语言 P2/主题 P3）未定 | 需课标 2022/2017 层级基准 + 多学科导入优先级 + 新学科 v3.2 URI 前缀；风险=各学科名称颗粒度不同、匹配率难复制 |
| 复杂关系可视化（Statement/Class/PART_OF） | 前端只展示"教材知识点→概念"关联，复杂关系语义重、直查 Neo4j；页面化设计明确"不做知识图谱关系可视化" | 需前端复杂关系可视化范围确认 + React Flow 扩展；风险=多类型节点/关系渲染性能与布局成本 |
| Neo4j 实时查询 | Java 后端无 Neo4j 集成；7 表 JOIN 全扫慢 SQL 坑在前（点击式下钻改造），实时查询重 | 已部分用"图谱关系直查 Neo4j + Redis TTL 300s + 降级"替代；风险=Neo4j 不可用拖垮导航 |
| 管理员审核/重跑 | 匹配评审系统（MySQL 审核表 + /api/kp-match/recommend + 审核导入）是设计规划（D16），代码无实现 | 需审核 UI + 审核后导入 Neo4j + 新知识点 v3.2 前缀；风险=批量误确认需 reviewer_id/time 回溯 |
| 批量定时任务（自动同步/定时聚类） | 同步为**手动按需触发**（非实时 CDC），面试项目不引入定时复杂度 | 需调度基础设施 + 幂等/断点续传；风险=定时自动同步与手动确认链路冲突 |
| 多版本教材（北师大/苏教版） | design D13 记录当前阶段不实现，专注人教版 | 需 v3.2 多版本教材（URI 改 {edition}-{grade}{semester}）+ version_code 字段 + 版本对比 |

> 以上 Non-Goal 全部是**方案边界**，正文任何一节都不得把"全学科/审核重跑/定时同步"描述成已实现功能——它们只在方案演进口径或本表出现。

## 落地真相（代码）

> ⚠️ **最大翻转（三个核心）**：①阶段 5 页面化是"方案拍板、数据层设计完成"——**Java/前端代码不在本仓**（aiEduPlatform/、aiEduPlatformFront/ 不存在），分析-11 基于 design 撰写并标注"非代码真值"，Python 仓能核验的只有数据管道侧落地；②阶段 4 的**匹配评审系统（审核重跑）是规划非已上线**，代码无实现（对账项 4）；③匹配率**当前批次 96.96%（1905 基线）vs 历史 97.1%（1740 基线）**是不同数据快照。

- **✅落地（阶段0-3 Python 数据管道）**：Neo4j 落地 7 类节点 6,757 个 + 8 类关系 20,887 条，两层图谱 + MATCHES_KG 连接真实导入；Phase0 爬取→Phase1 生成/清洗/推断（LLM 补 1052 知识点，平均置信 0.93）→Phase2 匹配（精确+向量粗筛+双模型投票）→Phase3 导入 MERGE 幂等（3.代码/分析-01）。
- **✅落地（阶段1 工程化）**：llmTaskLock 断点续传三件套真实存在——TaskState 按 task_id 落 JSON + CachedLLM SHA256 缓存 + ProcessLock 文件锁（design-python-2026-04-08 D1-D5；坑档案 J-KG8）。
- **✅落地（向量索引）**：匹配侧 bge-small-zh-v1.5 512 维预构建索引 `kg_vectors.npy`（1295×512）+ index_meta.json MD5 checksum 校验，懒加载 3.5GB vs 预构建约 10MB；服务侧 dashscope text-embedding-v3 768 维写 COS 向量桶（3.代码/分析-09）。
- **⚠️ 翻转①（页面化 Java/前端代码不在本仓）**：方案 B 的 8 张表 / @DS("kg") 双数据源 / React Flow 三栏只在 design 文档层面描述（design-backend-ui D1/D2/D14、design-frontend 2-9），**未真读 Java/前端代码**；且前端 design 标注图谱关系 `graph` 接口"后端当前未实现"、API 前缀前后端口径不一致（`/api/kg/**` vs `/api/auth/kg/**`）待联调（3.代码/分析-11；方案-代码对账 #19/#20）。
- **⚠️ 翻转②（匹配评审系统是规划）**：D16 的 MySQL 审核表 `textbook_kp_match_review` + `/api/kp-match/recommend` + 审核导入，edukg/scripts 与 ai-service/api 均无实现，仅有 `candidate_review` 记录字段——审核闭环是设计目标非上线功能（方案-代码对账 #4）。同样地，阶段 4 前置依赖"多证据融合"的 fuse_results 方法存在但**主链路未接入**，CLI 只产 llm_prereq.json，final_prereq.json 无脚本生产（方案-代码对账 #11）。
- **⚠️ 翻转③（匹配率批次差异）**：当前 `matches_kg_relations.json` 1905 条 = exact 1639 + llm_vote 208 + candidate_review 50 + none 8，匹配率 **96.96%**、平均置信 0.973；决策记录 1690/1740 = 97.1% 是 1740 基线快照——对外讲"~97%"准确，精确数字需带基线（方案-代码对账 #6）。
- **⚠️ 翻转（状态存储）**：design D12「MySQL 状态表替代 SQLite」，实际 llmTaskLock 的 TaskState 用 **JSON 文件落 output/progress/**，未见 MySQL 状态表实现——设计构想未落地（方案-代码对账 #3）。

## 追问与防御

**预期追问：全学科扩展做不做？**
→ **回答要点**：做，但是逐学科按优先级演进（数理化生 P1/语言 P2/主题 P3），不是本期。原因：全学科 56,391 知识点规模大、逐学科成本 10-20 元且优先级未定；数学只有约 1,740-1,905 个知识点。管道已通用（Phase0-3 与学科无关），扩学科只需跑同一管道 + v3.2 URI 前缀 + 课标 2022/2017 层级基准。

**预期追问：图谱页面化落地了吗？**
→ **回答要点**：数据层方案已拍板（方案 B：Neo4j→MySQL 同步 8 表 + 双数据源 + React Flow 三栏），但 Java/前端代码不在本仓、无法核验真值；Python 仓能确认的只有数据管道侧 6,757 节点/20,887 关系导入。前端 design 还标着 graph 接口未实现、API 前缀前后端不一致，属"联调收口"状态，不能讲成"已上线"。

**预期追问：下一步是什么？**
→ **回答要点**：三条线——①全学科扩展（P1 数理化生，管道复用）；②页面化联调收口（补 graph 接口、对齐 /api/kg 与 /api/auth/kg 前缀、点亮前端）；③GraphRAG 全链路（答疑/掌握度/学习路径消费闭环）。数据飞轮：答疑越多→掌握度越准→学习路径越准→更多答疑（参考：09 业务闭环）。

**预期追问：为什么先做数学？**
→ **回答要点**：数学结构化程度最高（教材层级清晰、人教版 JSON 初中完整可作为管道调试基线）、EduKG 语义层对数学概念覆盖好（1295 Concept），且是 K-12 刚需。先做数学能最快验证"两层图谱 + MATCHES_KG + 学习路径"可行性，再横向复制到理化生——匹配率 17%→97% 的坑（LLM 标准化、向量粗筛、双模型投票）都在数学上踩完，扩学科风险更低。
