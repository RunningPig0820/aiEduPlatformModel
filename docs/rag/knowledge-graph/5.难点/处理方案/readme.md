# 5.难点 处理方案

## 一、坑档案定位

**难点经验层（权威 0.8，切片池 doc_type=难点）**——每条坑一个 h3 块，回答"曾经怎么坏了、怎么修的"。与 `3.代码/`（证据层 code_analysis）互补：代码层讲"当前代码怎么实现"，坑档案讲"修复史 + 面试口述"。

> 三类坑的边界（重点）：
> - **真实踩坑**（✅已修复，进主体）：git 有修复提交 + 当前代码可核验 → 才进主体
> - **风险预判**（⚠️仅设计讨论，不进主体）：design 里"担心会 XX"但未实际发生 → 不写，或单列附录标注
> - **待决**（❓）：无结论 → 不写
>
> 判断标准一句话：**只有实际发生并修复过、且 git/代码能找到证据的才算坑**——避免 LLM 编"合理但假"的坑污染检索。

## 五、已知候选线索（从语料/代码初筛，是否真坑待 git 验证）

- 维度不一致（bge 512 / dashscope 768）——索引维度固定不可改
- 本地 embedding 内存大——预构建 10MB vs 懒加载 3.5GB、checksum 校验
- 双模型投票不一致——置信度 <0.7 丢弃
- 匹配失败 3%——置信度 0.5 不硬连 + 人工审核
- 断点续传（llmTaskLock）——LLM 推断中断
