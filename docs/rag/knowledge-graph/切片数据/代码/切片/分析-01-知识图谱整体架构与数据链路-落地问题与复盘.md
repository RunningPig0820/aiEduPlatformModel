## 隐性坑与注意事项

1. **在线服务查询标签 vs 离线导入标签不一致（最大坑）**：在线图谱服务的查询统一用 `Entity` 标签匹配，但离线导入落库的节点用的是具体标签（Textbook/Chapter/Section/TextbookKP/Concept/Statement/Class），全图没有统一的 `Entity` 标签。结果是：联调核对前，直接调实体搜索/知识树可能查不到离线导入的数据。两个出路——由 Java 通过通用接口动态建 `Entity` 节点，或确认在线查询只是"期望面"而非"实际数据面"。这是跨端联调必须先对账的点。
2. **知识树/学习路径/推荐是简化桩**：知识树不是真层级、学习路径不是前置链、推荐只看一跳邻居。页面化的真层级能力在 Java 同步 MySQL 侧，**不要从 Python 桥期待完整图谱能力**。
3. **裸 Cypher 查询是后门**：通用 CRUD 桥暴露任意 Cypher 执行，有内部 token 就能执行写操作（只读参数调用方可关），生产必须确保 token 不泄露。
4. **RAG 检索与图谱数据查询是两条独立链路**：AI 答疑 RAG 检索的是图谱**文档切片**（用来生成口述答案），不是 Neo4j 节点数据；图谱在线数据查询走另一套接口。面试表述不能混。
5. **通用接口默认主键是 id，图谱节点主键是 uri**：Java 调用通用接口需显式指定用 uri 当主键，否则查不到节点。
6. **Neo4j 客户端密码空默认**：缺密码配置时默认空串，启动不报错但连接失败——配置缺失被静默吞掉，排查成本高。

## 方案 vs 落地的复盘（原始设计 → 实际实现 → 影响）

**整体架构：两层图谱 + Neo4j + 离线/在线分离 按方案落地**
原始方案设计两层图谱 + Neo4j 存储 + 离线构建/在线消费分离；实际落地全量入库 6757 节点/20887 关系。✅落地——整体架构与原始方案一致，架构层没有走样。

**端点数口径翻转："八端点"实际是 10 路由**
原始方案口径称业务桥有"八端点"；实际落地有 10 个路由——差别在学生进度拆了查询/更新两个状态。⚠️翻转——对外口径"八端点"少算，文档/方案描述与实际路由数不一致。

**通用 Neo4j API：按方案落地**
原始方案规划通用接口（健康检查/统计/节点增删改查+批量+搜索+计数/关系/裸查询）；实际落地 12 个路由与方案一致。✅落地——通用 CRUD 桥完整按方案落地，是 Java 侧可依赖的稳定能力。

**服务查询标签翻转：统一 `Entity` vs 具体标签，可能查不到离线数据**
原始方案数据模型用具体标签（Textbook/Concept 等）；实际落地在线服务查询统一 `Entity` 标签，而离线导入用具体标签，两套标签体系可能不匹配。⚠️翻转——需跨端联调核对，直接影响在线查询能否命中离线入库数据。

**裸查询读写防护：有防护但缺强约束**
原始方案未特别声明裸查询读写约束；实际落地只读默认开启但调用方可以关掉。✅落地——默认有只读防护，但缺强约束，依赖调用方自觉。

**知识树/学习路径翻转：页面化要真能力，Python 桥是简化桩**
原始方案页面化期望真层级/前置链；实际落地 Python 桥给的是简化实现（知识树平铺、学习路径只返回单点）。⚠️翻转——真实能力在 Java/MySQL 侧，Python 桥只做演示级查询，跨端能力边界需讲清。
