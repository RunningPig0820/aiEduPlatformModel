## 业务描述与业务场景

**业务描述**：EduKG 和教材数据都缺小学数学知识点，而义务教育课标 2022 是唯一把小学知识点写全的权威文件——这条链路就是把扫描版课标 PDF 变成可入图谱的小学节点（概念/定义/关系），补齐语义层的小学缺口。

**业务场景**：
- 教研把课标 PDF 放进来，系统 OCR 后提取"100以内数的认识"这类教学知识点，拆成核心概念"数"+范围/动作属性建点
- 图谱里已有高中抽象概念，加小学数据不能污染已有节点——匹配上的复用 v0.1 URI、新增的用 v0.2 URI
- 构建关系时 312 条只有 47 条语义最模糊的 partOf/belongsTo 花 LLM 钱，其余规则化零成本

## 职责

**职责**：课标扫描版 PDF → 小学图谱节点/定义/关系（概念类 1 + Concept 20 + Statement 122 + 关系 312），过质量门禁后供导入。
**不做什么**：不做教材数据（那是 core/textbook）、不做前置依赖（那是 kg_inference）、不直接导入 Neo4j（输出 JSON 供校验后导入）。
**分工要点**：模块在 `edukg/core/curriculum/`（class_extractor/concept_extractor/statement_extractor/relation_extractor/teaching_kp_parser/kg_builder 等），OCR 结果在 `edukg/data/eduBureau/math/`。

## 高层业务调用链（课标→小学图谱构建）

```
课标 PDF（扫描版 189 页，2022 版）
  │ ① OCR（百度 OCR API，收费一次性）
  ▼
课标文本
  │ ② 知识点提取（LLM glm-4-flash 免费）→ 434 个教学知识点
  ▼
教学知识点解析（teaching_kp_parser，方案C：核心概念+教学属性拆分）
  │  "100以内数的认识" → 核心概念"数" + scope"100以内" + action"认识"
  ▼
③ 概念聚合 → 122 个概念（102 已存在 v0.1 + 20 新增 v0.2）
  │  过滤 15 个非核心（购物/招聘/游戏/素养）
  ▼
④ Class 推断（19 匹配已有 Class + 1 新建"数学符号"）
  ▼
⑤ Statement 生成（122 条定义，标签 `{概念}的定义`，LLM 已缓存）
  ▼
⑥ 关系提取（relation_extractor，规则 vs LLM 分流）→ 312 条关系
  ▼
⑦ 校验门禁（6 类本地校验 + 3 类 DB 冲突校验）
  │  冲突时"保留数据库版本、删生成版本"
  ▼
导入 Neo4j（v0.2 URI，与 EduKG v0.1 共存）
```

**文字复述链路**：课标 PDF（扫描版 189 页，2022 版）→ ① 百度 OCR（收费一次性）出课标文本 → ② LLM（glm-4-flash 免费）提取得 434 个教学知识点 → teaching_kp_parser 按方案C"核心概念+教学属性"拆分（"100以内数的认识"→核心概念"数"+scope"100以内"+action"认识"）→ ③ 概念聚合得 122 个概念（102 已存在 v0.1 + 20 新增 v0.2，过滤 15 个非核心）→ ④ Class 推断（19 匹配已有 + 1 新建"数学符号"）→ ⑤ Statement 生成 122 条定义（标签`{概念}的定义`，LLM 已缓存）→ ⑥ 关系提取 312 条（规则 vs LLM 分流）→ ⑦ 校验门禁（6 类本地 + 3 类 DB 冲突，冲突时"保留数据库版本、删生成版本"）→ 导入 Neo4j（v0.2 URI 与 EduKG v0.1 共存）。
