## 关键机制（代码事实机制视角）

### 8 步流水线：课标→图谱，成本分治贯穿全链路
整条链路 8 步，LLM 只出现在最必要的环节：OCR 用收费的百度 OCR（一次性成本，结果落盘复用）；知识点提取用免费 glm-4-flash；教学知识点解析用纯规则（方案C 拆分）；概念聚合与 Class 推断部分用 LLM；Statement 生成用 LLM 但已缓存；关系提取规则 vs LLM 分流；校验导入全规则。核心取舍是**能规则化就规则化，LLM 只在语义不可规则化处消耗**。

### 方案C 拆分：教学知识点"核心概念 + 教学属性"分离
教学知识点是"概念 + 教学属性"复合体（如"100以内数的认识"），直接建点会污染概念图谱。方案C 把复合体拆成核心概念"数"+ scope"100以内"+ action"认识"，只建核心概念节点、属性作字段保留——既保语义又防污染。

### URI 版本化：v0.1/v0.2 + is_existing 增量扩图
匹配到 EduKG 已有概念复用 v0.1 URI；新增概念用 v0.2 URI（拼音-md5_32bit）；每个概念带 version / is_existing 字段。结果 434 → 122 概念（102 v0.1 + 20 v0.2），过滤 15 个非核心（购物/招聘/游戏/素养）——增量扩图可溯源、可回滚，不破坏已有图谱。

### 关系生成"规则 vs LLM"分流
能规则化的一律规则化且 100% 可解释：SUB_CLASS_OF 靠规则映射零成本；RELATED_TO 规则匹配（Statement 标签去"的定义"即关联 Concept）；HAS_TYPE 规则 + LLM 推断低成本；只有语义最模糊的 PART_OF / BELONGS_TO 交 LLM。结果 312 条关系仅 47 条花 LLM 成本。

### 数据质量门禁：6 类本地校验 + 3 类 DB 冲突校验
导入前 6 类本地校验：关系类型合法 / 三元组完整 / URI 格式 / 自环 / 重复 / 双向冲突（partOf 与 belongsTo 方向不能并存）；3 类数据库冲突校验：Cypher 查 Neo4j 已有边，冲突时"保留数据库版本、删生成版本"，db_conflicts 明细返回 generated vs existing 供人工复核。

## 设计要点

- **方案C 拆分**：非结构化课标文本 → 图谱 Schema 的关键决策——"概念 + 教学属性"分离，既保语义又防污染。
- **规则优先、LLM 兜底**：能规则化（类型/层级/定义关联）全部规则化，只有语义最模糊的才交 LLM——成本控制贯穿全链路。
- **版本化扩图**：v0.1/v0.2 + is_existing 让增量扩图可溯源、可回滚，不破坏已有图谱。
- **人在环质量门禁**：导入前 6+3 校验 + DB 冲突保留已有，自动化 + 人工确认结合。
