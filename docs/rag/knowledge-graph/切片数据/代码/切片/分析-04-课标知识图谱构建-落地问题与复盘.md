## 隐性坑与注意事项

1. **直接建点污染图谱**：不拆复合体直接把"100以内数的认识"建 Concept 会污染概念图谱——方案C 拆分是前提，核心概念单独建点、教学属性作字段。
2. **新数据覆盖已有**：DB 冲突校验是硬门禁，冲突默认保留已有图谱、不覆盖权威数据——新增小学数据不能破坏已有高中语义层。
3. **OCR 一次性成本**：百度 OCR 收费，跑完一次就够；重跑要重花 OCR 钱，所以 OCR 结果必须落盘复用。
4. **双向冲突语义**：partOf 和 belongsTo 方向不能同时存在（A→partOf→B 与 B→belongsTo→A 语义自相矛盾），校验门禁专查此项。

## 方案 vs 落地的复盘（原始方案 → 实际落地 → 影响）

**小学数据来源**
原始方案（语雀/design 口径）称"小学数据从课标补充"；实际落地为 curriculum 8 步流水线 + eduBureau/math 课标 OCR 数据文件的完整管道。影响：小学知识点缺口被系统性补齐，不再依赖手工补数。✅落地——小学数据来源落地为 curriculum 8 步流水线 + 课标 OCR 数据文件。

**关系成本**
原始方案称"关系规则为主"；实际落地 312 条关系仅 47 条花 LLM（语义最模糊的 partOf/belongsTo），其余全部规则化、零成本且可解释。影响：成本控制符合预期，LLM 只在不可规则化处消耗。✅落地——关系成本"规则为主"落地为仅 47/312 条走 LLM。

**数据污染防护**
原始方案称"版本区分"；实际落地为 v0.1/v0.2 双版本 + is_existing 可溯源字段 + DB 冲突时保留已有版本三重防护。影响：增量扩图不污染已有语义层，可溯源、可回滚。✅落地——数据污染防护从"版本区分"落地为版本号 + is_existing + 冲突保留已有。

**校验输出接口契约**
原始方案称"质量门禁"；实际落地为 6 类本地校验（类型合法/三元组完整/URI 格式/自环/重复/双向冲突）+ 3 类 DB 冲突校验，db_conflicts 明细返回 generated vs existing，自动化 + 人工确认结合。影响：导入前质量可控，冲突条目可人工复核后再决定。✅落地——质量门禁落地为 6 类本地 + 3 类 DB 冲突校验。
