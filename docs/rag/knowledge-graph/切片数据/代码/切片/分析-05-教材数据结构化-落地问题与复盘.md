## 隐性坑与注意事项

1. **subject 硬编码"数学"**：Textbook 节点与 URI 生成器都写死数学，换学科要改代码，非配置化。
2. **TextbookKP URI 用全局序号而非语义名**：依赖跨教材全局递增计数；若只生成部分节点再单独调其他方法，序号从头计会导致 URI 碰撞/重复（内部有幂等缓存防重入，但方法间混用仍有风险）。
3. **标准化只用 DeepSeek 单模型，不走双模型投票**：面试/文档说"双模型投票"指的是匹配阶段（match_textbook_kp），不是标准化阶段，口径要分清。
4. **标准化缓存按 知识点名+学段+年级 共享**：同名知识点跨教材同阶段共用一条缓存，跨教材语义差异会被抹平。
5. **normalize_textbook_kp.py 把输出文件写两次**：无害但冗余。
6. **生成脚本的导入文件输出到教材目录根路径而非 output/**：找文件别找错目录。
7. **数据质量靠人审**：README 反复强调"爬虫下载数据不准，需要人工校验"，自动生成的中间 JSON 应人工确认再进匹配/导入。
8. **PROJECT_ROOT 计算两端不一致**：配置文件与标准化模块对仓库根目录的计算层级不同，改路径需两头对齐。

## 方案 vs 落地的复盘（原始设计 → 实际实现 → 影响）

**教材结构生成：落地**
原始方案（总揽 §3.2）由 generate_textbook_data.py 生成节点/关系 JSON；实际落地 data_generator + CLI，输出 6 个 JSON 文件。落地：教材节点/关系生成与设计口径一致。

**标准化模型：落地（单模型非双模型，注释明确）**
原始方案（总揽 §7）"标准化精确匹配…LLM 推断标准化名再匹配"；实际落地 KPNormalizer 只用 DeepSeek 单模型，代码注释明确"只用 DeepSeek，标准更严格"。落地：标准化确实用 LLM 推断标准化名，但实现为单模型而非双模型——双模型投票仅在匹配阶段使用，口径需区分。

**标准化位置：落地**
原始方案 core/textbook/README Phase2 为 build_vector_index → normalize → match；实际与代码 README 步骤 2.1/2.2/2.3 一致。落地：标准化位于向量索引构建之后、匹配之前。

**URI 编码：落地**
原始方案（总揽 §4.3）结构节点 `{publisher}-{grade}{semester}`、TextbookKP `textbook-{stage}-{seq:05d}`；实际与 URI 生成器/配置一致。落地：URI 编码方案完整落地。

**匹配数快照：翻转（旧快照 1009 vs 最终 1690）**
原始方案 core/textbook/README 标注 MATCHES_KG 约 1009 条；实际最终图谱 MATCHES_KG 为 1690 条（分析-01 记录），README 为旧快照。翻转：README 快照落后于最终数据，对账与汇报以最终 1690 为准。

**数据准确性：落地（含人工校验声明）**
原始方案默认爬虫数据可直接使用；实际代码/README 多处声明"爬虫数据不准，需人工校验"。落地：数据质量靠人工把关，自动生成的中间 JSON 需人工确认后再进匹配/导入。
