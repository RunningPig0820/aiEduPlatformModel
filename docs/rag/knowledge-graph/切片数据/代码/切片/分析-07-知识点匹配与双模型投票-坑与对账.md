## 隐性坑与注意事项

- **加权投票的 DS 否决权是数学结果不是显式分支**：`0.6+0.4` 结构下只有 DS=True 时 `weighted_score≥0.5` 才可能成立，代码注释已点明（dual_model_voter.py:365-366）。
- **不一致时置信度被 ×0.7 压低**：`winner_confidence*0.7` 后可能跌破 0.5，评审/统计时别只看 decision=True。
- **精确匹配用完整词**：`_expand_with_synonyms` 只在完全匹配时扩展同义词（`normalized_name == normalized_key`），"加法交换律"不会匹配到"加法"（kp_matcher.py:556-560）。
- **difflib 回退会漏语义**：纯字符相似度，同义不同字（如"小数"vs"小数概念"靠 SYNONYM_MAP 兜底）命中率低，是向量不可用时的降级方案。
- **缓存命中不重投**：缓存存的是完整 `vote_result`，改投票阈值/权重后旧缓存仍按旧结果返回（缓存键不含权重参数）。
- **结果文件 method 字段是分类依据**：exact_match / llm_vote / candidate_review / none / error 五态，`show_stats` 用 `r['method']` 分组（match_textbook_kp.py:232-234）。
- **评审系统无代码**：D16 描述的 MySQL 审核表/`/api/kp-match/recommend`/导入脚本在 `edukg/scripts` 与 `ai-edu-ai-service/api` 均未检索到实现；唯一痕迹是 `method='candidate_review'` 的 best_candidate 记录。

## 对账要点（方案 vs 代码现状复盘）

**✅落地：D6 匹配流水线**
原始方案"精确匹配→向量粗筛 top-20→双模型投票"；代码现状三段式全落地（kp_matcher.py exact_match/_retrieve_candidates/llm_match_with_cache）。结论 ✅ 落地。

**✅落地：D7 加权投票**
原始方案 WEIGHT_DS=0.6/WEIGHT_GLM=0.4/THRESHOLD=0.5、DS 否决；代码现状 dual_model_voter.py:356-396 全一致。结论 ✅ 落地。

**⚠️翻转：匹配率口径——语雀 1690/1740=97.1%（早期里程碑）→ 当前 1847/1905=96.96%**
语雀是早期里程碑口径，当前是后续 merge 后批次，口径不同批次不同，非实现错误。结论 ⚠️翻转（口径不同批次，非错误）。

**⚠️翻转：未匹配数量——语雀 308（297 投票不通过+11 无候选）→ 当前 58（candidate_review 50+none 8）**
不同批次所致，非实现偏差。结论 ⚠️翻转（不同批次）。

**⚠️方案有/代码无：D16 评审系统**
原始方案 MySQL 审核表 + `/api/kp-match/recommend` + 导入脚本；代码现状 `edukg/scripts` 与 `ai-service/api` 无对应代码，仅 candidate_review 记录。结论 ⚠️方案有/代码无。

**⚠️翻转：缓存键——语雀称 `md5(textbook_kp+kg_kp)` → 实际 `SHA256(prompt)[:16]`**
实际缓存键为 llm_cache.py:30 的 `SHA256(prompt)[:16]`，Prompt 含名称+描述+学段，与语雀口径不符。结论 ⚠️翻转。

**✅落地：三重优化——LLM 调用"40→2 次 API/知识点"**
原始方案注释口径 40→2 次/知识点；代码现状 LLM_CANDIDATE_LIMIT=3 + 0.5 阈值 + 早停逻辑全落地。结论 ✅ 落地。

**⚠️死代码：vote_match / vote_prerequisite**
模块文档把两者列为匹配/前置投票规则；代码现状两方法定义但主流程未调用（主流程走 `vote()`→`_check_consensus`）。结论 ⚠️死代码。
