## 隐性坑与注意事项

1. **加权投票的 DS 否决权是数学结果，不是显式分支**：在 DS=0.6/GLM=0.4 的权重结构下，只有 DeepSeek 判 True 时加权分才可能 ≥0.5，代码里没有显式写"DS 一票否决"，是权重设计自然产生的效果。
2. **不一致时置信度被压到胜者×0.7**：可能跌破 0.5，评审/统计时别只看 decision=True。
3. **精确匹配只认完整词**：同义词只在完全匹配时展开，"加法交换律"不会误配到"加法"。
4. **difflib 回退会漏语义**：纯字符相似度，同义不同字靠同义词表兜底，命中率低，是向量不可用时的降级方案。
5. **缓存命中不重投**：缓存存完整投票结果，改投票阈值/权重后旧缓存仍按旧结果返回（缓存键不含权重参数）。
6. **结果文件 method 字段是分类依据**：exact_match / llm_vote / candidate_review / none / error 五态，统计按 method 分组。
7. **评审系统只有设计没有代码**：设计里描述的 MySQL 审核表 / LLM 推荐接口 / 导入脚本在代码库均未检索到实现，唯一痕迹是 candidate_review 状态的 best_candidate 记录。

## 方案 vs 落地的复盘（原始设计 → 实际实现 → 影响）

**落地：D6 匹配流水线**
语雀/design 口径"精确匹配 → 向量粗筛 top-20 → 双模型投票"三段式全部落地，与设计一致。

**落地：D7 加权投票**
WEIGHT_DS=0.6/WEIGHT_GLM=0.4/THRESHOLD=0.5、DS 否决的加权设计全部落地，与设计一致。

**翻转：匹配率口径——语雀 1690/1740=97.1%（早期里程碑）→ 当前 1847/1905=96.96%**
语雀是早期里程碑批次，当前是后续 merge 后批次，口径不同批次不同，非实现错误。

**翻转：未匹配数量——语雀 308（297 投票不通过+11 无候选）→ 当前 58（candidate_review 50+none 8）**
不同批次所致，非实现偏差。

**方案有/代码无：D16 评审系统**
语雀/design 描述的 MySQL 审核表 + `/api/kp-match/recommend` 推荐接口 + 导入脚本在代码中无对应实现，仅 candidate_review 记录残留。

**翻转：缓存键——语雀称 md5(textbook_kp+kg_kp) → 实际 SHA256(prompt)[:16]**
实际缓存键是 Prompt 的 SHA256 截断 16 位，Prompt 含名称+描述+学段，与语雀口径不一致。

**落地：三重优化——LLM 调用 40→2 次/知识点**
LLM 候选上限 3 + 0.5 相似度阈值 + 命中早停全落地。

**死代码：vote_match / vote_prerequisite**
模块文档把两者列为匹配/前置投票规则，但两方法定义后主流程未调用（主流程走 vote()→_check_consensus）。
