## 架构分工（双端消费向量）

向量索引能力横跨两端：
- **匹配侧 edukg（离线管道）**：从 Neo4j 读图谱概念 → 本地 bge-small-zh-v1.5 编码 512 维 → 落盘索引四件套（向量 npy + 文本 json + 概念 json + 元数据 meta，含 checksum）。查询用 npy 点积做余弦相似度，一次构建、多次检索。
- **服务侧 ai-service（在线服务）**：用 dashscope text-embedding-v3（显式 768 维）把题型名/文本向量化，写入/查询腾讯云 COS 向量桶，按 vector_type 路由到 topic 池或 RAG 池。

**核心边界**：匹配侧是离线构建、查询走本地 npy 点积，不做服务侧在线检索；服务侧不落本地向量文件，向量统一存 COS 桶（Java 无 SDK，走 Python 桥）；两套 embedding 维度不同（512 / 768）、互相不通用。

## 关键机制

### 预构建索引 + checksum 校验（防脏数据）
- 匹配脚本每次启动全量编码 1295 概念要几十秒，预构建索引把启动耗时降到最低、内存从约 3.5GB 降到约 10MB。
- **checksum 做数据血缘**：用 Neo4j 内容指纹（uri+label 按 uri 排序后 MD5）标记索引版本，图谱变了 checksum 失配 → 索引判"过期"，宁可回退慢的懒加载也不拿脏索引匹配；再失败逐级回退字符串近似匹配。
- 构建/加载都强制离线模式，避免启动联网检查模型更新。

### 双轨 embedding 各司其职
- **匹配侧要本地批量、免费、快**（bge 512 维），做离线粗筛 top-20；
- **服务侧要在线、准确、与业务索引一致**（dashscope 768 维），做实时检索。
- 一个离线管道、一个在线服务，互不干扰。

### 失败语义分端不同
- 匹配侧走"降级链"（预构建 → 懒加载 → difflib 逐级后退），保证匹配任务总能跑；
- 服务侧"错误冒泡"：向量基础设施出错抛给端点返回 HTTP 错误码，由 Java 桥降级（回退字符规则 + 原样落库，不阻塞主链路），避免 Python 层吞错。

## 设计要点

- **构建/检索分离**：一次构建多次检索，免去每次全量 encode，是"预构建 vs 懒加载"的核心取舍。
- **checksum 做数据血缘校验**：图谱变了索引就"过期"，宁可回退慢的懒加载也不拿脏索引匹配。
- **双轨 embedding 各司其职**：离线管道（本地批量免费快）与在线服务（在线准确一致）互不干扰。
- **失败语义分端不同**：匹配侧逐级降级保完成，服务侧错误冒泡交 Java 桥降级。
