## 隐性坑与注意事项

1. **checksum 只含 uri+label**：只改 description 不会触发过期检测，可能拿到语义旧向量——索引过期检测有盲区，改描述要注意。
2. **COS 索引维度不可变**：向量索引建好不可改，换 embedding 模型/维度必须重建索引；服务侧 768 与匹配侧 512 两套独立，不能混用。
3. **预构建索引仍需加载模型**：轻量检索器只省了 1295 个概念的编码时间和内存，查询时仍需加载 embedding 模型——首次启动照样要读模型文件。
4. **put 后异步生效**：写向量成功不代表立刻能查到，紧跟的查询可能 miss（约 10 秒延迟），是最终一致语义。
5. **强制离线模式有前提**：首次运行若没下载过模型会直接失败（禁联网），需要先在有网环境预热模型缓存。
6. **`--status` 也依赖 Neo4j**：查状态要现场读图谱算 checksum 比对，图谱不可用时只能读到元数据部分。

## 方案 vs 落地的复盘（原始设计 → 实际实现 → 影响）

**双轨 embedding 落地**
原始方案设计 bge 本地 512 维匹配 + dashscope 768 服务侧；落地完全按此实现，匹配侧 512 维、服务侧显式 768 维。✅落地——双轨 embedding 与方案一致，两套各管一段。

**索引规模与口径核对**
语雀口径 kg_vectors.npy(1295×512) 与落地元数据实测 concept_count=1295、vector_dim=512 完全一致；懒加载内存约 3.5GB 也与注释一致。✅一致——索引规模、懒加载内存与方案对得上。

**预构建大小翻转：约 10MB → 实际约 3.1MB**
原始方案/注释口径预构建索引约 10MB；落地实测索引文件合计约 3.1MB（向量 npy 2.6MB + 概念 json + 文本 json）。⚠️翻转——注释"10MB"偏大，可能混了内存口径，实际落盘约 3.1MB，预构建比预期更轻。

**checksum 算法落地**
原始 design 只称"校验和"未指定算法；落地用 MD5（uri:label 按 uri 排序拼接）。✅落地——checksum 由 MD5 算法明确落地。

**检索耗时属注释口径**
代码注释声明单次检索 <10ms（懒加载）/ <5ms（预构建），但未实测。✅注释声明——耗时是注释口径，非实测数据。

**COS 索引维度固定一致**
原始 design（D2）"索引建好不可改"；落地显式指定 768 维并注释"必须与已建索引维度一致"。✅一致——维度固定与方案一致，换模型必须重建索引。
