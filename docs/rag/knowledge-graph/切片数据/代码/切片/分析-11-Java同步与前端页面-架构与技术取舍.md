## 架构分工与方案演进

**为什么不能前端直查 Neo4j**：Java 后端没有 Neo4j 集成、前端是独立 SPA、Neo4j 实时查询重——所以页面化不能靠前端直查图库。

**方案演进**：早期方案 A（Neo4j 实时查询、Java 直连图库）被否，已演进为**方案 B：Neo4j→MySQL 同步、前端读 MySQL，图谱关系仍直查 Neo4j**。MySQL 只存节点属性 + 层级关系，图谱关系（MATCHES_KG/PART_OF/RELATED_TO 等）不同步——避免无限业务事实污染权威图谱，配合"权威图谱零写入"约束（语雀 D13/D17）。

**分工**：Java 后端（双数据源 + 同步/导航/API）+ 前端 React SPA（三栏/懒加载/React Flow）。**注意：Java/前端代码均不在本仓，以下事实全部来自 OpenSpec design 文档（权威 0.7 设计素材），非代码真值。**

## 数据模型与同步机制

- **8 张表**：4 张节点主表（教材/章节/小节/知识点）+ 3 张层级关联表（教材→章节、章节→小节、小节→知识点，均带 order_index）+ 1 张同步记录表。
- **URI 主键**：不用自增 ID，直接用 Neo4j 的 URI 做跨库唯一锚点；同步按 URI UPSERT 幂等，URI 永不修改、改动走合并流程。
- **双数据源**：默认业务库 + `@DS("kg")` 路由图谱库 ai_edu_kg，strict 模式未匹配数据源直接抛异常；图谱 Service 单独绑事务。
- **状态机 active/deleted/merged**：所有主表带 status 与 merged_to_uri；导航/知识体系只查 active；deleted=Neo4j 已删（进度查询例外保留历史），merged=被合并（运营经 merged_to_uri 做进度迁移）。软删除让"删除"可回溯、进度历史不丢。
- **同步流程**：加锁（同一时间仅一个任务）→ 查 Neo4j 节点与层级 → URI 校验（非空/前缀合法/同批不重复，异常跳过）→ 单大事务内 UPSERT 节点主表 + 关联表清空重建 → 缺失节点置 deleted → 对账校验节点数/关联数 → 写同步记录。失败整体回滚、可重跑。
- **对账**：同步完成对比 MySQL vs Neo4j 节点数/关联数，不一致写 mismatched + 详情，前端在记录里标红。
- **手动按需同步而非 CDC**：demo 阶段避免实时监听复杂度，失败可重跑（UPSERT 幂等 + 单事务原子）。

## 降级与性能设计

- **图谱关系直查 Neo4j + Redis 缓存**（TTL 300s）：Neo4j 不可用返回空关联 + 可用性标记 false，前端隐藏图谱模块，不抛异常——核心导航不依赖图谱服务可用性。
- **批量关系接口避免 N+1**：概念关联查询支持批量，防止逐点请求拖垮 Neo4j。
- **前端逐级懒加载**：教材树展开才请求子节点并缓存、切教材根清缓存，6757 节点不一次性渲染。
- **React Flow 关系图**：优先后端返回的力导向初始坐标；节点过多提供"简化视图"只显示 Top 10；无数据给空态文案。
- **三栏布局**：左教材树 + 中 React Flow 关系图 + 右详情（2 层父级：小节+章节），父组件用 state+props 管理选中联动，不引入额外状态管理库。
