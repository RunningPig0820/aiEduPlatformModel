## 坑点复盘
**现象**：知识图谱从 MySQL 同步到 Neo4j 的全量同步是超长任务，某年级失败整个同步挂掉；崩溃后状态记录卡在 running，后续同步被阻塞；多人同时点"同步"还会并发写冲突。

**触发链路**：前端触发全量同步 → Java 把该教材版本+学科下所有年级一次性跑 → 任一年级抛错或进程被杀 → 同步记录停在 running。

**根因**：修前同步是单一大任务：没有按年级切分（一个失败全挂）、没有锁（并发触发互相覆盖）、崩溃后 running 记录无超时判定（后续同步永远认为"有任务在跑"）。

**解决思路与权衡**：按年级拆子任务（每个年级独立锁/记录/对账）+ Redis 分布式锁（锁粒度到 edition:subject:stage:grade，防并发互相覆盖）+ 卡死检测（超过 10 分钟的 running 记录标记 failed，解除阻塞）+ 对账（同步后比对 MySQL 与 Neo4j 计数，不一致记入对账状态）。

## 面试口述要点
长任务工程化三件套：拆粒度（一个大任务拆成可独立成功/失败/重试的子任务）、加锁（分布式锁防并发，锁粒度越小并发度越高）、状态自愈（running 要有超时判定，崩溃不留僵尸）。对账（MySQL vs Neo4j 计数比对）是同步类任务的可观测性兜底——不能只"跑完就算完"，要能证明两库一致。
