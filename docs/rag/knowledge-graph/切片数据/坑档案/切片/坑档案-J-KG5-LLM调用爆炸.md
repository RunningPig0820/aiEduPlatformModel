# 坑档案-J-KG5-LLM调用爆炸
> summary: LLM 调用爆炸：穷尽遍历 40 次 API/知识点，粗筛 + 早停 + 阈值 + 上限后提速约 50 倍
> 来源: 坑档案 ｜ 锚点: J-KG5 ｜ 节: 5.难点/坑档案.md
> COS路径: rag-slices/knowledge-graph/坑档案/坑档案-J-KG5-LLM调用爆炸.md
> 类别：开发难点
> target: 开发对账

---

**1. 问题现象**：知识点匹配跑不动——实测 3.5 小时只完成 290 个知识点（21.5%），照此估算全部 1350 个要 16+ 小时，且 API 账单爆炸。

**2. 触发流程**：每个教材知识点对 top-20 候选**逐个**做 LLM 双模型投票（GLM+DeepSeek 各 1 次 = 每次 2 次调用）→ 最坏 40 次 API/知识点；1350 × 5000 图谱概念全量遍历更不可行（约 675 万次调用）。

**3. 根因分析**：`problems_and_solutions.md` §二/§十三记录两层低效：① 粗筛前是"教材知识点 × 全部图谱知识点"全量 LLM 匹配，500 万次调用量级；② 粗筛后仍**穷尽遍历** top-20 候选，即使第一个候选已匹配成功也把 20 个全调完，`for candidate in top_20: llm_vote(candidate)` 无提前终止。

**4. 排查过程**：`match_textbook_kp.py --dry-run` 估算 `estimate_match_cost`（`kp_matcher.py:1308-1340`）打印 LLM 调用次数与成本；实测日志显示"3.5 小时完成 290 个"，按分钟推算吞吐不足 0.15 个/分钟。

**5. 解决方案 & 改动点**：三重优化（`kp_matcher.py`）：① **向量粗筛**——`LocalVectorRetriever`/`PrebuiltIndexRetriever` 先语义检索 top-20 候选，把"全量遍历"变"粗筛候选"（`kp_matcher.py:630-702` `_retrieve_candidates`）；② **相似度阈值** `SIMILARITY_THRESHOLD = 0.5`，低相似度候选直接跳过不调 LLM（`kp_matcher.py:729,780-783`）；③ **LLM 调用上限 + 早停** `LLM_CANDIDATE_LIMIT = 3`，只对前 3 个候选投票，命中立即 break（`kp_matcher.py:727,786-796,825-826,852-853`）。效果：调用 500 万→2.7 万（-99%），吞吐 0.14 个/分钟 → ~7 个/分钟，**整体提速约 50x**。提交：`126d210 [知识图谱]-[添加 sentence-transformers 模型]`（向量粗筛）、`03f3f75`（早停+阈值+上限，problems 文档 §十三）。

**6. 面试口述要点**：LLM 管道的第一优化原则是**减少调用次数**（比换更快的模型划算得多）——粗筛把"全量比对"变"top-k 候选"、阈值把"低相关候选"拦截在模型外、上限+早停保证"第一个命中就收工"。三步叠加把单知识点最坏 40 次调用压到 0~6 次。要能讲清"为什么阈值 0.5、上限 3"的取舍：候选质量高时前几个就够，超过 3 个仍不中说明粗筛本身就差，继续调是浪费。
