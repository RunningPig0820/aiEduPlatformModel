# 双模型投票具体怎么工作的？为什么两模型不一致不是直接丢而是加权仲裁？
> summary: 数据关联引导问题回答：两模型并行投票、一致采纳取平均；不一致按 WEIGHT_DS=0.6/GLM=0.4 加权、阈值 0.5 仲裁（DS 一票否决）、通过后置信度×0.7 打折，不丢是避免牺牲召回

> 类别：数据关联

**核心结论**：GLM-4-flash + DeepSeek 并行投票，两模型一致才采纳并取平均置信度；不一致时按 WEIGHT_DS=0.6/WEIGHT_GLM=0.4 加权、阈值 0.5 仲裁（数学上只有 DeepSeek=True 才可能过线，即 DS 一票否决），通过后置信度×0.7 打折——不直接丢是为了不牺牲召回，加权是最小可行的仲裁。

## 分层展开
- **一致才采纳**：`DualModelVoter.vote` 用 asyncio.gather 并行调两模型，`_check_consensus` 比较 decision；两模型一致→consensus=True，置信度取两模型均值——抑制单模型幻觉（单模型可能自信地错，两模型一起错概率低得多）（依据：分析-07 / 完善文档 05）。
- **不一致→加权仲裁**：weighted_score = 0.4×(GLM=True) + 0.6×(DS=True)，≥THRESHOLD=0.5 才采纳；只有 DeepSeek=True 时 0.6≥0.5 才成立——DS 一票否决是 0.6+0.4 结构的数学结果，不是显式分支；采纳时 confidence=winner×0.7、vote_type='weighted'（依据：分析-07 / 坑档案 J-KG6）。
- **为什么不是直接丢**：两模型对语义边界天然有分歧（GLM 偏宽松、DeepSeek 偏严格），修前"一致才采纳、不一致丢弃"把"可以仲裁的冲突"当"不可用结果"，牺牲召回（依据：坑档案 J-KG6）。
- **为什么不用 majority vote**：只有两个模型，没有多数；加权是把"模型质量不对称"编码进去的最小可行仲裁——DeepSeek 更严格（几乎不误报）给 0.6、GLM 宽松给 0.4（依据：完善文档 05 / 坑档案 J-KG6）。
- **口径提醒（翻转）**：`vote_match`/`vote_prerequisite` 是死代码（定义但主流程未调用），匹配主链路走 `vote()`→`_check_consensus`→加权；design 的 0.9/0.7 匹配分档在死代码 vote_match 里未生效（依据：完善文档 05 / 分析-07）。

## 追问防御
- **可能追问：DeepSeek 否决权是显式 if 分支吗？** → 不是，是加权算术结果：WEIGHT_DS=0.6>THRESHOLD=0.5，weighted_score 只有 DS=True 才可能≥0.5，代码注释已点明"只有 DeepSeek=True 才可能过阈值"（依据：分析-07 / 坑档案 J-KG6）。
- **可能追问：不一致被仲裁通过会不会误判？** → 置信度×0.7 打折，避免"仲裁出来的结果"冒充高置信；但加权路径确实允许 DS 一票通过（GLM=False 也过），这是"用严格模型压误判"与"保召回"的取舍（依据：分析-07 / 分析-08）。
- **可能追问：投票结果怎么审计？** → 缓存存完整 vote_result（含两模型响应/决策/理由），能解释"为何判不匹配"；缓存键 SHA256(prompt)[:16]（依据：分析-07 / 完善文档 05）。
