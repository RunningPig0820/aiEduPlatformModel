# LLM 推断/匹配是 2-3 小时的长任务，中断了怎么办？
> summary: 开发难点引导问题回答：llmTaskLock 三件套——TaskState 检查点（每 10 节存）+CachedLLM（SHA256 结果缓存）+ProcessLock 进程锁，中断可续、同 prompt 不重复花钱；注意前置推断 --resume 未落地

> 类别：开发难点

**核心结论**：靠 `core/llmTaskLock` 三件套——**TaskState 检查点**（每完成一节/一个知识点落盘，重启 resume 过滤已完成）+ **CachedLLM 结果缓存**（同 prompt 不重复调 API）+ **ProcessLock 进程锁**（防多进程并发写进度），让 LLM 推断/匹配这类 2-3 小时长任务中断可续、已花的钱不丢。

## 分层展开
- **TaskState 检查点**：按 task_id 落 JSON 文件（output/progress/），推断侧每 `checkpoint_interval=10` 节 `_save_state()` 一次，恢复时从 checkpoints 捞 completed 结果、过滤 pending_sections；匹配侧从 checkpoints 恢复 results + completed_uris；状态写入用临时文件 + rename 原子写 + 备份防写坏（依据：分析-06 / 坑档案 J-KG8）。
- **CachedLLM 结果缓存**：缓存键 `SHA256(prompt)[:16]`（llm_cache.py:30），相同知识点对不重复调 API；缓存存完整 vote_result（含两模型响应/决策/理由）可审计；缓存命中返回 `from_cache=True`（依据：分析-06 / 完善文档 05）。
- **ProcessLock 进程锁**：portalocker 文件锁包住批量循环，防多进程并发跑同一推断/匹配、互相覆盖进度（依据：坑档案 J-KG8 / 分析-06）。
- **效果**：推断 2-3 小时、匹配 1-2 小时长任务中断可续；实际数据 8255 个缓存文件省 16,510 次 API 调用（依据：完善文档 05）。
- **口径提醒（翻转）**：前置依赖推断的 `--resume` **未落地**——infer_prerequisites.py 参数只有 --dry-run/--batch-size/--stats，infer_batch 签名无 resume，中途失败需重跑；缓存键是 SHA256(prompt)[:16] 不是语雀说的 md5，改提示词模板=旧缓存全失效（依据：分析-08 / 完善文档 05）。

## 追问防御
- **可能追问：缓存键是什么？** → SHA256(prompt)[:16]——Prompt 含名称+描述+学段，改提示词模板旧缓存全失效；不是语雀早期口径的 md5(textbook_kp+kg_kp)（依据：完善文档 05 / 分析-06）。
- **可能追问：断点粒度多细？** → 推断按节、每 10 节存一次检查点；匹配按知识点对（checkpoints 恢复 results+completed_uris）——粒度越细中断丢得越少（依据：分析-06 / 坑档案 J-KG8）。
- **可能追问：前置推断中断能续吗？** → 不能——前置推断 --resume 未落地，这是方案（D5/D11）与代码现状的差异，要如实讲（依据：分析-08）。
