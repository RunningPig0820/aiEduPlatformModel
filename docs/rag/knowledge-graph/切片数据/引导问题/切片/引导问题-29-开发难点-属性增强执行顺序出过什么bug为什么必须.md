# 属性增强执行顺序出过什么 bug？为什么必须"先推断后增强"？
> summary: 开发难点引导问题回答：增强跑在 LLM 推断前，推断出的 1052 个新知识点全没属性，覆盖率仅 22%（299/1350）；属性增强依赖"所有知识点已生成"，必须"先推断后增强"，规则步骤设计成 --force 幂等重跑

> 类别：开发难点

**核心结论**：出过"增强跑在 LLM 推断前"的顺序 bug——属性增强只处理了先有的 299 个知识点，后由 LLM 推断出的 1052 个新知识点全没属性，覆盖率仅 22%；因为属性增强依赖"所有知识点已生成"，所以必须**先推断后增强**，且规则类步骤要设计成 `--force` 幂等重跑以便低成本补。

## 分层展开
- **现象**：textbook_kps.json 里 1350 个知识点只有 299 个带 difficulty/importance/cognitive_level/topic 属性，覆盖率 22%——教学属性面板大量显示默认值/缺失（依据：坑档案 J-KG2）。
- **触发流程**：管道①enhance_kp_attributes.py 对现有 299 个增强 → ②infer_textbook_kp.py LLM 推断 1052 个 → ③merge_inferred_kps.py 合并成 1350 个——增强只跑在①，②新增的从没经过增强（依据：坑档案 J-KG2）。
- **根因**：步骤依赖顺序被隐式假设——增强依赖"所有知识点已生成"，但生成被拆成"先规则后 LLM 两批"，顺序写错就漏一批；KPAttributeInferer.infer_batch 只遍历入参 kps，不自愈补跑（依据：坑档案 J-KG2）。
- **解法**：对全量 1350 个重新跑 `enhance_kp_attributes.py --enhance --force` 强制覆盖，再 --merge 合并回主文件；属性推断是纯规则（无 LLM），重跑成本低（依据：坑档案 J-KG2 / 完善文档 04）。
- **关联坑（topic 继承污染）**：topic 直接继承章节，导致"加法"落在"位置"章被错标成"图形与几何"——靠匹配到的 Concept 的 Class 类型修正 144 个（数与代数 855→891、图形与几何 359→315），但这是数据级一次性修正**未固化进代码**，重跑属性增强会退回章节继承（依据：坑档案 J-KG3）。

## 追问防御
- **可能追问：为什么属性增强不用 LLM？** → 属性（难度/重要性/认知层级）客观可枚举，用规则快、可复现、不编造；刻意不用 LLM（依据：完善文档 04 / 引导问题.md 2）。
- **可能追问：现在 topic 还会错吗？** → 默认逻辑仍继承章节 topic，Class 修正是数据级一次性未固化到代码，重新跑属性增强会退回章节继承——这是"数据级修正未落到代码"的教训（依据：坑档案 J-KG3）。
- **可能追问：怎么防再犯？** → 规则类步骤设计成 `--force` 幂等重跑，发现覆盖率不对能低成本补；步骤间前置关系显式写进 README/编排脚本（依据：坑档案 J-KG2）。
