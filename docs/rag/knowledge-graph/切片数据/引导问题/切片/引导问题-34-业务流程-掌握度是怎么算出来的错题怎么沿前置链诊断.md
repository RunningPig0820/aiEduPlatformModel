# 掌握度是怎么算出来的？错题怎么沿前置链诊断薄弱根因？

> summary: 业务流程引导问题回答：掌握度=错题→对应知识点→前置依赖链→结合正确率/次数算出，靠PREREQUISITE+RELATED_TO沿前置链定位"当前点没掌握vs前置没学好"

> 类别：业务流程

**核心结论**：掌握度按「错题 → 对应知识点 → 前置依赖链 → 结合正确率/次数」事件链算出，诊断靠 PREREQUISITE 前置链 + RELATED_TO 语义关联，沿链定位"当前点没掌握 vs 前置没学好"。

## 分层展开
- **掌握度计算链路**：错题 → 定位到对应知识点 → 沿前置依赖链回查 → 结合正确率/次数算出掌握度 → 定位薄弱根因。（依据：完善文档 09）
- **诊断依据**：PREREQUISITE 前置链 + RELATED_TO 语义关联——沿前置链区分"当前点没掌握"还是"前置没学好"，这是薄弱根因诊断的核心机制。（依据：完善文档 09）
- **与 GraphRAG 联动（设计）**：错题 → 前置链 → 算掌握度 → 定位薄弱根因；答疑记录回流支撑家长端报表。（依据：完善文档 09）
- **落地边界（掌握度主体翻转）**：design 中掌握度主体从知识点翻转为题型（topic_key）、解析管线五步、权威图谱零写入，均在 design-backend-kp-matching-lightup（D2/D16/D17）；但 Java/前端代码不在本仓，属"非代码真值"。（依据：完善文档 09 / 分析-11）
- **前置依赖真相**：主链路 PREREQUISITE 实际是 LLM 双模型投票 + 0.8 单阈值产出；三来源融合（fuse_results）方法存在但未接入 CLI 主链路，final_prereq.json 无生产方——设计上"教材顺序/定义依赖/LLM 多证据融合"未落地。（依据：完善文档 09 / 分析-08）
- **派生信号零写入**：掌握度是派生信号，只存 MySQL，不写权威图；Neo4j 只读。（依据：完善文档 09 / 分析-01）

## 追问防御
- **可能追问：掌握度数值可靠吗？** → 事件驱动可追溯（每道题对错都有记录）+ 前置依赖带置信度与 reason + 低置信过滤，不是拍脑袋。（依据：引导问题.md §7 / 完善文档 09）
- **可能追问：孩子到底是当前点没会还是前置没会？** → 沿前置链定位薄弱根因——靠 PREREQUISITE 前置链区分"当前点没掌握 vs 前置没学好"。（依据：完善文档 09）
- **可能追问：前置依赖是哪儿来的？** → 主链路为 LLM 双模型投票（一致采纳/不一致加权 DS=0.6/GLM=0.4，≥0.8 落 PREREQUISITE、<0.8 落候选），过 DAG 无环验证；三来源融合未接主链路，如实讲。（依据：分析-08 / 完善文档 09）
