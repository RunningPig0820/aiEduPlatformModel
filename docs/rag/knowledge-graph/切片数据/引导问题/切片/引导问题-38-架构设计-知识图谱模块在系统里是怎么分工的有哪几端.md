# 知识图谱模块在系统里是怎么分工的？有哪几端？

> summary: 架构设计引导问题回答：五端分工——Python edukg管道离线构建+Neo4j最终存储+ai-service桥在线暴露+Java同步MySQL+前端React SPA只读，数据流单向
> 权威度: 1.0（合成问答答案切片，非原始证据）
> 模块: knowledge-graph
> COS路径: rag-slices/knowledge-graph/引导问题/引导问题-38-架构设计-知识图谱模块在系统里是怎么分工的有哪几端.md
> 类别：架构设计

**核心结论**：五端分工——Python edukg 管道离线构建 + Neo4j 最终存储 + ai-service 桥在线暴露 + Java 同步 MySQL + 前端 React SPA 只读；数据流单向：数据来源 → Python → Neo4j →（ai-service 桥 / Java 同步 MySQL → 前端）。

## 分层展开
- **五端职责表**：① Python edukg 管道（离线构建，数据来源→加工→导入 Neo4j，Phase0-3）；② Neo4j（最终存储，7 类节点/8 类关系，两层图谱，权威冻结只读）；③ ai-service 桥（在线 API，api/kg.py 业务查询 + api/neo4j.py 通用 CRUD）；④ Java 后端（页面化同步 Neo4j→MySQL 8 张表、导航/知识体系 API、掌握度派生）；⑤ 前端 React SPA（三栏布局只读消费，逐级懒加载）。（依据：完善文档 03 / 分析-01 / 分析-11）
- **数据流向**：数据来源（EduKG TTL/main.ttl/人教版爬虫/课标）→ Python edukg 管道 → Neo4j → 在线两条消费链路：① ai-service 桥（api/kg.py + api/neo4j.py）供前端/答疑；② Java 同步 MySQL → 前端 SPA 只读，图谱关系直查 Neo4j。（依据：完善文档 03）
- **关键设计**：两层图谱靠 MATCHES_KG 软连接（置信度≥0.5）互不污染；页面化走方案 B（Neo4j→MySQL 同步、前端读 MySQL）；同步用 @DS("kg") 双数据源、状态机 active/deleted/merged、单大事务 + 对账；图谱关系直查 Neo4j + Redis TTL 300s 降级。（依据：完善文档 03 / 分析-11）
- **⚠️ 落地边界**：本仓可核验 Python 管道与 ai-service 桥；Java/前端代码不在本仓，分析-11 基于 design 撰写、标注"非代码真值"；在线查询统一用 `:Entity` 标签而离线导入用具体标签（Textbook/Concept 等），联调前直接调 /entities、/tree 可能查不到导入数据（最大坑）。（依据：完善文档 03 / 分析-01 / 分析-11）

## 追问防御
- **可能追问：Python 桥和 Java 怎么分？** → 在线图谱查询走 Python 桥（api/kg.py 业务 + api/neo4j.py 通用 CRUD，x-internal-token 鉴权）；Java 做页面化同步 + 导航/知识体系 API + 掌握度派生。Python 管图谱数据与查询，Java 管页面与派生。（依据：完善文档 03 / 分析-01）
- **可能追问：core/rag/query.py 算图谱桥吗？** → 不是——它是 AI 答疑口述 RAG 检索编排（检索图谱文档切片），图谱数据查询走 api/kg.py + api/neo4j.py，两条链路独立。（依据：完善文档 03 / 分析-01）
- **可能追问：页面化真的落地了吗？** → 方案 B 已拍板、design 三份一致，但 Java/前端代码不在本仓、graph 接口未实现、API 前缀前后端不一致（/api/kg/** vs /api/auth/kg/**），属"联调收口"状态，不能讲成已上线。（依据：完善文档 03 / 分析-11）
