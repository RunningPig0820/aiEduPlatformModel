# 为什么离线构建和在线消费要分离？Neo4j 为什么只是"最后仓库"？

> summary: 架构设计引导问题回答：关系处理在Python/CSV完成、Neo4j只是最后仓库——计算与存储分离+MERGE幂等可重跑+权威只读零写入，在线消费走Python桥与Java同步MySQL

> 类别：架构设计

**核心结论**：离线构建把关系处理在 Python/CSV 完成、Neo4j 只做最终仓库——计算与存储分离 + MERGE 幂等可重跑 + 权威只读零写入；在线消费走 Python 桥（api/kg.py / api/neo4j.py）与 Java 同步 MySQL，不直查图库做重活。

## 分层展开
- **计算与存储分离（方案 C）**：关系处理在 Python/JSON/CSV 内存完成，Neo4j 只是最后仓库；CSV/JSON 可教研维护、权威基准冻结（决策 D2）。（依据：完善文档 03 / 分析-10）
- **MERGE 幂等可重跑**：11 个 import 脚本按依赖顺序（Class→Concept→Statement→关系→教材→章节→小节→知识点→归属→匹配）全 MERGE 幂等，重复导入更新属性/跳过已有关系，失败后重导不产生重复；支持 --dry-run/--clear/--stats 三种运行模式。（依据：分析-10 / 分析-01）
- **权威图谱零写入**：Neo4j 只读，业务派生数据（掌握度/点亮/题型）只存 MySQL，物理上不污染权威图（决策 D17）。（依据：完善文档 03 / 分析-01）
- **在线消费分离**：在线查询走 api/kg.py（业务查询）+ api/neo4j.py（通用 CRUD）+ Java 同步 MySQL——Python 桥的知识树/学习路径是简化桩，真层级在 Java/MySQL 侧；离线构建与在线消费解耦，互不影响。（依据：完善文档 03 / 分析-01）
- **在线查询降级**：图谱关系直查 Neo4j + Redis TTL 300s 缓存 + `neo4jAvailable:false` 空关联降级，导航不依赖图谱服务可用性。（依据：完善文档 03 / 分析-01）

## 追问防御
- **可能追问：在线查询慢怎么办？** → 图谱关系直查 Neo4j + Redis key `kg:neo4j:{uri}:{query_type}` TTL 300s 缓存；Neo4j 不可用返回空关联 + `neo4jAvailable:false`，不抛异常。（依据：完善文档 03 / 分析-11）
- **可能追问：为什么不在 Neo4j 上直接做在线业务？** → 方案 A（Neo4j 实时查询）被否——Java 无 Neo4j 集成、前端独立 SPA、实时查询重，改为方案 B（同步 MySQL 前端只读）。（依据：完善文档 03）
- **可能追问：离线数据改了在线怎么感知？** → 手动按需同步（非 CDC）+ 对账校验；在线 `:Entity` 标签 vs 离线具体标签不一致是真实运维坑，联调前必须对齐。（依据：分析-11 / 分析-01）
