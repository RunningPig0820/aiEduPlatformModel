# 为什么选 Neo4j 而不是 MySQL 或 ES？

> summary: 项目介绍引导问题回答：核心查询是"前置依赖链"多跳图遍历，MySQL 多跳 JOIN 难写难优化、ES 只有全文检索没有图语义；Neo4j 原生图查询 + 可解释路径，CSV 批量导入比 TTL 直导快 10 倍以上

**核心结论**：核心查询是"前置依赖链"这类多跳图遍历——MySQL 多跳 JOIN 难写难优化、ES 只有全文检索没有图语义；Neo4j 原生图查询 + 可解释路径，且 CSV 批量导入比 TTL 直导快 10 倍以上。

## 分层展开
- **核心查询是图遍历**：学生答疑要定位"这个题考哪个知识点、前置是什么"，掌握度诊断沿前置链找根因，学习路径要有知识点依赖关系——这些本质是多跳图遍历（依据：完善文档 01 为什么）
- **MySQL 的短板**：多跳 JOIN 难写难优化，不适合"前置依赖链"这类递归遍历（依据：完善文档 01 / knowledge-graph.md）
- **ES 的短板**：只有全文检索能力，没有图语义，答不了"概念间怎么关联"（依据：完善文档 01 / knowledge-graph.md）
- **Neo4j 的优势**：原生图查询 + 可解释路径；`neo4j-admin import` 对 CSV 批量导入是 TTL 直接导入的 10 倍以上（语雀-决策记录 D1 / 方案选型对比 选型1）（依据：完善文档 01 为什么 Neo4j）
- **不是替代关系**：MySQL/ES 用作页面化只读与全文检索，不是要替代图数据库（依据：完善文档 01 追问与防御 / knowledge-graph.md）

## 追问防御
- **可能追问：MySQL/ES 完全不用吗？** → 页面化走 MySQL 只读 + 全文检索，不是替代关系；Neo4j 承担权威图谱与关系查询，MySQL 承担页面化只读，各司其职（依据：完善文档 01 追问与防御）
- **可能追问：图数据量大时 Neo4j 性能够吗？** → 当前 6757 节点/20887 关系量级很小；且离线构建/在线消费分离，Neo4j 只做最后仓库，关系直查配 Redis TTL 300s 缓存降级（依据：完善文档 01 / 引导问题.md 数据存储）
