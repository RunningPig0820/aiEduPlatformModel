# 图谱关系（MATCHES_KG/PART_OF/RELATED_TO）为什么不同步到 MySQL？

> summary: 数据存储引导问题回答：关系直查 Neo4j 避免无限业务事实污染权威图谱 + 减少同步复杂度；查不到时走 Redis TTL 300s 缓存 + 空关联降级，导航不依赖图谱可用性
> 权威度: 1.0（合成问答答案切片，非原始证据）
> 模块: knowledge-graph
> COS路径: rag-slices/knowledge-graph/引导问题/引导问题-55-数据存储-图谱关系MATCHES_KGPART_OF.md
> 类别：数据存储

**核心结论**：关系（MATCHES_KG/PART_OF/RELATED_TO）直查 Neo4j，避免"无限的业务事实"污染权威图谱 + 减少同步复杂度；查不到时走 Redis TTL 300s 缓存 + 空关联降级，导航不依赖图谱可用性。

## 分层展开
- **避免污染权威图谱**：关系是权威图谱语义的一部分（MATCHES_KG 匹配、PART_OF 部分、RELATED_TO 语义关联），不同步到 MySQL 避免无限业务事实污染权威图谱 + 减少同步复杂度（依据：引导问题.md 数据存储）
- **MySQL 只存结构**：MySQL 页面化只存教材结构 8 表（t_kg_textbook/chapter/section/knowledge_point + 层级关联表 + 同步记录表），用于前端教材导航，不含关系语义（依据：完善文档 02 存储拓扑）
- **关系怎么查**：关系直查 Neo4j（api/kg.py + api/neo4j.py）；查不到时走 Redis TTL 300s 缓存 + 空关联降级 + `neo4jAvailable:false`，导航不依赖图谱可用性（依据：引导问题.md 数据存储 / 分析-01）
- **降低同步复杂度**：只同步结构层（页面化浏览需要），语义关系不同步，避免 8 类关系跨库一致性维护成本（依据：引导问题.md 数据存储 / 完善文档 02）

## 追问防御
- **可能追问：查不到怎么办？** → Redis TTL 300s 缓存 + 空关联降级，导航不依赖图谱可用性；服务未起/超时直查降级（依据：引导问题.md 数据存储 / 分析-01）
- **可能追问：那页面上的关联关系哪来的？** → 页面化走教材结构（Neo4j→MySQL 同步），关系语义消费走在线图谱查询；两套分开，各答各的需求（依据：引导问题.md 数据存储 / 架构设计）
