# 匹配评审系统（人工审核闭环）现在上线了吗？

**核心结论**：**没有上线**。匹配评审系统（D16：MySQL 审核表 `textbook_kp_match_review` + `/api/kp-match/recommend` + Web 人工确认回写 MATCHES_KG）**代码无实现**——唯一痕迹是 `method='candidate_review'` 的 best_candidate 记录字段，人工审核闭环是设计规划非已上线功能。

## 分层展开
- **设计口径**：语雀/design D16 描述 MySQL 审核表 + LLM 推荐接口 + Web 人工确认闭环，未匹配按颗粒度差异 297 / 图谱缺失 11 分类（早期 308 口径）（依据：完善文档 05 / 完善文档 08）。
- **落地真相（方案有/代码无）**：edukg/scripts 与 ai-service/api 均未检索到审核表/推荐接口/导入脚本实现；唯一痕迹是匹配结果文件里的 `method='candidate_review'` 的 best_candidate 记录字段（依据：分析-07 / 完善文档 05 / 完善文档 04）。
- **当前未匹配处理**：置信度<0.5 不硬连（不建 MATCHES_KG），未匹配留在图谱外——当前 58 个（candidate_review 50 + none 8），非语雀的 308（不同批次）（依据：完善文档 05 / 分析-07）。
- **面试口径**：如实讲"审核闭环未上线，是设计规划"——匹配失败的兜底现在是"留 candidate_review 字段"而非"人工审核流程"（依据：完善文档 05 / 引导问题.md 9）。
- **关联 Non-Goal**：管理员审核/重跑在页面化设计里也是 Non-Goal——需审核 UI + 审核后导入 Neo4j + 新知识点 v3.2 前缀，风险是批量误确认需 reviewer_id/time 回溯（依据：完善文档 08）。

## 追问防御
- **可能追问：未匹配的知识点怎么处理？** → 目前不过阈值不硬连留在图谱外，candidate_review 记录 best_candidate 待人工（规划）；无线上审核流程（依据：完善文档 05 / 分析-07）。
- **可能追问：为什么不做？** → 复杂度后置：需审核 UI、审核后导入 Neo4j、v3.2 前缀，且批量误确认风险需要回溯机制——本期自动化优先（依据：完善文档 08）。
- **可能追问：那"人在环"是不是没了？** → 人在环是设计目标（低置信降级候选待人工补审），但线上审核闭环未实现，只有 candidate_review 记录字段——如实区分方案与落地（依据：完善文档 05 / 完善文档 06）。
