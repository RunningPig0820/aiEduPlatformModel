## 坑一：匹配率 17% 根因 = 数据抽象层级错位

一开始匹配率只有 **17%**（LLM 匹配仅 2%），一开始以为是算法不行，查下来根因是**数据抽象层级错位**：

| 侧 | 内容 |
|---|---|
| 教材知识点 | 小学 940（**69.6%**）/ 初中 252 / 高中 158，是"1-5 的认识""连加连减"这种具体知识 |
| EduKG 概念 | 1,295 个，几乎全是"余弦定理""一元二次方程"这种高中抽象概念 |

**具体知识点直接匹配抽象概念，天然对不上**——这不是 LLM 能力问题，是数据不在一个抽象层级。

- **根因**：69.6% 教材知识点是小学具体知识，EduKG 概念几乎全是高中抽象概念，抽象层级错位
- **修复**：不是换算法，而是**在匹配前先用 LLM 把教学名标准化成抽象概念列表**再匹配——"1-5 的认识"→[数的认识,自然数,数字]→匹配"自然数"（相似度 0.711）；"连加连减"→[减法]（0.655）；"秒的认识"→[秒]（0.830）

> 面试讲法："匹配率 17% 的根因是抽象层级错位——69.6% 小学具体知识点对不上 EduKG 高中抽象概念；解法是 LLM 标准化预处理把教学名翻译成抽象概念列表再匹配。教训是别一上来就怀疑算法，先查数据是不是在同一个抽象层级。"

## 坑二：Topic 继承污染的逆向修复（数据血缘 bug）

匹配工程里还踩了一个**数据血缘 bug**：知识点属性 `topic` 直接继承章节，结果"加法"知识点出现在"位置"章节，被错标成"图形与几何"。

- **根因**：属性规则里 topic 简单继承章节，但章节语义和知识点语义不一定一致
- **修复是逆向数据流**——用**下游匹配结果回改上游字段**：知识点匹配到的 EduKG Concept → 拿它的 Class 类型 → 反推规则映射 topic
- **映射表**：数学概念/数学运算 → 数与代数；几何图形/几何性质 → 图形与几何；统计概念 → 统计与概率
- **结果**：**修正 144 个**（数与代数 +36、图形与几何 -44）

> 面试讲法："踩过数据血缘 bug——topic 直接继承章节，加法在位置章节被错标成图形与几何；用下游匹配到的概念 Class 类型反向修正了 144 个。教训是简单继承会出错，数据血缘要能反查。"
