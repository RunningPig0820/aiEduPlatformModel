## 清洗踩过的坑：让面试有血有肉

### 坑一：属性补全顺序搞反了，先增强后推断

当时属性增强是放在 LLM 推断**之前**跑的，结果 LLM 推断出来的 1052 个知识点**一个属性都没有**，整体覆盖率只有 22%。

- **根因**：流水线顺序依赖，先增强的只覆盖了已存在的知识点，推断出来的没赶上
- **修复**：调整顺序——先推断补全知识点，再统一补属性，1052 个全部补齐

> 面试讲法："踩过流水线顺序的坑——先增强后推断，推断出来的 1052 个知识点全没属性；调成先推断后增强就对了。教训是数据管线的顺序本身也是要验证的。"

### 坑二：知识点专题继承错了，靠匹配结果校正

属性规则里 `topic` 直接继承章节，但这个策略有 bug：**"加法"这个知识点出现在"位置"这个章节，就被错标成了"图形与几何"**。

- **根因**：规则继承简单，但章节语义和知识点语义不一定一致
- **修复**：用知识点匹配到的 Concept 的 Class 类型来校正，批量修正了 144 个

> 面试讲法："简单继承会出错——加法在位置章节被错标成图形与几何；后来用匹配到的图谱概念类做二次校正。"

### 坑三：小学和高中知识点是空的，得靠 LLM 补

数据下载下来才发现：**小学 3-6 年级和高中必修的知识点字段是空的**，只有初中是完整的。

- 缺的用 **LLM 根据章节信息（学段/年级/章节名/小节名）推断**知识点，补了 **1052 个**，平均置信度 0.93
- LLM 推断是长任务（2-3 小时），所以配套做了**断点续传**（llmTaskLock），中断了接着跑

> 面试讲法："EduKG 和教材数据在小学高中都是空的，用 LLM 根据章节信息推断补了 1052 个，平均置信 0.93；因为是长任务还做了断点续传。"

### 坑四：匹配率从 17% 提到 97.1% 的历程

匹配率是数据质量的核心指标，讲这个历程最能体现工程能力：

- **最初**：纯靠 LLM 匹配，匹配率只有 17%，而且遍历所有候选 LLM 调用爆炸（500 万次）
- **演进**：改成三段式——① 精确匹配（标准化 + 同义词）兜住 86.8% ② bge 向量粗筛 top-20 把候选压下来 ③ 只有拿不准的才交 LLM 双模型投票
- **结果**：匹配率 **97.1%**（精确 1511 + LLM 179 + 未匹配 50），LLM 调用从 500 万降到 2.7 万（**降 99%**），整体提速约 50 倍

> 面试讲法："匹配率从 17% 提到 97.1%——核心是别让 LLM 干所有事：精确匹配兜确定性、向量粗筛压候选、LLM 只处理拿不准的，LLM 调用降了 99%。"
