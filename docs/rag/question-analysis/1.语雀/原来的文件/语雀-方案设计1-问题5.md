# 问题5（语雀原稿）

我们设计需要有个这个前提 我们有一个完整的 知识点和题库的表 但是我们现在是确实的
我现在也没有能力补全这个

现在我们需要通过产品的手段完成 知识点和题库的补全 就是因为这个前提我们需要解决现在的问题

我们现在的解决方案是 通过llm分析题目和知识点的关系

我们需要考虑到会出现什么场景

1. 题目 每次都匹配出相似的题型但叫法不一样怎么解决
2. 我们的知识图片是uri的 我们怎么把题型和 知识点关联 也有题型和知识点名称不一样的情况
3. 我们后续会兼容掉有题型的情况吗
4. 我们可以通过自动化llm/大数据的功能 自动补充题型吗


回答前提我确认了：我们不能依赖「现成的完整知识点+题库标注」作为地基，要靠 LLM + 产品闭环把它长出来。
  那么你这 4 个场景，其实都指向同一个设计核心。先给一句话总纲，再逐个拆：

  ▎ 题型名不是锚点，URI 才是锚点。题型名只是「把观测聚类」的 key——key
  ▎ 可以长不一样，只要最终都能指到同一个 URI。

  Q1：相似题型叫法不一怎么解决？

  分两层，确定性优先、LLM 兜底：

  层1 观测聚类时（确定性，无 LLM）：
    归一化（TopicKeyNormalizer）→ 折叠全角/空白/末尾标点
    → 聚合同一个「变体桶」（“鸡兔同笼问题” 两次）
    → 跨变体桶合并：比 kp\_uri 集合重叠 ≥70% → 视为同一题型，收进别名表

  层2 长尾同义词（LLM/大数据，慢路径）：
    无 kp 重叠但有语义相似（“牛吃草” vs “牛顿问题”）→ 离线 LLM 判同义词 → 并别名

  变体桶合并是现在就该做的确定性机制（上一轮说的别名表方案）；LLM 同义词留大数据阶段（design Decision
  17 本来就是这么定的）。

  Q2：知识点是 URI、题型名 ≠ 知识点名，怎么关联？（核心）

  关键：不是「题型名直接等于知识点名」，而是两跳桥接，终点落到 URI：

  题型名 “鸡兔同笼问题”          ← 题型空间（无限、叫法随 LLM 漂移）
     │ ① LLM 翻译：题型名 → 候选知识点名（教材叫法）
     ▼
  知识点名 “鸡兔同笼”            ← 知识点空间（教材叫法，有限）
     │ ② 镜像校验：findByLabel / findByLabelLike → 教材知识点
     ▼
  TextbookKP URI  math#textbook-…  ← 锚点（唯一、可图链接、可聚合）
     │ ③ 观测共现：obs(topic\_label, kp\_uri) 累积 → 题型库 kp 分布

+ 在线：resolve ③ 的 LLM 两段式就是这条桥——题型名 → LLM 生成知识点名 → 镜像校验出 URI。
+ 离线：聚合把同 topic\_label 的 obs 按 kp\_uri 聚类出 t\_kp\_question\_type\_kp(question\_type\_id, kp\_uri,
  ratio, grade\_range)，题型和知识点就这样关联起来，且带着年级分布和占比。
+ 题型名和知识点名永远可以不一样，因为关联靠的是观测终点（URI）+ 翻译（LLM→镜像），不靠名字相等。

  ⚠️  一个硬前提要标出来：LLM 只能挂到镜像里已有的 URI。镜像（kg-sync
  教材知识点）就是封闭宇宙，如果教材同步不全，题型翻译出的知识点名会校验失败 → PENDING →
  人工兜底。所以「补镜像」是这条链路的一个外部依赖（不在本 change 内，但设计要预留
  PENDING→审核→补镜像的出口）。

  Q3：后续会兼容「有题型」的情况吗？

  会，而且现在设计题型库时就要预留来源维度。现状：答疑侧题型是独立枚举，明确不绑作业域
  QuestionType（memory 里的决策）。但这不等于不兼容——题型库应该设计成跨来源收敛：

  题型库 canonical 题型 ← 来源：① 答疑 obs（现在）
                            ② 题型分析 student\_vote（前端方案）
                            ③ 题库域已有题型标签（未来种子）★

  兼容方式：题库里已经打了题型标签的题 = 免费的种子观测。批量扫这类题 → LLM 关联出它的知识点 → 以
  source=QUESTION\_BANK 写 obs → 进聚合。这能大幅加速冷启动（题库题量远大于在线答疑观测量）。别名表 +
  合并机制天生就支持「多个来源的同义题型并到一个 canonical」。

  Q4：可以自动化 LLM/大数据自动补充题型吗？

  反应式（reactive）已经建好，主动式（proactive）是下一步：

  reactive（已有）：学生真实做到 → obs → 凌晨聚合 → CANDIDATE → STABLE
                    ✓ KpQuestionTypeAggregationService + LLM 归纳 ratio 已在跑
  proactive（缺口）：批量扫题库未标注题 → LLM 题型识别 → 批量写 obs → 聚合
                    = 把前端「题型分析贴题」那条链路离线化、批量化

  proactive 就是你说的「自动补题型」的正解，而且它正好复用前两轮讨论的东西：analyze-question
  的题目理解（在线）抽出来做批量版，跑定时任务扫题库 → 题型名 + LLM 关联 → obs →
  聚合。这同时也是补全题库标注（题目↔知识点）的产品闭环——不需要人工一条条标，靠 LLM 初筛 + 学生确认 +
  聚合阈值三层过滤。

  一张图收拢

```plain
          题目来源                              离线闭环（凌晨）
答疑 decide ──┐                             ┌─► 聚合 → CANDIDATE
题型分析贴题 ──┼─► 在线 resolve ──► obs ────┤    ├─ 别名合并(kp重叠)
题库批量扫瞄 ──┘  (镜像→题型库→LLM两段式)     │    ├─ LLM 归纳 ratio
(proactive)                                 │    └─ STABLE(≥10+审核)
                                            └─► 回写先验 → 解析管线②复用
题型名 = 聚类 key  │   URI = 锚点          题型库 = 跨来源收敛 + 别名
```

  Q1(别名/合并) + Q2(LLM 翻译→URI) + Q3(跨来源收敛) + Q4(reactive+proactive)
  是同一套机制的四张脸——核心都是「题型名当 key、URI 当锚、观测+LLM 当桥」。
