  坑 1：题型名能不能匹配上（alias 问题）

  两个数据源各有一个“题型名”：

+ analyze-question 返回的 topicLabel —— 它认出的题型名
+ getMastery 返回的 items[].topicLabel —— 掌握度表里的题型名

  要做“识别→查掌握度”，前端就得拿 analyze-question.topicLabel 去 getMastery.items 里 find(item =>
  item.topicLabel === result.topicLabel)。这一步能不能找到，取决于两个名字是不是同一个字符串。

  会 miss 的情况（alias）：

  后端契约里已经写了「题型库命中支持别名——相似题型名收敛到 canonical」。也就是说后端自己内部就有：

+ 学生题目 → LLM/镜像识别 → 可能是“相遇问题”
+ 题型库里 canonical 名是“行程问题”

  如果 analyze-question 返回的 topicLabel 是已收敛的 canonical 名（“行程问题”），那和 getMastery
  里存的“行程问题”就能匹配上 ✓
  但如果不收敛，返回了原文“相遇问题”，getMastery 里只有“行程问题”，那 find 就找不到 →
  查不到掌握度，展示成“未开始”，而实际上这个学生可能早就在练行程问题了。

  真实例子（前面联调踩过的）：

+ 贴“鸡兔同笼” → topicLabel: “鸡兔同笼”
+ 贴“x²-5x+6=0” → topicLabel: “一元二次方程”（原文可能叫“解一元二次方程”，收敛成“一元二次方程”）

  后果： 匹配不上不是报错，是静默降级——该题型的掌握状态不显示。如果 alias
  常见，这个功能就会经常“失灵”，学生看不懂为什么有时候有状态有时候没有。

  解法（3 选 1）：

+ A（推荐，零前端成本）：让后端保证 analyze-question 返回的 topicLabel 就是
  canonical（后端已经在做收敛，让它在返回前也用同一套收敛）——前端直接等号匹配即可
+ B：后端给 analyze-question 响应加一个 masteryKey（或 topicKey）字段，和掌握度的 key 同构，前端用这个
  key 查，不碰名字
+ C：前端做模糊/别名归一——不可靠，别做

  坑 2：两层 PENDING 语义冲突

  这是最阴的坑——同一个词 PENDING，在两个接口里含义完全不同：

  ┌─────────────────┬─────────────────────────────────────────────────────────────────┬─────────────┐
  │      接口       │                      status=PENDING 的含义                      │  出现在哪   │
  ├─────────────────┼─────────────────────────────────────────────────────────────────┼─────────────┤
  │ analyze-questio │ 题型没认出来（低置信/冷启动猜不出）                             │ 分析结果卡  │
  │ n               │                                                                 │ 片          │
  ├─────────────────┼─────────────────────────────────────────────────────────────────┼─────────────┤
  │ getMastery      │ 题型认出来了，但关联的知识点待确认（学生做过这类题，掌握度已挂  │ 掌握度数据  │
  │                 │ 起）                                                            │             │
  └─────────────────┴─────────────────────────────────────────────────────────────────┴─────────────┘

  如果前端不区分，会发生这种 bug：

  学生贴一道题 → analyze-question 返回：
  { topicLabel: “鸡兔同笼”, status: “PENDING”, confidence: 0, knowledgePoints: [], candidates: [...] }

  前端一看 status === 'PENDING'，脑子一热直接走了“待确认”分支 → 展示“暂无法确认关联知识点”+ 候选列表。

  可是 —— 这个 PENDING 是 analyze-question 的，含义是“我连题型都没敢确定”。跟掌握度、跟知识点确认半毛钱关
  系没有。学生此时应该看到的是“题型不确定，给你几个候选猜一下”。

  反方向也危险： 从 getMastery 拿到：
  { topicLabel: “鸡兔同笼”, masteryLevel: 50, status: “PENDING” }
  这个 PENDING 是“题型掌握度挂起，等确认知识点”，不是“题型没认出来”。

  两套 status 千万不要共用同一个判断变量/同一个分支逻辑。

  正确的分层逻辑：
  识别结果（analyze-question.status）：
    RESOLVED → 题型确定 → 下一步去查掌握度
    PENDING  → 题型不确定 → 展示候选/空态，到此为止，不去碰掌握度

  掌握度（getMastery item.status + masteryLevel）：
    status=RESOLVED + masteryLevel=75 → 已掌握
    status=RESOLVED + masteryLevel=50 → 练习中
    status=RESOLVED + masteryLevel=25 → 待巩固
    status=PENDING → 待确认（知识点挂起）

  一句话总结：analyze-question 的 PENDING 是“认不出题型”，getMastery 的 PENDING
  是“题型已练、知识点待认”。两层永远分开判，别用一个变量。

  坑 3：未命中题型（学生没做过这类题）

  场景： analyze-question 成功识别出题型了（RESOLVED），getMastery 里查不到这个题型。

  含义： 这个学生从来没练过这类题 —— 掌握度表是「做过才有」的，没做题就不会有记录。

  真实例子： 学生贴“鸡兔同笼”，识别成功，getMastery.items 里只有“行程问题”“一元二次方程”，没有“鸡兔同笼”
  → 查不到。

  如果不好好处理，会有三种错误：

1. 显示“待巩固/待确认” ——
  错！这是最坏的。待巩固=学过但不行，待确认=学过但知识点挂起。学生没做过，凭什么待巩固？等于诬陷他。
2. 显示空 → 学生一脸懵 —— 找到了就显示、找不到就空白，学生不知道为什么有的题有状态有的没有。
3. 把“未命中”当成“待确认”混进去 —— 和坑 2 叠加，概念彻底乱。

  正确展示：
  查不到 → 明确显示“未开始”（灰态 / 或直接不显示掌握度区）
          文案：这个题型你还没做过题，去做题积累掌握度

  和坑 1 的关系：

+ 坑 1 的 alias 不匹配 = 本来有记录但没查到（false miss，数据有但匹配错）
+ 坑 3 = 真的没有记录（true miss，学生真没练过）
  是“题型已练、知识点待认”。两层永远分开判，别用一个变量。

  三个坑放一起的完整判断链

  analyze-question 结果
    ├─ status=PENDING ──────────────→ 展示候选/空态【坑2：题型不确定，到此为止】
    └─ status=RESOLVED (topicLabel)
         ├─ 在 getMastery 命中 ──────→ 四态徽标 (已掌握/练习中/待巩固/待确认)
         │      └─ 这里命中靠名字等号匹配【坑1：alias 会 miss】
         └─ 在 getMastery 未命中
              ├─ 真没做过 ───────────→ “未开始”灰态【坑3】
              └─ 该命中没命中 ───────→ 后端收敛问题【坑1，前端无解】

  要我把这套判断链和三个坑写进方案里吗？重点是 design 决策 3 那块——掌握度标注从“预留、接
  kp-coverage“改成”本期渲染、接 getMastery + 四态映射 + 三坑处理“。
