## 硬性规则（强制继承）

### 术语强制统一
canonical标准题型 / 派生层 / obs观测层 / 掌握度 / 解析管线 / 动态涌现 / 两域解耦。禁止自创别名。

### 状态判定标准
- ✅【已落地设计】文档+代码双存在、可观测实现
- ⚠️【建议项(未实现)】仅文档构想、无代码落地
- ❓【待决策】无明确结论

### 证据标注规范
1. 语雀证据：`证据：语雀-原文件-xxx.md`
2. 代码证据：`文件:函数/类/逻辑片段`，禁止编造行号
3. 不可读来源如实标注，不脑补

### RAG 专属结构强制规则
1. **禁止横向大宽表作为主体内容**（切片断裂、语义丢失）。
2. **每一个技术选型点 = 一个独立 `### 选型N` 小节**，单条可单独召回，一个 chunk = 一组选型。
3. 每个小节固定结构：
   - 顶部状态标签：`> 状态：✅/⚠️/❓`
   - 顶部 1-2 句**检索摘要**（向量召回核心）
   - **内部载体：结构化分级条目**（选型场景 / 候选方案A/B/C（各带优劣，含致命短板）/ 最终拍板 / 拍板理由）——多候选对比用分级列表，**不用竖向窄表**（候选描述塞进单格会过长、切片后难读）。决策/场景等单主体文档才用竖表。
4. 消除问答口吻、全正式技术陈述。
5. 同类信息合并、无重复。
6. **否决方案必须写明致命短板**，不允许只写优点。
7. 拍板理由必须具体，可引用 `D#X` 决策编号。

### 输出自检规则
1. 状态标记无混淆。
2. 所有落地项带真实证据。
3. 无口语、无讨论式文本。
4. 术语完全统一。
5. 无重复选型。
6. 结构符合单 Chunk 单选型规范。

## 任务：生成【语雀-方案选型对比.md】

### 文档用途
用于回答系统所有架构选型取舍问题：为什么用MySQL、为什么不用纯LLM、为什么题型做锚点、为什么放弃自动关联等。

### 输出固定结构
1. 文档头部：元信息 + 【文档说明】——说明正文分块用于 RAG 检索，末尾总表仅人工查阅、不入库。
2. 正文：**8 大选型逐一独立 H3 小节**，每小节固定字段：
   - 选型场景
   - 各候选方案优劣（含致命缺陷）
   - 最终拍板结果 + 状态
   - 详细拍板理由（可引用 D#）
3. 文档末尾：【附录-原始总表】——标注仅供人工查阅、不参与向量切片。

### 必须覆盖的 8 大选型范围
1. 存储选型：MySQL派生层 vs Neo4j物化扩展 vs Java直调COS
2. 关联引擎选型：纯LLM vs 向量最近邻 vs 字符规则 vs 分层混合
3. 掌握度锚点选型：题型锚点 vs 知识点锚点
4. 掌握度算法选型：累计平均 vs max单调不减 vs EWMA
5. 关联模式选型：全自动涌现关联 vs 人工查表维护
6. 向量路由选型：多索引vector_type vs 单索引filter
7. 关联确认机制选型：人工/学生众包/学生澄清/LLM自动
8. LLM候选约束选型：开放域自由猜测 vs 年级封闭域池

### 校验强制要求
- 每个被否决方案必须写致命问题。
- 所有拍板结果带 ✅/⚠️/❓。
- 理由不空泛、必须落地到架构问题。
- 结构 100% 适配切片：一条选型 = 一条检索单元。

### 选型1：派生层存储方案选型
> 状态：✅ 已落地
> 检索摘要：派生层最终选用MySQL作为主存储，禁止写入权威Neo4j图谱，规避无限题型空间导致的图爆炸、图谱污染问题，Neo4j仅按需阶段性物化。

- 选型场景：题型派生数据、观测数据、掌握度数据存储方案选择
- 候选方案A：MySQL 派生层
  - 方案A优劣：读写速度快、支持事务、便于数据审核；支持无限题型空间，可写、可改、可回滚，完全隔离权威图谱。
- 候选方案B：Neo4j 物化扩展层
  - 方案B优劣（致命短板）：支持图遍历、可做薄弱溯源；但无限题型挂载有限知识点，会引发图爆炸、直接污染权威教育局图谱，风险极高。
- 候选方案C：Java 直调 COS
  - 方案C优劣（致命短板）：Java侧零依赖架构简单；但无法复用向量Bucket能力，后续RAG检索需要重新搭建存储体系，扩展性差。
- 最终拍板：MySQL 派生层为主；Neo4j仅阶段2按需物化（ExtAlias + ALIAS_OF）
