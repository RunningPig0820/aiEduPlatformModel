## 一、架构层决策

### D1 权威图谱零写入，派生层（MySQL）承载
> 检索摘要：选择 MySQL 派生层，不写入修改权威 Neo4j 图谱，避免权威图谱被无限题型空间污染，复用原有图谱 URI 结构。

| 属性 | 内容 |
|---|---|
| 背景 | 题型空间无限（鸡兔同笼/相遇/浓度），知识点有限；把无限挂有限会图爆炸、污染权威图 |
| 演进 | 早期考虑物化进 Neo4j 扩展层 → 拍板 MySQL 派生层 |
| 拍板理由 | 权威图物理上不可能被污染；派生层可写可改可回滚 |
| 系统影响 | 图逻辑靠"持 URI 借结构"（expandNode 复用），不建图 |
| 证据 | 语雀-方案设计1-问题1；[总揽§1] |

### D8 两域解耦 + 域 B 独立化（查表只读 + ADMIN 维护）
> 检索摘要：关闭 obs 自动关联涌现链路，域 B 改为管理员手动维护查表模式，隔离题目解析链路与题型关联逻辑，降低系统复杂度。

| 属性 | 内容 |
|---|---|
| 背景 | 早期 obs 共现自动关联 + 挂起 + LLM 归纳 ratio |
| 演进 | obs 自动关联涌现链路 → 业务不成熟收敛，切换域 B 只读管理员维护 |
| 拍板理由 | 自动关联引入 5 环节分散本期核心（题目→题型→掌握度）；防污染权威图谱 |
| 系统影响 | 停用自动涌现链路；getMastery PENDING 语义改为"canonical 未归属" |
| 证据 | design-backend Decision 9/10；[总揽§7] |

### D13 Python 桥向量 + vector_type 多索引路由
> 检索摘要：Java 不直接调用 COS 与 Embedding，通过 HTTP 桥调用 Python 服务；vector_type 参数做多索引路由，支持后续扩展 question、rag 索引。

| 属性 | 内容 |
|---|---|
| 背景 | COS 向量检索无 Java SDK；Java 不碰 embedding API / COS SDK |
| 演进 | 定稿方案，Python 侧统一接管向量操作 |
| 拍板理由 | Java 经 TopicVectorStore 桥 HTTP 调 Python；vector_type 必填路由（本期 topic，question/rag 占位） |
| 系统影响 | 向量操作全在 Python 侧；多索引加索引零代码改动 |
| 证据 | api/vector.py；design-python Decision 1/5 |

## 二、掌握度口径决策

### D2 掌握度主体 = 题型（非知识点）
> 检索摘要：掌握度统计主体从知识点切换为题型，学生掌握对象是解题模式，mastery 信号输出题型 label，知识点由后端派生计算。

| 属性 | 内容 |
|---|---|
| 背景 | 早期方案掌握度按知识点 URI；学生掌握的是解题模式 |
| 演进 | 2026-08 翻转，主体从知识点改为题型 |
| 拍板理由 | 题目天然可聚到题型、可打分可观测、落库不裂行；直接输出知识点名会污染后端题型库 |
| 系统影响 | mastery_signals.topic_label 输出题型；知识点由后端派生 |
| 证据 | models/tutoring.py:KpSnapshot 注释；prompts.py:78-83 |

### D3 掌握度 = 累计平均正确率（替代 max 单调不减）
> 检索摘要：掌握度算法替换 max 单调不减，改为累计平均正确率，得到 0-100 连续分值，解决答错无法降分、掌握度虚高问题。

| 属性 | 内容 |
|---|---|
| 背景 | 现状 max 单调不减 = 置信度视角，答错永不降、虚高，算不出正确率 |
| 演进 | 早期 max 单调不减 → 累计平均 |
| 拍板理由 | 正确率视角可解释、可回查、稳定不抖动；"练 10 道对 6 道=60%" |
| 系统影响 | 掌握度从离散四档变连续 0-100，getMastery BREAKING |
| 证据 | 语雀-方案设计2-问题3；[总揽§3.3] |

### D4 掌握度信号映射 + per-题型打折
> 检索摘要：定义答疑行为得分权重，答对 1.0、求助答对 0.5、答错 0；前 N 题做分数打折，缓解首题答错带来掌握度假低。

| 属性 | 内容 |
|---|---|
| 背景 | 掌握信号需定义（答对/求助/答错）；首题答错会造成假低 |
| 演进 | 定稿 |
| 拍板理由 | 区分不同答题行为质量；首题打折降低单次作答对掌握度的冲击 |
| 系统影响 | 掌握表只被 AI 答疑信号更新；题型分析页无对错信号 |
| 证据 | 语雀-方案设计2-问题3；design-backend Decision 3 |

### D12 掌握信号唯一来源 = AI 答疑
> 检索摘要：掌握度更新信号仅来自 AI 答疑链路；题型分析页面只采集题目，不产生答题对错信号，不会更新掌握度。

| 属性 | 内容 |
|---|---|
| 背景 | 掌握信号需明确来源 |
| 演进 | 定稿 |
| 拍板理由 | 只有答疑有真实答题行为（对错）；题型分析页只记题目无对错 |
| 系统影响 | 掌握表只被答疑链路信号更新 |
| 证据 | 语雀-方案设计2-问题3；[总揽§3.3] |

### D14 两层 PENDING 语义分离
> 检索摘要：区分 analyze-question 与 getMastery 的 PENDING 语义，不再复用同一个状态字段；识别失败与掌握度未归属是两类业务状态。

| 属性 | 内容 |
|---|---|
| 背景 | analyze-question 与 getMastery 都用 PENDING 但含义相反 |
| 演进 | 定稿，两套 PENDING 语义完全解耦 |
| 拍板理由 | analyze PENDING=题型没认出（展示候选/空态）；getMastery PENDING=题型已练、知识点待确认；绝不共用一个判断变量 |
| 系统影响 | 前端状态展示分层判断，识别失败不查掌握度 |
| 证据 | 语雀-方案设计2-问题1 坑2 |

## 三、向量&聚集归并算法决策

### D5 编辑距离 ≤1 近字归并移除
> 检索摘要：移除编辑距离<=1 字符归并逻辑；形近字、错别字、近似题型的归并全部交给题型名字向量层处理，避免"一元一次/一元二次"误合并。

| 属性 | 内容 |
|---|---|
| 背景 | 早期字符规则按编辑距离 ≤1 归并近字变体 |
| 演进 | 联调发现误并 → 移除字符归并逻辑 |
| 拍板理由 | "一元一次/一元二次"一字之差与错别字"方成/方程"同为距离 1，字符级无法区分 |
| 系统影响 | 近字/错别字归并全交给题型名向量层 |
| 证据 | design-backend Decision 4；[总揽§3.4] |

### D6 聚集依据 = 题型名向量单信号（题目向量不落库）
> 检索摘要：动态聚集只使用题型名向量，题目向量本期不作为聚集依据；相似题检索属于非本期目标，question 索引仅做占位预留。

| 属性 | 内容 |
|---|---|
| 背景 | 语雀早期建议题目向量为主 + 题型名向量为辅 |
| 演进 | 收敛为题型名向量单信号 |
| 拍板理由 | 相似题检索本期 Non-Goal；动态聚集只需要题型名向量 |
| 系统影响 | question 索引仅配置占位，后续启用零架构改动 |
| 证据 | models/vector.py:22；design-backend Non-Goals |

### D7 归并阈值 distance ≤ 0.2 保守
> 检索摘要：向量归并阈值设定 0.2；宁可拆分也不误合并，防止不同题型样本互相权重污染；相遇、行程这类距离 0.332 直接拆分。

| 属性 | 内容 |
|---|---|
| 背景 | 归并粒度需要旋钮 |
| 演进 | spike 标定后定稿 0.2 保守阈值 |
| 拍板理由 | 同型 ~0.077 / 异型 ≥0.33 有清晰间距；误并的题权重互相污染，宁可拆不误并 |
| 系统影响 | "相遇(0.332)/行程"默认拆分 |
| 证据 | vector_store.py；design-backend Decision 6 |

### D9 聚合触发阈值（CANDIDATE/STABLE 两级）
> 检索摘要：题型库两级状态；CANDIDATE 靠学生样本数量触发；STABLE 需要人工审核门禁，STABLE 题型进入解析管线先验池。

| 属性 | 内容 |
|---|---|
| 背景 | 个体观测如何沉淀为精选题型 |
| 演进 | 定稿两级状态机制 |
| 拍板理由 | CANDIDATE = 去重学生 ≥3 且总命中 ≥5（单生偶然不算）；STABLE = 审核通过 + 学生 ≥10 + 近30天仍增长（人工门禁） |
| 系统影响 | 题型库两级状态，STABLE 进入解析先验 |
| 证据 | 语雀-方案设计1-问题1；[总揽§5.2] |

| 属性 | 内容 |

| 演进 | 定稿 |
| 拍板理由 | 不污染数据；宁可看不到，不给假数据 |
| 系统影响 | 前端渲染"疑似待确认"虚线态 |
| 证据 | 语雀-方案设计1-问题1；[总揽§6] |

## 七、掌握度底盘 & 题型分析（OpenSpec design 增量）

### D18 题目表 + 掌握表两表分离（事实源 + 聚合结果）
> 检索摘要：新增题目记录表作为事实源，掌握表作为聚合结果，两表隔离「题目证据」与「聚合值」，后续改折扣/信号重算聚合即可，题目证据不丢。

| 属性 | 内容 |
|---|---|
| 背景 | 掌握度数据底盘零散：无题目记录，掌握表 key 是字符串级归一，算不出「练了几道、答对几道」正确率 |
| 演进 | 无统一题目表 → 新增 `t_student_question_record` + 改造 `t_student_topic_mastery`（加 source/train_count，mastery 语义改累计平均） |
| 拍板理由 | 题目表是事实源（含对错信号与引导轮数可回查）；掌握表是聚合结果（canonical key + 累计平均）；两表隔离后可重算聚合不丢证据 |
| 系统影响 | 全入口题目统一落库（AI 答疑唯一产生信号，题型分析页只记题不产生信号）；掌握度每行有题目证据可跳回原题 |
| 证据 | design-backend-question-type-mastery Decision 1 |

### D19 掌握信号跟题目走（PENDING 照常采集）
> 检索摘要：题型名未识别（PENDING）的题照常采集对错信号落题目表，题型归属确定后再聚合进掌握表，不因题型待定丢信号。

| 属性 | 内容 |
|---|---|
| 背景 | PENDING 是「题型暂时没认出」，不代表「题没做」 |
| 演进 | 信号等题型确定才记 → 信号跟题目走先落表 |
| 拍板理由 | 答对/答错信号是确定的，不能因题型待定就丢；否则 PENDING 高频场景掌握度大面积漏采 |
| 系统影响 | 题目表先落，canonical 归属（聚集/人工）确定后再聚合进掌握表 |
| 证据 | design-backend-question-type-mastery Decision 8；design-frontend-question-type-mastery Decision 4 |

### D20 题目理解端口抽象，Java LLM 默认实现（prompt 注入题型库收词）
> 检索摘要：新增 QuestionUnderstandingPort 端口，Java KpQuestionAnalyzer 默认实现，prompt 注入题型库 top-N 已收词约束命名，降低题型名变体漂移。

| 属性 | 内容 |
|---|---|
| 背景 | 题目文本 → 题型名的题目理解只在 Python decide 会话内（SSE 绑定），无独立 REST |
| 演进 | 无独立题目理解 → domain 端口 + Java LLM 默认实现（端口预留可换 Python 独立端点） |
| 拍板理由 | Java 自包含不阻塞跨仓库；prompt 注入题型库已收词让命名偏向现有词汇（别名合并之外第一道防线，纯 prompt 零成本） |
| 系统影响 | 换实现只动 infra 装配，不动 domain/application；analyze-question 依赖该端口 |
| 证据 | design-backend-kp-question-analysis D1 |

### D21 analyze-question 纯分析不写 obs（浏览不产生学习信号）
> 检索摘要：题型分析端点是只读解析，除封闭域池约束 top-1 直接落 RESOLVED obs 外不写观测，浏览行为不污染聚合统计。

| 属性 | 内容 |
|---|---|
| 背景 | resolve 是 label 级且写 obs；题型分析是浏览行为，写 obs 会污染聚合 |
| 演进 | resolve 复用 → 抽 persistObs 开关，analyze 走只读解析 |
| 拍板理由 | 浏览不产生学习信号；唯一例外：封闭域池约束 top-1 直接落 RESOLVED obs（最可能信号进数据喂聚合，题型库冷启动也能沉淀），学生确认 vote 可覆盖纠正 |
| 系统影响 | 题型分析页贴题不产生学习信号，掌握度只被 AI 答疑更新（D12） |
| 证据 | design-backend-kp-question-analysis D2 |

### D22 题型库别名合并：kp 分布重叠 ≥70% → canonical + 别名表
> 检索摘要：相似题型名按知识点分布重叠（≥70%）收敛到 canonical 题型 + 别名表，查询统一走 findByTopicLabelOrAlias，聚合阈值不再被变体稀释。

| 属性 | 内容 |
|---|---|
| 背景 | 聚合按 topic_label 逐字聚类，相似题型叫法不一裂成重复条目、聚合阈值被劈开稀释 |
| 演进 | 逐字聚类 → 新表 `t_kp_question_type_alias` + kp_uri 重叠 ≥70% 判变体折叠 |
| 拍板理由 | 变体题型的语义锚是它指向的知识点，kp 重叠是确定性信号、零 LLM、零误判成本；字符串/归一化兜不住「鸡兔同笼」vs「鸡兔同笼问题」 |
| 系统影响 | 解析管线②/vote/analyze/聚合统一走别名命中；canonical 名只增不改（合并只加别名） |
| 证据 | design-backend-kp-question-analysis D3/D4 |

### D23 图片题目多模态直看（question-understand 独立端点，不经 OCR）
> 检索摘要：图片题目默认走多模态视觉模型直接看图，不经 OCR（OCR 仅前端失败兜底），独立 stateless 端点模型写死视觉，非视觉风险隔离。

| 属性 | 内容 |
|---|---|
| 背景 | 图片题识别原方案走通用 chat（方案 A）；通用路由可能命中非视觉模型图就废 |
| 演进 | 方案 A 通用 chat → 方案 B 独立视觉端点（不经 /api/llm/chat） |
| 拍板理由 | 不是所有模型都有视觉功能；方案 B 模型写死视觉 + 独立端点，非视觉风险天然隔离；Python 模型写死（Java 不指定，方舟开通 ID 不同改 Python 一行） |
| 系统影响 | POST /api/tutoring/question-understand（image_url/topic_hint/grade → topic_labels/question_kps）；topic_labels 空 = 识别失败 → PENDING 降级 |
| 证据 | design-backend-kp-question-analysis D13 |

### D24 设计原则：逻辑优先于数据准确，数据可后整理
> 检索摘要：先打通「题目→关联→确认→沉淀」逻辑闭环，不因数据残缺阻塞实现；各类数据错误由后续机制整理（vote 纠正/维护重判/别名合并/管理端审核）。

| 属性 | 内容 |
|---|---|
| 背景 | 镜像/题型库残缺是冷启动常态，数据不准易阻塞流程 |
| 演进 | 追求数据准确先行 → 逻辑优先，错误后整理 |
| 拍板理由 | 恒非空返回「池内最相近」允许出错，错误由 vote 纠正/维护重判/别名合并/管理端审核整理，而非阻止流程 |
| 系统影响 | 先跑通逻辑闭环，质量收敛依赖真实数据飞轮（学生确认参与），是产品积累曲线而非代码交付 |
| 证据 | design-backend-kp-question-analysis D11 |

### D25 mastery_snapshot 脱钩（题型与知识点快照不同源）
> 检索摘要：mastery_signals 不再优先复用掌握度快照候选，题型与知识点快照不同源；mastery_snapshot 保留在契约里降级为背景参考或不提。

| 属性 | 内容 |
|---|---|
| 背景 | 旧 mastery_snapshot 是知识点 label 快照，无法为题型提供候选 |
| 演进 | 快照优先复用 → 脱钩（保留字段、降级为背景参考） |
| 拍板理由 | 题型与知识点快照不同源，知识点快照不能给题型候选；question_kps 仍可参考快照（继续知识点） |
| 系统影响 | Java 契约不动、字段默认空；prompt 中降级为背景参考或不提 |
| 证据 | design-python-ai-tutoring-topic-mastery-signal Decision 3 |

### D26 题型名稳定规范（prompt 约束 + few-shot，后端只字面归一化）
> 检索摘要：prompt 强制同一题型用最常见最短规范名 + few-shot 锚定常见题型；后端只做字面归一化不做同义词聚类，稳定性负担在 prompt 端。

| 属性 | 内容 |
|---|---|
| 背景 | LLM 天生爱换说法，「鸡兔同笼」vs「鸡兔同笼问题」会被当两个题型 |
| 演进 | 无约束 → prompt 约束 + few-shot 锚定（鸡兔同笼/相遇问题/牛吃草） |
| 拍板理由 | 后端只做字面归一化（全角半角/空白/去语气词），不做同义词聚类；命名稳定性负担前移到 prompt |
| 系统影响 | 题型名稳定依赖 prompt + 后端字面归一化兜底（不完美，本期不做同义词聚类） |
| 证据 | design-python-ai-tutoring-topic-mastery-signal Decision 4 |

### D27 封闭域约束选择信任模型（top-1 直接落 obs，学生确认 = 正确）
> 检索摘要【未接线建议】：封闭域池约束的信任模型——top-1 直接落 RESOLVED obs 喂聚合，学生确认=正确可覆盖纠正；本期 analyze 未接池约束，迭代启动时接线即用。

| 属性 | 内容 |
|---|---|
| 背景 | 开放域自由猜测空候选是流程死穴（D15 建议封闭域）；池约束编排已实现未接线 |
| 演进 | 开放域自由猜测 → 封闭域池内选择（KpPoolAssociateService 已交付、有测试，analyze ② 处接线即用） |
| 拍板理由 | top-1（最可能）+ top-N（候选）：top-1 不管置信多低直接进数据让题型库冷启动也能沉淀；学生确认=正确，vote 覆盖 top-1 纠正 |
| 系统影响 | 本期范围降级未接线；接线后恒返回池内 top-N 绝不空、消灭跨学段错误、结果确定性 |
| 证据 | design-backend-kp-question-analysis D8 |
