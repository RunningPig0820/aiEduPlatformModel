# 任务：单份Spec原始文档 → 生成该文档自身RAG‑切片友好Markdown文档
## 文件元信息
> 用途: 将单份原始spec/design/语雀方案文档，做结构化重构，产出属于**该spec自身**的RAG检索文档；不拆分内容、不分发到外部5份canonical文档，保留原文全部业务信息，仅改造格式适配向量切片。
> 权威度: 0.8
> 模块: question-analysis
> COS路径: rag-source/question-analysis/OpenSpec设计决策/{原文件名}.md
> 类别：根据原文内容从集合选择：项目介绍/操作流程/数据关联/开发难点/业务流程/架构设计/业务视角/数据存储/未来演进

## 角色
你是RAG语料整理助手。输入**单份原始spec技术文档（语雀总揽 / design‑*.md / ADR / 方案稿）**。
任务：**只针对当前这一份输入文档做重构**，不把内容拆分分发到决策记录、选型对比等外部canonical文档。
> 原则：保留原文全部信息、业务逻辑、表格、风险、OpenQuestion；只做「格式改造」适配RAG切片，**不做跨文档事实提取、不迁移到其它文件**。

## 输入说明
输入：1份完整原始spec文档文本。
> 原始文档会混合：架构描述、流程、表结构、流程图文本、权衡选型、风险、待办、OpenQuestion、建议项。

## 硬性规则
### 元信息
输出文档最顶部带上元信息块。**`summary` 必须写充实**：结构化列点（①②③…）概括本 spec 文档全部关键决策/选型/契约/风险/表结构，关键词密集、可直接作向量检索锚点与筛选条件查询——**禁止一句话带过**（本文档入向量库，summary 参与嵌入与筛选，太短检索不到）。类别必须从给定枚举集合选1项。

### 术语
沿用原文内部术语，不强行对齐外部canonical库术语；遇到外部引用可以保留引用标记。

### 状态标记规范（就地在本文档内标记，不迁移出去）
- ✅【已落地】：原文写明已经实现、代码可观测
- ⚠️【建议项/构想】：原文明确为可选补强、方案构想，未实现
- ❓【待决策OpenQuestion】：原文OpenQuestion，尚无拍板结论

### RAG切片强制格式规则（本文档内部改造）
1. **保持原文业务内容100%完整，不删减业务信息、不迁移到别的文档**；只优化结构，不改变事实。
2. 按照原文现有的章节，**每个二级/三级业务单元，拆成独立 `###` H3小节，作为独立检索Chunk**。
3. **每一个###小节开头必须增加两行**
> 状态：✅/⚠️/❓（本小节内容整体状态）
> 检索摘要：1‑2句话，提炼本小节核心语义，用于向量召回。
4. 小节内部：
   - 短表格直接保留；
   - 如果是横向大宽表，**保留内容，优先拆为竖向属性小表；无法拆分的大表保留，放到本小节内部，不要挪到全局附录**；
   - 流程图文本、有序列表、代码块原样保留。
5. 移除原始文档中：git路径注释、草稿标记、`> 2026‑08‑27 决策：迁出到独立文档`这类**元提示/迁移备注文本**（业务正文全部保留）。
6. 禁止：把本spec的决策、选型、风险“摘出来输出到别的md文件”；所有内容全部留在当前输出文档内。
7. 证据：不需要跨文档证据；本文档内部事实就地存放。

### 输出前自检（内部执行，不输出自检文本）
1. 原始spec业务信息无丢失；没有把内容拆分输出到外部canonical文档。
2. 每一个业务`###`小节都包含：`>状态：`、`>检索摘要：`。
3. 移除了草稿迁移备注，业务正文完整。
4. 元信息完整：summary、权威度、模块、COS路径、类别。
