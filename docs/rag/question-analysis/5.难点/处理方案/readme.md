# 5.难点 处理方案

> 状态：2026-08-27 坑档案 8 坑（J-QT1~8）已产出；提示词从 ai-tutoring 副本重写为 question-analysis 专属（补来源铁律/元信息头/业务绑定/坑编号）。缺口见下。

## 一、坑档案定位

**难点经验层（权威 0.8，切片池 doc_type=难点）**——每条坑一个 h3 块，回答"曾经怎么坏了、怎么修的"。与 `3.代码/`（证据层 code_analysis）互补：代码层讲"当前代码怎么实现"，坑档案讲"修复史 + 面试口述"。

> 三类坑的边界（重点）：
> - **真实踩坑**（✅已修复，进主体）：git 有修复提交 + 当前代码可核验 → J-QT1~8 全部是这种
> - **风险预判**（⚠️仅设计讨论，不进主体）：design 里"担心会 XX"但未实际发生 → 不写，或单列附录标注
> - **待决**（❓）：无结论 → 不写
>
> 判断标准一句话：**只有实际发生并修复过、且 git/代码能找到证据的才算坑**——避免 LLM 编"合理但假"的坑污染检索。

## 二、数据来源（本层立身之本）

- **三端 git 历史**：Python `aiEduPlatformModel` / Java `aiEduPlatform` / 前端 `aiEduPlatformFront`——每条坑 `git commit + 文件:行号` 双证据
- **代码现状**：修复提交对应的当前代码（修的代码 = 3.代码 里读到的代码）
- **线索源**：语雀 spike/联调记录、design 决策（只当线索，不当坑证据）

## 三、与其它层的关系

| 关系 | 说明 |
|---|---|
| 与 3.代码 | 代码层讲现状实现，坑档案讲修复史；两者必须口径一致（修的就是 3.代码 读到的） |
| 与 4.完善文档 | 完善文档「开发难点」节引用坑档案作追问素材 |
| 与 ai-tutoring 坑档案 | **业务不混**——question-analysis 坑只落题型分析/掌握度/向量收敛链路（学科门/题型识别/归并/累计平均/两域），ai-tutoring 的 OCR/流式/答疑护栏坑不进来 |

## 四、存量与增量

- 存量：`坑档案.md` J-QT1~8（向量写入延迟/编辑距离误并/PENDING 语义冲突/embedding 维度/alias miss/开思考拖慢/字段改名脱节/闭集外误判）
- 增量：新增坑从 J-QT9 起编号；提示词支持单坑追加/重写，不整篇重做
- 生成：`处理方案/提示词/坑-提示词.md`（真挖三端 git log 第一铁律 + 六段复盘 + 双证据）

## 五、写作要点

- 六段结构强制：问题现象 → 触发流程 → 根因分析 → 排查过程 → 解决方案&改动点 → 面试口述要点
- 面试口述要点段是坑档案独有高价值（技术权衡 + 踩坑收获），突出"默认值不信任""静默降级"这类可迁移教训
- 现象→根因→修复因果链自洽；元信息头 5 行标准（summary/权威度0.8/模块/COS路径/类别）
