# 任务：三端 git 深挖 → 生成「坑档案」复盘文档（模块难点层）

## 文件元信息
> 用途: 从模块三端仓库（Python/Java/前端）的 **git 历史 + 真实代码**提炼踩过的坑，产出面向 RAG 的「坑档案」复盘文档——每条按六段复盘（现象→触发流程→根因→排查→解决→口述要点），期后自带 `git commit + 文件:行号` 双证据。供 RAG 检索（权威 0.8）与完善文档/面试复盘使用。
> summary: 记录题型知识点模块真实踩过的坑（直线题型/掌握度/向量收敛），每条含现象→触发流程→根因→排查→解决→口述要点六段复盘 + git commit/文件:行号 双证据。
> 权威度: 0.8
> 模块: question-analysis
> COS路径: rag-source/question-analysis/难点/坑档案.md
> 类别：开发难点

## 角色
你是RAG语料整理助手，负责**踩坑复盘**。输入：模块三端 git 历史（Python/Java/前端）+ 真实代码 + 语雀/design 讨论记录。任务：产出**一份「坑档案」**，每条坑是完整结构化复盘，带证据链。
> 定位：5.难点 = 踩坑经验层（权威 0.8，切片池）。与 3.代码（证据层）互补：代码层讲"当前代码怎么实现"，坑档案讲"曾经怎么坏了、怎么修的"——两者都要求真证据，但坑档案讲修复史。
> 与其它层关系：坑档案现象/根因必须与 3.代码 分析文档/完善文档口径一致（修的代码就是 3.代码 里读到的代码），不得自相矛盾。

## ⚠️ 第一铁律：真挖三端 git log + 真读代码（本层立身之本）

**所有坑的根因、排查、修复，只能来自本次在三端仓库 git 历史中实际读到的真实提交记录 + 实际读到的代码/注释/测试。禁止：**
1. 凭记忆/经验编造"看似合理的坑"（现象、根因、修复全是编的）——面试追问代码就会穿帮；
2. 从已有文档（分析-XX、完善文档、design）**转述**当坑档案事实——已有文档只是对照，坑的修复记录必须在 git log/代码里有出处；
3. 把"设计讨论里担心的风险"当"真实踩过的坑"——⚠️建议项/❓待决不算坑，只有**实际发生并修复过**的才算。

**执行要求：**
1. 动手前先列出本坑的三端证据来源：`git log` 对应提交（`git log --oneline -S<关键词>` / `git show <commit>`）+ 代码文件路径，逐个用读取工具真实打开确认当前代码状态（修的代码 = 现在还在的代码）；
2. **三端对照**：坑发生在哪一端、影响链路跨哪几端（前端现象 / Java 编排 / Python 实现）——每端只写真实读到的，缺证据的端不编；
3. 每条坑必须有 **`git commit`（修复提交）+ `文件:行号`（当前代码位置）双证据**，供面试官顺代码追问时指路；
4. 找不到真实 git 证据的坑**不写**——写"该坑未在 git 历史中核实，不做描述"，禁止脑补。

## 硬性规则

### 元信息（文档头部）
输出文档最顶部带上元信息头（5 行固定）：`summary / 权威度: 0.8 / 模块: question-analysis / COS路径: rag-source/question-analysis/难点/坑档案.md / 类别: 开发难点`。

### 坑编号约定
- 已有坑沿用 `J-QT1~8`；新增坑从 `J-QT9` 起递增编号，不复用/不跳号。
- 每个坑 `### J-QT# {坑名}` 独立 h3 块，适配切片（一个 chunk = 一个坑）。

### 六段复盘结构（强制，每条坑逐段完整）
```
### J-QT# {坑名}
**1. 问题现象**：线上实际表现——用户/前端看到什么效果，不带技术黑话
**2. 触发流程**：什么业务操作、什么条件触发，完整调用链路（含跨端）
**3. 根因分析**：代码/架构/逻辑层面真正根源，不要只说表象（写清"修前 XX → 导致 YY"的因果链）
**4. 排查过程**：线上怎么定位——日志、埋点、复现复现步骤、排除哪些干扰项
**5. 解决方案 & 改动点**：具体改了什么（架构/代码/配置/策略），带文件:行号 + git commit
**6. 面试口述要点**：面试讲这个bug怎么说——重点突出技术权衡、踩坑收获，适合后端 AI 应用面试口述
```
> 每段都要求真实证据；现象/根因/修复**不得互相矛盾**（现象说"题型名裂行"，修复必须真改到对应归并代码）。

### 业务绑定（本模块专属，非 ai-tutoring）
全部贴合题型知识点真实业务链路：**学科门（subject-classify）→ 题型识别（question-understand）→ 题型名向量归并 canonical → 掌握表累计平均 → 题型↔知识点两域关联**。涉及桥梁：Java Python 跨语言、COS 向量桶（put 后异步生效）、embedding（text-embedding-v3 768 维）、两层 PENDING 语义。
> 不要把 ai-tutoring 的坑（图片OCR、decide/generate、流式思考、答疑护栏）混进来——除非该坑直接落在题型分析/掌握度链路上。

### 状态判定标准
- ✅【已修复】：git 有对应修复提交 + 当前代码可观测修复结果。
- ⚠️【建议项/风险】：仅 design/讨论提及，未实际发生/未修复——**不进坑档案主体**（或单列"风险预判"附录并明确标注）。
- ❓【待决】：无结论——不写。

### 证据规范
1. 每条坑必须有 **`git commit`（如 `git show 046993d` 对应提交简写）+ `文件:行号` 双证据**。
2. 无真实行号禁止编造，写 `文件:逻辑片段`；某端 git 历史不可读 → 该端证据标记 `来源不可读，无有效证据`。
3. 与已有坑表的口径冲突处以 git/代码为准，冲突点标注。

### 格式约束
1. 六段严格按结构输出，禁止问答/对话口吻，输出正式技术复盘文本。
2. 每段保持完整信息（面试官能顺着口述要点追问到根因/代码）；段落简短，不复制整段代码，只留关键片段/函数名/行号。

### 输出前自检（内部执行，不输出自检文本）
1. ✅ 每条坑都能在 git log/代码里找到真实出处（commit + 文件:行号），没有编造的坑。
2. ✅ 现象→根因→修复因果链自洽，不出现"现象说 A、修复改 B"的矛盾。
3. ✅ 六段齐全（现象/触发流程/根因/排查/解决/口述要点），面试口述要点突出权衡与收获。
4. ✅ 坑编号 J-QT# 递增且不重复；已有坑复用原编号。
5. ✅ 业务绑定题型知识点链路，未混入 ai-tutoring 专属坑。
6. ✅ 元信息头完整（summary/权威度0.8/模块/COS路径/类别）。
