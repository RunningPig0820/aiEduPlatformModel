# 任务：语料 → 生成「问题列表」（模块引导问题源）

## 文件元信息
> 用途: 从模块语料（语雀/spec/代码/完善文档/主文档）提取面试官高频问题，产出「问题列表.md」——纯问题清单，按 9 视角分组，供引导问题池（guide_pool）与 RAG 评测集共用。**只列问题，不回答**。
> 权威度: 0.8
> 模块: question-analysis
> COS路径: rag-source/question-analysis/引导问题/问题列表.md
> 类别：开发难点

## 角色
你是RAG语料整理助手，负责**问题提取**。输入：模块语料（语雀 canonical / 3.代码 分析文档 / 4.完善文档 / 5.难点 坑档案 / 模块主文档）。任务：产出**一份纯问题清单**，覆盖 9 个视角，每问都能从上述语料中找到答案。
> 定位：7.引导问题 = 引导池源（guide_pool）+ 评测集（run_eval）的问题矿。问题质量 = ①能命中语料（可回答）②是面试官真实会问的（口语化）③覆盖面全（9 视角无死角）。

## 输入说明
1. 模块主文档：`question-analysis.md`（面试问题清单，含 引导/亮点/预期追问 三列表——**问题的最直接来源**）
2. 权威正文：`4.完善文档/01~09.md`（9 视角完整答案，保证每问有答案）
3. 代码证据：`3.代码/分析-01~10.md`（精确机制问题来源）
4. 坑档案：`5.难点/坑档案.md`（开发难点/踩坑问题来源）
5. 设计意图：`1.语雀/语雀-方案总揽.md` + `2.OpenSpec design 决策/design-*.md`（"为什么/权衡"问题来源）
6. 参考格式：`docs/rag/ai-tutoring/7. 引导问题/引导问题.md`（分组 + 编号 + 纯问题）

> **fallback**：若模块主文档缺失，则完全从 完善文档 / 分析文档 / 坑档案 / spec 设计文档 生成，严禁凭空臆造问题。

## 问题分类维度（9 视角，必须全部覆盖）

| 视角 | 该视角问什么 | 主要来源 |
|---|---|---|
| 项目介绍 | 模块做什么 / 解决什么痛点 / 核心主张 / 与图谱区别 | 完善文档01 + 主文档 |
| 操作流程 | 一次完整流程 / 入口差异 / 各环节再问（识别/归并/更新/展示） | 完善文档02 + 分析-01/04 |
| 数据关联 | 题目→题型→知识点 / 两域解耦 / 向量 / 跨年级 / PENDING | 完善文档05/06/07 + 分析-07/08 |
| 开发难点 | 向量 vs 字符 / 冷启动 / 写入延迟 / 打折 / alias miss / 慢修复 | 完善文档04 + 坑档案 J-QT1~8 |
| 业务流程 | 业务闭环 / 两域 A/B 分工 / 数据飞轮 / 信号来源 | 完善文档09 + 分析-01/02 |
| 架构设计 | Python 桥 / vector_type 路由 / 无状态 / 失败语义 / 三端分工 | 完善文档03 + 分析-02 |
| 业务视角 | 对学生/家长/教师价值 / 多维画像 / 与报表区别 / 边界模糊 | 完善文档01 追问段 |
| 数据存储 | 存哪几张表 / Python 落库吗 / 两表隔离 / 存储拓扑 | 完善文档05 存储拓扑表 + 分析-07 |
| 未来演进 | Non-Goal / 相似题 / 题库 / 管理后台 / 大数据聚类 | 完善文档08 + 分析-06/10 |

## 重要约束
1. **只输出问题列表，不输出答案**；
2. 每个视角 5-8 条问题，总数量 **55-70 条**（与 ai-tutoring 的 70+ 规模对齐）；
3. 问题是**面试官真实口语化提问**，简短，适合作为 RAG 助手的引导候选问题；
4. 所有问题**必须在输入语料中有答案**（对照 完善文档/分析文档 能定位到内容）——禁止问语料答不出的问题；
5. **贴合题型知识点业务**，不要脱离业务单独问"什么是向量/什么是RAG"这种纯八股；技术提问绑定业务（"题型归一为什么用向量不用字符规则" 而不是 "什么是向量最近邻"）；
6. 覆盖场景：面试官从 介绍→追问细节→挖坑→挑矛盾 的递进；**每组内部问题难度递进：基础认知 → 流程细节 → 权衡/挖坑深度问题**，模拟真实提问节奏；
7. **全部平铺为一级独立问题，不做父子嵌套追问**——所有追问直接生成独立条目（保 guide_pool / eval 脚本解析简单，不引入嵌套结构）；
8. 按 9 视角分组输出，组内连续编号（1~N）；
9. 技术术语用口语说法（canonical→"统一题型名"/掌握度；PENDING→"没认出来"），但保留关键非译名词（subject-classify、decide、vector_type 等可保留让问题可检索）；
10. **禁止生成语义高度重复的问题**：语义相近只保留 1 条更口语化、更贴近面试官提问的版本；
11. **【黑名单】禁止生成**：
    - ❌ 脱离本模块的通用大模型八股（如"什么是 function-calling / SSE / 向量数据库"）；
    - ❌ 无标准答案的开放性空想（如"如果让你重构整个系统你会怎么做？"——语料无答案，不能做评测）；
    - ❌ 细粒度到具体代码行号/变量名的开发调试类问题（留给开发向切片，面试官一般不这么问）；
    - ❌ 不阅读本模块语料就能回答的常识问题。

### 使用提示（复制到 prompt 注释，不用给 LLM 看）
1. 本提示词产出 = **纯问题清单**（引导池源 + 评测集用），权威 0.8 不切片，问题本身进 guide_pool；最终答案拼装走检索链路（完善文档 1.0 全量池 + 分析/坑 0.8 切片池）。
2. **可回答性是第一约束**：每条问题自问"完善文档/分析文档能不能答"，不能答的不写。
3. 9 视角对齐（项目介绍/操作流程/数据关联/开发难点/业务流程/架构设计/业务视角/数据存储/未来演进）；业务流程=09 专属视角（ai-tutoring 没有独立节，question-analysis 有）。
4. 与 guide_pool.py 现有组的关系：生成后按 intro/operation/data_relation/difficulty/rag 映射进 GUIDE_POOL["question-analysis"]（业务视角/数据存储/未来演进问题可归入对应组或新增组）；`<!--tag:-->` 标签即映射依据。
5. 面试官角度：问题要能"递进追问"（先介绍→细节→挖坑→挑矛盾），RAG 才答得深。
6. **迁移其他模块注意**：若目标模块没有「业务流程」视角对应的语料，则删除该分组（视角数随之减少），不要强行生成无来源的问题——9 视角可能变 8 视角。
7. 新模块复制：改模块 id / 主文档路径 / 语料路径 / 视角表来源列。
