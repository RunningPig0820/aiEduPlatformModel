## 隐性坑与注意事项

- **识别失败不是错误**：空结果 → Java PENDING（低置信挂起，走澄清卡），不编造题型名。（`question_understand.py:109-111`）
- **两层 PENDING 分开**（语雀-方案设计2-问题1 坑2）：analyze-question 的 PENDING = "题型没认出来"；getMastery 的 PENDING = "题型已练、知识点待确认"。Python 侧只产生前者（空结果），后者在 Java。（`models/tutoring.py:170-176`）
- **"知识点："行要单独拆**：混进 topic_labels 会把知识点当题型。（`question_understand.py:60-64`）
- **topic_hint 冷启动跳过**：题型库为空时 `_build_system` 不注入词表，模型自拟题目名动态涌现。（`question_understand.py:48-50`）

## 对账要点（方案 vs 代码 复盘）

**1. 文本题识别 → ✅ Java 承担**：原始方案对"文本题怎么识别题型"未明确。实际落地：Python 无此端点，文本题由 Java `KpQuestionAnalyzer` 自研识别器承担。业务影响：Python 只覆盖图片题视觉识别，文本题识别归属 Java，两侧职责按题图/文本分界清晰。

**2. WEAK 状态 → ⚠️翻转（WEAK→PENDING 降级）**：接口契约上 WEAK 状态在旧设计中曾返回 RESOLVED conf=70。实际落地：Python 侧不落 RESOLVED 状态，识别不出时空 labels 返回，Java 侧降级为 PENDING（挂起走澄清卡）。业务影响：低置信不再给"假装确定"的结果，转为待确认流程，规避错误题型误导。

**3. 题型名上限 → ✅落地**：方案口径 `KpQuestionAnalyzer` 题型名 1~5 个。实际落地：`_MAX_TOPIC_LABELS=5` 硬上限，与 Java 1~5 保持一致。业务影响：两侧上限对齐，跨端数据不越界。

**4. topic_hint 词表 → ✅落地**：设计 D1/D3 建议用题型库词表收敛命名漂移。实际落地：`topic_hint` 注入 system prompt 作为"参考题型名词表"（"优先从这些名字里选，词汇不足可自拟"）。业务影响：从源头压低题型名变体漂移，冷启动库空时仍可自拟动态涌现。
