## 业务描述与业务场景

**业务描述**：一道题的「作答记录 + 掌握度 + 会话状态」最终存在哪、怎么回流给下一次决策——这是业务数据的完整落库与回读链路，也是"掌握度可追溯"的根基。

**业务场景**：
1. 学生答完一道「鸡兔同笼」→ 题目落题目表（事实源，可回查原题），掌握度更新掌握表——下次看「掌握度页·查看原题」能跳到那一次作答。
2. 多轮答疑中会话状态在 Java Redis，学生断开重连会话不丢；AI 服务本身无状态，任何一轮都可被新机器接管。
3. 系统把学生已有掌握度快照回流给下一次 decide——"记得你以前这类型不行"，薄弱题型优先讲解。

## 职责

数据流的**全局视角**：Python 侧 stateless 不落业务库，只产出信号 + 向量原语；落库/存储全在 Java（题目表 + 掌握表 + Redis 会话 + 向量桶）。

## 高层业务调用链（数据流转与落库）

```mermaid
flowchart TD
    FE[前端] -->|贴题/答疑| JAVA[Java 编排]
    JAVA -->|①学科门| SC[subject-classify → 学科闭集]
    JAVA -->|②图片题型识别| QU[question-understand → topic_labels + question_kps]
    JAVA -->|③每轮决策| DECIDE[decide SSE → ActionMeta]
    DECIDE -->|mastery_signals 题型三档| SIGN[信号]
    DECIDE -->|eval.correct| EVAL[对错信号]
    QU -->|题型名| VEC[vector put/query → COS 向量桶 唯一存储]
    SIGN -->|落库| Q1[(t_student_question_record 题目表事实源)]
    EVAL -->|结算累计平均| Q2[(t_student_topic_mastery 掌握表)]
    SC -->|学科闭集| Q3[(会话 Redis)]
    Q1 -->|查看原题 session_id| FE2[掌握度页跳转题目]
```

**文字链路复述**：前端把题目/答疑请求发给 Java 编排层；Java 依次调用三路下游——① `subject-classify` 得学科闭集，② `question-understand` 得 topic_labels + question_kps 并取题型名写入 COS 向量桶（put/query，向量桶是 Python 唯一存储），③ 每轮 `decide` 走 SSE 返回 ActionMeta。decide 产出的 mastery_signals（题型三档）落 `t_student_question_record` 题目表作事实源，eval.correct 对错信号结算累计平均落 `t_student_topic_mastery` 掌握表；学科闭集存会话 Redis。题目表以 session_id 关联原题，掌握度页「查看原题」据此跳转。
