## 业务描述与业务场景

**业务描述**：题型（解题模式）与教材知识点（课程概念）是两个不同实体：**掌握度锚题型**，题型↔知识点的关联映射独立维护，两者互不污染——这样「我会鸡兔同笼」和「鸡兔同笼对应教材哪个知识点」是两条干净的业务线。

**业务场景**：
1. 学生在知识点总览页看知识地图、题目命中题型后想关联到教材概念——映射来自运营后台手动维护（域 B 独立），AI 服务不碰图谱，不脏化权威数据。
2. 语法调用只"顺带"输出题目知识点（question_kps）作展示；真正的题型↔知识点映射在 Java 派生层查表只读，使命中则给权威分布、未命中则空知识点待补。
3. 答题信息不出现在 Neo4j 权威图谱上——图谱只被"借结构"展开，衍生关系全在 MySQL 派生层，坏了不波及时权威数据。

## 职责

Python 侧**无任何题型↔知识点映射逻辑**，且被显式禁止（`models/tutoring.py:73-76`）。图谱点亮是独立变更（kp-matching-lightup）；题型↔知识点关联放 Java 派生层（查表只读 + ADMIN 手动维护，域 B 独立化）。

## 高层业务调用链（题型↔知识点关联，域 A/B 解耦）

```mermaid

    subgraph 域A 题目→题型 本期
    A1[题目] -->|decide| A2[mastery_signals 题型三档]
    A2 -->|topic_label| A3[掌握表 canonical key 累计平均]
    end
    subgraph 域B 题型→知识点 独立维护
    B1[题型库 t_kp_question_type] -->|findByTopicLabelOrAlias| B2[识别题型查映射]
    B2 -->|命中| B3[返回权威分布 只读]
    B2 -->|未命中| B4[仅题型+canonical+空知识点 不挂起不写obs]
    B3 -->|ADMIN 手动维护| B5[题型↔知识点映射]
    end
    A3 -.canonical 名对接.-> B2
    Python -.仅输出信号 question_kps 顺带.-> A2
    Python -.显式禁止做映射.-> X[models/tutoring.py:73-76]
```

**文字链路复述**：域 A（本期，题目→题型）：题目 → decide → 输出掌握度题型三档信号（mastery_signals）→ 以 topic_label 进掌握表按 canonical key 累计平均。域 B（独立维护，题型→知识点）：题型库 t_kp_question_type → findByTopicLabelOrAlias 识别题型查映射 → 命中返回权威分布（只读）/ 未命中返回"仅题型+canonical+空知识点"（不挂起、不写 obs）→ ADMIN 手动维护题型↔知识点映射。两域靠 canonical 名对接（A3 -.canonical 名对接.-> B2）；Python 仅"顺带"输出 question_kps 信号到 A2、且显式禁止做映射（models/tutoring.py:73-76）。职责归属：Python = 无状态信号源（无映射逻辑）；Java 派生层 = 查表只读 + ADMIN 维护；Neo4j = 只借结构不写入。
