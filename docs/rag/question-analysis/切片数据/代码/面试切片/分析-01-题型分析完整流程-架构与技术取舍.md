## 架构分工（微服务怎么分）

系统分两端协作：
- **Python AI 桥（无状态）**：只做 LLM 决策 + 向量原语，不落任何业务库。四个能力端点——学科门判定（K12 学科闭集，识别不了返回空放行）、图片题题型识别、答疑决策流式接口（输出动作 + 掌握度信号）、题型名向量存查。
- **Java 平台层**：编排 + 题型名归一到 canonical + 掌握度计算落库 + 答疑会话存储（Redis）。题型↔知识点映射在 Java 派生层。

**核心边界**：Python 无状态可水平扩展，状态全在 Java（Redis/掌握表/题目表）；Python 显式禁止做题型↔知识点映射，防止污染权威图谱。

## 关键机制

### 题型名归一（动态聚类）
- 学生题型名是 LLM 输出的弱标注（鸡兔同笼/鸡兔同笼问题/假设法会飘）。
- 解法：题型名向量查最近邻（cosine），distance ≤ 0.2 归并到已有 canonical；无近邻则首题建锚、动态涌现。**canonical 是"长出来的"，不是预置的**。
- 落库全在 Java：题目表（事实源）+ 掌握表（canonical key + 累计平均）。

### 降级策略（多类兜底）
- 学科门/图片识别：慢或失败快速返回空结果，Java 降级处理（非数学跳过 / 识别失败 PENDING 挂起），**不让调用方无限等**。
- 决策流式接口：原始流失败降级非流式四段结构化管线；换题信号直接短路返回 switch（不调 LLM，确定性 100%）。

## 设计要点

- **Python 纯智能无状态**：不落库，所有状态在 Java Redis/掌握表；Python 只做 LLM + 向量原语——可水平扩展、单次调用可重试。
- **信号跟题目走，不跟题型走**：PENDING 题型照常采信号落题目表，归属确定后再聚合——不因题型待定丢数据。
- **失败语义分治**：业务判定（学科门/题型识别）吞异常降级空结果（宁返回空不阻塞）；向量基础设施错误冒泡让 Java 感知后降级——两类失败语义刻意不对称。
