## 隐性坑与注意事项

1. **文本题题型识别在 Java，Python 只有图片题端点**——容易被误认为 Python 收全部题目识别，实际文本题是 Java 自研识别，图片题才走 Python。跨端职责要讲清。
2. **PENDING 不是错误**：识别失败 = 返回空结果 → Java 降级 PENDING 挂起（走澄清卡），不是 Python 抛异常。识别失败是业务判定，不是故障。
3. **掌握度信号只能在答疑链路产生**：decide 输出掌握度信号，题型分析页只记题不产生对错信号——因为只有答疑有真实的答题行为。
4. **换题短路易误判**：学生换新题时 Java 发换题信号，直接返回 switch 收尾，这是确定性逻辑不是模型决策——排查时别当 bug。

## 方案 vs 落地的复盘（原始设计 → 实际实现 → 影响）

**掌握度主体翻转：知识点 → 题型**
原始方案设计掌握度基于"知识点 URI"计算；落地时做了重大调整，改为基于**题型名（canonical）**计算掌握度。影响：学生掌握的是"解题模式"（鸡兔同笼类题做得怎么样），不是抽象知识点；题目天然可聚到题型、可打分可观测，落库不裂行。

**掌握度数值翻转：离散四档 max 单调不减 → 连续 0-100 累计平均**
原始方案用 mastered/practicing/struggling 三档、答错不降分（max 单调不减）；落地改为**连续百分比累计平均**。影响：能算"练了几道、答对几道"的可解释数字，答错会真实反映，避免掌握度虚高。

**canonical 来源翻转：预置题型池 → 动态涌现**
原始方案预置题型池、新名归进池；落地改为**首题建锚、后续向量最近邻自动靠拢**。影响：没有题库也能跑，题型从学生做题数据里"长出来"。

**聚集依据翻转：题目向量为主 → 只题型名向量单信号**
原始方案想题目向量为主 + 题型名向量为辅；落地只用**题型名向量**做归并。影响：相似题检索本期不做，掌握度/动态聚集用题型名向量足够。

**文本题识别接口契约：方案未明确 → Java 自研承担**
原始方案未明确文本题由谁识别；落地 Python 无此端点，Java 自研题型识别器承担。影响：跨端边界更清晰——Python 只管图片题 + LLM 决策，文本题识别归 Java。

**掌握度信号字段改名：kp_label → topic_label**
原始信号字段叫 kp_label（知识点标签），落地改为 topic_label（题型标签），Java 用 @JsonAlias 兼容旧字段。影响：避免后端题型库混入知识点名，整条链路口径统一为题型。
