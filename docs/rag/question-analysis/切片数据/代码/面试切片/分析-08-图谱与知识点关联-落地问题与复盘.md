## 隐性坑与注意事项

1. **Python 收 question_kps 但不能反查图谱**：question_kps 只是模型顺带输出，不送去匹配；匹配/映射全在 Java 派生层。
2. **PENDING 语义更新**：getMastery 的 status=PENDING 不再来自 obs，改为"题目记录有但 canonical 未归属"（Java 侧）。
3. **停用自动涌现链路**：obs 共现→自动关联、挂起、学生 vote、聚合批处理、覆盖度派生——已停用，前端已不消费。

## 方案 vs 落地的复盘（原始设计 → 实际实现 → 影响）

**Python 映射职责翻转：早方案 Python 桥 → Python 显式禁止，Java ADMIN 维护**
原始方案 Python 做题型↔知识点映射；落地 Python 显式禁止，映射移到 Java ADMIN 维护接口。影响：权威图谱零写入红线，域名 B 独立化，Python 保持纯智能。

**自动涌现链路翻转：obs 共现自动关联 → 停用，改手动/只读**
原始方案 obs 共现自动关联 + 聚合批处理；落地全部停用，改查表只读 + ADMIN 维护。影响：避免自动关联污染权威图谱，业务不成熟时手动更稳。

**PENDING 语义翻转：obs 挂起（知识点待确认）→ 题目记录有但 canonical 未归属**
原始方案 PENDING 来自 obs 挂起；落地改为"题目记录有但 canonical 未归属"。影响：语义更准确，识别层 PENDING 与掌握度层 PENDING 分离。

**Neo4j 写入确认（✅零写入）**
Neo4j 只借结构不写入——权威图不被污染，关联错只在派生层可纠错。
