**要点**：原始问答材料先汇总成方案总揽再入库——问答口吻不适合 RAG，汇总成正式综述后切片质量高。

### 第 ② 步：文档对齐（方案 vs 代码）

产出 `方案-代码对账.md`，本模块核心口径翻转 6 处：

| # | 项 | 方案 → 代码现状 |
|---|---|---|
| 1 | 掌握度主体 | 知识点 URI → **题型**（canonical 题型名） |
| 2 | 掌握度数值 | 离散四档 max 单调不减 → **连续 0-100 累计平均** |
| 3 | canonical 来源 | 预置题型池 → **动态涌现**（首题建锚） |
| 4 | 聚集依据 | 题目向量为主 + 题型名向量为辅 → **只题型名向量单信号** |
| 5 | PENDING 语义 | obs 挂起（知识点待确认）→ **题目记录有但 canonical 未归属** |
| 6 | 字符归一 | 编辑距离 ≤1 近字归并 → **移除**（会误并"一元一次/一元二次"），全交向量层 |

### 第 ③ 步：完善文档 8 节

按第三节标题写，权威 1.0 是主答案，质量最关键。写作时以 `语雀-方案总揽.md` 为动机源、`3.代码/分析-*.md` 为落地真值、design 为方案口径。

### 第 ④ 步：切片

**语料整理方法论（本模块沉淀的关键经验）：**

1. **语雀问答材料先汇总成总揽再进语料**——问答口吻（来回质疑/提问者视角）不适合 RAG，先整理成正式综述，切片质量才高。
2. **问题列表先于完善文档**——把语雀里待解决/待决策的事项先提炼成问题列表，让"已定/建议项/待决"在写正文前浮出，正文不臆造未决事项。
3. **决策/选型迁出为独立文档**——决策记录/方案选型对比这类表格化条目，独立成文 + 切片后每块就是"一条决策/一组选型"，RAG 命中粒度最好；总揽保持叙述性综合，只留指针，不双维护。
4. **提示词库单任务独立**——每个文档一个独立提示词（决策/选型/演进/边界/联调 + 辅助A增量/B校验/C术语），各自自包含通用底座（术语统一/状态判定/证据规范/自检），放一起生成容易格式漂移，剥离独立后单任务生成质量更好。
5. **RAG 块级结构（语料梳理核心）**——条目型文档每条一个 `### H3` 独立块 + 顶部 `> 状态` + `> 检索摘要`（1-2 句作向量锚点）+ 内部窄表/分级列表 + 文档末尾附录标注"仅供人工查阅，不参与 RAG"——**一个 chunk = 一条决策/选型/场景/问题/阶段**，适配标题切片，命中粒度最好。禁止宽横向大表作主体（切片行被切断、语义断裂）。
6. **双池入桶**——完善文档（权威 1.0）直接整篇进全量池（一个问题=一节完整答案）；语雀/OpenSpec/坑/引导（0.7~0.8）切片进切片池（细粒度块）。

## 九、实际操作顺序实录（2026-08-26~27，按真实发生顺序，顺序=方法论精华）

> 本实录记录第一轮语料梳理**真实执行顺序**（含迭代/纠错）。顺序本身就是关键经验——哪些先做、哪些后做、为什么迭代，都影响结果质量。

### Phase 1 语雀整理（先汇总，后提炼）

| 步骤 | 做了什么 | 关键经验 |
|---|---|---|
| ① | 语雀 11 份问答 → **方案总揽**(正式综述, 去问答口吻) | 先汇总成综述再进语料；问答口吻不适合 RAG |
| ② | 语雀问题 → **问题列表**(30 题, ✅/⚠️/❓ 状态) | 问题先于正文，让待决事项浮出，正文不臆造 |
| ③ | 代码深读(Explore agent) → **分析-01~10**(落地真相+行号) | 落地真相先行，对账才有依据 |

### Phase 2 完善文档（对账后写正文）

| 步骤 | 做了什么 | 关键经验 |
|---|---|---|
| ④ | 方案 vs 代码 → **方案-代码对账**(6 处口径翻转) | 先知道"方案≠代码"再写正文 |
| ⑤ | **完善文档 8 节**(权威 1.0, 为什么→方案→落地真相→追问防御→证据) | 权威正文，直接全量入库 |

### Phase 3 补充视角文档（提示词的迭代：合并→块化→剥离→删索引）

| 步骤 | 做了什么 | 关键经验 |
|---|---|---|
| ⑥ | 建提示词库(合并文件) → 生成 5 文档 + 术语表 | 初版是宽表 |

| ⑧ | **提示词剥离独立**(决策→边界→选型→演进→联调→辅助A/B/C) | 放一起生成格式漂移，单任务独立质量更好 |
| ⑨ | 删总索引(独立提示词自包含) | 导航价值有限，文件名一一对应 |

### Phase 4 spec 处理（评估→删→恢复→归档→补充语雀方案）

| 步骤 | 做了什么 | 关键经验 |
|---|---|---|
| ⑩ | 看 2.OpenSpec design 决策 → 找每个 spec 解决什么问题(问题地图) | spec 的 Context = 设计动机 = 语料"为什么"源头 |

### Phase 5 目录重组（语料层分离）

| 步骤 | 做了什么 | 关键经验 |
|---|---|---|
| ⑰ | `处理方案/`(readme+提示词) + `原来的文件/`(原始素材归档) + `design-*.md`(spec 自身 RAG 文档,根目录) 分层 | **顶层=进库整合文档，原来的文件/=证据源，处理方案/=工具，design-*.md 根目录/=spec 自身进池文档** |

### 顺序方法论总结

1. **先汇总再提炼**：语雀问答 → 总揽(综述) → 问题列表(待决浮出)，顺序不可反。
2. **落地真相先行**：代码深读 → 对账 → 才写权威正文，防止正文臆造。
3. **提示词先合并后剥离**：初版合并生成发现格式漂移 → 剥离独立 → 删总索引，迭代方向是"越独立越好"。
4. **RAG 块级结构是后补的认知**：宽表不行 → 豆包格式(###+状态+检索摘要+附录)，这是语料质量的转折点。
5. **spec 先价值评估再处置**：找问题地图 → 评估删 → 用户纠正恢复 → 归档 → 建增量桥，顺序是"先理解价值再动手删"。
6. **spec 双轨：补充语雀方案 + 自身成文进池**：OpenSpec design 的 Context/Decisions = 语雀方案"为什么"的增量来源，也是自身 RAG 文档的信息主体——① 跑 `spec信息补充提示词` 把收敛事实折入语雀 canonical（决策/选型/场景/问题/演进，递增编号+证据）回答"为什么"；② 跑 `spec文件整理提示词` 把每份 design 各自成文 `2.OpenSpec design 决策/design-*.md`（100% 保留 Migration/Risks/OpenQuestions，summary 写充实作检索锚点）进池补细节。原始 design 归档 `原来的文件/` 仅人肉溯源。
