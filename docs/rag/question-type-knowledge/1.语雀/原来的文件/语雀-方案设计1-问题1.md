现在方案已经完成落成 能整体来帮我梳理一下这个方案 主要梳理的几个点

1. 题目和知识点如何绑定的

2. 题型和知识点如何派生关联的

3. 如果题型和知识点和关联错误后 后续数据清洗可以纠正吗 而且不影响原来的数据

因为如果数据频繁修改其实是一个很吃数据清理的准确性

4. 还有没有我没有了解的点


先看全局：方案的骨架

```plain
                   ┌─────────────────────────────────┐
                   │   权威图谱（只读，永不写）          │
                   │  Neo4j 教育局数据 + kg-sync 镜像   │
                   │  节点 key = TextbookKP URI         │
                   └───────────────▲──────────────────┘
                       只「借」kp_uri 做钩子（不写入）
                   ┌───────────────┴──────────────────┐
                   │   派生层（MySQL ai_edu_learning，可写可改）│
                   │                                    │
                   │  ① t_kp_derived_obs    个体观测（无限）  │
                   │  ② t_kp_question_type  题型库主表（有限）  │
                   │  ③ t_kp_question_type_kp 题型↔知识点分布 │
                   └───────────────▲──────────────────┘
                                   │ 解析管线命中后落库
                   ┌───────────────┴──────────────────┐
                   │   掌握度 t_student_kp_mastery（单源）│
                   │   前端图谱按 URI 匹配 → 点亮        │
                   └──────────────────────────────────┘
```

  核心设计哲学就一句话：「无限的业务事实」和「有限的权威结构」彻底分开。题目/题型是无限的（鸡兔同笼、相遇
  、浓度…无穷），教材知识点是有限的。所以无限的东西永远不写进权威图，只在 MySQL 派生层里“借用”权威图的
  URI。

---

1. 题目和知识点如何绑定？

  绑定发生在解析管线（TutoringKpResolverImpl 重写），4 步按序命中：

  AI 答疑 decide 输出题型 label（如“鸡兔同笼”）+ 学生年级
          │
          ▼
  ① kg 镜像 精确/LIKE 匹配          ——命中——▶ 绑定完成（0 成本，现有逻辑）
          │ 未命中
          ▼
  ② 题型库 年级匹配                   ——命中——▶ 绑定完成
     （查分布桶：该题型在你这个年级，哪个 kp 占比最高）
          │ 未命中
          ▼
  ③ LLM 消歧                        ——高置信——▶ 绑定完成
     （label + 候选知识点列表 → 选最匹配 + 给置信度）
          │ 低置信
          ▼
  ④ PENDING 挂起                    ——▶ 不绑定，进入待确认队列

  绑定的产物是一条观测记录（t\_kp\_derived\_obs 一行）：

  ┌──────────────────────────────┬────────────────────────────────┐
  │             字段             │              含义              │
  ├──────────────────────────────┼────────────────────────────────┤
  │ student\_id                   │ 谁                             │
  ├──────────────────────────────┼────────────────────────────────┤
  │ topic\_label                  │ 什么题型（“鸡兔同笼”）         │
  ├──────────────────────────────┼────────────────────────────────┤
  │ kp\_uri                       │ 绑到了哪个知识点（假设法 URI） │
  ├──────────────────────────────┼────────────────────────────────┤
  │ student\_grade                │ 解析时他的年级（快照）         │
  ├──────────────────────────────┼────────────────────────────────┤
  │ confidence / source / status │ 置信度 / 来源 / 状态           │
  └──────────────────────────────┴────────────────────────────────┘

  关键点：“绑定”= 新增一条指向权威图 URI 的观测，而不是改动知识点表本身。

  年级锚是绑定的灵魂：同一个“鸡兔同笼”，四年级绑「假设法」，七年级绑「二元一次方程组」。年级是强先验但非
  硬规则——跨年级薄弱被当成 feature（一个七年级学生卡在四年级的假设法，这本身是重要信号）。

2. 题型和知识点如何派生关联？

  这是两层派生，从无限收敛到有限：

  个体观测（无限，每个学生每道题一条）
      │  按 topic\_label 跨学生「共现聚合」
      ▼
  题型库（有限精选，一个题型一条）
      │  审核
      ▼
  STABLE 稳定题型（进入解析先验，服务全体学生）

  聚合规则：

  ┌───────────┬───────────────────────────────────────┬──────────────────┐
  │   阶段    │               触发条件                │       说明       │
  ├───────────┼───────────────────────────────────────┼──────────────────┤
  │ CANDIDATE │ 同一题型 ≥3 名学生 且 总命中 ≥5       │ 自动，阈值可配置 │
  ├───────────┼───────────────────────────────────────┼──────────────────┤
  │ STABLE    │ 审核通过 + ≥10 名学生 且 近30天仍增长 │ 人工门禁         │
  └───────────┴───────────────────────────────────────┴──────────────────┘

  题型 ↔ 知识点是 1:N，用年级分布桶存：

  「鸡兔同笼」题型
     ├─ 假设法         (年级 4-6, 38人)  ratio=64%
     └─ 二元一次方程组 (年级 7-8, 21人)  ratio=36%

  解析管线第②步就是查这张分布表，按学生年级取占比最高的 kp。这就是“大数据手段整理”的雏形——多数同学在同一
  知识点下挂了相同题型，就沉淀成“这个知识点的题型”，但业务隔离、不污染权威图。

3. 关联错了能纠正吗？会不会影响原数据？（你最关心的点）

  结论：能纠正，且设计上专门为“可纠错 + 不脏数据”做了 6 层保障。

  3.1 能纠正——两条路径

  ┌──────┬────────────────────────────────────┬────────────────────────────────────────┐
  │ 路径 │                触发                │                  动作                  │
  ├──────┼────────────────────────────────────┼────────────────────────────────────────┤
  │ 自动 │ 维护闭环周期任务检测到冲突         │ 高置信 → 自动重判更新；低置信 → 转人工 │
  ├──────┼────────────────────────────────────┼────────────────────────────────────────┤
  │ 人工 │ 挂起审核管理面（GET/POST pending） │ 管理员确认正确的 kp\_uri                │
  └──────┴────────────────────────────────────┴────────────────────────────────────────┘

  冲突信号自动来自 4 处，不用人盯：

1. decide 诊断冲突：LLM 说“卡在假设法”，但观测记了二元一次方程组
2. 掌握度矛盾：该生二元一次方程组已 mastered，却还在鸡兔同笼上 struggling 且归到它
3. 年级分布异常：某题型在某年级段出现非预期尖峰
4. 低置信：confidence < 阈值直接重判

  3.2 不影响原数据——这是方案的重心，逐条拆

  你担心“频繁修改很吃数据清理的准确性”，方案就是用这几条把“修改”的代价压到最低：

  ① 权威图零写入（最硬的一道防线）
  错误永远只发生在 MySQL 派生层。Neo4j 和 kg-sync
  镜像只读，怎么改派生层都不会脏到教育局的权威数据。你的“原数据”（权威图谱）物理上就不可能被污染。

  ② 观测是“打标重判”，不是“覆盖删除”
  NEW ──▶ RESOLVED ──▶ CONFLICTED ──▶ READJUDICATED（重判改对）
                                └────▶ HUMAN\_REVIEW（转人工）
  重判时更新该行 kp\_uri + status=READJUDICATED，保留 first\_seen\_at 时间线。改错了也留痕，能回溯。

  ③ 掌握度回退：打标 MIGRATED + 人工复核，不自动删
  这是最关键的防“误伤”设计。如果解析把「二元一次方程组」错判成「假设法」，错记在假设法上的掌握度不自动删—
  —因为自动删可能丢掉真实信号。只打标 MIGRATED + 记迁移日志 +
  挂人工复核。数据宁可“暂存可疑”，也不“误删真实”。

  ④ UNIQUE 去重，避免重复膨胀
  UNIQUE(student\_id, topic\_label, kp\_uri)。同生同题型同 URI 再次命中，只
  occurrence\_count+1，不建新行。所以“命中频繁”≠“数据频繁改”，大部分只是计数器 +1。

  ⑤ source 溯源 + 保守原则
                                └────▶ HUMAN\_REVIEW（转人工）
  重判时更新该行 kp\_uri + status=READJUDICATED，保留 first\_seen\_at 时间线。改错了也留痕，能回溯。

  ③ 掌握度回退：打标 MIGRATED + 人工复核，不自动删
  这是最关键的防“误伤”设计。如果解析把「二元一次方程组」错判成「假设法」，错记在假设法上的掌握度不自动

  后续所有学生解析都跟着修正。这就是你说的“共享维护”——一次纠错，全局受益，而不是每条数据都要单独清理。

  3.3 一个诚实的边界

  有一个点我得点明：人工 confirm 本身也是可能错的。如果一个管理员把「鸡兔同笼」错误确认到了假设法，这个错误
  会通过题型库先验“放大”给所有学生。但兜底是——它仍然在派生层、仍然可再次被冲突检测 +
  重判纠正、仍然不碰权威图。所以错误的影响被限制在派生层内 + 可再次纠错，不会造成不可逆损伤。

4. 你可能还没了解的点

  我挑几个方案里“藏得比较深、但影响你决策”的点：

  ┌─────┬──────────────────┬─────────────────────────────────────────────────────────────────────────────┐
  │  #  │        点        │                             为什么你可能没注意                              │
  ├─────┼──────────────────┼─────────────────────────────────────────────────────────────────────────────┤
  │ 1   │ 挂起根本不落掌握 │ 解析失败/挂起的 label 不写 t\_student\_kp\_mastery，只在前端渲染“疑似待确认”虚 │
  │     │ 度               │ 线态。这是“不污染”的最干净实现——宁可看不到，也不给你一条假数据。            │
  ├─────┼──────────────────┼─────────────────────────────────────────────────────────────────────────────┤
  │ 2   │ 两维显示模型     │ 掌握度显示 = 掌握值(75/50/25) × 置信档位(确定/疑似)。一个“疑似”的薄弱点，视 │
  │     │                  │ 觉上是虚线+角标，不会被当成“确认薄弱”渲染成红色。                           │
  ├─────┼──────────────────┼─────────────────────────────────────────────────────────────────────────────┤
  │ 3   │ 掌握度“只升不降” │ 现有掌握度单调策略（只升、显式纠正才降）本期保持不动。错解析回退只打标，本  │
  │     │ 策略不变         │ 期不做自动迁移——迁移是 Open Question，默认留到后续。                        │
  ├─────┼──────────────────┼─────────────────────────────────────────────────────────────────────────────┤
  │     │                  │ 题型库的未来消费方：变式题生成、错题本分组、薄弱点溯源——全是                │

  │     │ 待你拍板         │                                                                             │

  │     │                  │ 聚合后归档“控制，但分表/清理是后续技术债，本期没做。                        │

  ▎ 影响原数据靠“权威图零写入 + 打标而非删除 + 掌握度不自动删 +
  ▎ 保守自动改“四重保障——错误永远被困在可变的派生层内，且可再次纠正
