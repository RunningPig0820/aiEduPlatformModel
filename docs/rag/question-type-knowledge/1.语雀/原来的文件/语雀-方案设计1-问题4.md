告诉你是鸡兔同笼问题 和鸡兔同笼 都大致说明的是一个题型 我们现在的设计是可以完成 相似知识点的挂靠吗

  鸡兔同笼）能不能挂靠到同一知识点」。让我先把现有代码里各层的真实行为确认清楚，再回答。

⏺ 代码确认完毕。你的直觉是准的——现状是「半挂靠」：能挂到同一知识点，但不能合并相似题型名。让我把三层路
  径完整梳理出来。

  现状：挂靠分三层，终点收敛、题型名不合并

  一个题目进来，resolve(题型名) 依次走三条路，终点（知识点）是收敛的，但题型名不合并：

  题目文本
     │ 题目理解（Python decide 或独立 LLM）
     ▼
  题型名 “鸡兔同笼问题”
     │
     ├─ ② 题型库 findByTopicLabel(“鸡兔同笼问题”)  ← 逐字精确！题型库有这个条目 →
  按条目挂靠（含年级分布/ratio）
     │      “鸡兔同笼问题” 和 “鸡兔同笼” 是两条目，互不相干
     │
     ├─ ① mirror exact/LIKE “鸡兔同笼问题”  ← 教材知识点一般叫“鸡兔同笼”，“问题”后缀精确/LIKE 大概率
  miss
     │
     └─ ③ LLM 两段式兜底：LLM 生成候选知识点名 → 镜像校验
            题型名 → “鸡兔同笼”(知识点名) → 镜像命中 → 挂到同一点       ← 这里两个变体收敛了！

  关键点：③ 的 LLM 两段式是「知识点名」层面的收敛——不管题型名叫「鸡兔同笼问题」还是「鸡兔同笼」，LLM
  最终都会把它们映射到镜像里的同一个教材知识点（如「数学广角—鸡兔同笼」）。所以挂靠的终点是收敛的。

  真正的缺口（你问对的地方）

  问题出在 obs 分桶和聚合：aggregate() 用 groupingBy(getTopicLabel)
  逐字聚类（KpQuestionTypeAggregationService:69），TopicKeyNormalizer 故意不剥离「问题」后缀（design
  Decision 17：同义词聚类留大数据阶段）。于是：

  obs:  学生A “鸡兔同笼问题”→KP  学生B “鸡兔同笼问题”→KP    学生C “鸡兔同笼”→KP   学生D “鸡兔同笼”→KP
          ↓ 分桶                                ↓ 分桶
       bucket(“鸡兔同笼问题”) 学生=2 <3阈值 ✗      bucket(“鸡兔同笼”) 学生=2 <3阈值 ✗

  两个变体都达不到 CANDIDATE 阈值（≥3 学生/≥5 命中）——信号被稀释了。就算都够阈值，也会建成两个并行的
  CANDIDATE，指向同一批知识点。前端「题型分析」页一旦上线，学生就会直接看到这些重复题型。

  收敛方案：聚合时按「kp 分布重叠」合并 + 别名表

  这不是要推翻 Decision 17（LLM 同义词聚类仍留大数据），而是把确定性的廉价部分提前：

  聚合建新 CANDIDATE 前：
    findByTopicLabel(label)          ← 逐字命中 → 更新现有条目（现状）
    miss → 与现有题型比 kp_uri 集合重叠 ≥ ~70%
          │ 是 → 不新建：label 记为现有题型的「别名」+ 桶观测折叠进现有分布
          │ 否 → 新建 CANDIDATE（现状）

  数据模型：t_kp_question_type_alias(alias_label UNIQUE, question_type_id FK)
  查询：findByTopicLabel(label) → findByTopicLabelOrAlias(label)（resolve ② 和聚合都改这一处）

  效果：三个变体 → 一个题型 → 一套 kp 分布。resolve
  时不管叫「鸡兔同笼」还是「鸡兔同笼问题」都命中同一先验；学生 vote 的 topicLabel 也会落到同一个
  canonical 题型，不再制造重复条目。成本：1 张别名表 + 1 个查询方法 +
  聚合逻辑加一段重叠判断，确定性、无 LLM、在线路径零负担。
