## 一、存储选型

### 选型1：派生层存储方案选型
> 状态：✅ 已落地
> 检索摘要：派生层最终选用MySQL作为主存储，禁止写入权威Neo4j图谱，规避无限题型空间导致的图爆炸、图谱污染问题，Neo4j仅按需阶段性物化。

- 选型场景：题型派生数据、观测数据、掌握度数据存储方案选择
- 候选方案A：MySQL 派生层
  - 方案A优劣：读写速度快、支持事务、便于数据审核；支持无限题型空间，可写、可改、可回滚，完全隔离权威图谱。
- 候选方案B：Neo4j 物化扩展层
  - 方案B优劣（致命短板）：支持图遍历、可做薄弱溯源；但无限题型挂载有限知识点，会引发图爆炸、直接污染权威教育局图谱，风险极高。
- 候选方案C：Java 直调 COS
  - 方案C优劣（致命短板）：Java侧零依赖架构简单；但无法复用向量Bucket能力，后续RAG检索需要重新搭建存储体系，扩展性差。
- 最终拍板：MySQL 派生层为主；Neo4j仅阶段2按需物化（ExtAlias + ALIAS_OF）
- 拍板理由：严格遵循权威图谱零写入原则（D1），保证权威图不被业务数据污染；MySQL支撑无限题型空间，可运维可回滚；图能力仅在需要遍历场景时按需物化，可过滤还原纯教育局标准视图。

## 二、关联引擎选型

### 选型2：题型与知识点关联引擎选型
> 状态：✅ 已落地
> 检索摘要：放弃纯LLM、纯字符、纯向量单一引擎，最终采用**分层混合关联引擎**，确定性规则优先、向量聚类兜底、LLM仅做最终仲裁，解决自由猜测不可控问题。

- 选型场景：题目自动识别、题型归一、知识点关联的核心引擎方案
- 候选方案A：纯LLM关联
  - 方案A优劣（致命短板）：语义灵活、可适配变体；但开放域自由猜测不稳定，易出现空候选、跨学段错配，调用成本高、不可控。
- 候选方案B：题型名向量最近邻
  - 方案B优劣：结果确定、成本低、支持动态聚类；依赖题型名语义区分度，需要动态涌现池支撑。
- 候选方案C：纯字符规则匹配
  - 方案C优劣（致命短板）：零成本、绝对确定；仅能处理前缀、全半角等表层变体，无法覆盖语义同型题型。
- 候选方案D：分层混合引擎
  - 方案D优劣：分层各司其职、确定性优先、异常兜底；架构分层略复杂，但稳定性、可控性、准确率最优。
- 最终拍板：分层混合关联引擎
- 拍板理由：纯LLM存在严重空候选、跨学段错误问题（D15）；纯字符无法识别语义题型；纯向量无法处理冷启动命名；分层架构可实现：字符归一拦脏数据、向量动态聚类归并题型、LLM兜底仲裁命名（D6）。

## 三、掌握度锚点选型

### 选型3：掌握度统计锚点主体选型
> 状态：✅ 已落地
> 检索摘要：掌握度统计主体从知识点改为题型，学生掌握度基于canonical题型聚合统计，知识点由题型被动派生，避免图谱映射错误、数据裂行问题。

- 选型场景：学生掌握度数据统计、聚合、落库的核心锚点
- 候选方案A：以题型为锚点
  - 方案A优劣：题目天然聚合到题型，向量聚类稳定、可打分、可观测、落库不裂行；贴合学生解题学习的真实认知模式。
- 候选方案B：以知识点为锚点
  - 方案B优劣（致命短板）：贴合课程体系、贴合图谱结构；但依赖label-URI解析映射，极易出错，需要大量人工维护，学生行为无法精准对应。
- 最终拍板：掌握度主体=题型，知识点由题型派生
- 拍板理由：学生真实学习行为是解题、掌握解题模式，题型可量化可统计；知识点映射链路长易出错，直接统计知识点会污染题型业务库（D2）。

## 四、掌握度算法选型

### 选型4：学生掌握度计算算法选型
> 状态：✅ 已落地
> 检索摘要：放弃max单调不减、EWMA算法，采用**累计平均正确率**作为唯一掌握度算法，实现0-100连续可解释正确率，解决掌握度虚高、无法回查问题。

- 选型场景：学生单题型掌握度分数计算逻辑
- 候选方案A：累计平均正确率
  - 方案A优劣：公式可解释、可回查、数据稳定不抖动，真实反映做题正确率；支持0-100连续分值。
- 候选方案B：max单调不减算法
  - 方案B优劣（致命短板）：仅代表历史最优置信度，答错无法降分，掌握度普遍虚高，无法统计真实正确率。
- 候选方案C：EWMA指数加权平均
  - 方案C优劣（致命短板）：对近期做题更敏感；算法黑盒、无法溯源、无法解释，不适合学生学情展示。
- 最终拍板：累计平均正确率算法
- 拍板理由：max算法只能体现置信度、无法输出正确率；EWMA不透明不适合业务展示；累计平均完全贴合用户认知，可解释可审计（D3）。

## 五、关联模式选型

### 选型5：题型-知识点关联维护模式选型
> 状态：✅ 已落地
> 检索摘要：关闭全自动涌现关联模式，采用**域B查表只读+管理员手动维护**模式，砍掉多环节自动链路，简化核心流程、杜绝权威图谱污染。

- 选型场景：题型与知识点的长期关联维护、更新、迭代模式
- 候选方案A：全自动关联（obs共现+LLM归纳+自动涌现）
  - 方案A优劣（致命短板）：纯数据驱动、自动化程度高；引入5条复杂链路，分散核心业务重心，业务不成熟极易产生脏数据、污染权威映射。
- 候选方案B：查表只读+ADMIN手动维护
  - 方案B优劣：关联关系可控、可解释、可人工修正；需要少量人工维护成本，稳定性极强。
- 最终拍板：域B独立、查表只读、管理员手动维护
- 拍板理由：自动关联链路过多、不可控，严重分散本期核心迭代（题目→题型→掌握度）；手动查表模式零污染、可审计、可稳定迭代（D8）。

## 六、向量路由选型

### 选型6：向量索引路由架构选型
> 状态：✅ 已落地
> 检索摘要：采用**vector_type多索引必填路由**架构，隔离不同业务向量索引，未来新增索引零代码改造，规避单索引过滤的架构局限。

- 选型场景：COS向量检索的索引路由、多业务向量隔离架构
- 候选方案A：vector_type多索引必填路由
  - 方案A优劣：索引完全隔离、业务互不干扰；后续新增question、rag索引无需改契约，扩展性极强；仅需每次显式声明类型。
- 候选方案B：单索引+metadata过滤
  - 方案B优劣（致命短板）：部署简单；跨业务查询受限，后续扩索引需要修改底层契约，架构不通用。
- 最终拍板：多索引路由，本期启用topic索引，question/rag预留占位
- 拍板理由：COS向量查询单次仅支持单索引，多索引架构适配未来扩展，实现零改造扩容，统一Python向量桥路由规范（D13）。

## 七、关联确认机制选型

### 选型7：题型关联结果确认机制选型
> 状态：✅ 已落地
> 检索摘要：放弃纯人工、纯学生众包单一模式，采用**LLM主裁判+学生意图投票+人工边界仲裁**分层信任模型，兼顾规模化与数据准确性。

- 选型场景：低置信题型关联、歧义题型的最终确认机制
- 候选方案A：纯人工打标
  - 方案A优劣（致命短板）：人工精准度有限、脱离解题场景，效率极低，无法规模化。
- 候选方案B：纯学生众包
  - 方案B优劣（致命短板）：数据量大；易被恶意乱点污染，完全不可控。
- 候选方案C：学生澄清意图投票
  - 方案C优劣：学生是学习意图唯一权威，可修正LLM错误；需要投票稀释防恶意。
- 候选方案D：LLM高置信自动确认
  - 方案D优劣（致命短板）：规模化能力强；存在高置信幻觉，自信错误无法自检出问题。
- 最终拍板：分层信任模型：LLM自动兜底 + 学生意图投票 + 人工边界仲裁
- 拍板理由：学生主观意图为核心软信号，多人投票稀释恶意；LLM处理绝大多数常规场景；人工仅兜底边界异常，兼顾规模与质量（D16）。

## 八、候选约束选型

### 选型8：LLM候选生成约束策略选型
> 状态：⚠️ 建议项（未落地）
> 检索摘要：放弃开放域自由猜测方案，建议落地**年级封闭域候选约束**，LLM仅从学生当前年级知识点池选候选，彻底解决空候选、跨学段错误问题。

- 选型场景：LLM题型识别候选生成策略约束
- 候选方案A：开放域自由猜测
  - 方案A优劣（致命短板）：极度灵活；冷启动、陌生场景下频繁空候选、跨学段乱关联，严重影响体验。
- 候选方案B：学生年级封闭域池内选择
  - 方案B优劣：强制在合法知识点池内选择，结果恒非空、杜绝跨学段错误；依赖年级知识点池完备性。
- 最终拍板：推荐落地：封闭域池内选择（待实现）
- 拍板理由：开放域自由猜测是流程死穴，高频空候选；年级锚定封闭域可100%消灭跨学段错配、稳定候选输出（D15）。

## 附录：原始方案选型总表（仅供人工查阅，不用于RAG检索）

> ⚠️注意：向量切片不要依赖本表，业务检索请使用上面分章节单选型小节。

#### 1. 存储选型
选型点：派生层存储
- A. MySQL 派生层：快、可事务、好审核；无限题型空间可写可改｜拍板：✅ MySQL 派生层（现状）；Neo4j 阶段2 物化（ExtAlias + ALIAS_OF）｜理由：数据量上来能力强；权威图零写入（D1）；阶段2 需要图遍历时才物化，可过滤还原纯教育局视图
- B. Neo4j 物化扩展层：可图遍历（薄弱溯源）；但无限题型挂有限知识点会图爆炸、污染权威图
- C. Java 直调 COS：全 Java 零依赖；但不用 Vector Bucket、后续 RAG 要另起

#### 2. 关联引擎选型
选型点：题型↔知识点关联引擎
- A. 纯 LLM：灵活、可处理语义变体；但自由猜测不可控（空候选/跨学段错配）、成本高
- B. 题型名向量最近邻：确定性、便宜、可聚类；但需池或动态涌现、对数学术语区分度依赖 spike
- C. 字符规则：确定性、免费；但只拦变体（解/求前缀），覆盖不了语义同型
- D. 分层混合：各层各司其职、确定性优先、LLM 兜底；实现复杂度稍高｜拍板：✅ 分层混合｜理由：纯 LLM 自由猜测不可控（D15）；字符规则覆盖不了语义同型；向量最近邻确定性/便宜、零锚点动态涌现（D6）

#### 3. 掌握度锚点选型
选型点：掌握度锚点
- A. 题型：题目天然可聚到题型（canonical 向量聚类稳定、可打分可观测、落库不裂行）；贴合学生认知｜拍板：✅ 题型；知识点由题型派生｜理由：学生做的是题、题对应题型可测；知识点映射依赖图谱、易错需维护（D2）
- B. 知识点：课程锚点、挂图谱直观；但映射依赖 label→URI 解析、易错需 ADMIN 维护

#### 4. 掌握度算法选型
选型点：掌握度算法
- A. 累计平均正确率：new=old×n/(n+1)+score×1/(n+1)；正确率视角、可解释可回查、稳定不抖动｜拍板：✅ 累计平均｜理由：max 算不出正确率（置信度视角虚高）；EWMA 难解释难回查（D3）
- B. max 单调不减：置信度视角、答错永不降；简单但虚高、算不出正确率
- C. EWMA：对近期更敏感；但难解释、难回查

#### 5. 关联模式选型
选型点：题型↔知识点关联模式
- A. 自动关联：obs 共现 → LLM 归纳 ratio；数据驱动但引入 5 环节（状态机/聚合批处理/LLM 归纳/vote 澄清/派生覆盖度）、业务不成熟易污染
- B. 查表只读 + ADMIN 维护：入口只读、独立维护；可控但需要人工配数据｜拍板：✅ 查表只读 + ADMIN 手动维护（域 B 独立化）｜理由：自动关联 5 环节分散本期核心（题目→题型→掌握度）；手动维护一张表可演示/可解释/可控（D8）

#### 6. 向量路由选型
选型点：向量索引路由
- A. 多索引 vector_type 必填：索引隔离、将来加索引 Java 契约零改动；但每次显式声明｜拍板：✅ 多索引（topic 本期，question/rag 配置占位）｜理由：单索引将来切多索引要改契约；COS query 一次一个索引（D13）
- B. 单索引 + metadata filter：一个索引、filter 筛选；但契约要变、跨索引查询受限

#### 7. 确认机制选型
选型点：关联确认机制
- A. 纯人工打标：开发者/教研脱离解题、可能错；等于不专业人工替代不专业 LLM
- B. 学生众包：量最大；但恶意乱点/捣乱污染数据，完全交给用户不成立
- C. 学生澄清意图：问"你想学哪个"（主观意图）学生唯一权威；source=student_vote、confidence=60
- D. LLM 高置信自动：规模化；但高置信幻觉会绕过低置信挂起｜拍板：✅ 分层信任模型｜理由：问意图非事实，学生是意图唯一权威；防恶意 4 招（只碰自己/票数稀释/不暴露底层/跳过弃权）；人工只处理极少数边界（D16）

#### 8. 候选约束选型
选型点：关联候选生成
- A. 开放域自由猜测：灵活；但无数据锚时 LLM 自由猜测，空候选频繁（5 次 4 空）、跨学段错配
- B. 封闭域池内选择：从有限选项选、恒非空；但依赖年级知识点池完备性｜拍板：⚠️ 封闭域池内选择（建议项）｜理由：题目 + 该生年级知识点池 → LLM 只能从池里选 → 恒返回 top-N 不空；年级锚定消灭跨学段错误（D15）
