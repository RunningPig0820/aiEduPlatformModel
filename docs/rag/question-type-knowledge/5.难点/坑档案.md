# 题型知识点 坑档案

> 用途：题型分析/掌握度链路真实踩过的坑，6 段复盘（问题现象→触发流程→根因→排查→解决→口述要点）。
> 权威度 0.8 ｜ 来源：ai-edu-ai-service spike/联调记录 + 语雀方案讨论 2026-08。

## J-QT1 向量写入延迟：put 后立即 query 查不到

**问题现象**：首题建锚后立查最近邻，返回空 `vectors: []`，动态聚集没反应。

**触发流程**：题型名向量入库（`put_vectors`）→ 立即 `query_vectors` 查近邻。

**根因**：COS 向量索引 **put 后 ~10s 异步构建**，立即 query 命中不到刚写入的向量。

**排查**：spike 反复 put→query，发现写入生效延迟稳定 ~10s（非网络/权限问题）。

**解决**：① 首题建锚后不立查（本身无近邻）；② 聚集编排「put 后查」路径容忍延迟/留重试。（`core/tutoring/vector_store.py:126-127` 注释）

**口述要点**：COS 向量桶写入是异步生效的，spike 实测要等 ~10 秒才能查到——所以"建锚后立刻查近邻"这个路径是有坑的，我们设计成首题建锚不立查，后续题目查询时近邻已经可见。

## J-QT2 编辑距离误并：一字之差与错别字无法区分

**问题现象**："一元一次方程"和"一元二次方程"被字符级规则归并成同一题型。

**触发流程**：字符规则按编辑距离 ≤1 归并近字变体。

**根因**："一元一次/一元二次"**一字之差**与错别字"方成/方程"**同为距离 1**——字符级无法区分是"语义不同的真题型"还是"错别字"，会误并。

**排查**：联调发现近字归并把相似但不相同的题型并了。

**解决**：**编辑距离 ≤1 近字归并移除**，近字/错别字归并全交给题型名向量层（语义最近邻正确区分"一次/二次"、归并"方成/方程"）。（design Decision 4）

**口述要点**：字符级近字归并有个致命缺陷——"一元一次"和"一元二次"是一字之差，错别字"方成/方程"也是一字之差，编辑距离都是 1，字符规则分不清哪个该并哪个不该并。所以把近字归并砍了，交给向量层，用语义最近邻区分。

## J-QT3 两层 PENDING 语义冲突

**问题现象**：前端用一个 `status === 'PENDING'` 分支同时处理两类完全不同的状态，导致"题型没认出来"和"知识点待确认"混成一种展示。

**触发流程**：`analyze-question` 返回 PENDING（题型没敢确定）→ 前端按"待确认"分支展示候选；`getMastery` 返回 PENDING（题型已练但知识点待确认）→ 前端也走"待确认"。

**根因**：同一个词 PENDING 在两个接口里含义完全不同——analyze 的 PENDING = "识别失败"；getMastery 的 PENDING = "题型掌握了但知识点挂起"。共用一个变量必然混。

**排查**：语雀-方案设计2-问题1 逐坑拆解发现。

**解决**：**两层分开判**——识别结果（analyze.status）：RESOLVED → 查掌握度 / PENDING → 展示候选，到此为止；掌握度（getMastery.status）：RESOLVED+四档 / PENDING → 待确认。绝不共用一个判断变量。

**口述要点**：这个坑最阴——同一个词 PENDING，两个接口含义完全相反。识别层的 PENDING 是"我连题型都没敢确定"，掌握度的 PENDING 是"题型已练、知识点待确认"。如果前端用一个变量判断，学生看到的就是错误的状态。解决就是分层：识别失败就不查掌握度，识别成功才看四态。

## J-QT4 embedding 维度坑：默认 1024 与索引对不上

**问题现象**：写入索引的向量维度与索引声明维度不一致，查询报错或结果为空。

**触发流程**：`text-embedding-v3` 不显式 `dimensions` → 输出 1024 维 → 写进 768 维索引。

**根因**：dashscope `text-embedding-v3` **默认输出 1024 维**，合法维度 1024/768/512…，不显式指定就 1024，与建的 768 维索引对不上。**索引维度建好后不可改**。

**排查**：spike 第一步验证 `dimensions=768` 实际输出 768 维。

**解决**：**`dimensions=768` 写死常量**；spike 顺序必须是"先验证维度 → 再建索引"，不可颠倒。（`core/tutoring/vector_store.py:26-28`）

**口述要点**：embedding 的维度必须和索引维度严格一致，这是建索引前就要钉死的。text-embedding-v3 默认输出 1024 维，不显式传 768 就和索引对不上，而且索引建好后改不了。所以 spike 第一步就是验证显式 768 的实际输出。

## J-QT5 alias 匹配 miss：analyze 返回原始名查不到掌握度

**问题现象**：学生"鸡兔同笼"练了很多，掌握度页却显示"未开始"。

**触发流程**：`analyze-question` 返回原始题型名（"解一元二次方程"）→ 前端拿它查 `getMastery`（key=canonical "一元二次方程"）→ 等号匹配 miss → 误判未开始。

**根因**：analyze 返回的 topicLabel 没过聚集 post-process，不是 canonical；掌握表 key 是 canonical。名字不对齐，前端查不到。

**排查**：语雀-方案设计2-问题1 坑1 拆解 + 联调踩过（贴"x²-5x+6=0"→"一元二次方程"原文叫"解一元二次方程"）。

**解决**：**后端保证 analyze-question 返回的 topicLabel = canonical**（返回前也过聚集 post-process）——前端直接等号匹配即可。（design Decision 9）

**口述要点**：这个坑是"静默降级"——匹配不上不报错，直接显示未开始。原因是 analyze 返回的是 LLM 原始名，掌握表 key 是向量归并后的 canonical 名，两个名字对不上。解法是让 analyze 返回前也过一遍聚集归一，前端用 canonical 名等号匹配。

## J-QT6 学科门/题型识别开思考拖慢 50~145s

**问题现象**：学科门判定一次要 50~145 秒，答疑链路等死。

**触发流程**：subject-classify / question-understand 用默认参数调 LLM（开思考）。

**根因**：开思考（thinking）模式下模型长思考，学科门这种简单判定也拖到分钟级。

**排查**：实测开思考 50~145s、关思考秒出。

**解决**：**统一"慢修复"**——关思考（thinking disabled）+ 20s 超时 + 关 SDK 重试；慢/失败快速返回空结果，Java 走降级（闭集外放行 math / 空 topic_labels 降级 PENDING）。（`subject_classify.py:66-73`、`question_understand.py:82-91`）

**口述要点**：前置判定环节最怕变卡点。我们实测开思考模式下学科门要 50~145 秒，这不可接受。所以专门做了慢修复：关思考 + 20 秒超时 + 关重试，宁可快速失败让 Java 走降级，也不让主链路等。

## J-QT7 掌握度信号字段改名脱节

**问题现象**：掌握度信号静默丢失（mastery_signals 为空）。

**触发流程**：`kp_label → topic_label` 改名 → `structured.py` 的 `_schema_instructions` 纠错提示词仍硬编码 `"kp_label"` → 模型输出旧名 → Pydantic 校验 topic_label 缺失 → 反复纠错失败 → 掉进兜底 fallback → 信号丢失。

**根因**：function calling schema（绑定 Pydantic 模型，自动变 topic_label）与纠错提示词字段名**脱节**——模型按提示词输出 kp_label，schema 要 topic_label，永远校验不过。

**排查**：改名后信号丢失，追到纠错提示词。

**解决**：`_schema_instructions` 纠错提示词同步改为 `"topic_label"`；测试断言纠错提示词含 topic_label。（design-python-ai-tutoring-topic-mastery-signal Decision 2）

**口述要点**：字段改名是个连环坑——Pydantic schema 会自动跟上新字段名，但纠错提示词里硬编码的旧名不会。模型按提示词输出旧名，schema 要新名，一直校验失败最后掉兜底，掌握度信号就静默丢了。改名必须连纠错提示词一起改。

## J-QT8 闭集外误判：把地质/天文归成 other

**问题现象**：非 K12 学科内容被归为 other，语义污染。

**触发流程**：subject-classify 解析到闭集外内容（如"地质""天文"）→ 归到 other。

**根因**：other 的语义是"明确非学科内容"，但闭集外是"**不知道**"——两回事。硬归类会污染 other 桶。

**排查**：`_parse_subject` 设计讨论发现。

**解决**：**闭集外 → None（不是 other）**，Java 按 math 放行（宁漏拦不误拦）。（`subject_classify.py:45-55`、测试 `test_subject_classify.py:71-78`）

**口述要点**：other 和 None 语义必须分开——other 是"明确非学科"，None 是"我不知道"。把地质天文硬归到 other 是污染，返回 None 让上游放行更安全。宁可放过，不可误判。
