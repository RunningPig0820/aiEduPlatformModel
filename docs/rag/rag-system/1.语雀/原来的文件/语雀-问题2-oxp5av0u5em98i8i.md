  第 3、4 点——面试官到底会问什么，这是整个系统的发动机。

  先把你的四点需求钉死

  ① 页面锚定（前端主动传页） —— 这设计很好，而且它天然把系统分成两种模式：

  ┌─ 页面模式: 点击"知识图谱" → 前端传 page=知识图谱 ─────────┐  
  │   界面先弹出该页概览卡 → 之后的问答全部锁定在这一页文档内    │  
  └────────────────────────────────────────────────────────┘  
  ┌─ 全局模式: 问题跨页/没点页面 → 全局检索 ──────────────────┐  
  │   "对比知识图谱和AI答疑的定位" → 不锁页, 跨页检索          │  
  └────────────────────────────────────────────────────────┘

  页面锚定让检索确定性大幅提升，也让回答可解释——"这个问题锁定了知识图谱页，所以我在它的文档里检索"。

  ② 权限感知 —— 这不是"哪些文档给面试官看"那么简单，是每个页面挂一个权限标签（学生/教师/家长/管理员），对  
  话时按当前角色过滤：

  每个页面 → 权限标签(角色/数据权限)        学生端页面 → 需学生权限  
  用户角色(前端传 / demo 模拟切换)  → 检索+生成时过滤  
  无权限 → 返回"该页面需要学生权限"提示, 不吐内容

  面试现场这是个炸点：当着面试官的面切角色，"学生模式下问组织中心 →  
  返回权限不足"，比任何口头解释都直观。你正好有组织中心的 school_user/角色模型做真实依据。

  第 4 点：反向整理文档 —— 关键洞察

  我现在必须给你泼一盆冷水：你现有文档答不了上面这些问题。

+ "为什么拆 decide/generate" —— 答案在代码注释和 git commit 里，语雀文档没有
+ "掌握度为什么挂题型" —— 答案在 mastery_snapshot 的变更记录里，不在产品文档
+ "97.1% 匹配率怎么做到" —— 在 PROJECT_SUMMARY / 导入脚本里，语雀没有
+ "流式延迟多少" —— 在联调记录/排查文档里（backend-connectivity-2026-08-19.md）

  所以"反向整理"不是把现有文档换个顺序，而是新造一层"面试 Q&A 索引"：

  现有语料(按设计结构组织) ── 答不了"为什么/难点/指标"这类问题  
         ↓ 反向整理: 把散落在 代码/git/语雀/排查记录 里的答案沉淀出来  
  ┌──────────────────────────────────────────────┐  
  │ 面试Q&A索引层: 每页 5~8 个高频问题条目          │  
  │   每个条目 = 问题 + 答案要点 + 引用原始文档段落   │  
  └──────────────────────────────────────────────┘  
        ↓ RAG 检索这个索引层 → 命中即答  
        ↓ 答案底部引用原始文档段落 → 可溯源、可深挖

  这个"两层语料"设计是整件事的灵魂：RAG   
  真正检索的是"问题索引层"（答案可控、可预演），原始文档作为证据层提供溯源。面试前你把 20  
  来个问题的答案自己先过一遍——面试官问的任何问题你心里都有底，RAG 只是帮你现场组织语言。

  到这里，需要你定的关键决定
