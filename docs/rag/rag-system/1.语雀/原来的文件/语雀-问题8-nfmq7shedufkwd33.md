6. 我们需要有题型引导 在每个对象项目页面下 我们需要有引导语 每次完成尽量 尽量让用户往 1 项目介绍 / 2 项目如何操作 / 4

8. 输出的时候 需要将 查询的文档给展示到对话中 可以点击查看原文 , 每次对话的时候 都需要展示 通过自有知识库获取的
9. 核心目标

构建一个面向学生的“RAG项目介绍助手”。该助手需严格遵循RAG标准流程（权限校验 → 意图识别 → 语义分析/Query改写 → 多路召回 →
重排 → 生成），并将流程中的关键中间状态实时透传给前端，实现可观测的“白盒化”问答体验。

2. 身份鉴权（硬性拦截）

后端必须从可信源（如Token或网关解析的Header）获取当前用户角色，严禁信任前端Body传参。仅当角色明确为“学生”时放行；若为非
学生或角色缺失，直接返回固定403拒绝语，不进入后续任何RAG流程，不消耗任何Token。

3. 模块边界与拒答策略（硬边界）

明确划定本助手的服务禁区：AI答疑、知识图谱、题型分析 三个业务模块的问题一律拒绝。在意图识别层需增加硬路由规则：但凡问题
涉及“系统架构/代码实现/部署流程/评测方案/接口设计”，强制路由至 RAG项目 知识库；但凡问题明确指向上述三个禁区模块，直接返
回固定话术“该问题涉及其他业务模块，我尚未掌握”，严禁调用LLM生成拒答语（节省成本）。

固定兜底语

4. 语义分析展示层（前端可观测）

在流式输出的元数据阶段，必须向前端透传以下3项语义处理结果：

原始问题：用户输入。

改写后问题：经Query改写后的检索式。

意图分类标签：最终判定的路由目标（如 #rag_project 或 #reject）。

5. 多路召回与引用透明度（核心交互）

最终只展示经RRF重排后喂给LLM的Top-K块（建议K=3），严禁将所有召回原始列表全量吐给前端。

每个展示块必须附带：

块标题/摘要

文件路径（前端实现“点击查看原文”）

is_quoted 标签（标识该块是否被LLM最终引用为答案依据）

前端展示时，被引用的块高亮，未被引用的灰显折叠，以维护回答的严谨性。

引用判定规则：is_quoted 标签不依赖LLM主观自述，采用确定性硬匹配——生成完成后，遍历每个候选块的
content_preview（或原文片段），在最终答案字符串中做最长公共子串匹配，任意连续8个中文字符（或12个英文字符）命中即标记
is_quoted = True。该逻辑由后端实现，无需LLM额外输出。

6. 对话引导机制（静态化降本）

每次问答完成后，由后端从预设静态池（非LLM生成）中随机抽取2~3条引导建议返回前端，强制引导学生围绕以下方向追问：①项目整体
介绍、②项目操作流程、③数据关联逻辑、④技术难点与解决方案。严禁动态生成引导语以节省Token和耗时。

提前让后端准备一个 suggestions_pool.json，格式如：

每个项目的引导话术可能都不一样 也可以做成一个 llm 生成一个话术

json

{

  "project_intro": ["想了解RAG的整体架构吗？", "想知道这个系统解决了什么痛点吗？"],

  "operation": ["如何部署这套RAG系统？", "接口调用流程是怎样的？"],

  "data_relation": ["知识库的数据是如何流转的？", "向量和BM25是怎么协同的？"],

  "difficulty": ["RRF融合算法有什么难点？", "评测体系是如何设计的？"]

}

7. 健壮性与熔断机制（工程底线）

分层超时：召回层硬超时 2秒（单路超时则自动降级为纯另一路），生成层硬超时
8秒。超时后直接返回已召回的清单或固定兜底语，严禁无限阻塞。

断连取消：后端必须监听前端连接状态（如FastAPI的
is_disconnected()），一旦检测到前端主动断开，立即中止底层LLM的流式请求，防止后端空转烧钱。

“生成超时后，不走LLM，直接返回召回清单。格式固定为：‘我找到了以下相关资料，但生成完整答案超时了，您可以直接点击查看原文
：块1标题、块2标题、块3标题。’这样用户虽然没拿到润色后的答案，但拿到了原始资料，体验是正向的、非报错的，不会觉得系统崩
了。”

建议：超时降级话术也直接写死在代码里，不调LLM，成本为0。

8. Token消耗统计（透明计费）

每次问答返回体中需包含详细的 tokens_usage
对象，至少包含：prompt_tokens、completion_tokens、cache_hit_tokens（缓存命中）、total_tokens。同时需携带 trace_id
供前端断线后补查。

  The core tension to resolve

  The 08-21 design's entire premise was "给面试官讲清 4 个业务页面". Today's spec inverts it: "只讲 RAG
  项目本身，业务模块问题一律拒答". That's not a small tweak — it's a product-scope reversal. Today's point 5
  ("ai答疑/知识图谱/题型分析/RAG项目 明确拒绝") reads like the list includes RAG项目 too, but section 3 clarifies
  RAG项目 is the routing target (涉及架构/代码/部署/评测/接口 → 强制路由 RAG项目), and only the 3 业务模块 are 禁区.

  So the question is: is today's project-intro-rag (only-RAG-project, student-facing, white-box) a replacement of the
  08-21 change, or a separate/new thing?

  Architecture: it maps cleanly onto the tutoring gateway pattern

  The white-box pipeline stages map naturally onto the Java 网关 + Python 无状态 agent split the tutoring system already
  uses:

  前端学生页 ──(session, STUDENT)──► Java 网关 (角色门 403)
                                       │ 透传 SSE: permission → intent → rewrite → recall → rerank → token
                                       ▼
                                Python RAG 引擎 (无状态)
          intent 硬路由 ──► Query改写 ──► 多路召回(向量+BM25) ──► RRF Top-3 ──► doubao 流式
                                            │ 2s 超时降级              │ is_quoted 后置硬匹配
                                            ▼                          ▼
                                     召回块清单(标题/路径/摘要)    done + tokens_usage + trace_id

  Which stages live in Java vs Python is itself a decision:

+ 角色门 / SSE 中继 → Java（可信 session，跟 tutoring 一致；Python 不碰会话）
+ 意图硬路由 + 禁区拒答 → 纯规则即可，但放哪一层？(08-21 的范围门是 Python 后置；今天的意图路由更像前置分类)
+ is_quoted LCS 硬匹配 → 生成完成后在引擎侧做，但前端要的是"生成中实时引用"——是 done
后补发，还是流中边生成边匹配？（8/12 字符窗口对流式 chunk 不友好）

  Decisions I'd surface before formalizing

1. 与 08-21 project-intro-rag 的关系：改造它 vs 新建独立 change？（涉及知识库语料是否复用 rag-index）
2. 禁区边界：AI答疑/知识图谱/题型分析 全部拒答？那"组织中心"呢（08-21
曾覆盖）——不在禁区列表里，算可答还是默认边界回答？
3. 意图识别层位置与实现：纯规则硬路由（零成本、可展示）还是快模型分类（更像"语义分析"）？你 spec 里两处都提到了。
4. 引导语静态池 vs LLM 生成：spec 结尾自己也留了这个口子（"也可以做成一个 llm 生成一个话术"）。
5. cache_hit_tokens：doubao/ark 的 usage 是否真返回 prompt_cache_hit_tokens？这需要验证，否则只能"估算"。
