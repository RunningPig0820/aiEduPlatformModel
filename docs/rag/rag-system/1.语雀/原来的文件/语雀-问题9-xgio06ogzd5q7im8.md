## 问题
1. "没有找到知识文档"的拒答——是发生在意图层（LLM  
  判到知识图谱→查无语料→固定话术），还是范围门（检索置信度低）？我们选择应该两者都要，但话术/事件要对齐。
2. 切换功能点后，前一个 answer 的 SSE 已经流了一半——你说的是"下一轮切换"还是"生成中切换"？生成中切换涉及中止当前 LLM流，复杂度完全不同。下一轮切换"还是"生成中切换" 哪个复杂 哪个更能符合业务 



## 回答
下一轮切换更符合业务，也更简单。生成中切换在工程上是另一量级的事——而且真到了生成中，"切换"这个意图基本不存在  
  了。

  为什么生成中切换既复杂又没什么业务价值

  ┌─ 下一轮切换 ─────────────────────────────────────────────────┐  
  │  Q1 → intent → recall → generate → SSE流完 → done            │  
  │        学生问 Q2 (指向另一功能/模块)                            │  
  │  Q2 → intent 发现 anchor 变了 → 发 switch 事件 → 重置上下文     │  
  │        → rewrite → recall → generate → done                   │  
  │                                                               │  
  │  复杂度：intent 每轮本来就跑，多一次"当前锚点 vs 已锚定"对比      │  
  │  成本：switch 前零生成 token                                  │  
  └───────────────────────────────────────────────────────────────┘

  ┌─ 生成中切换 ─────────────────────────────────────────────────┐  
  │  Q1 → intent → recall → generate 开始流...                   │  
  │           学生中途插入 Q2 → 必须：                             │  
  │            ① 中止上游 doubao HTTP 流(服务端取消)               │  
  │            ② 已流的半截答案作废(前端要能打断渲染)               │  
  │            ③ 半截 token 已计费——中止不退款                     │  
  │            ④ 之后还要再起一轮新 generate                      │  
  │  复杂度：①②③④ 全新增，且 Python 服务端取消上游流不可靠         │  
  │  成本：Q1 半截 token 白烧 + Q2 全量                            │  
  └───────────────────────────────────────────────────────────────┘

  业务上"生成中切换"其实不存在。学生会做的动作只有两个：

1. 等当前回答流完，再问新问题 → 天然是下一轮；
2. 不想等了/突然想岔开 → 前端 关闭 fetch，后端 is_disconnected() 感知断开 → 中止流。这本质是客户端取消，不是意图切换。

  所以正确的模型是：

+ 意图层面的切换判定，只发生在下一轮（每个 turn 开头的 intent，跟 tutoring 换题判定收敛 Java 完全同构）。
+ 生成中 只做一件事：is_disconnected() → 中止，防止空转烧钱（spec 第 7 条已经要求了）。 
+ 前端在 Q1 还在流、学生又发 Q2 时，走"取消 Q1 fetch → 立即发 Q2"的常规 chat UX，后端不用做任何流内切换逻辑。

  ▎ 唯一的反例：如果产品坚持"回答到一半、因为识别到学生问的其实是另一模块，服务端主动掐断当前流"——那才需要生成中切换，但  
  ▎ 代价是半截 token + 打断感 + 上游取消不可靠，不建议做。

  "没有找到知识文档"两者都要 —— 同意，设计成双门共享固定话术

  你说的"两者都要"其实正好是两道互补的闸，都产同一个固定拒答话术（不调 LLM）：

  学生问题  
     │  
     ├─ 意图门 (turn 开头, intent 后立即判, 最便宜)  
     │     LLM 判到 anchor=知识图谱/题型分析/RAG(无语料模块)  
     │     → 固定话术"该模块暂未收录，我尚未掌握"  [不 recall, 不 generate, 0 token]  
     │  
     └─ 范围门 (recall 之后, 检索置信度低于阈值)  
           intent 没拦下、但语料里确实没有相关内容  
           → 同一个固定话术  [付了 recall, 省 generate]

  两道门为什么都要：

+ 意图门：拦截"明确指向禁区/无语料模块"的问题——零检索零生成，学生问"知识图谱掌握度怎么算"立刻拒，不浪费。
+ 范围门：兜住"意图没分类到禁区、但语料没覆盖"的边角问题（比如问了个 RAG 文档里从没提过的细节）——这是 08-21 里  
范围门=检索置信度 的本意。

  事件流里两道门要能区分（白盒要求）：意图门拒答发 event: reject + reason: module_not_covered；范围门拒答发 event:   
  boundary + reason: no_relevant_doc。前端可以据此展示"拒绝发生在哪一层"。

  这对 SSE 事件契约意味着

  每轮事件序列:  
    intent    (LLM 结构化: anchor/switch/ambiguous) ── 可含 reject  
    rewrite   (改写后 query)                          ── 可含  
    switch    (anchor 变了, 上下文重置)               ── 条件  
    rerank    (RRF top-3 块: 标题/摘要/file_path)     ── 先发, 供引用面板  
    token     (生成流)  
    reject / boundary  (两道门任一道触发 → 无 token 流)  
    done      (answer + quoted_keys + tokens_usage + trace_id + suggestions)

  switch 事件的语义：不掐断任何在途流（在途流要么完了、要么被 is_disconnected 取消），它只作用于下一个 turn   
  的上下文——重置锚点、清掉上轮召回、重新走 rewrite→recall。
