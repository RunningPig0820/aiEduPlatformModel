## 一、检索架构选型

### 选型1：检索池层数选型
> 状态：✅ 方案拍板｜⚠️ 代码落地（形态演进：doc_type=qa/source → rag-full/rag-slice 双物理索引 + module 过滤）
> 检索摘要：最终采用索引层预写QA池+源文档池双池检索，引导问题走索引层稳定可控，自由问题走源文档池纯RAG真发挥；方案"同一COS索引用 doc_type 区分"落地为两个物理索引 rag-full/rag-slice + metadata.module 过滤。

- 选型场景：检索池到底几层，决定 RAG 有多"真"、能否证明检索能力
- 候选方案A：单索引层（20~30 条 QA 条目）
  - 方案A优劣（致命短板）：引导问题全可控；但自由问题命中不了就直接边界拒绝，面试官问个没准备的只能答"不在范围"，RAG 能力没有证据。
- 候选方案B：索引层 + 源文档双池
  - 方案B优劣：引导问题走索引层稳定可控，自由问题走源文档池纯 RAG 真发挥（能答没准备的问题）；代价是自由问题不可控一点。方案设计为两池同写一个 COS 索引，用 doc_type metadata 区分。
- 候选方案C：纯全文检索（无索引层）
  - 方案C优劣（致命短板）：最"纯 RAG"；但答案不可控、无法预演，面试现场最容易翻车。
- 最终拍板：双池检索（索引层 QA 池 doc_type=qa + 源文档池 doc_type=source）
- 拍板理由：引导问题要稳定可控、自由问题要证明 RAG，一池满足不了两个目标；"源文档池 = 真的检索"正是 RAG 能力证据（D2）。
- 落地对账：⚠️ 演进——代码落地为两个物理 COS 索引 `rag-full`（整篇 23 块）+ `rag-slice`（切片 294 块），metadata 10 字段无 doc_type（`build_index.py:145-157`，注释"doc_type 与 module 同值冗余已去掉 2026-08-26"）；双池隔离靠 metadata.module + 查询侧 Filter($eq) 下推（`query.py:458-465`）+ 池前缀 key；"预写 QA/引导可答"由切片池引导问题块 + 双向量 -q 问题路承接（`query.py:487-504`）。结论=方案双池拍板成立，形态 doc_type→pool+module。
- 落地对账（页面锚定反转）：⚠️ 反转/演进——方案"前端传 `page` + 页面模式锁页/全局模式跨页"（D3）在代码中**无 page 参数**，演变为两层锚定：模块级 `current_project`/intent `anchor`（决定选哪个语料池，`select_corpus` 按 module 过滤）+ 节级 `locked_sections`（`ANCHOR_WEIGHT=1.5`，`query.py:665`）——**节级锁页从"过滤"退化为"加权 ×1.5"**（只加权不过滤，过滤发生在模块级）；页面模式/全局模式 ≈ locked_sections 非空/空，无显式模式布尔；⚠️ 白盒链路 `recall` 写死 `locked_sections=[]`（`assistant.py:118`），节级锚定加权被旁路，仅 1.6C 端点完整传入。结论=page 参数未落地，模块锚定+节加权落地。

### 选型2：索引层答案形态选型
> 状态：✅ 方案拍板｜✅ 代码落地（白盒链路已实现）
> 检索摘要：索引层存"问题+答案要点+引用"而非完整答案，检索仍走向量，命中后 LLM 按要点现组织语言并强制引用，避免 RAG 沦为查表、又避免纯检索不可控；代码白盒 generate 已按精排 Top-K 块现组织语言。

- 选型场景：索引层存完整答案还是答案要点，决定 RAG 是"真"还是"虚"（整个系统的十字路口）
- 候选方案A：完整答案全预写
  - 方案A优劣（致命短板）：绝对可控、永不翻车；但 RAG 沦为一个 fancy 查表，面试官一问"检索体现在哪"就露怯。
- 候选方案B：答案要点 + LLM 生成
  - 方案B优劣：索引层存答案要点和强制引用原文段落，LLM 每次从检索到的上下文现组织语言；检索/增强/生成都真实发生，RAG 能力看得见摸得着；需要控制 prompt 让它按要点答否则会跑偏。
- 候选方案C：纯检索生成（不预写）
  - 方案C优劣（致命短板）：最"纯 RAG"；但答案不可控，面试现场最容易翻车。
- 最终拍板：答案要点 + LLM 生成（索引层存"问题+答案要点+引用"，检索仍走向量，命中后要点+引用传给模型生成）
- 拍板理由：面试官能看见 RAG 在动，是"能力证明"；要点提前写仍可控，等于"提纲你定，措辞 AI 来"；若只做查表，检索和打分就全是假的（D6 否决"预写完整答案直发→RAG 沦为查表"）。
- 落地对账：✅ 白盒链路 `stream_generate` 基于精排 Top-K 块 + 改写 query 调 doubao 流式现组织语言（`assistant.py:411-477, 634`）；`_GEN_SYSTEM` 硬性约束"只基于召回语料、末尾统一贴参考来源、正文不插标记"（`query.py:692-748`）；引导题=池内原题直出（不预写完整答案，见选型12 反转）。结论=落地。

### 选型3：检索路数（多路召回）选型
> 状态：✅ 方案拍板｜✅ 代码落地（路数扩充：双路→双池三路四路 RRF）
> 检索摘要：放弃纯向量或纯关键词单路召回，采用向量+BM25 多路召回互补，语义召回与精确关键词召回并行，且天然构成降级链（embedding 挂→纯 BM25）；代码落地为双池三路四路 RRF 融合。

- 选型场景：召回走单路还是多路，决定检索质量与降级能力
- 候选方案A：纯向量召回
  - 方案A优劣（致命短板）：语义召回强；但精确术语、拼写变体覆盖弱，且 embedding API 一挂整个召回链路就断。
- 候选方案B：纯 BM25 关键词召回
  - 方案B优劣（致命短板）：零成本（本地 jieba）、确定性高、可作向量挂掉时的降级；但无语义泛化，同义改写覆盖不了。
- 候选方案C：向量 + BM25 多路召回
  - 方案C优劣：语义与关键词互补，一路挂了另一路兜底；代价是多一路的融合处理（RRF）。
- 最终拍板：多路召回（向量 + BM25）
- 拍板理由：embedding 挂→纯 BM25 是既有降级矩阵的设计（D10）；多路召回是白盒流水线"召回"阶段的可展示点，代码落地为 retrieve_vector / retrieve_bm25 双路召回（问题8 明确"多路召回 向量+BM25"）。
- 落地对账：✅ 落地并扩充——代码为**双池三路**：全量池向量(rag-full) + 切片池双向量(rag-slice `-c` 内容路 / `-q` 问题路) + 本地 BM25（jieba+Okapi），四路各贡献 `1/(RRF_K+rank)` 进 RRF（`query.py:518-525, 637-659`）；任一向量路 2s 超时 → 空路降级 + degraded 标记（`assistant.py:71-88`，`RAG_RECALL_TIMEOUT=2.0`）。结论=方案拍板成立，路数超集落地。

### 选型4：融合与重排选型
> 状态：✅ 方案拍板（08-21 否决 RRF → 08-25 采用）｜✅ 代码落地（RRF_K=60 × authority × anchor_w）
> 检索摘要：08-21 显式否决重排模型（"小语料不需要"），08-25 引入 RRF 融合向量+BM25 多路召回结果，Top-K=3 喂 LLM，排名融合免去跨路分数归一问题；范围门阈值用召回置信度而非 RRF 相对分（2026-08-25 校正）。

- 选型场景：多路召回结果如何融合、是否引入重排模型
- 候选方案A：引入重排模型（cross-encoder 精排）
  - 方案A优劣（致命短板）：精排最准；但 08-21 显式否决——"小语料不需要重排模型"，对几十条语料是过度设计，加复杂度和延迟。
- 候选方案B：单路加权和
  - 方案B优劣：打分公式 score=相似度×问题类型×页面锚定加权（D5）是单一信号加权；但对多路召回结果无融合机制，跨路分数不可比、权重靠人工调。
- 候选方案C：RRF 融合
  - 方案C优劣：按倒数排名融合，免分数归一，小语料够用；Top-K=3 只把精选块喂给 LLM，杜绝全量召回列表外泄。
- 最终拍板：RRF 融合（08-25 引入，Top-K=3）；打分公式沿用相似度×类型×锚定加权
- 拍板理由：08-21 显式否决重排模型"小语料不需要"；08-25 为多路召回引入 RRF 作为轻量融合，按排名融合对分数尺度不敏感；打分公式多信号加权 + 阈值已足够区分命中与超范围（D5、问题8）。
- 落地对账：✅ 落地——`RRF_K=60`（`query.py:43`），`score = RRF × authority × anchor_w`（`query.py:667`），权威度(1.0 完善文档/0.8 代码/0.7 语雀)连乘、节锚定命中 ×1.5；白盒 rerank 事件只回传 `RERANK_K=3` 精排块（`assistant.py:31`，严禁吐全量召回列表）；⚠️ 范围门阈值语义 2026-08-25 校正为**召回置信度**（向量=1-平均余弦距离、BM25=`min(1.0,top_score/10)`），非 RRF 相对分（RRF 分 0.01~0.05 量级永远够不到 0.75/0.5，`assistant.py:385-386` 注释）。结论=落地。

### 选型5：引用判定选型
> 状态：✅ 方案拍板｜✅ 代码落地（lcs_quote_match + 先灰后亮）
> 检索摘要：放弃 LLM 自述引用，采用 is_quoted LCS 确定性硬匹配（连续 8 个中文字符或 12 个英文字符命中即标记引用），rerank 块先发灰显、done 后补发 quoted_keys 高亮；全部未命中时标注"引用未能精确匹配"不假装。

- 选型场景：怎么判定召回块是否被最终答案引用，维护白盒引用严谨性
- 候选方案A：is_quoted LCS 确定性硬匹配
  - 方案A优劣：生成完成后遍历候选块 content_preview 在答案字符串中做最长公共子串匹配，任意连续 8 个中文字符或 12 个英文字符命中即 is_quoted=True；确定性、不依赖 LLM 主观自述、后端实现零额外 LLM 输出。
- 候选方案B：LLM 自述引用
  - 方案B优劣（致命短板）：让模型自己说引用了哪个块；不可靠，自述与真实依据可能不一致，白盒露怯。
- 候选方案C：无引用
  - 方案C优劣（致命短板）：答案不带任何依据；quoted_keys 为空时答案照常显示但没有支撑，白盒反而露怯。
- 最终拍板：is_quoted LCS 硬匹配（8 中/12 英），rerank 块先发（灰显），done 后补发 quoted_keys（高亮）
- 拍板理由：8 中文字符匹配必须生成完才能算，所以 rerank 先发灰显、done 后补 quoted_keys 高亮，"先灰后亮"避免引用面板闪跳；quoted_keys 为空→答案标注"引用未能精确匹配"，不假装有引用（问题8 §5、问题11 #3/#10）。
