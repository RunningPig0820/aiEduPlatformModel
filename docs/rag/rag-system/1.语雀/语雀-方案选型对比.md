## 文档说明

本文档记录 RAG 问答系统全部关键技术选型的多方案对比、优劣取舍、最终落地结论与否决原因。每条选型为独立小节，适配标题切片策略，**单选型=单Chunk**，用于RAG精准检索。文档末尾附带原始总表附录，**仅供人工查阅，不送入向量检索库**。

> 阅读提示：正文分块小节为 RAG 检索主体；附录原始总表仅供人工翻阅，不要依赖表格做召回。

## 一、检索架构选型

### 选型1：检索池层数选型
> 状态：✅ 已落地
> 检索摘要：最终采用索引层预写QA池+源文档池双池检索，引导问题走索引层稳定可控，自由问题走源文档池纯RAG真发挥；两池同写一个 COS 索引用 doc_type=qa/source 区分。

- 选型场景：检索池到底几层，决定 RAG 有多"真"、能否证明检索能力
- 候选方案A：单索引层（20~30 条 QA 条目）
  - 方案A优劣（致命短板）：引导问题全可控；但自由问题命中不了就直接边界拒绝，面试官问个没准备的只能答"不在范围"，RAG 能力没有证据。
- 候选方案B：索引层 + 源文档双池
  - 方案B优劣：引导问题走索引层稳定可控，自由问题走源文档池纯 RAG 真发挥（能答没准备的问题）；代价是自由问题不可控一点。两池同写一个 COS 索引，用 doc_type metadata 区分。
- 候选方案C：纯全文检索（无索引层）
  - 方案C优劣（致命短板）：最"纯 RAG"；但答案不可控、无法预演，面试现场最容易翻车。
- 最终拍板：双池检索（索引层 QA 池 doc_type=qa + 源文档池 doc_type=source）
- 拍板理由：引导问题要稳定可控、自由问题要证明 RAG，一池满足不了两个目标；"源文档池 = 真的检索"正是 RAG 能力证据（D2）。

### 选型2：索引层答案形态选型
> 状态：✅ 已落地
> 检索摘要：索引层存"问题+答案要点+引用"而非完整答案，检索仍走向量，命中后 LLM 按要点现组织语言并强制引用，避免 RAG 沦为查表、又避免纯检索不可控。

- 选型场景：索引层存完整答案还是答案要点，决定 RAG 是"真"还是"虚"（整个系统的十字路口）
- 候选方案A：完整答案全预写
  - 方案A优劣（致命短板）：绝对可控、永不翻车；但 RAG 沦为一个 fancy 查表，面试官一问"检索体现在哪"就露怯。
- 候选方案B：答案要点 + LLM 生成
  - 方案B优劣：索引层存答案要点和强制引用原文段落，LLM 每次从检索到的上下文现组织语言；检索/增强/生成都真实发生，RAG 能力看得见摸得着；需要控制 prompt 让它按要点答否则会跑偏。
- 候选方案C：纯检索生成（不预写）
  - 方案C优劣（致命短板）：最"纯 RAG"；但答案不可控，面试现场最容易翻车。
- 最终拍板：答案要点 + LLM 生成（索引层存"问题+答案要点+引用"，检索仍走向量，命中后要点+引用传给模型生成）
- 拍板理由：面试官能看见 RAG 在动，是"能力证明"；要点提前写仍可控，等于"提纲你定，措辞 AI 来"；若只做查表，检索和打分就全是假的（D6 否决"预写完整答案直发→RAG 沦为查表"）。

### 选型3：检索路数（多路召回）选型
> 状态：✅ 已落地
> 检索摘要：放弃纯向量或纯关键词单路召回，采用向量+BM25 多路召回互补，语义召回与精确关键词召回并行，且天然构成降级链（embedding 挂→纯 BM25）。

- 选型场景：召回走单路还是多路，决定检索质量与降级能力
- 候选方案A：纯向量召回
  - 方案A优劣（致命短板）：语义召回强；但精确术语、拼写变体覆盖弱，且 embedding API 一挂整个召回链路就断。
- 候选方案B：纯 BM25 关键词召回
  - 方案B优劣（致命短板）：零成本（本地 jieba）、确定性高、可作向量挂掉时的降级；但无语义泛化，同义改写覆盖不了。
- 候选方案C：向量 + BM25 多路召回
  - 方案C优劣：语义与关键词互补，一路挂了另一路兜底；代价是多一路的融合处理（RRF）。
- 最终拍板：多路召回（向量 + BM25）
- 拍板理由：embedding 挂→纯 BM25 是既有降级矩阵的设计（D10）；多路召回是白盒流水线"召回"阶段的可展示点，代码落地为 retrieve_vector / retrieve_bm25 双路召回（问题8 明确"多路召回 向量+BM25"）。

### 选型4：融合与重排选型
> 状态：✅ 已落地
> 检索摘要：08-21 显式否决重排模型（"小语料不需要"），08-25 引入 RRF 融合向量+BM25 多路召回结果，Top-K=3 喂 LLM，排名融合免去跨路分数归一问题。

- 选型场景：多路召回结果如何融合、是否引入重排模型
- 候选方案A：引入重排模型（cross-encoder 精排）
  - 方案A优劣（致命短板）：精排最准；但 08-21 显式否决——"小语料不需要重排模型"，对几十条语料是过度设计，加复杂度和延迟。
- 候选方案B：单路加权和
  - 方案B优劣：打分公式 score=相似度×问题类型×页面锚定加权（D5）是单一信号加权；但对多路召回结果无融合机制，跨路分数不可比、权重靠人工调。
- 候选方案C：RRF 融合
  - 方案C优劣：按倒数排名融合，免分数归一，小语料够用；Top-K=3 只把精选块喂给 LLM，杜绝全量召回列表外泄。
- 最终拍板：RRF 融合（08-25 引入，Top-K=3）；打分公式沿用相似度×类型×锚定加权
- 拍板理由：08-21 显式否决重排模型"小语料不需要"；08-25 为多路召回引入 RRF 作为轻量融合，按排名融合对分数尺度不敏感；打分公式多信号加权 + 阈值已足够区分命中与超范围（D5、问题8）。

### 选型5：引用判定选型
> 状态：✅ 已落地
> 检索摘要：放弃 LLM 自述引用，采用 is_quoted LCS 确定性硬匹配（连续 8 个中文字符或 12 个英文字符命中即标记引用），rerank 块先发灰显、done 后补发 quoted_keys 高亮。

- 选型场景：怎么判定召回块是否被最终答案引用，维护白盒引用严谨性
- 候选方案A：is_quoted LCS 确定性硬匹配
  - 方案A优劣：生成完成后遍历候选块 content_preview 在答案字符串中做最长公共子串匹配，任意连续 8 个中文字符或 12 个英文字符命中即 is_quoted=True；确定性、不依赖 LLM 主观自述、后端实现零额外 LLM 输出。
- 候选方案B：LLM 自述引用
  - 方案B优劣（致命短板）：让模型自己说引用了哪个块；不可靠，自述与真实依据可能不一致，白盒露怯。
- 候选方案C：无引用
  - 方案C优劣（致命短板）：答案不带任何依据；quoted_keys 为空时答案照常显示但没有支撑，白盒反而露怯。
- 最终拍板：is_quoted LCS 硬匹配（8 中/12 英），rerank 块先发（灰显），done 后补发 quoted_keys（高亮）
- 拍板理由：8 中文字符匹配必须生成完才能算，所以 rerank 先发灰显、done 后补 quoted_keys 高亮，"先灰后亮"避免引用面板闪跳；quoted_keys 为空→答案标注"引用未能精确匹配"，不假装有引用（问题8 §5、问题11 #3/#10）。

## 二、两道门与边界选型

### 选型6：权限模型选型
> 状态：✅ 已落地
> 检索摘要：demo 用页面权限标签+前置校验（学生=最高权限）做展示属性，不接真角色体系；08-25 收严为可信源角色门（Java 网关取角色，非学生固定 403 不耗 token）。

- 选型场景：权限如何落地——展示属性 vs 真角色体系 vs 可信源硬拦截
- 候选方案A：真角色体系（全局权限中心真实接入）
  - 方案A优劣（致命短板）：权限模型正规；但接入成本重、与"项目介绍演示"定位不符，demo 现场无法演示切换，明确不做。
- 候选方案B：页面权限标签 + 前置校验（demo 学生=最高权限）
  - 方案B优劣：每页挂权限标签、前端渲染，进页面/会话时前置校验"当前页权限点 vs 角色"；省一层复杂度，机制保留可切换演示；落地为 x-internal-token 鉴权。
- 候选方案C：可信源角色门（Java 网关硬拦截 403，08-25 收严）
  - 方案C优劣：从 Token/网关 Header 取角色，严禁信任前端 body 传参；仅学生放行，非学生/角色缺失直接固定 403，不进入 RAG 流程不耗 token；依赖 Java 网关可信 session。
- 最终拍板：权限门=页面权限标签+前置校验（demo 学生=最高权限，x-internal-token 鉴权）✅；08-25 演进方向=可信源角色门 Java 硬拦截
- 拍板理由：08-21 定位面试演示，权限做成展示属性省一层复杂度（D4、design Non-Goals）；08-25 spec 防前端伪造 body，收严为可信源取角色固定 403（问题8 §2）；真角色体系接入成本重且 demo 无法演示（问题3）。

### 选型7：范围判定选型
> 状态：✅ 已落地
> 检索摘要：范围门=检索置信度即范围判断（索引层阈值 0.75 / 源文档池 0.5），语料即边界，不单独做"是否覆盖"分类器；08-25 增加意图门硬路由作前置拦截，两道门共用固定拒答话术。

- 选型场景：怎么判断问题是否在语料覆盖范围内，避免没检索到还硬编答案
- 候选方案A：单独"是否覆盖"分类器
  - 方案A优劣（致命短板）：意图分类正规；但多一个易错组件，与范围门职责重叠，弃。
- 候选方案B：检索置信度即范围（范围门 0.75/0.5）
  - 方案B优劣：检索不到高置信条目→说明没覆盖→边界回答；纯 RAG 机制，"我的语料就是边界"逻辑自洽且可讲。
- 候选方案C：意图门硬路由（08-25 补充）
  - 方案C优劣：意图层硬路由——架构/代码/部署/评测/接口→强制路由 RAG 项目；AI答疑/知识图谱/题型分析→固定拒答；零检索零生成 0 token。
- 最终拍板：范围门=检索置信度（0.75/0.5）✅ + 意图门硬路由（08-25）双门互补，共用固定拒答话术，事件 reject vs boundary 可区分
- 拍板理由：范围门用检索置信度，语料即边界，无需单独分类器（D4 备选否决"单独覆盖分类器"）；意图门拦截明确指向禁区/无语料模块的问题，零成本（问题8 §3）；两道门职责不同——意图门前置拦截最便宜，范围门后置兜底语料未覆盖边角（问题9）。

## 三、成本与生成选型

### 选型8：生成模型选型
> 状态：✅ 已落地
> 检索摘要：生成链路落地 doubao 流式（复用 ark_stream + usage 真算），质量与答疑链路一致且 usage 改动只做一次；免费 glm-4-flash 是"边际成本趋近 0"的成本叙事备选。

- 选型场景：生成模型用谁，直接决定成本故事与链路复用
- 候选方案A：免费 glm-4-flash
  - 方案A优劣：成本故事最强——"本地 bge embedding + 免费生成模型，这套 RAG 的边际成本趋近于 0"；但与答疑链路模型不一致，无法复用 ark_stream 的 usage 改造。
- 候选方案B：doubao（答疑同款）
  - 方案B优劣：质量和答疑链路一致，可复用 ark_stream（usage 改动只做一次）；token 单价付费，费用换算数字没那么好看。
- 候选方案C：待定（未定模型）
  - 方案C优劣（致命短板）：无确定性，影响成本展示与链路复用，不采纳。
- 最终拍板：doubao 流式生成（复用 ark_stream + 强制引用 + usage 真算）✅；免费 glm-4-flash 作为成本叙事备选
- 拍板理由：D6 生成链路落地 doubao 流式+强制引用+按页标注，D7 token 真算按 doubao 单价换算（实测 ¥0.016/条）；复用 ark_stream 让 usage 改造只做一次（问题5 B）；面试成本叙事若要"边际成本趋近 0"，可切免费模型但需另起链路。

### 选型9：token 统计选型
> 状态：✅ 已落地
> 检索摘要：token 消耗采用 usage 真算（请求体加 stream_options.include_usage，解析结尾 usage chunk，流结束更新），拿不到 usage 时降级 tokenizer 估算并标注"估算"。

- 选型场景：token 成本展示怎么算——真算还是估算
- 候选方案A：usage 真算（流结束更新）
  - 方案A优劣：请求体加 stream_options={"include_usage": true}，解析最后一个 choices 为空但带顶层 usage 的 chunk，流结束时取 prompt/completion_tokens；embedding 侧抓 resp.usage.total_tokens；数据真实。
- 候选方案B：tokenizer 估算
  - 方案B优劣（致命短板）：实现简单；但只是估算，与真实计费有偏差，只能标注"估算"。
- 最终拍板：usage 真算（流结束更新）✅；拿不到 usage 时降级 tokenizer 估算并标注"估算"
- 拍板理由：成本是 RAG 最大实战痛点，真算+展示=成本控制叙事；流式 usage 只在结尾返回，所以"结束后更新"是踩过流式坑的加分细节（D7、问题3/4）；cache_hit_tokens 若 ark 不返回也走估算兜底（问题11 #7）。

## 四、展示与部署选型

### 选型10：流程图选型
> 状态：✅ 已落地
> 检索摘要：数据流流程图预置 mermaid（完善文档第 4 节内）为主，命中"数据流"类问题直接渲染，零渲染风险；动态生成仅兜底。

- 选型场景：数据流图怎么给——预置还是动态生成
- 候选方案A：预置 mermaid
  - 方案A优劣：每模块完善文档第 4 节存一张 mermaid 数据流图，命中"数据流"类问题直接渲染；稳定、快、面试不翻车。
- 候选方案B：动态生成（LLM 现场生成 mermaid）
  - 方案B优劣（致命短板）：炫、有差异化；但 LLM 现场生成的 mermaid 有语法/渲染风险，格式不可控，面试现场容易翻车。
- 最终拍板：预置 mermaid 为主（每模块第 4 节），动态生成仅兜底
- 拍板理由：demo 可靠性优先，预置零渲染风险（D8）；动态生成仅作未预置时的备选通道，演示不依赖（问题5 C）。

### 选型11：演示部署选型
> 状态：✅ 已落地
> 检索摘要：索引抽象层双轨部署——demo 默认本地 FAISS 兜底、生产走 COS 向量桶，COS 预建索引避开 10s 异步生效，面试现场零网络风险。

- 选型场景：demo 演示跑本地还是 COS，兼顾生产叙事与现场可靠性
- 候选方案A：本地 FAISS
  - 方案A优劣：面试现场零网络依赖绝不出错；但不是生产链路叙事。
- 候选方案B：COS 向量桶
  - 方案B优劣（致命短板）：生产链路好讲；但有 10s 异步生效 + 网络风险，当着面试官的面断网就完了。
- 候选方案C：索引抽象层双轨（demo 本地 + 生产 COS，COS 预建索引）
  - 方案C优劣：同一接口抽象，demo 默认本地 FAISS、UI 标注"生产环境走 COS"；COS 用预建索引避开 10s 异步写后不可即查。
- 最终拍板：索引抽象层双轨——demo 本地 FAISS 兜底 + 生产 COS 向量桶（预建索引）
- 拍板理由：demo 可靠性优先，本地兜底本身就是重试降级的最好故事且能真演示（问题1 ④）；COS 保留生产链路叙事，预建索引避开 10s 异步（D11、完善文档05）。

## 五、引导与交互选型

### 选型12：引导语选型
> 状态：✅ 已落地
> 检索摘要：引导语静态化降本——suggestions_pool.json 静态池每次问答后随机抽 2~3 条按 4 方向引导；引导问题本身是索引层入口，规范问题+变体文案配对强制走检索；禁止 LLM 动态生成。

- 选型场景：引导面试官问什么的引导语怎么来，控制在可控路径内
- 候选方案A：索引层预写引导（规范问题+变体文案配对）
  - 方案A优劣：引导问题=索引层入口，UI chips 点击命中索引层 QA；每页写两套文案（UI 变体 + 索引规范问题）让检索真实发生，避免"点按钮=预定答案"。
- 候选方案B：suggestions_pool.json 静态池随机（08-25 简化）
  - 方案B优劣：每次问答完成后从预设静态池随机抽 2~3 条返回前端，强制引导 4 方向（项目介绍/操作流程/数据关联/技术难点）；非 LLM 生成，0 token 0 耗时。
- 候选方案C：LLM 动态生成引导语
  - 方案C优劣（致命短板）：话术更贴当前问答；但每次问答多一次 LLM 调用，费 token 费时，与"静态化降本"目标相悖。
- 最终拍板：引导语静态化——suggestions_pool.json 静态池随机 2~3 条 ✅；引导问题=索引层预写规范问题，配变体文案走检索
- 拍板理由：引导语静态化降本、0 token（问题8 §6 明确"严禁动态生成引导语以节省 Token 和耗时"）；引导问题作为索引层入口保证可控可预演（问题3 ③）；LLM 动态生成是"省 token 考量"的反面（问题8 spec 结尾自留口子但主拍板静态池）。

### 选型13：会话切换选型
> 状态：✅ 已落地
> 检索摘要：功能点切换只在下一轮发生（intent 每轮判锚点变化→发 switch 事件→重置上下文），放弃生成中切换——后者需中止上游流、作废半截答案、白烧 token，复杂度高且无业务价值。

- 选型场景：切换功能点发生在哪一轮
- 候选方案A：下一轮切换
  - 方案A优劣：intent 每轮本来就跑，多一次"当前锚点 vs 已锚定"对比；switch 前零生成 token，成本极低。
- 候选方案B：生成中切换
  - 方案B优劣（致命短板）：①中止上游 doubao HTTP 流 ②半截答案作废 ③半截 token 已计费不退款 ④再起新一轮；Python 服务端取消上游流不可靠，复杂度与成本全面新增。
- 最终拍板：下一轮切换（switch 事件只作用于下一轮上下文：重置锚点、清上轮召回、重走 rewrite→recall）
- 拍板理由：业务上"生成中切换"其实不存在——学生只会等流完再问下一轮，或不想等就前端取消 fetch（is_disconnected 中止）；生成中切换复杂度高且无业务价值（问题9）。

## 六、评测选型

### 选型14：评测框架选型
> 状态：✅ 已落地
> 检索摘要：评测聚焦 hit@k + LLM 判分（answer_quality）两个核心信号，分层先测检索后测答案；明确不做 RAGAS 全量框架，评估集按 5 类场景扩充。

- 选型场景：怎么证明 RAG 系统靠谱——可量化、可复现、可追溯
- 候选方案A：RAGAS 全量框架
  - 方案A优劣（致命短板）：行业标准、可对比分数；但框架重，与"聚焦核心信号"目标不符，明确不做全量引入。
- 候选方案B：hit@k + LLM 判分（评测 agent）
  - 方案B优劣：先测"检索是否捞得对"（hit@k），再测"答案是否答得好"（answer_quality LLM 判分），分层定位问题；判分确定性硬化（模型只报 covered_count/fabricated，分数硬算可复现）。
- 最终拍板：评测 agent——hit@3 + answer_quality + cost/latency（离线工具，服务面试质量把关）
- 拍板理由：不做 RAGAS 全量框架，聚焦 hit@k + LLM 判分两个核心信号（eval agent Non-Goals）；分层评估先测检索后测答案，问题可定位到具体一条评测（问题12、eval D3/D4）；评估集每模块 ≥5 条、覆盖 5 类场景，扩充到 30~50 条（问题12）。实测 baseline：hit@3=0.80、质量分 3.6~4.6/5、单条成本 ¥0.016、耗时 5.7s（完善文档08）。

#### 1. 检索池层数选型
选型点：检索池几层
