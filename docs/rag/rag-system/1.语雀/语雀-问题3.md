问题

1. 要做“问题索引层” 这个本来就不是 纯 RAG 我就是给面试官介绍我的项目的 RAG只是证明我的RAG能力
2. 不要真接角色体系 现在直接最朴素的方法 页面上就有权限 让前端长
3. 我们要把常用的问题 去引导面试官问 这些数据都是我们提前准备好的
4. 每一轮的token 数量需要 展示的 这个是成本控制的提现

回答锁死你的四个决定

1. 问题索引层 = 你的“话术库”，RAG = 引擎 —— 定位很清晰：这不是纯 RAG 项目，是“用 RAG
引擎驱动一个项目介绍系统”。面试官看的是你的 RAG 能力，你卖的是项目本身。
2. 权限 = 展示属性 —— 每个页面挂一个权限标签，前端渲染出来，答案里也带一句“该功能面向学生端”。不做真角
色体系。这反而好，省一层复杂度。
3. 引导问题 = 索引层的入口 —— 索引层里的每个问题条目，就是 UI
上展示给面试官的“你可能想问”按钮。面试官点按钮（安全路径），RAG 从预置条目取答案。
4. Token 展示 = 成本叙事 —— 每轮展示 token 消耗。这是 RAG 项目最有价值的加分点之一，因为成本正是 RAG
最大的实战痛点。

  现在讨论第一个、也是最关键的问题：答案到底是“预写”还是“生成”？

  这是整个系统的十字路口，决定你的 RAG 是“真”还是“虚”：

  ┌─────────┬───────────────────────────┬──────────────────────────┬────────────────────────────────┐
  │  路线   │           做法            │           优点           │              代价              │
  ├─────────┼───────────────────────────┼──────────────────────────┼────────────────────────────────┤
  │ A.      │ 答案文字全写好，RAG       │ 绝对可控，永不翻车       │ RAG 沦为一个 fancy 查表，面试  │
  │ 全预写  │ 只负责“找到这条”          │                          │ 官一问“检索体现在哪”就露怯     │
  ├─────────┼───────────────────────────┼──────────────────────────┼────────────────────────────────┤
  │ B. 要点 │ 索引层存答案要点和原文引  │ 检索/增强/生成都真实发生 │ 需要控制 prompt                │
  │ +生成   │ 用，LLM 每次从检索到的上  │ ，RAG 能力看得见摸得着   │ 让它按要点答，否则会跑偏       │
  │         │ 下文现组织语言            │                          │                                │
  ├─────────┼───────────────────────────┼──────────────────────────┼────────────────────────────────┤
  │ C.      │ 不预写，全靠全文检索      │ 最“纯 RAG”               │ 答案不可控，面试现场最容易翻车 │
  │ 纯检索  │                           │                          │                                │
  └─────────┴───────────────────────────┴──────────────────────────┴────────────────────────────────┘

  我强烈建议 B：索引层存“答案要点 + 强制引用原文段落”，LLM 实时生成。

  理由有二：

+ 面试官能看见 RAG 在动——每轮检索了哪几段、上下文拼进去、LLM
基于上下文组织语言、答案底部带出处引用。这是“能力证明”，A 路线证明不了。
+ 你依然可控——要点是提前写的，LLM 只是把要点展开成话，再强制带引用。等于“提纲你定，措辞 AI 来”。

  而且 B 路线面试官问“你为什么不直接预写好答案”时，你能答：“因为我要验证我的检索真的能把对的上下文捞回来
  ，如果只做查表，那我的 RAG 检索和打分就全是假的。”——这句话本身就是加分答案。

  这是现在最需要你拍板的一件事：索引层存的是“完整答案”还是“答案要点”？

  第二个讨论点：Token 展示怎么做才好看

  不是简单显示一个数字。既然要体现成本控制，就把它做成一段完整叙事：

+ 每轮明细：输入(query + 检索到的 N 段上下文共 X tokens) + 输出(答案 Y tokens) = Z tokens
+ 可视化检索成本：直接显示“本轮检索了 3 段上下文 (450 tokens)”——让面试官直观看到 RAG 为什么费
token（检索越多越贵）
+ 累计 + 费用换算：整场会话累计 token 数，按模型单价换算成 ¥。费用控制在面试展示里极抓眼球
+ 成本控制故事（你代码里已经有底子）：本地 bge 免费 embedding / top-K 限制上下文膨胀 / 查询 LRU
缓存（你 LLM 已有缓存模式）/ 降级到关键词检索的便宜路径

  一个技术坑提前预警：流式输出时的 usage 统计——火山方舟/dashscope 的流式接口可能最后才返回
  usage，或者干脆不返回。要么等流结束拿 usage，要么用 tokenizer
  估算。这个到时候要专门处理，但它在设计讨论里是加分细节（说明你踩过流式的坑）。

  第三个讨论点：引导问题的“叙事顺序”

  既然用引导问题控制面试官，那就别让问题乱排——让问题顺序讲一个故事：

  页面概览 → 为什么这么设计 → 数据怎么流转 → 最大的难点 → 关键指标/权衡

  面试官跟着顺序点下来，就像你在讲一段有起承转合的介绍，而不是被抽查。而且问完引导问题后，要留一个口子：“
  你可以自由问任何问题”——这是自由模式，走纯检索，翻车也不怕，因为有个边界兜底。

  自由模式的兜底（面试官问了没准备的）：

+ 检索置信度低于阈值 →
不硬答，返回引导：“这个问题不在本次介绍范围，目前主要覆盖了这几个模块，你可以问……”
+ 这个“不硬编答案”本身就是你自适应判断的展示——宁可说不知道，不编。

  到这里，demo 的完整流程已经能画出来了

  面试官点开一页(如 AI答疑)
    → 前端传 page
    → 页面概览卡 + 权限标签 + 引导问题chips(按叙事排序)
    → 面试官点chips / 自由输入
    → RAG: 锁定页面 → 检索问题索引层 → 取要点+原文
    → LLM 按要点生成 + 强制引用
    → 回答卡片 + 出处 + (流程图) + 本轮 token 明细
    → 继续追问/换页
