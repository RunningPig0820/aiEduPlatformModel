# 分析-04 检索编排

> summary: RAG 检索编排核心 —— 双池三路召回(全量池向量/切片池双向量/BM25 本地) → 四路 RRF(RRF_K=60) × 权威度(authority) × 页面锚定加权(1.5) → top-5 → doubao 生成。两条线上线: 1.6C 端点(`POST /api/tutoring/rag/query`)与白盒 SSE 链路(`POST /api/rag/assistant/ask`)。范围门(0.75/0.5)只落地白盒 `check_boundary`, 1.6C 端点无; 权限门代码无(角色门在 Java); `rag_query()` 为 NameError 死代码; token 真算已在 ark_stream 修复, 但 1.6C 端点不采、embedding 侧不抓。
> 权威度: 0.8

> 类别: 操作流程

## 业务描述与业务场景

检索编排是 RAG 问答系统的中枢环节。面试官提问进入后, 系统先做**意图钩子**(判模块锚点 + 语义类别 + 是否需要澄清/切换模块), 再走**双池检索**(索引层切片池 + 源文档全量池, 向量 + BM25 三路召回), 经 **RRF 融合 × 权威度分层 × 页面锚定加权** 得到 top-K 命中块, 最后 doubao 生成面试口述风格答案并附引用来源。

双线并行:
- **1.6C 简洁契约线**: `POST /api/tutoring/rag/query`, 返回 `{answer, references, intent, version}` 固定结构, 面向后端/前端渲染 (api/rag.py:75-142)。
- **白盒 SSE 线**: `POST /api/rag/assistant/ask`, 逐事件 `intent → (clarify|switch) → rewrite → rerank → (boundary|token*) → done` 流式输出, 面向"可解释"演示 (api/rag_assistant.py:105-141, assistant.py:543-652)。

## 代码事实

### 1. 检索走哪几个来源(双池三路, 均带行号证据)

四路 RRF 输入 (query.py:637-641 注释 + orchestrate 参数):
1. **全量池向量路** `rag-full`: `retrieve_vector(question, vector_type="rag-full", module=corpus)` (query.py:518), 走 COS 桶 `rag-1318177119` + index `rag-full` (vector_store.py:106-121, settings.py:99-105)。语料 = 整篇文档, 实测 23 块 (rag_slices_full.jsonl)。
2. **切片池内容路** `rag-slice` (-c): `retrieve_vector(..., top_k=VEC_K+2)` 后 `_split_roles` 拆 key 后缀 `-c` (query.py:520-522, 487-504)。语料 = 细节切片块, 实测 294 块 (rag_slices.jsonl)。
3. **切片池问题路** (-q): 同一次向量召回拆出 key 后缀 `-q` 的记录 (query.py:498-500)。同块 -c/-q 双向量分别贡献 RRF (互补)。
4. **BM25 本地全文路**: `retrieve_bm25(question, select_corpus(blocks, corpus))` — jieba 分词 + 本地 jsonl 全文打分 (query.py:523-525, 565-578), 纯本地无外部依赖, 断电可用。

语料来源: `MODULE_DATA` 全模块 jsonl (ai-tutoring + question-analysis), 模块靠 `tags.module` 区分 (query.py:37-40, 436-449)。`_load_all_blocks` 合并所有池、缺失文件跳过 (query.py:442-449)。

向量层过滤: `build_filter` 仅按 `module` 做 COS `$eq` 过滤 (query.py:458-465), 防其他模块相似向量挤占 top-k; `categories` 参数保留兼容但**不再过滤** (query.py:461-463, 475)。

### 2. RRF 融合公式/参数 (RRF_K=60)

- `RRF_K = 60` (query.py:43)。
- orchestrate 内对四个 rank 字典(全量向量/切片内容/切片问题/BM25)做并集, 每路贡献 `1.0 / (RRF_K + rank)` (query.py:650-659)。rank 为 `enumerate` 序号, 从 0 起 (query.py:643-646)。
- 最终得分 = `rrf * authority * anchor_w` (query.py:667), 按得分降序取 top_k (query.py:669-671)。
- BM25 的 key 由 `_key_of` 生成与向量 key 同规则 (`rag-{pool}/{module}/{file}/{anchor}#{idx}`) (query.py:584-592, 575), 保证两路可并集融合。

### 3. 权威分层怎么参与排序

- 权威度来自语料块 `tags.authority`, 缺省 `0.7` (query.py:664)。
- 排序乘法因子: `score = rrf × authority × anchor_w` (query.py:667)。
- 命中项带 `authority` 字段回传 (query.py:677, 113), 供前端/生成标注。
- 实测语料 authority 取值 `{1.0(完善文档/引导问题), 0.8, 0.7(语雀等原始语料)}` (rag_slices.jsonl 首块 tags: 引导问题 authority=1.0, rag_slices_full.jsonl 首块语雀 authority=0.7)。
- 语义: 权威度作为 RRF 分数的乘性权重, 高权威块(完善文档 1.0)即使 RRF 略低也能排前。

### 4. 两道门在哪个函数生效(重点核实)

**权限门: 代码无实现。**
- 全 rag 模块 grep `权限/角色/permission` 仅命中注释: assistant.py:549 "无 permission——Python 生产端点不产, Java 网关从 intent 转发"; api/rag_assistant.py:9 "permission 由 Java 网关产(角色门在 Java)"。
- 1.6C 端点只有 `verify_internal_token`(服务级 x-internal-token 鉴权, 非页面权限点) (api/rag.py:64, 81)。
- 结论: 方案 D4 "权限门(前置校验 当前页权限点 vs 角色)" 是 Java 网关职责, Python 检索编排侧**未落地**。

**范围门(0.75/0.5): 只在白盒 `assistant.check_boundary` 生效, 1.6C 端点没有。**
- 常量: `BOUNDARY_VEC_CONF = 0.75` / `BOUNDARY_BM_CONF = 0.5` (assistant.py:388-389)。
- 判定函数 `check_boundary`: 空 rerank → 拒答; 或 `vec_conf < 0.75 且 bm_conf < 0.5` → 拒答; 单路高即过 (assistant.py:394-408)。
- 白盒链路内调用: `vec_conf = max(vec.confidence, vec2.confidence)`, `check_boundary(rec["rerank"], vec_conf, bm_conf)` → boundary 事件 + 立即 done, 不调 generate (assistant.py:616-625)。
- 1.6C 端点**未调用** check_boundary: 只有 `if not hits: 拒答"语料未覆盖"` (api/rag.py:119-126), 无任何置信度阈值判断。
- 置信度来源: 向量 = `1 - 平均余弦距离` (query.py:481-484); BM25 = `min(1.0, top_score/10)` (query.py:577)。

### 5. top-K 取值与 usage 真采/token 统计

- **top-K**: `TOP_K = 5`(生成用块数) (query.py:44); `BM25_K = 10`(BM25 召回数) (query.py:45); `VEC_K = 12`(向量召回数) (query.py:46); `RERANK_K = 3`(白盒 rerank 前端回传块数) (assistant.py:31); `HIT_K = 5`(评测 hit@k) (eval_agent.py:31)。1.6C 请求 `top_k` 默认 5, ge=1 le=20 (models/rag.py:14)。
- **usage 真采: 分三处, 结论不同**:
  - 白盒 SSE 线**真采**: `stream_generate` 传 `include_usage=True` 给 ark_stream (assistant.py:448), 流末尾 usage chunk 经 `_parse_sse_lines` 解析 (ark_stream.py:57-61, 128-129) yield `{type:"usage"}` (assistant.py:476-477), 最后 `assemble_usage` 组装 prompt/completion/cache_hit/total 进 done.tokens_usage (assistant.py:486-502, 514)。→ 语雀问题4 "现有代码在丢 usage" 的坑**已修**。
  - 评测线**真采**: `generate(hits, question, return_usage=True)` 读 `resp.usage_metadata` → prompt/completion/total (query.py:776-782), eval_agent 再算 cost (eval_agent.py:49, 263)。
  - **1.6C 端点不采**: 调用 `rag_core.generate(hits, rewritten)` 未传 return_usage (api/rag.py:130), 且 `RAGQueryResponse` 模型**无 usage/token 字段** (models/rag.py:39-44)。→ 对账要点。
  - **embedding 侧不抓**: `vector_store.embed()` 只返回向量, 未读 `resp.usage.total_tokens` (vector_store.py:87-103)。方案 D7 计划抓 embedding token, 代码未做 → 对账要点。

### 6. `rag_query()` 是死代码, 且会 NameError

- 定义于 query.py:789-814, 全仓库**无任何调用**(grep 仅命中定义处、注释、同名端点函数 api/rag.py:76)。
- api/rag.py:83 注释明确 "需绕开 rag_query 的整链路" —— 1.6C 端点自行重排了完整链路, 不调它。
- eval_agent.py:13 注释 "评测走真实检索原语(retrieve_vector/retrieve_bm25/orchestrate), 不走 rag_query"。
- 关键缺陷: 函数体第 812 行 `"intent": strategy` 引用了**未定义变量** `strategy`(函数作用域内只有 blocks/it/corpus/dual/hits/references; 模块级无 strategy), 一旦被调用立即 `NameError: name 'strategy' is not defined`。
- 结论: 死代码, 调用即崩, 现状由 api/rag.py 与 assistant.py 各自内联替代。

### 7. 类别过滤(locked_categories)已被禁用(1.13.2 决策)

- intent 仍产出 `locked_categories`(9 类切片闭集) (query.py:324-327)。
- 但 `build_filter` 只按 module 筛 (query.py:458-465), `retrieve_dual` 注释明确 "locked_categories 保留参数兼容, 不再过滤" (query.py:514-516), orchestrate 注释 "不做类别过滤/提权" (query.py:666-667)。
- 根因(代码注释): LLM 判类别不准, 类别过滤会误伤相关块 (query.py:461-463)。

## 隐性坑

1. **`rag_query()` 是 NameError 死代码**: query.py:789-814 定义了完整问答入口, 但第 812 行引用未定义 `strategy`, 调用即崩; 全仓库无调用, 1.6C 端点与评测都明确绕开。
2. **1.6C 端点没有范围门**: 置信度阈值 0.75/0.5 只存在于白盒 `check_boundary`; 1.6C 端点仅凭 "hits 是否为空" 拒答 —— 低置信但非空命中会直接进生成, 可能硬编。
3. **权限门是 Java 的事**: Python 侧没有页面权限点过滤, 只有 x-internal-token 服务鉴权; 方案 D4 的"按角色过滤可检索页"在 Python 检索编排中不存在。
4. **1.6C 端点不采 usage**: 虽然 ark_stream 已修好流式 usage(白盒真采), 但 1.6C 走 `generate` 非流式且不传 `return_usage=True`, 响应模型无 usage 字段 → 这条线上的 token 成本不可见。
5. **embedding token 未统计**: `vector_store.embed()` 不抓 `resp.usage.total_tokens`, 方案 D7 计划的 embedding 单列成本落空。
6. **categories 过滤语义脱节**: intent 仍花 LLM 成本产出 `locked_categories`, 但检索层已禁用类别过滤(1.13.2), 产了不用。
7. **双向量 -c/-q 占 top-k**: 切片池每块双向量, 向量 top-k 需 `VEC_K+2` 补偿 (query.py:519-521); orchestrate 同块两路各自贡献 RRF, 逻辑对但检索成本翻倍。
8. **RRF 分数量级小**: RRF 得分约 0.01~0.05(1/(60+rank)), 不能直接当置信度与 0.75/0.5 阈值比 (assistant.py:385-386 注释) —— 所以范围门必须另用召回 confidence。
9. **BM25 置信度粗糙**: `min(1.0, top_score/10)` (query.py:577) 是经验标定, 与向量置信度(1-平均距离)不同量纲, 双阈值并比有口径差异。
10. **权威度缺省 0.7**: 语料块缺 `authority` 标签时按最低档 0.7 参与乘性排序 (query.py:664), 会系统性压低无标签块的最终分。

## 设计要点

- **打分公式** `score = RRF(四路) × authority × anchor_w` (query.py:667), 三信号相乘: RRF 管多路互补、authority 管语料可信度分层、anchor_w 管页面锚定(命中节 ×1.5, query.py:665)。与方案 D5 "similarity × 问题类型 × 页面锚定" 对应, 但实现用 RRF 替代了纯相似度。
- **页面锚定两层**: 节级 `ANCHOR_RULES`(关键词→完善文档节 01-08, query.py:51-62)+ 模块级 `MODULE_ANCHOR_RULES`(关键词→模块锚点, query.py:71-76); 白盒/1.6C 优先 LLM 结构化 intent, 失败回退关键词两层 (query.py:306-316)。
- **双池语义**: `rag-full` 全量池(整篇, 管整体问题) + `rag-slice` 切片池(细节块); 引导问题块(authority 1.0)混在切片池中作为"可控 QA"层 (settings.py:97-98, query.py:31-40)。
- **多模块隔离**: 四模块闭集 `MODULE_ANCHORS` (query.py:68), 向量层 module Filter 下推 + `select_corpus` 本地选池 + intent LLM 判 anchor 三方一致 (query.py:609-617, 458-465)。
- **白盒事件时序冻结**: `intent → (clarify|switch) → rewrite → rerank → (boundary|token*) → done`, boundary 短路纪律(不调 generate, 0 token) (assistant.py:549-556, 615-625)。
- **降级不破结构**: 1.6C 四条降级路径(向量挂/生成挂/无命中/异常)响应结构不变, 前端只按同一结构渲染 (api/rag.py:10-15, 120-142)。
