## 为什么（语雀/动机）

面试官最爱问"开发中遇到什么坑、怎么解决"。RAG 系统自己踩过的坑，既要讲业务坑（AI答疑：判分误判/降级矩阵），也要讲 RAG 技术坑（本模块：检索/切片/索引/流式/契约）。坑档案 K1~K10 全部来自真实开发记录、每条带 git commit；未修复风险单列附录 A1~A11——面试被问"已知不完善"也敢如实讲。

## 怎么设计（方案）——按坑分组

**① 语料/切片**

- **版本矛盾策展**：现象：语料出现空模板/多版本（08-21 范围 vs 08-25 反转 vs 定稿），方案与代码漂移；根因：语料不全或多版本并存；解决：以代码现状为最终真相，完善文档向代码对齐、冲突以代码为准——V4 三端对账 37 项专抓"方案有/代码无"漂移。K# 不适用，属策展基线。
- **双池键冲突 / 索引键缺 module 段（K10）**：ai-tutoring 与 question-analysis 共用 rag-full/rag-slice，各自"完善文档 01-08"同名文件生成相同 key、后写覆盖先写，keymap 只剩后写块；根因是键规则 `{池}/{file}/{anchor}#{idx}` 不含业务命名空间；解决是 `make_key` 加 module 段 `rag-{pool}/{module}/...`（build_index.py:59-65 + query._key_of 同步），252 passed。
**② 检索**

- **关键词锚定太粗（K1）**：覆盖核对 6/10，"怎么/如何"万能词把问题锁错节（应锁 05/08 却锁到 02/06）；根因是 ANCHOR_RULES 字面匹配读不懂语义重点；解决是 classify 升级 LLM 语义判断（闭集 6 类映射锁节）、关键词降级保底 → 10/10，"接口不变、换实现"。
- **summary 翻译错位（K9）**：引导题点击后检索不到自身答案块（BM25 第 7、向量不进 top）；根因是引导题 summary 被 LLM 翻成"答案式描述"，与用户 query（问题标题）语义错位；解决是 summary 直接用 meta["anchor"] 标题（md_to_jsonl.py:111-117）→ BM25 第 1、向量 sim 0.85——离线切片元数据语义必须与线上 query 语义对齐。
**③ 生成**

- **流式 usage 丢失（K6）**：SSE 流式结束前端成本面板拿不到 token 明细（0 或空）；根因是请求体没带 stream_options.include_usage（OpenAI 兼容流式默认不回）+ 解析器不认结尾 usage chunk（choices 空带顶层 usage，schema 与中间不同）；解决是 ark_stream.py:128-129 加 include_usage + 抓结尾 chunk + assemble_usage 进 done.tokens_usage。⚠️ 半修：1.6C /query 与 embedding 仍未采（A2）。
- **引导 LLM 改编池外（K7）**：点"结束建议"候选题答非所问/拒答；根因是 gen_suggestions 用 LLM 改编池内原题、引入池外概念（如"向量索引"）无切片对应；解决是反转——结束建议直接池内原题直出（0 token），牺牲多样性换 100% 可答，"引导问题=索引层入口"的可答性闭环。
**④ 工程**

- **COS role mode 拒普通对象（K3）**：jsonl 副本传 COS 普通对象报 `AccessDenied: bucket is role mode`；根因是向量桶只服务向量 API、拒普通对象写入；解决是副本留本地 scripts/rag/data/，BM25/反查从本地读。
- **评测集被 gitignore 挡（K5）**：eval jsonl 无法 git add；根因是 data/ 整目录忽略误伤该入库的小配置；解决是 data/* + 例外 !data/eval/——运行时产物忽略、固定配置入库。
- **索引键冲突（K10 工程视角）+ embedding 维度锁死**：共享物理索引=多租户，key 先想清命名空间，否则"后写覆盖先写"隐性丢数据（见①）；同类坑：embedding 索引维度建好锁死、换模型=全量重建 + checksum 校验。
- **环境 langchain 冲突（K4）**：conda 默认环境两套 langchain 版本不匹配（LangSmithParams ImportError）；根因是 user-site 与 conda 环境互相踩；解决是统一 ai-edu-ai-service/venv，全量 315 通过。
**⑤ 契约**

- **指代词硬路由（K8）**："这个功能的底层是怎么实现的？"被 intent 按 D4 硬路由到 rag-system 必然拒答；根因是没解析指代词=current_project；解决是 _INTENT_SYSTEM 加指代词规则 + 优先级放宽 + 确定性兜底 _deictic_anchor（query.py:275-290）——LLM 不听话也能兜住，硬路由只保留"无指代 + 明确问 RAG 整体"。
- **sessionId 非 UUID（A5，未修复）**：前端 generateSessionId() 返回 `sess_<时间戳>_<随机串>`，非语雀 D-C 的 UUID；根因是契约写 UUID、实现随手生串；现状：Java 按字符串处理未爆雷、无修复 commit，对账如实标注。

## 落地真相（代码）

- **坑档案 K1~K10 全带 git commit**：K1 1d3b09c / K2 b13220b / K3 dea1c23 / K4 56a84bf / K5 ea5fd03 / K6 62e9794 / K7+K8 ee4f8d6 / K9 b4cec79 / K10 802d275，见 `5.难点/坑档案-开发与验证.md`。
- **底层能力是 V1~V4 验证方法论**：覆盖核对（语料完备先于检索质量）→ 评测 agent（hit@k 测检索、质量分测答案、trace 回溯定位"问题在哪一层"）→ 三层测试（纯函数/判分 mock/外部边界 mock）→ 三端对账（方案↔代码抓漂移）。K2 是典型：分数低先查判分器与评测集（2.60→4.60），别急着怀疑检索/生成。
- **降级矩阵（D10）**：多路召回本身就是降级备份（向量挂→纯 BM25）；生成失败→召回块清单当答案（不空答）；全挂→边界话术（不编造）；兜底全写死 0 token 短路防无谓成本；评测走真实检索原语不降级。
- **现状风险（未修复，一句带过）**：A1~A11——范围门 0.75/0.5 仅白盒生效（1.6C 无门）、usage 半修（1.6C/embedding 仍丢）、degraded 标记未透传 SSE、评测集 module 硬编码 ai-tutoring、sessionId 非 UUID、close 不中止在途流、rag_query 死代码 NameError、Java askStages 桩替、COS 写后异步生效延迟。

## 追问与防御

- **"开发中最大的坑是什么？"** → 不是单点 bug，而是"方案/代码漂移"——V4 对账抓出范围门仅白盒、usage 半修、rag_query 死代码；坑档案 K1~K10 每条可核 commit，证明"真的踩过、真的修了"。
- **"怎么证明坑修好了？"** → 分层验证：覆盖核对 10/10 证明语料完备、评测 hit@k + 质量分（2.60→4.60）分层证明检索/答案、trace 回溯定位层；每个 K# 有对应 commit 与测试（252 passed）。
- **"降级矩阵怎么设计？"** → 多路召回本身就是备份；生成失败降级召回清单；全挂边界话术；兜底全 0 token 短路；评测不降级，不让降级掩盖真实质量。
- **"哪些已知不完善？"** → 诚实列 A1~A11（范围门仅白盒、1.6C/embedding usage 未采、sessionId 非 UUID、close 不中止在途流、rag_query 死代码等）——知道边界在哪，正是对账方法论的价值。
