# 07 坑与验证

> summary: 解答「RAG 怎么证明有效 + 怎么验证」——分层验证体系不混为一谈: V1 覆盖核对(先证语料完备再谈检索质量)、V2 评测 agent(hit@k 测检索 + LLM 判分测生成, 分层定位)、V3 三层测试(纯函数/判分 mock/外部 mock)、V4 三端对账(抓"方案有/代码无"漂移); 评测走真实检索原语不降级; 当前基线 hit@5=0.583 / 质量 3.833 / 均成本 ¥0.018 / 报告按语料版本对比; 真实踩坑以 K2 为教训——首跑检索全对但质量分 2.60, trace 回溯定位到判分侧, 分数低先查判分器与评测集, 别急着怀疑检索/生成。

## 为什么（语雀/动机）

RAG 问答系统用于面试/汇报，核心是**用数据证明有效**——不能只说"感觉答得还行"（语雀-问题12 的"证明方案"）。要能回答三层：语料覆盖了面试官要问的问题吗（覆盖核对）？检索捞得对、答案答得好吗（评测 agent）？踩过什么坑、怎么修的（真实踩坑 = 可信度）？

## 怎么设计（方案）

**分层验证，不混为一谈**（对齐 rag-eval-agent D3，先测检索再测答案）：

1. **V1 覆盖核对**（先验证语料完备）：问题表 5 类各取代表问题，逐个跑 `classify + orchestrate`，看锁定节是否命中期望节（项目介绍→01/03、操作→02/06、难点→04/07、数据关联→05、最危险→08）——语料完备性是检索质量的前提。
2. **V2 评测 agent**（再验证检索+生成质量）：评测集逐条 → hit@k 测"检索捞得对不对"（引用命中客观率）、LLM 质量分 0~5 测"答案答得好不好"；hit@k 先定位检索层，质量分再定位生成层。
3. **V3 测试 agent 三层**：纯函数可单测（hit@k/聚合）、判分 mock 可注入（`judge_quality(..., llm=...)`）、外部边界 mock（不碰真实 COS/LLM）。
4. **V4 三端对账**（开发后期抓文档漂移）：以代码真读为最终真相，把语雀方案/OpenSpec 口径逐项对照代码现状（`方案-代码对账.md` 37 项），抓"方案写了但代码没有/只做一半"——单看方案或单看代码都发现不了。

**评测走真实检索原语、不降级**——直接调 `retrieve_dual`/`orchestrate`，向量挂了就暴露，不让降级掩盖真实质量问题（这是"自证"可信度的关键）。

## 落地真相（代码）

**验证体系落地**：V1 由 LLM 意图识别承接（关键词"怎么/如何"万能词稀释 → 覆盖核对 6/10→10/10，接口不变 API 零改动）；V2 由 `run_eval` + `eval_agent` 落地——评测集 6 条（5 类各 1 + 边界拒答）、HIT_K=5（由 3 改 5 对齐生成 top-5）、判分 LLM 只报事实 `{covered_count, fabricated, rationale}`、分数由 `_score_from_covered` 规则硬算（覆盖比例分档 + 编造封顶 3 分）、trace 落盘 + `--compare` 报告对比；V3 判分/检索核心均纯函数、判分 LLM 可注入；V4 对账抓到范围门仅白盒生效、`rag_query()` 死代码、DEGRADED 标记未透传 SSE 等漂移。

**当前基线（可对面试说）**：覆盖核对 10/10；最新报告（`2026-08-26-259c06`）**hit@5=0.583（hit_cases 5/6）/ 质量 3.833 / 均成本 ¥0.0181 / 均耗时 17.4s**；报告按语料版本（date-全块text sha1[:6]）命名，`run_eval --compare` 对比 hit@k/质量/成本/耗时四指标升降。注意 hit_cases 与 hit_at_k_avg 是两套口径（任一引用命中 vs 引用命中比例）。

**真实踩坑演进（教训总结，不堆行号）**：

- **K2 首跑检索对但答案漏 → 判分侧修复（最核心教训）**：首跑 5 条 hit@3=0.80 但质量分均 2.60，其中 2 条"检索全对但答案差"（hit@3=1.0）——trace 回溯发现**不是生成层问题**：判分 prompt 认不出同义表述（"ScoreMapper 累计"="题型掌握度回流"）、误判语料有支撑的表述为"编造"、无评分锚定；评测集 expected_points 混入不适用该问题的细节。修复判分 prompt（同义覆盖即算覆盖 + 传语料块供"编造"判定 + 0~5 锚定）+ 收窄评测集 → **质量 2.60→4.60**，hit@3 不变。**分数低先查判分器和评测集，别急着怀疑检索/生成；分层定位要分层修。**（git `b13220b`）
- **K1 覆盖核对 6/10→10/10**：`ANCHOR_RULES` 关键词锚定太粗，"怎么/如何"万能词把所有问题锁到操作节 → `classify` 升级 LLM 语义判断（闭集 6 类映射锁节，关键词降级保底）。
- **K6~K10 工程坑**：流式 usage 丢失（请求带 `include_usage` + 解析流末尾 usage chunk）、引导 LLM 改编引入池外概念破坏可答性（反转池内原题直出，0 token）、指代词"这个功能"被硬路由到 rag-system 必然拒答（`_deictic_anchor` 确定性兜底）、引导 summary 用翻译版语义错位（summary=问题标题）、多模块共用索引同名文件键冲突（key 加 module 段）。
- **环境/工程坑**：conda langchain 版本冲突（统一 `ai-edu-ai-service/venv`）、COS 向量桶 role mode 拒普通对象（jsonl 副本留本地）、评测集 jsonl 被 gitignore 挡（`data/*` + `!data/eval/` 例外）。

## 追问与防御

- **"怎么证明 RAG 有效？"** → 分层验证：覆盖核对 10/10 证语料完备；hit@k 是引用命中客观率（纯函数）；LLM 判分只报事实、分数硬算、编造封顶 3 分；报告按语料版本可 `--compare` 对比——每层都讲得清"证明的是什么"。
- **"评测集是你自己写的，凭什么可信？"** → 评测走真实检索原语不降级（向量挂了就暴露）；expected_references 回查完善文档（节号真实存在）；判分是独立 LLM 非自评，判分时传语料块供"编造"判定（答案在语料有支撑即非编造）。
- **"分数低怎么定位？"** → 分层定位：先 hit@k 看检索层，再质量分看生成层；K2 教训——检索全对但分数低，先查判分器和评测集（同义误判/expected_points 混入），别急着改生成代码。
- **"评测集才 6 条、够吗？"** → 如实承认局限：方案目标每模块 30~50 条，现状仅 ai-tutoring 6 条，`eval_dataset` 硬编码单模块、无 rag-system 评测集——这是待补的现状风险（附录 A4），不是已修复坑。
