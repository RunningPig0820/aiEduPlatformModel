## 一、验证方法（怎么证明 RAG 有效）

### V1. 覆盖核对（先验证语料完备，再验证检索质量）
- **方法**：从问题表（`ai-tutoring.md`）5 类各取代表问题，逐个跑 `classify + orchestrate`，看**锁定节是否命中期望节**（项目介绍→01/03、操作→02/06、难点→04/07、数据关联→05、最危险→08）。
- **价值**：先确认"语料覆盖了面试官要问的所有方向"，再谈检索准不准——**语料完备性是检索质量的前提**，分层验证不混为一谈。
- **证据**：`1d3b09c`（1.7 完整性检查 + LLM 意图识别）

### V2. 评测 agent（检索 vs 生成，分层定位问题）
- **方法**：评测集 5 条（5 类各 1）→ `run_eval.py` → 每条算 **hit@3**（检索命中）+ **answer_quality**（LLM 判分 0~5）+ 聚合报告。
- **关键设计**：评测走**真实检索原语**（`retrieve_vector`/`retrieve_bm25`/`orchestrate`），**不走带降级语义的 API**——向量挂了就暴露，不让降级掩盖真实质量问题。
- **价值**：hit@k 测"检索捞得对不对"，质量分测"答案答得好不好"，**先测检索再测答案，分层定位**（对齐 rag-eval-agent D3）。
- **证据**：`21e3000`（3 评测 agent）+ `ea5fd03`（2 评测集）

### V3. 测试 agent 的三层
- **纯函数可单测**：hit@k 计算、指标聚合是纯函数，离线断言（`test_eval_agent.py`）。
- **判分 mock 可注入**：`judge_quality(..., llm=...)` 注入 FakeLLM，测"解析失败重试1次记0"等边界。
- **外部边界 mock**：`retrieve_vector`/`generate`/`_load_blocks` 全 monkeypatch，单测不碰真实 COS/LLM（对齐 test_vector_store 模式）。

### V4. 三端对账验证（方案↔代码逐项核对，抓"方案有/代码无"漂移）
- **方法**：以 `3.代码/分析-01~09` 代码真读为最终真相，把语雀方案/OpenSpec spec 口径逐项对照代码现状——`方案-代码对账.md` 37 项（12 核心变化 ⚠️ / 12 已落地 ✅ / 6 明确不做 🚫 / 7 关键边界），每项带证据（文件:行号）。三端（Python `aiEduPlatformModel` / Java `aiEduPlatform` / 前端 `aiEduPlatformFront`）都要真读代码，不引用语雀行号当真相。
- **价值**：能抓到"方案写了但代码没有/只做了一半"的漂移——范围门 0.75/0.5 仅白盒生效（1.6C 端点无门，docstring 高于实际）、引导"变体文案"被反转为池内原题直出、`DEGRADED_*` 标记定义但未透传 SSE、sessionId 非 UUID、close 不中止在途流、`rag_query()` 死代码 NameError。单看方案或单看代码都发现不了，对账是开发中后期抓"文档漂移"最有效的手段。
- **局限**：对账只标"现状 vs 方案"，不自动区分"该坑已修复" vs "仍是风险"——后者要靠 git 历史核修复 commit 才能定性（本档案 K6~K10 是修复过、附录是未修复）。
- **证据**：`6009cdb`（方案-代码对账 37 项）+ `3.代码/分析-01~09` + `e47cdee`（补分析-08/09）

## 二、踩坑与演进（为什么加意图识别、召回率变化）

### K1. 关键词锚定太粗，"怎么/如何"万能词稀释了意图分类（覆盖核对 6/10 → 10/10）
- **坑**：`ANCHOR_RULES` 用关键词锁节，"怎么/如何"是万能词，把所有问题锁到 02/06（操作），稀释了 05（数据关联）和 08（最危险）。
- **现象**：覆盖核对 10 个代表问题只匹配 6 个期望节——"答疑和知识图谱怎么联动"（应锁 05）被"怎么"误锁到 02/06。
- **根因**：关键词匹配是字面匹配，无法理解语义重点；万能疑问词是噪音。
- **解决（演进）**：`classify` 意图钩子升级为 **LLM 语义判断**（doubao mini 关思考 + 20s 超时，闭集 6 类映射锁节），关键词降级保底。覆盖核对升到 **10/10**，且语义理解更准（"知识图谱联动"→05、"讲讲天气"→其他）。
- **价值**：这正是 rag-eval-agent 的意图钩子设计（1.6B）"接口不变、换实现"的落地——`classify(question) → {locked_sections, strategy}` 返回结构没变，API 零改动。
- **证据**：`1d3b09c`（LLM 意图识别）

### K2. 首跑评测：检索全对但答案漏要点/编造（真问题在判分侧非生成侧）
- **坑**：评测 agent 首跑 5 条 → hit@3=0.80、质量分均 2.60。
- **关键信号**：2 条是"检索全对（hit@3=1.0）但答案质量差"——如"一次完整答疑怎么走"检索到正确块，但被判分"漏了类型先行流式/Java 护栏，还编造 Java 编排"。
- **根因（trace 回溯后修正）**：**不是生成层问题，是判分侧 + 评测集**——
  ① 判分 prompt 认不出同义表述（要点"ScoreMapper 累计"=答案"题型掌握度回流"）、误判语料有支撑的表述为"编造"、无评分锚定 → 好答案被打低分。
  ② 评测集 expected_points 混入不适用该问题的细节（B3门控/澄清卡 是"掌握度怎么算"的要点，非"怎么联动"）。
- **解决（`b13220b`）**：判分 prompt 强化（同义覆盖即算覆盖 + 传语料块供"编造"判定 + 0~5 评分锚定）+ 评测集 expected_points 收窄 → **质量分 2.60→4.60/5**（操作 2→5、数据关联 0→4、难点 3→5、最危险 4→5），hit@3 保持 0.80。
- **价值/教训**：评测 agent 的 trace 回溯——**分数低先查判分器和评测集，别急着怀疑检索/生成；分层定位要分层修**。否则会错误地去改生成代码。
- **证据**：`21e3000`（首跑 + trace）+ `b13220b`（判分/评测集修复）

### K3. COS 向量桶 role mode 拒收普通对象（jsonl 副本方案调整）
- **坑**：设计时想"jsonl 语料副本传 COS 普通对象 `rag/{version}/rag_slices.jsonl`"（供 BM25/反查运行时拉取），实测 `put_object` 报 `AccessDenied: bucket is role mode`。
- **根因**：向量桶（Vertex Bucket）是 role mode，**只服务向量 API，拒普通对象写入**。
- **解决**：jsonl 副本留本地 `scripts/rag/data/rag_slices.jsonl`（本就是 build 输入，BM25/反查从本地读）；tasks.md 1.6A 同步调整说明。
- **证据**：`dea1c23`（纯 COS 入桶 + 调整说明）

### K4. conda 默认环境 langchain 版本冲突（LangSmithParams ImportError）
- **坑**：默认 `python`（conda）跑测试，`langchain_openai`（user-site 1.1.12）import 时报 `cannot import name 'LangSmithParams' from 'langchain_core'`。
- **根因**：user-site 的 langchain_openai 与 conda 的 langchain-core（0.1.23）版本不匹配——一个环境两套 langchain，互相踩。
- **解决**：统一用 `ai-edu-ai-service/venv`（langchain-core 1.2.20 + langchain-openai 1.1.11 匹配），CLAUDE.md 更新所有命令 + 环境警告；全量 315 通过（仅真实 API 测试需密钥）。
- **价值**：环境隔离是前提——之前 RAG 生成一直想绕开 langchain 写 openai 直连，其实修好环境就能用现成 LLMFactory。
- **证据**：`56a84bf`（CLAUDE.md venv 统一）+ 本会话环境诊断

### K5. 评测集 jsonl 被 gitignore 挡（数据文件 vs 配置的边界）
- **坑**：评测集 `data/eval/ai-tutoring.jsonl` 无法 `git add`——`data/` 整目录被 .gitignore 忽略（挡大文件 npz/jsonl）。
- **根因**：`data/` 规则设计为"大文件"，但误伤了**该入库的小配置**（评测集）。
- **解决**：改为 `data/*` + 例外 `!data/eval/`，大文件仍忽略、评测集强制入库——语义清晰（运行时产物忽略，固定配置入库）。
- **证据**：`ea5fd03`

### K6. 流式 token usage 丢失（"真算 + 结束时更新"落地）
**1. 问题现象**：成本展示场景——RAG 助手 SSE 流式回答结束后，前端成本面板拿不到本轮 token 明细（0 或空），"token 真算"变成摆设，无法证明成本可观测。
**2. 触发流程**：提问 → 白盒链路 `stream_generate` → `ark_stream` 流式拉 doubao → 流结束 → `done` 事件 → 前端 CostBar。丢 usage 发生在 `ark_stream` 这一层：流式请求没带 `include_usage`，且流末尾"choices 为空但带顶层 usage"的 chunk 没被解析。
**3. 根因分析**：修前两层都丢——①请求体无 `stream_options={"include_usage": true}`（OpenAI 兼容流式不加这个，服务端一般不会返回 usage）→ 流里根本没有 usage；②`_parse_sse_lines` 只解析 `reasoning/content/tool_calls`，就算流里带 usage 也被丢弃。两层都丢，所以"真算 + 流结束更新"无从落地。
**4. 排查过程**：语雀-问题4 评审直接核流式代码定位（2026-08-24）：先查请求体有没有 `include_usage`（没有），再查解析器抓没抓结尾 usage chunk（没有）——是代码评审 + "OpenAI 兼容流式默认不返回 usage"的知识判断，不是线上日志。
**5. 解决方案 & 改动点**：白盒引擎 `62e9794` 落地两个小改动——`ark_stream.py:128-129` 请求体加 `payload["stream_options"] = {"include_usage": True}` + `_parse_sse_lines` 识别流末尾 usage chunk 并 yield；`assistant.py:448` `stream_generate` 传 `include_usage=True`、`476-477` 消费 usage delta、`486-502` `assemble_usage` 组装 prompt/completion/cache_hit/total → `done.tokens_usage`（`assistant.py:514/651`），前端 CostBar 展示四字段。⚠️ **半修**：1.6C `/query`（`api/rag.py:130` generate 不带 return_usage、`models/rag.py:39-44` 无 usage 字段）与 embedding（`vector_store.py:87-103` 未抓 resp.usage）仍未采——见附录 A2。
**6. 面试口述要点**：讲"流式输出的 usage 统计是 RAG 成本展示的隐性坑"——usage 只在流末尾的专用 chunk 返回、默认不带；要做"结束后更新"必须显式请求 `include_usage` 并解析结尾 chunk（choices 为空带顶层 usage，schema 与中间 delta 不同）。踩坑收获：流式协议层"你不主动要、服务端就不给"的默认值，以及"结尾 chunk 与中间 chunk 不同 schema"。
- **证据**：`62e9794`（白盒引擎 include_usage）+ `语雀-问题4`（"现有代码在丢 usage"）+ 附录 A2

### K7. 结束建议 LLM 改编引导语 → 池外概念匹配不到答案
**1. 问题现象**：每轮回答结束前端展示"结束建议"候选题；学生点其中一题，问出去后答非所问/拒答——引导价值断裂，引导题本应带学生到高频方向。
**2. 触发流程**：回答完成 → `gen_suggestions` 用 LLM"换提问方法"把池内原题改编 → 前端 chips → 学生点击 → `POST /ask` 检索。改编后的新问题引入了池外概念，切片池没有对应块 → 低置信 → 拒答。
**3. 根因分析**：修前 `gen_suggestions` 依赖 LLM 改编，如把池内"题目记录/错误事件/掌握度三张表关系"编成"题目数据怎么和向量索引关联"（引入池外概念"向量索引"）→ 新问题没对应切片 → 检索不到。本质：引导语"自由发挥"破坏了"引导问题=索引层入口"的可答性闭环——只有池内原题才保证 100% 有切片（双向量 `-q` 问题路命中 sim~0.99）。
**4. 排查过程**：用户实测（2026-08-26）点"结束建议"改编题复现匹配不到答案，对照 known-issues 问题6"引导建议太随机、很多不可答"翻版；定位到 `gen_suggestions` 的 LLM 改编逻辑。
**5. 解决方案 & 改动点**：`ee4f8d6` 反转——结束建议直接返回池内原题（0 token，不做 LLM 改编）：`assistant.py:334-344` `_pool_suggestions` 池内抽样（必含 ≥1 条 rag 组）、`347-355` `gen_suggestions` 池内原题直出、`326-331` 注释记录反转原因；删 `_SUGGEST_SYSTEM`/`_suggest_scope`。
**6. 面试口述要点**：讲"引导系统的可答性闭环"——引导问题必须从"语料可答的底座池"取原题，LLM 自由改编会引入池外概念破坏检索。技术权衡：牺牲"引导语多样性"换"100% 可答 + 0 token"，代价是引导题固定。
- **证据**：`ee4f8d6`（引导可答性修复）+ `assistant.py:326-331`

### K8. 指代词"这个功能"被硬路由到 rag-system 必然拒答
**1. 问题现象**：学生在"AI答疑"功能页问"这个功能的底层是怎么实现的？"，助手答"未找到关联文档，我尚未掌握。"——当前功能页问本功能的架构/底层，必然拒答，且是架构/难点高频方向，体验断裂。
**2. 触发流程**：`current_project=ai-tutoring` + "这个功能的底层是怎么实现的？" → `intent` 意图层 → anchor 被 LLM/规则判成 `rag-system` → `rewrite="rag-system功能底层实现方式"` → rag-system 无语料切片 → rerank 空 → boundary `low_confidence` 拒答。
**3. 根因分析**：三处叠加（known-issues 问题7，2026-08-26 三端联调自测复现）——①intent 把"底层实现/架构"按 D4 硬路由到 rag-system，没解析指代词"这个功能"= current_project；②D4 硬路由规则过激进：current_project 明确时，"XXX 功能的底层"应在当前模块架构语料（ai-tutoring 有 03-架构与微服务分工 等），而非一律 rag-system；③意图判到无语料模块 → rerank 空 → 必然拒答。
**4. 排查过程**：三端联调自测复现：`current_project=ai-tutoring` + "这个功能的底层是怎么实现的？"，看 intent 输出 `anchor=rag-system`（❌ 应为 ai-tutoring）、rewrite 被带偏；确认 Java 正确透传了 current_project，问题收敛在 Python 意图层。
**5. 解决方案 & 改动点**：`ee4f8d6`（后端建议 4 改法）——①`_INTENT_SYSTEM` 加指代词规则（"这个功能/它/本功能/当前功能/这个项目"→ current_project）；②优先级规则放宽：只有"无指代 + 明确问 RAG 系统整体实现"才选 rag-system；③ctx_line 强约束"这个功能=current_project，不要因底层/实现/架构跳 rag-system"；④确定性兜底 `query.py:275-290` `_deictic_anchor`——问题含指代词且未点名其他模块名 → 强制 anchor=current_project（LLM 不听话也能兜住）。验证："这个功能的底层"→ai-tutoring；"RAG 系统整体架构是什么？"→rag-system（硬路由保留）。
**6. 面试口述要点**：讲"指代词消解 + 硬路由边界的权衡"——意图路由要区分"点名词"（RAG 系统整体 → 跨模块硬路由）与"指代词"（这个功能 → 锚定当前模块）；光靠 LLM 不可靠，要加确定性兜底（指代词词表 + 模块闭集判断），"LLM 不听话也能兜住"是工程可靠性的关键。
- **证据**：`ee4f8d6` + `query.py:275-290`（`_deictic_anchor`）；线索源 known-issues 问题7（git `f98c0e0` 中价值/`known-issues-java-rag-project-intro-assistant.md` 可恢复）

### K9. 引导问题 summary 用 LLM 翻译版 → 语义错位召回不到
**1. 问题现象**：引导题（"AI答疑如何使用？"）点击后检索不到自己的答案块，BM25 排第 7、向量路不进 top——引导题作为"索引层入口"失灵。
**2. 触发流程**：引导题点击 → 检索 → 切片池 `-q` 问题路 embedding/BM25。切片池里引导题块 summary 是 LLM 翻译版（"AI答疑如何使用？"被翻成"学生端拍题/打字/粘贴...使用闭环"），embedding/BM25 用 summary+text 与 query 语义错位。
**3. 根因分析**：引导问题块 summary 用 LLM 翻译（把问题标题译成"答案式描述"）→ 索引向量/BM25 检索特征（summary+text）与用户 query（原问题标题）语义错位（实测 sim 0.65）→ 向量路不命中、BM25 靠后。本质：引导题这类"问题即内容"的块，summary 应等于"用户会问的问题"，翻成答案式描述反而错位。
**4. 排查过程**：实测"AI答疑如何使用？"命中情况：BM25 第 7、向量 slice 不进 top、orchestrate 不进 top6——检索全偏；对照切片数据发现引导题 summary 是翻译版。
**5. 解决方案 & 改动点**：`b4cec79`（用户方案）——引导问题 summary 直接用问题标题（anchor），不做 LLM 翻译：`md_to_jsonl.py:111-117` 对引导问题 source，summary=`meta["anchor"]`（标题）、不读翻译头（防御 md 头再被翻译，jsonl 仍用标题）；90 个引导问题切片头 summary 改为标题；重新生成 `rag_slices.jsonl` + 重入切片池。实测：BM25 第 7→第 1、向量 slice 不进 top→第 1（sim 0.8513）、orchestrate 不进 top6→#1 命中目标块。

### K10. 多模块共用索引同名文件键冲突被覆盖
**1. 问题现象**：ai-tutoring 与 question-analysis 两模块共用 `rag-full`/`rag-slice` 索引，各自都有"完善文档 01-08"这类同名文件——后入库的覆盖先入库的，检索命中后 keymap 只剩后写的块，跨模块块丢失。
**2. 触发流程**：`build_index` 把各模块 jsonl 入 `rag-full`/`rag-slice` → `make_key` 生成块唯一 key → query 检索命中返回 key → `_key_of`/keymap 反查块。键不含 module 段时，两模块同名文件生成相同 key。
**3. 根因分析**：块 key 规则只有 `{池}/{file}/{anchor}#{idx}`，不含 module 段——多模块共用同一物理索引时，跨模块同名文件（每个模块都有完善文档 01-08）生成相同 key，后写覆盖先写（COS 向量桶按 key upsert），检索命中后 keymap 只映射到后写块。
**4. 排查过程**：多模块入库后，qa 向量命中后 keymap/BM25 无块被丢弃（此前 `85941ac` 修过"模块化 jsonl 加载"），继续追到键冲突：跨模块同名文件 key 相同。
**5. 解决方案 & 改动点**：`802d275`——键规则加 module 段 `rag-{pool}/{module}/{file}/{anchor}#{idx}`：`build_index.py:59-65` `make_key` 加 module 参数、`query.py` `_key_of` 同步；测试 mock 命中键补 module。验证：`_key_of(ai-tutoring/01-模块)` ≠ `_key_of(question-analysis/01-模块)`，252 passed。
**6. 面试口述要点**：讲"多模块共索引的键设计"——共享物理索引时，块唯一键必须含业务命名空间（module），否则同名文件互相覆盖。踩坑收获：共享资源（索引/缓存/表）引入多租户/多模块时，key 设计先想清命名空间，这类"后写覆盖先写"是典型隐性丢数据。
- **证据**：`802d275`（键规则加 module 段）+ `build_index.py:59-65`
