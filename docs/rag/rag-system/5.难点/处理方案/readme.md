## 一、坑档案定位

**难点经验层（权威 0.8，切片池 doc_type=难点）**——每条坑一个 h3 块，回答"曾经怎么坏了、怎么修的、怎么验证 RAG 有效"。与 `3.代码/`（证据层 code_analysis）互补：代码层讲"当前代码怎么实现"，坑档案讲"修复史 + 验证方法 + 面试口述"。

> 三类坑的边界（重点）：
> - **真实踩坑**（✅已修复，进主体）：git 有修复提交 + 当前代码可核验 → K1~K5 全部是这种
> - **风险预判**（⚠️仅设计讨论，不进主体）：design 里"担心会 XX"但未实际发生 → 不写，或单列附录标注
> - **待决**（❓）：无结论 → 不写
>
> 判断标准一句话：**只有实际发生并修复过、且 git/代码能找到证据的才算坑**——避免 LLM 编"合理但假"的坑污染检索。

- **本仓 git 历史**：`aiEduPlatformModel`（本模块只有 Python 服务，**无 Java/前端三端**，不涉及多仓）——每条坑 `git commit + 文件:行号` 双证据
- **代码现状**：修复提交对应的当前代码（修的代码 = 3.代码 里读到的代码，即 `ai-edu-ai-service/core/rag/` + `scripts/rag/` + `api/`）
- **线索源**：语雀 spike/联调记录、design 决策、`5.难点/坑档案-开发与验证.md` 已有内容（只当线索，不当坑证据）
