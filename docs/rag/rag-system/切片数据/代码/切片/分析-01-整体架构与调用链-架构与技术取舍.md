## 双池落地（核心机制 1）

双池不是方案里的 doc_type=qa/source 区分，而是**两个独立的 COS 向量索引**：
- **全量池（rag-full）**：整篇文档入池，共 23 块，服务"整体/自由问"——回答需要通读全文的问题。
- **切片池（rag-slice）**：细节块 + 引导问题，共 294 块，服务"引导/细节"——每个细节块独立可检索。
- key 规则为 `{池前缀}/{module}/{file}/{anchor}#{idx}`，前缀即 `rag-{pool}`，并加 module 段防止跨模块同名文件覆盖。

**双向量设计**：切片池每块写两个向量 key，后缀 `-c` 内容路（embed(summary+text)）与 `-q` 问题路（embed(summary)）。查询侧按 key 后缀拆成两路，再并入四路 RRF——全量路 + 切片内容路 + 切片问题路 + BM25。这样引导类问题能被 -q 问题路高命中（sim~0.99），细节类问题靠 -c 内容路。
全量池是单向量条件式：`summary+全文 ≤5000 字符` 则 embed(summary+全文)，超限（大语雀 10~12K 字符）只 embed(summary)。
metadata 10 字段无 doc_type——方案里的 qa/source 分类在代码里被 module + pool 取代。

## 页面锚定（核心机制 2）

方案 D3 的"前端传 page + 页面模式锁页/全局模式跨页"在代码中**没有 page 参数**，演变为两层锚定：
1. **模块级**：请求字段 current_project + 意图 LLM 输出的 anchor（模块闭集），决定从哪个模块语料池召回——这是真正的"过滤"层。
2. **节级**：locked_sections（01~08 完善文档节），来自关键词表或 LLM category 映射；在打分里节命中加权 1.5——**节级锚定只加权不过滤**。
页面模式/全局模式 ≈ locked_sections 非空/空，没有显式模式布尔。
一个重要细节：白盒链路里 recall 写死 `locked_sections=[]` 且只传 locked_categories，**节级锚定加权 1.5 在白盒链路被旁路**，只走模块级过滤；旧 query 端点则把完整上下文传入，节级锚定生效。即同一问题两个入口召回排序可能不同。
另有指代词确定性兜底：强制"这个功能/它/本功能"指代 current_project，防止 LLM 因"底层/实现"跳去别的模块。

## 两道门（核心机制 3）

- **权限门（前置）**：Python 侧代码未见实现——所有端点只有内部服务鉴权，请求模型无 role/permission 字段，角色门由 Java 网关承接。
- **范围门（后置，只在白盒链路）**：阈值 `vec 0.75 / bm 0.5`，判定逻辑是"rerank 空 → 拒答；非空但双路置信都低于阈值 → 拒答"（单路高即过）。触发 → boundary 事件 + 固定话术"未找到关联文档，我尚未掌握。"，**短路不调生成**——这是刻意的成本控制：冒烟测试发现 rerank 空时 doubao 会自生成"未覆盖"话术浪费 32 token，编排器必须防无谓成本。
- 旧 query 端点无阈值门，只有"无命中 → 拒答"的粗粒度空命中判断。

## token 真算（核心机制 4）

- **白盒链路**：生成直连方舟并开启 include_usage，流末尾的 usage chunk 被解析组装成 prompt/completion/cache_hit/total，进 done 事件。**真采自流末 usage chunk，非估算**；cache_hit 取不到时归 0。
- **评测**：评测的生成调用读 usage_metadata 算成本。
- **未真采/未暴露**：旧 query 端点响应没有 usage/token 字段；embedding tokens 未单列（embed 不返回 usage，方案里"embedding 单列"未落地）。
