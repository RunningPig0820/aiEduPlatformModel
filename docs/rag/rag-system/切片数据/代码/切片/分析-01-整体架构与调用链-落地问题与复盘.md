## 隐性坑与注意事项

1. **两个入口行为不一致**：旧 query 端点有节级锚定加权，白盒 ask 链路节锚定被旁路——同一问题两个入口召回排序可能不同，排查时不能假设两入口等价。
2. **范围门只在白盒链路**：旧 query 端点没有 0.75/0.5 阈值门，只有空命中拒答。方案里"两道门"对旧端点实际只有一道（且是粗粒度）。
3. **权限门整体不在 Python**：面试若问"权限门怎么实现"，代码里只有内部服务鉴权，角色门在 Java，Python 侧没有权限点校验实现。
4. **rag-system 自身语料为空**：anchor=rag-system 的问题当前必然边界拒答；引导入口返回的入口题（"能不能先介绍一下RAG项目？"）也因无 rag-system 语料而答不出。这是"语料整理中"的过渡状态。
5. **两个评测报告端点选报告逻辑不一致**：一个按文件名排序取末位、一个按修改时间——版本是语料 sha1 前缀、与时间无关，文件名排序不可靠。同一份报告两端点可能返回不同"最新"。
6. **类目过滤已被废弃**：LLM 输出的 9 类 categories 仅签名兼容，向量层/编排层都不再按类别过滤（LLM 判类别不准，类别过滤误伤相关块）。若读旧设计以为会筛类别会误判行为。
7. **切片池双向量 -c/-q 各占一个 top-k 位**：向量 top-k 多取 2 补偿同块双记录占位。
8. **生成降级话术固定**：白盒链路生成超时/异常降级话术写死、0 token；旧 query 端点降级是把 references 拼成文本当答案——两种降级产物格式不同。
9. **history 只消费最近 3 轮**（含澄清轮），Java 传再多也截断；Python 不落会话态，跨轮状态靠 Java Redis。
10. **评测"不降级"**：评测走真实检索原语，向量挂了评测会暴露失败而不是走降级——评测时 COS/网络不稳会得到差的指标，这是特性不是 bug。

## 方案 vs 落地的复盘（原始设计 → 实际实现 → 影响）

**双池形态演进：doc_type 分类 → 两个独立 COS 索引**
原始方案是"索引层池（doc_type=qa 预写 QA）+ 源文档池（doc_type=source）"同索引用 doc_type 区分；实际落地为两个独立 COS 索引——全量池（23 块整篇）+ 切片池（294 块细节），key 含池前缀 + module，metadata 不再有 doc_type（注释明确 doc_type 与 module 同值冗余已去掉）。"预写 QA/引导可答"由切片池引导问题块 + 双向量 -q 问题路承接。演进——双池形态落地，分类口径从 doc_type 换成 pool + module。

**引导问题变体方案被实测反转**
原始方案 D3 设计"UI 引导问题 = 索引层规范问题的变体写法"，本意是强制检索真发生；实际落地为结束建议直接返池内原题、不做 LLM 改编（代码注释记录了用户实测：LLM 改编会偏离池内范围、产生无对应切片的新问题匹配不上）。翻转——变体方案被实测否定，改池内原题 0 token 100% 可答。

**页面锚定演进：page 参数 → 模块 + 节两级锚定**
原始方案 D3 让前端传 page、页面模式锁页检索 / 全局模式跨页；实际没有 page 参数，演变为 current_project（模块）+ 意图 anchor（模块）+ locked_sections（节）+ 节命中加权 1.5。页面模式≈locked_sections 非空。演进——page 参数未落地，模块锚定 + 节加权落地。

**节级"锁页过滤"演进为"只加权不过滤"**
语雀问题1 里说"检索只在该页面的文档内做"（过滤语义）；实际节级只是加权 1.5 不是过滤，真正的过滤发生在模块级（按 module 选语料池），而且白盒链路里节加权被旁路。演进——锁页过滤 → 模块过滤 + 节加权。

**权限门整体不做在 Python**
原始方案 D4 设计"前置校验当前页权限点 vs 角色"；Python 代码里所有端点只有内部服务鉴权，请求模型无 role/permission 字段，角色门由 Java 网关承接。🚫不做（Python 侧）/ 由 Java 承接。

**范围门部分落地：只白盒链路生效**
原始方案 D4/D5 设计"索引层 0.75 / 源文档池 0.5 → 边界回答不硬编"；实际阈值落地（vec 0.75 / bm 0.5），判定"双路都低才拒、单路高即过"，触发后短路不调生成；但旧 query 端点没有阈值门，只有空命中拒答。部分落地——只白盒链路。

**token 真算部分落地：生成/评测真采，embedding 单列未做**
原始方案 D7 设计"usage 流结束更新 + embedding 单列"；实际白盒链路在流末 usage chunk 真采 token（含缓存命中数）、评测也真采 usage 算成本；但 embedding tokens 未单列，旧 query 端点响应也不吐 usage。部分落地——生成/评测真采；embedding 单列未落地；旧端点不吐。

**评测 agent 落地：hit@3→hit@5，判分方式重构**
原始方案 D4 是 hit@3 + LLM 打 0~5 分 + 版本对比；实际 HIT_K 演进为 5，判分改为 LLM 只输出 covered_count/fabricated、分数由规则硬算（编造 ≥1 处封顶 3 分），评测集仅 ai-tutoring 6 条（含 1 条边界拒答）。落地——hit@3→hit@5，判分方式重构。
