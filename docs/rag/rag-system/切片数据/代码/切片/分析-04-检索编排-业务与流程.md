## 业务描述与业务场景

检索编排是 RAG 问答系统的中枢环节。面试官提问进入后, 系统先做**意图钩子**(判模块锚点 + 语义类别 + 是否需要澄清/切换模块), 再走**双池检索**(索引层切片池 + 源文档全量池, 向量 + BM25 三路召回), 经 **RRF 融合 × 权威度分层 × 页面锚定加权** 得到 top-K 命中块, 最后 doubao 生成面试口述风格答案并附引用来源。

双线并行两个对外入口:
- **1.6C 简洁契约线**: 非流式 JSON 返回 `{answer, references, intent, version}` 固定结构, 面向后端/前端渲染。
- **白盒 SSE 线**: 流式输出, 逐事件 `intent → (clarify|switch) → rewrite → rerank → (boundary|token*) → done`, 面向"可解释"演示, 把检索编排每一步过程暴露给前端。

## 职责(模块分工)

- **检索编排核心模块**: 意图钩子(intent/classify)、查询改写、双池三路召回、编排器、生成、顶层编排入口(死代码)。
- **白盒链路编排模块**: 事件生成、范围门、流式生成、引用判定、引导。
- **1.6C 端点层**: 简洁契约端点 + 查看原文 + 评测 API。
- **白盒 SSE 端点层**: ask/guide/eval/report 等端点。
- **向量底层**: embedding(dashscope 768d) + 向量查询(COS, 按 vector_type 路由桶 + Filter 下推)。
- **方舟流式客户端**: include_usage + usage chunk 解析(token 真算载体)。

## 高层业务调用链(问题 → 双池检索 → RRF → 两道门 → topK → 生成)

**1.6C 简洁契约线:**
```
POST 简洁契约端点
→ 服务级鉴权(x-internal-token, 非权限门)
→ 全模块 jsonl 合并加载
→ LLM 意图判定(anchor/category/categories)
→ 查询改写(口语 → 检索式)
→ 双池三路召回
     ├─ 全量池单向量
     ├─ 切片池双向量(-c 内容 / -q 问题)
     └─ 本地 BM25
     (异常 → 降级纯 BM25, 空向量结果)
→ RRF × 权威 × 锚定 融合排序
→ 无命中 → 拒答"语料未覆盖"(非置信度范围门)
→ doubao 生成(不采 usage)
     (异常 → 召回清单当答案, 不空答)
→ 返回 answer / references / intent / version
```

**白盒 SSE 线:**
```
POST 白盒 SSE 端点 → pipeline_events 事件流
→ 问候检测(0 token 短路)
→ LLM 意图判定
→ 澄清(resolve_clarify: 歧义 & 候选≥2 & 未澄清过)
→ 切换(resolve_switch: 检测到切换 → 目标锚点)
→ 查询改写
→ 双池三路召回(单路 2s 超时降级)
→ 范围门(check_boundary 0.75/0.5, 短路不调生成)
→ 流式生成(ark_stream 流式, usage 结尾)
→ 引用判定 + 引导 + done
```

**端到端一句话**: 问题进来 → 意图钩子定锚点/类别/澄清需求 → 查询改写 → 双池三路召回(全量向量 / 切片双向量 / BM25) → RRF×权威×锚定融合 → 两道门(范围门仅白盒, 权限门在 Java 网关) → top-K → doubao 生成附引用; 1.6C 线返回固定结构, 白盒线 SSE 逐事件流式输出。
