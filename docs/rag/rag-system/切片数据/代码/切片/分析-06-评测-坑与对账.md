## 隐性坑与注意事项

- **hit_cases 与 hit_score 是两套口径**：`hit_cases` 按 `bool(hit_score>0)` 计（任一引用命中即算），`hit_at_k_avg` 按引用命中比例平均。最新报告 hit_at_k_avg 0.583 但 hit_cases 5/6（`reports/2026-08-26-259c06.json`）——"5 条有命中"不等于"引用命中比例高"。
- **判分失败被记 0 分、不是剔除**：judge_quality 两次解析失败 → score=0 + judged=False（`eval_agent.py:161`），会拉低 quality_avg；aggregate 里 `judged_ratio < 1` 提示有判分失败（`eval_agent.py:383`）。
- **编造封顶只在覆盖>0 时生效**：covered=0 直接 0 分，fabricated 分支不参与；若预期"0 覆盖 + 有编造"应更重罚，但代码没有。
- **判编造的语料看不全**：只拼前 4 块 × 600 字（`eval_agent.py:139`），第 5 块以后及超 600 字部分模型看不到，可能漏判支撑/误判编造（prompt 里已写"600 字截断无法验证的部分不算编造"缓解）。
- **评测集只能建 ai-tutoring**：`_validate` 硬编码 `module == "ai-tutoring"`（`eval_dataset.py:76`），即使 `load_dataset(module="rag-system")` 也会因 item.module 不匹配抛错——这是"没有 rag-system 评测集"的代码根因，多模块评测需要先改这里。
- **_compare 只和最后一份报告比，不是固定基线**：取 `reports[-1]`（排序最后一份，`run_eval.py:58`）；报告文件名 = 语料版本（date-sha1[:6]），同一语料重跑会覆盖同名报告（`_save_report` 按 version 命名），可能丢历史。
- **version 是语料内容指纹，不是运行时间**：`_current_version` = 全块 text sha1[:6]（`query.py:817-823`），同一天多次改语料会产生不同 sha 报告（如 2026-08-25 有两份：27f329 与 e966ac）。
- **边界拒答的 precision 恒为 0**（`eval_agent.py:331`）且计进 precision_at_k_avg；hit 恒为 False、hit_score 0，但正确拒答 score=5 计入 quality_avg。
- **判分与生成共享 TUTORING_DECIDE_MODEL**：判分成本与生成成本同源计算（`calc_cost` 硬编码 doubao 单价），若换模型需同步改单价。

## 对账要点（方案 vs 代码 复盘）

**hit@k 的 k（方案 vs 实现）**：方案口径 design D4 是"k 取 3（源文档池 top-k）"，完善文档 08 写的也是"hit@3 0.80"；实际落地 `HIT_K=5`（2026-08-26 注释 3→5，对齐生成上下文 top-5）。⚠️翻转：k 由 3 改 5，指标口径变化，历史 hit@3 数字不可直接对比。

**判分输出（方案 vs 实现）**：design D5 原设计"输出 {score, rationale}"；实际落地 LLM 只输出 {covered_count, fabricated, rationale}，score 由 `_score_from_covered` 确定性硬算。⚠️翻转：判分改为确定性硬算分，LLM 不再直接出分。

**判分维度（方案 vs 实现）**：design D4 原定"准确性/引用正确性/覆盖要点"三维；代码只按 covered_count + fabricated 两维，引用正确性改由 D3 quoted_valid 纯函数补位。⚠️部分落地：维度拆分，引用校验独立成纯函数。

**编造封顶 3 分（方案 vs 实现）**：design 未提"封顶"；代码新增 fabricated → min(base, 3)。➕代码新增硬约束：编造权重高于遗漏。

**question_type 闭集（方案 vs 实现）**：design D2 原定"概览/为什么/数据流/难点/指标"；实际 `VALID_TYPES` = 项目介绍/操作/数据关联/难点/最危险/边界拒答。⚠️翻转：分类体系改名，并新增边界拒答类型。

**评测集规模（方案 vs 实现）**：design D2 原定"每模块 5 条 × 5 模块 = 25 条"；实际仅 ai-tutoring.jsonl 6 条（5 正常 + 1 边界），无 rag-system/其他模块评测集。⚠️未覆盖：评测集仅 1 个模块 6 条，与 25 条方案差距大。

**边界拒答评测（方案 vs 实现）**：原 25 条方案未含边界拒答评测；代码新增 `BOUNDARY_TYPE` + `_boundary_trace`。➕超方案：1.13 双池后新增。

**真实检索原语（方案 vs 实现）**：design D3 要求"走 rag-retrieval"；实际走 retrieve_dual/orchestrate 真实原语不降级。✅落地：评测自证可信。

**cost/latency（方案 vs 实现）**：design D4 要求"prompt+completion × 单价 / 检索+生成+总耗时"；实际 `calc_cost` 纯函数 + latency 三段时间。✅落地。

**trace + 报告对比（方案 vs 实现）**：design D6 要求"逐条 trace + 报告对比"；实际 trace_latest.jsonl + reports/{version}.json + `--compare`。✅落地。

**每阶段可测试（方案 vs 实现）**：design D7 要求"纯函数可单测"；实际 hit_at_k/precision_at_k/calc_cost/_score_from_covered 均纯函数，判分 LLM 可注入。✅落地。

**评测集条数（完善文档 08 vs 代码）**：完善文档 08 写"评测集 5 条（5 类各 1）"；实际 ai-tutoring.jsonl 6 条（含边界拒答）。⚠️过时：6 条含边界。

**指标数值（完善文档 08 vs 代码）**：完善文档 08 写"hit@3 0.80 / 质量 3.6~4.6 / 单条 ¥0.016 / 5.7s"；最新报告 2026-08-26 为 hit@5 0.583 / 质量 3.833 / 均 ¥0.0181 / 17.4s（reports/2026-08-26-259c06.json）。⚠️过时：双向量 + 6 条 + 判分硬算后指标变化。
