**1. 问题现象**：学生在"AI答疑"功能页问"这个功能的底层是怎么实现的？"，助手答"未找到关联文档，我尚未掌握。"——当前功能页问本功能的架构/底层，必然拒答，且是架构/难点高频方向，体验断裂。

**2. 触发流程**：`current_project=ai-tutoring` + "这个功能的底层是怎么实现的？" → `intent` 意图层 → anchor 被 LLM/规则判成 `rag-system` → `rewrite="rag-system功能底层实现方式"` → rag-system 无语料切片 → rerank 空 → boundary `low_confidence` 拒答。

**3. 根因分析**：三处叠加（known-issues 问题7，2026-08-26 三端联调自测复现）——①intent 把"底层实现/架构"按 D4 硬路由到 rag-system，没解析指代词"这个功能"= current_project；②D4 硬路由规则过激进：current_project 明确时，"XXX 功能的底层"应在当前模块架构语料（ai-tutoring 有 03-架构与微服务分工 等），而非一律 rag-system；③意图判到无语料模块 → rerank 空 → 必然拒答。

**4. 排查过程**：三端联调自测复现：`current_project=ai-tutoring` + "这个功能的底层是怎么实现的？"，看 intent 输出 `anchor=rag-system`（应为 ai-tutoring）、rewrite 被带偏；确认 Java 正确透传了 current_project，问题收敛在 Python 意图层。

**5. 解决方案 & 改动点**：`ee4f8d6`（后端建议 4 改法）——①`_INTENT_SYSTEM` 加指代词规则（"这个功能/它/本功能/当前功能/这个项目"→ current_project）；②优先级规则放宽：只有"无指代 + 明确问 RAG 系统整体实现"才选 rag-system；③ctx_line 强约束"这个功能=current_project，不要因底层/实现/架构跳 rag-system"；④确定性兜底 `query.py:275-290` `_deictic_anchor`——问题含指代词且未点名其他模块名 → 强制 anchor=current_project（LLM 不听话也能兜住）。验证："这个功能的底层"→ai-tutoring；"RAG 系统整体架构是什么？"→rag-system（硬路由保留）。

**6. 面试口述要点**：讲"指代词消解 + 硬路由边界的权衡"——意图路由要区分"点名词"（RAG 系统整体 → 跨模块硬路由）与"指代词"（这个功能 → 锚定当前模块）；光靠 LLM 不可靠，要加确定性兜底（指代词词表 + 模块闭集判断），"LLM 不听话也能兜住"是工程可靠性的关键。
