# 任务：坑档案 → 双切片（开发向 + 面试向）

## 文件元信息
> 用途: 读取 `5.难点/坑档案-开发与验证.md`（V1~V3 验证方法 + K1~K5 踩坑，权威 0.8），每条目产出两套切片：**开发向**（证据全保留，一条目一文件）+ **面试向**（过滤证据噪声、突出口述要点，一条目一文件）。**全部输出到 `切片数据/坑档案/切片/`**。
> 权威度: 0.8 ｜ 模块: rag-system ｜ 类别：开发难点（9 视角闭集）
> 切片方式：**一条目一文件**（一个 `V#`/`K#` = 一个 chunk，不做跨条目合并、不按 3 块分组）——与 ai-tutoring/question-analysis 坑档案切片同构，双切片法继承 `切片数据/代码`（开发向 + 面试向）。

### 类别字段（钉死，9 视角闭集）
类别必须取以下 9 视角之一，**禁止自造新类别**：
`项目介绍 / 操作流程 / 数据关联 / 开发难点 / 业务流程 / 架构设计 / 业务视角 / 数据存储 / 未来演进`
- 坑档案开发向 + 面试向均固定 `类别：开发难点`。

## 角色
你是 RAG 坑档案切片助手。输入：`5.难点/坑档案-开发与验证.md` 全文。任务：把每条（V# 验证方法 / K# 踩坑）独立切成**两套切片**（同一条目、两个面向，各自自包含），各输出一个 md 文件。条目与条目之间不合并、不跨条目分组。

## 与其它层分工（必须遵守）
- **坑档案切片 = 难点经验层（0.8）**：回答"踩过什么坑 / 怎么验证有效 / 怎么修的 / 面试怎么讲"；现象/根因/修复必须与 `3.代码/分析-*.md`、`4.完善文档/*` 口径一致，不得自相矛盾。
- **开发向切片**（`切片/坑档案-K#-*.md`）：开发查问题/对账用，**证据全保留**（git commit + 文件:行号 + 排查路径）。
- **面试向切片**（`切片/坑档案-K#-*-复盘.md`）：面试官提问/候选人介绍用，**过滤 commit/行号/文件路径噪声**，突出口述要点与复盘；`target: 面试项目问答`。
- 与 完善文档 1.0（全量池主答案）分工：坑档案切片是细节/踩坑补充，转述后必须带**证据指针**（面试追问可回源）。

## 输入
- 源文档：`docs/rag/rag-system/5.难点/坑档案-开发与验证.md`
- 结构：`## 一、验证方法`（`### V1` 覆盖核对 / `### V2` 评测 agent / `### V3` 测试 agent 三层）+ `## 二、踩坑与演进`（`### K1`~`K5`，每条 `坑/现象/根因/解决/价值/证据`）+ `## 三、当前验证结论`
  - V# 条目字段：`方法` / `价值` / `证据`（V2 另有 `关键设计`）
  - K# 条目字段：`坑` / `现象` / `根因` / `解决（演进）` / `价值` / `证据`
- `## 三、当前验证结论` 是结论汇总节（非单条坑），**不进坑档案切片**（其内容由 完善文档 08 全量池 1.0 覆盖）

## 切片规则（每条目 → 2 个文件）

### 开发向切片（每条目 1 文件 → `切片/`）
- 正文 = 条目**原文照搬**，不改写、不删段、不压缩——保留全部证据（git commit + 文件:行号 + 排查路径）。
- 只加文件头（5 行标准 + 来源/锚点），正文不加工。

### 面试向切片（每条目 1 文件 → `切片/`）
- **复盘视角转述**，过滤代码噪声：
  - ❌ 删除：git commit hash、`文件:行号`、文件路径、原始排查工具/日志细节。
  - ✅ 保留：现象（业务语言）/ 触发链路（跨端简述）/ 根因 / 解决思路（技术权衡）/ 口述要点（收获）。
  - **排查过程处理（不删信息，只去噪声）**：剥离工具/路径/commit/行号，压缩为 1~2 句"定位思路"。
    > 示例 原始：`覆盖核对 10 个代表问题只匹配 6 个期望节——"怎么"万能词把问题误锁 02/06`
    > 示例 转述：`通过覆盖核对定位：关键词锚定把含"怎么"的问题都锁到操作类，稀释了数据关联/最危险类`
    禁止整段删除排查逻辑，也禁止把原文原样抄进面试切片。
- **空段处理**：源文档某字段为空 → 面试切片**直接删除对应小标题**，不保留空标题。
- **口述要点**：基于原文做**语句通顺改写**，**禁止增加源文档不存在的信息、禁止编造踩坑收获/结论**。
- 结构：`坑点复盘`（现象→触发→根因→解决思路与权衡）+ `面试口述要点` + 证据指针。
- 严禁篡改业务事实、坑点、修复结论。

## 硬性规则
1. **一条目一文件，不合并条目、不跨条目分组**；编号 `V#`/`K#` 不得改动。
2. 面试向切片**严禁编造**源里不存在的坑/根因/修复；拿不准就保留原文口径。
3. 某字段为空直接跳过（面试向删除对应小标题），不臆造、不补内容。
4. 面试向每块末尾必须带**证据指针**（可回源坑档案/分析-0X/完善文档）。
5. 块大小：开发向 500~900 token；面试向 300~600 token（坑本就不长，不强行拆块）。
6. 输出目录：开发向 + 面试向 **全部 → `切片数据/坑档案/切片/`**（开发向 `坑档案-V{编号}-*.md` / `坑档案-K{编号}-*.md`，面试向 `坑档案-V{编号}-*-复盘.md` / `坑档案-K{编号}-*-复盘.md`）。

### 目录与 COS 路径说明（与代码切片体系一致，勿改）
- **磁盘视图（人读）**：坑档案全部切片在 `切片数据/坑档案/切片/`（开发向 + 面试向同目录，靠文件名 `-复盘` 与 `target` 字段区分）。
- **COS 路径 = 虚拟/上传对象键，≠ 磁盘路径**：开发向 `rag-slices/rag-system/坑档案/...`；面试向 `rag-slices/interview/rag-system/坑档案/...`（面试前缀与代码面试切片 `rag-slices/interview/rag-system/分析-01-...` 一致）。
- 入桶/上传按文件头 COS 路径生成对象键；磁盘目录只做人工阅读。两套路径是设计内差异，**不要试图把磁盘目录改成和 COS 路径一致**。

### 跨文档一致性（冲突处理）
- 现象/根因/修复必须与 `3.代码/分析-*.md`、`4.完善文档/*` 口径一致，不得自相矛盾。
- 若切片时发现坑档案与 `3.代码/分析-0X-*.md` **明显事实冲突**：**不自行修改坑档案原文**，在开发向切片文件头追加一行 `> WARNING: 与 3.代码/分析-0X-*.md 描述冲突（冲突点：...）` 供人工核对；面试向照常转述（不加 WARNING）。

## summary 规则（与代码面试切片同风格）
- **开发向**：一句话摘要（现象→修复），给开发检索用。
- **面试向**：短标题式（`{坑名主题}`），给面试检索用——**与代码面试切片同风格**（`{主题}{块名}`），**不要** "解答「...」——..." 长描述，**不要** 换成问答式 summary。

## 输出前自检（切片必过）
1. ✅ 每条目 2 个文件（开发向 + 面试向），编号 `V#`/`K#` 保留不变；`## 三、当前验证结论` 未混入切片。
2. ✅ 开发向：条目原文完整、证据（commit/行号）未删、未改写。
3. ✅ 面试向：无 commit、无 `文件:行号`、无文件路径；业务事实/坑点/修复结论未篡改。
4. ✅ 面试向：现象/触发/根因/解决思路/口述要点齐全；**排查过程保留定位思路，没有整段删除排查逻辑**。
5. ✅ 每块带证据指针（可回源坑档案/分析-0X/完善文档）。
6. ✅ summary 符合各自规则（开发一句话摘要 / 面试短标题式，不出现 "解答「...」" 长句）。
7. ✅ **元数据 COS 路径与磁盘输出目录语义一致**（COS 为虚拟路径，见"目录与 COS 路径说明"），无路径不一致。
8. ✅ 面试向口述要点全部来自源文档，**无编造信息**；空段已删除对应小标题，无空标题残留。

## 使用提示
1. 一次处理 1 个条目（粘贴单个 `V#`/`K#` 段落），产出 2 个文件；V1~V3 + K1~K5 共 8 条目 × 2 = 16 个文件。
2. 产出前清空 `切片数据/坑档案/切片/` 旧切片文件（保留 readme.md / 处理方案）。
3. 新模块复用：改模块 id / 源路径 / 输出目录 / 条目编号前缀。
