## 回答

**核心结论**：普通 RAG 丢一堆文档就能问；它限定"**产品 = 讲清每个页面，RAG = 证明能力的引擎**"，靠双池检索 + 页面锚定 + 两道门 + 白盒 SSE + 引用硬匹配 + token 真算把能力显式演示出来。

**分层展开**：
- **普通 RAG**：丢文档→embedding→向量检索→LLM 生成，黑盒出答案，检索过程不可解释、能力无法证明（依据：完善文档 01/03）。
- **本系统限定**：产品 = 讲清每个页面（语料层，完善文档 8 节=问法清单）；RAG = 证明能力的引擎（检索层）；一份语料两用，一鱼两吃（依据：完善文档 01）。
- **六个显式机制**：
  - **双池检索**：索引层预写 QA 池（引导可控）+ 源文档池（自由纯 RAG 证据），两池分层各管一目标（依据：完善文档 03）。
  - **页面锚定**：检索限定模块/节，确定性可解释（落地为 current_project 模块过滤 + 节级加权 ×1.5，无 page 参数）（依据：完善文档 03 / 分析-04）。
  - **两道门**：权限门（Java 角色门"能不能看"）+ 范围门（白盒 0.75/0.5 置信度"有没有覆盖"）（依据：完善文档 03）。
  - **白盒 SSE**：意图→改写→召回→重排→生成全阶段事件透传前端，看着系统一步步答出来（依据：完善文档 02）。
  - **引用硬匹配**：is_quoted 用 LCS 最长公共子串判定，纯函数不靠 LLM 自述（依据：完善文档 03）。
  - **token 真算**：流式 usage 真采、成本可展示（依据：完善文档 03）。
- **落地翻转**：方案"doc_type 双池 + 前端传 page + 引导变体强制检索"落地为双物理索引 `rag-full`/`rag-slice`（无 doc_type）、`current_project` 模块锚定（无 page）、引导"池内原题直出"（不做 LLM 改编）——讲区别时按"演进后口径"说（依据：完善文档 03 / 分析-01）。
