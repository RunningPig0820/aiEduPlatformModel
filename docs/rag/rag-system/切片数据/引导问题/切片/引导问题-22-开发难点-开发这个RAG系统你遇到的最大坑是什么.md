## 回答

**核心结论**：不是单点 bug，而是**方案/代码漂移**——V4 三端对账抓出范围门仅白盒生效、usage 半修、rag_query 死代码；坑档案 K1~K10 每条可核 git commit，证明真踩过真修了。

**分层展开**：
- **最大的坑 = 方案/代码漂移**：文档里写了但代码没有/只做了一半——单看方案或单看代码都发现不了，靠 V4 三端对账（语雀方案/OpenSpec 口径逐项对照代码真读，37 项）才抓出来（依据：完善文档 06 / 坑档案 V4）。
- **V4 对账抓出的典型漂移**：范围门 0.75/0.5 **仅白盒链路生效**（1.6C 端点无阈值门、docstring 自称"置信度过低→拒答"与实际不符）；token usage **半修**（白盒流式已修、1.6C/embedding 仍丢）；`rag_query()` 是 **NameError 死代码**（引用未定义变量 strategy，全仓库无调用）（依据：完善文档 06 / 分析-04）。
- **证明真实踩过**：坑档案 K1~K10 每条带 git commit（K1 1d3b09c / K2 b13220b / K3 dea1c23 … K10 802d275），可核，证明"真的踩过、真的修了"（依据：完善文档 06 / 坑档案）。
- **未修复风险（诚实口径）**：附录 A1~A11——sessionId 非 UUID、close 不中止在途流、评测集 module 硬编码 ai-tutoring、DEGRADED 标记未透传 SSE 等，知道边界在哪正是对账方法论的价值（依据：完善文档 06 / 坑档案）。
