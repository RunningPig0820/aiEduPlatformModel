### 角色门（权限门）与鉴权

后端从**可信源**（Token/网关 Header）取角色，**严禁信任前端 Body 传参**；仅当角色明确为"学生"时放行，非学生/角色缺失→直接返回固定 403 拒绝语，不进入任何 RAG 流程、**不消耗任何 Token**。证据：语雀-原文件-问题8.md。08-21 时期为页面权限标签 + demo 学生=最高权限（前置校验机制保留），08-25 收严为可信源取角色。证据：design-python-project-intro-rag.md Non-Goals / 问题8.md。

⚠️【落地】**权限门在 Java 网关**（`RagAssistantController.requireStudent` → `TutoringAuth.isStudent(session)`），仅 STUDENT 放行、**body 传 role 一律忽略**、非学生/角色缺失固定 403（`ResponseStatusException(FORBIDDEN)`，不进入 RAG 流程、不产生 trace）；**Python 代码无权限门**——`api/rag.py`/`api/rag_assistant.py` 仅 `verify_internal_token`（内部服务鉴权），请求模型无 role/permission 字段（`api/rag_assistant.py:9` 明确"permission 由 Java 网关产"）。⚠️【定稿 D-B】`permission` 事件 = `{role, allowed, traceId}`，trace_id 由 Java 入口生成，流开始前端即可取（断线补查不依赖 done）。证据：分析-01/04；design-java D1/D-B。

### 选型6：权限模型选型
> 检索摘要：demo 用页面权限标签+前置校验（学生=最高权限）做展示属性，不接真角色体系；08-25 收严为可信源角色门（Java 网关取角色，非学生固定 403 不耗 token）；Python 侧仅 x-internal-token 服务鉴权、无权限门。

- 选型场景：权限如何落地——展示属性 vs 真角色体系 vs 可信源硬拦截
- 候选方案A：真角色体系（全局权限中心真实接入）
  - 方案A优劣（致命短板）：权限模型正规；但接入成本重、与"项目介绍演示"定位不符，demo 现场无法演示切换，明确不做。
- 候选方案B：页面权限标签 + 前置校验（demo 学生=最高权限）
  - 方案B优劣：每页挂权限标签、前端渲染，进页面/会话时前置校验"当前页权限点 vs 角色"；省一层复杂度，机制保留可切换演示；落地为 x-internal-token 鉴权。
- 候选方案C：可信源角色门（Java 网关硬拦截 403，08-25 收严）
  - 方案C优劣：从 Token/网关 Header 取角色，严禁信任前端 body 传参；仅学生放行，非学生/角色缺失直接固定 403，不进入 RAG 流程不耗 token；依赖 Java 网关可信 session。
- 最终拍板：权限门=页面权限标签+前置校验（demo 学生=最高权限，x-internal-token 鉴权）✅；08-25 演进方向=可信源角色门 Java 硬拦截
- 拍板理由：08-21 定位面试演示，权限做成展示属性省一层复杂度（D4、design Non-Goals）；08-25 spec 防前端伪造 body，收严为可信源取角色固定 403（问题8 §2）；真角色体系接入成本重且 demo 无法演示（问题3）。
- 落地对账：✅ 权限门在 **Java 网关**（`RagAssistantController.requireStudent` → `TutoringAuth.isStudent(session)`），仅 STUDENT 放行、body 传 role 一律忽略、非学生/角色缺失固定 403（`ResponseStatusException(FORBIDDEN)`，不进入 RAG 流程、不产生 trace）；**Python 代码无权限门**——`api/rag.py`/`api/rag_assistant.py` 仅 `verify_internal_token`（内部服务鉴权），请求模型无 role/permission 字段（`api/rag_assistant.py:9` 明确"permission 由 Java 网关产"）。结论=方案拍板成立，落地在 Java 侧。

### 选型16：权限角色来源取值选型
> 检索摘要：角色从可信源（Token/网关 Header/可信 session）取，严禁信任前端 body 传参；仅学生放行，非学生/角色缺失固定 403、不进入 RAG 流程 0 token；08-21 demo 曾允许 role 走 body，08-25 反转禁 body。

- 选型场景：角色值从哪来，防前端伪造（权限门的取值可信性）
- 候选方案A：前端 body 传 role（08-21 demo）
  - 方案A优劣（致命短板）：前端可任意传 role，权限形同虚设；面试问"怎么防伪造/越权"当场翻车。
- 候选方案B：可信源取值（session/网关 Header）
  - 方案B优劣：Java 网关从 `HttpSession.getAttribute("role")`（或网关 Header）取角色，前端 body 传 role 一律忽略；仅 STUDENT 放行，非学生/角色缺失固定 403，不进入 RAG 流程、不落 trace、不耗 token。
- 最终拍板：可信源取值（D1/D-B）
- 拍板理由：spec 硬性要求"严禁信任前端 body 传参"（D1）；与 tutoring 认证桥接一致，前端走 Java 网关、Python 不自己认证不碰会话，保住"Python 无状态"边界；备选"Python 自校验"破坏无状态边界弃。
- 落地对账：✅ 落地——`RagAssistantController.requireStudent` 从 session 取角色、body role 忽略（design-java D1/D-B）；`permission` 事件 = `{role, allowed, traceId}`，trace_id 由 Java 入口生成、流开始前端即可取（断线补查不依赖 done）。结论=落地。
